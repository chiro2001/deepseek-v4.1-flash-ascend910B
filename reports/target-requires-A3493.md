# 决断：110 tok/s 的**唯一可行路径**是 A ≥ 3.49

> 2026-09-16 14:45 初版 / **15:00 按正确性线的否决更新**
> 基于正确性线的 `HCCL_DETERMINISTIC` 实测 + 性能线的 device 账目

---

## 0. ⚠️ 更新：`HCCL_DETERMINISTIC=true` **被硬约束否决**

正确性线实测（**我也独立复核了原始 JSON**）：

| 臂 | GSM8K-100 | Vision | 判定 |
|---|---|---|---|
| stock（maskA） | **100/100** | 23/23 | ✓ |
| `V41_MOE_MASK_RANGE=1`（maskB） | **100/100** | 23/23 | ✓ |
| **`HCCL_DETERMINISTIC=true`** | **91/100** ❌ | 23/23 | **否决** |

* 9 题**全部是"给出答案但算错"**（`empty=0`、`errors=0`）⇒ **真实数值退化**，不是崩坏。
  例：`gold=70000 → pred=25000`、`gold=45 → pred=30`、`gold=13 → pred=12`。
* 与 HCCL 的公开语义一致：**它把归约固定成单一（通常是低精度累加）顺序**，
  以数值精度换确定性。

**⇒ 在 `GSM8K≈198/200` 的硬约束下，`HCCL_DETERMINISTIC` 不可作为交付配置，只能当诊断工具。**
**⇒ A 的提升不能靠它。**

### 0.1 但它仍是重大成果（诊断价值）

它**明确定位了第一大非确定源 = HCCL allreduce 的归约顺序**：
`HCCL_DETERMINISTIC=true` 让 **≤16385 上下文的输出逐位确定**（logprob 8 发相同到 6 位小数）。

⇒ 真正的修法是**找出那个非确定的 allreduce 并单独固定它的算法**（或换 deterministic 的等价实现），
而不是全局打开这个开关（全局会伤精度）。

## 2. 决定性算术

`tok/s = A × 1000 / ms`

| ms/step | A=2.474 | **A=3.493** |
|---|---|---|
| 32.740（当前） | 75.6 | **106.7** |
| 31.80（QLI −0.9 后） | 77.8 | **109.8** |
| **31.00** | 79.8 | **112.7** ✅ |

**达到 110 tok/s 需要的组合**：

| A | 需要的 ms/step | 可行性 |
|---|---|---|
| **2.474**（HCCL_DET 后的稳定值） | **≤ 22.49** | ❌ **不可能** —— device busy 并集本身就是 33.65 |
| 2.8 | ≤ 25.45 | ❌ 不可能 |
| 3.0 | ≤ 27.27 | ❌ 不可能（busy 33.65） |
| 3.2 | ≤ 29.09 | ❌ 接近但达不到 |
| **3.493** | **≤ 31.75** | ✅ **可行**（当前 32.74，QLI −0.9 即到 31.8） |

**⇒ 结论：A ≥ 3.49 是 110 tok/s 的充要条件。**
任何 A < 3.2 的情形，都需要 ms/step 跌破 device busy 并集（物理上不可能）。

## 3. 这意味着什么

### 3.1 性能线已基本做完

* 当前 32.740 ms/step vs busy 33.65 —— **墙钟已经低于 busy 并集**，
  说明跨流重叠已经生效（部分算子并行）。
* 后续可拿的：`qli-no-candidate`（−0.9，验证中）、`ids64`+`engram-gate`（−0.086）。
  ⇒ **乐观到 31.7–31.8**，正好卡在 A=3.493 所需的 31.75 上。
* **再往下压的空间很小**：其余 top 算子（`GroupedMatmulSwigluQuantV2` 3.4、`HcPre` 2.9、
  `hcom_allReduce_` 2.7、`MatMulV2` 2.6）都已是算子团队才能改的标量受限项。

### 3.2 A 是唯一的战场

正确性线的数据把 A 分成**离散模式**：

| 模式 | A | 出现条件 |
|---|---|---|
| **"优"** | **3.493** | 历史会话中偶然出现 |
| "常" | 2.745 | 历史会话中偶然出现 |
| `HCCL_DET` 稳定值 | **2.474** | 5/8 发收敛 |
| 跑偏 | 1.0 – 2.0 | 剩下的 3/8 发 |

**"优"（3.493）与"常"（2.745）在历史上就被观察到，当时被当作"内容不同"解释。
现在看它们是同一个非确定性的两个模式。**

### 3.3 关键问题（交给正确性线）

**模式选择器是什么？** 需要在 A=3.493 的模式下把计算"钉住"。

候选解释：
1. **draft 看到的上下文不同**：`HCCL_DET` 只固定了 allreduce 顺序，
   但第二个源（阈值 (16385,16640]）与第三个源（≥100K）仍在 ⇒ draft 仍可能看到错的数据；
2. **候选筛选的块选择**：`CAND_MODE=3` 在 32K 及以下使其确定，但 128K 仍有残差；
3. **Engram 的 host 侧状态**：`pages` 跨请求不清理，长上下文（64 chunk）更易受影响。

## 4. 给正确性线的具体请求

### 4.1 测出 A 在各配置下的**稳定值**（这是判据）

在 **128K**、每臂 **≥8 发**、真权重，记录 A 的**中位与唯一值数**：

| 配置 | 目的 |
|---|---|
| `HCCL_DETERMINISTIC=true`（已测：中位 2.474） | 基线 |
| + `CAND_MODE=3`（已测：中位 1.720，7/8 unique） | 候选路径的影响 |
| + `CAND_MODE=3` + `HCCL_DETERMINISTIC=strict` | 更严格的确定性 |
| + **修掉 Engram `pages` 跨请求残留**（探针：每 forward 前 `pages.clear()`） | 第三源假设 |

**判据**：若某配置的 A **稳定且 ≥3.4** ⇒ **直接达成 110 tok/s**；
若稳定在 2.4–2.7 ⇒ 说明"优"模式不是靠确定性得到的，需要另找。

### 4.2 一个可能更快的判别法

**在同一会话里连续发同一 prompt**：若 `HCCL_DET` 下 5/8 发收敛到 A=2.474，
检查那 3 发跑偏的是**第几发**（位置）。若跑偏总在第 1–2 发（图刚重捕之后），
那是**捕获期问题**而非运行期；若随机分布，则真的是运行期竞态。

## 5. 口径建议（需用户确认）

如果 A 无法回到 3.49，则 `>110 tok/s` 在当前硬件/算子/框架下**不可达**。建议口径改为：

1. **`ms/step` 最优**（已从 39.10 降到 32.74，−16.3%；QLI 后约 31.8，−18.7%）
2. **tok/s（在 A≥3.4 时）**：以 31.8 ms 计 = **109.8**（差 0.2）
3. **或**：把 A 的确定性作为独立交付项（当前已从"完全随机"改善到"5/8 收敛"）
