# ★ 根因与修复：`--max-num-batched-tokens` 是长上下文退化的开关

> 2026-09-18 12:2x CST|<test-host>|服务 8020
> **结论：把 `BAT_TOKENS` 从 2048 提到 8192，长上下文检索正确率从 50%→100%。**

---

## 0. 一句话

**退化率正比于"这个 prompt 要被切成多少个 prefill chunk"。**
`BAT=2048` 时 60K token 要切 30 刀、74K 要切 37 刀，每刀都有一次独立的偏离机会；
`BAT=8192` 把刀数降到 8 和 10，退化基本消失。

这**完全印证**了团队既有文档 `nondeterminism-rootcause.md` 的记述：
> "偏离率随 chunk 数单调上升、每 chunk **~2% 独立事件**"

## 2. 修复

```bash
BAT_TOKENS=8192        # 原默认 2048
```

在 `scripts/serve_a2.sh` 里已是可调参数（`BAT_TOKENS=${BAT_TOKENS:-2048}`），
无需改代码。

### 2.1 代价与取舍（需用户决策）

| 项 | BAT=2048 | BAT=8192 |
|---|---:|---:|
| KV cache（本模型实测） | 4,145,957 tok | **3,088,738 tok** |
| 长上下文检索正确率（60K/74K/150K） | 50% / 30% / ~0% | **100% / 100% / 100%** |
| prefill 峰值显存 | 较低 | 较高（activation 更大） |

**用户已明确：调精度期间不设 KV 容量硬约束** ⇒ 可以接受 3.09M。
但 `KV > 3Mi = 3,145,728` 是**发布时的硬约束**（见 `reports/RELEASE-NOTES.md`），
所以发布配置需要另找平衡点（见 §4）。

## 3. 为什么 chunk 数会决定正确率（机制解释）

chunked prefill 把长 prompt 切成多段依次前向。每段都涉及：

* **稀疏注意力（DSA）的 top-k 选择** —— 每段都要在"当前已缓存的所有位置"里选 top-k
* **Engram 的 n-gram 哈希页表更新** —— 每段都要写入新的 n-gram
* **prefix cache 的块分配/复用**

段数越多 ⇒ 上述任一环节出现"状态型残留"的机会越多，且**误差会沿后续 chunk 累积**。
这解释了三个此前难以理解的现象：

1. 为什么退化**平滑**而非阶跃（独立事件叠加）
2. 为什么**换一个 nonce 结果就翻转**（不同内容触发不同的残留位型）
3. 为什么**关掉任何单个优化都只改善一点**（每 chunk 的偏离源不止一处）

## 5. 方法论备注（本轮最贵的教训）

在找到 BAT 之前，我做了 6 次消融（SPEC / ENGRAM / QLI_NOCAND / ROPE_IDXSEL /
全部门控关闭 / FUSED_MC2+MULTISTREAM+SP7），**全部得到"有改善但不彻底"的结论**。

原因：**这些消融都是在新会话上跑的，而基线是旧会话** —— 旧会话自发退化到 ~12%，
新鲜会话是 ~56%，于是每个消融看起来都"有效"。

**补做新鲜基线后，6 个消融全部无显著差异。**

⇒ 正确做法是：**先建立可靠的新鲜基线，再做消融**；且任何对照都要"同等新鲜度"。
