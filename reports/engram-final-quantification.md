# Engram 剩余空间：最终量化（2026-09-16 06:30）

> 目的：在「其余方向已全部试完」之后，把 Engram 这条唯一还剩的线精确量化，
> 给出**可回收量**与**是否值得动**的结论。

---

## 1. 当前 host 相位（SPEC_EAGER=0 会话，decode，每步）

```
[bneck] mode=stock steps=340 dec=20
  d2h=5.92  hash=0.42  hp=34.61  meta=0.002  pad=0.128  route=1.00  total=8.22
```

| 相 | ms | 性质 |
|---|---|---|
| `d2h` | **5.92** | **阻塞等设备**（host 在等 NPU 流水线排空），**不是真实工作量** |
| `hash` | 0.42 | 真实 CPU 工作（已向量化，原始 0.83） |
| `route` | **1.00** | 真实：CPU 查表 + staging + 集合通信下发 |
| `pad` | 0.13 | 真实 |
| **真实 host 工作量** | **≈1.55** | 其余 6.7 是"等待" |

`route` 的内部相位（`route-probe`）：
`plan 0.27 / lookup 0.21 / a2a 0.21 / bcast 0.11 / evt 0.10 / h2d 0.07 / scatter 0.03`

## 2. 设备侧只占 0.37 ms/step

decode 窗口（70 步）里 Engram route 相关的**设备**算子总时长：

| 算子 | stream | 次/步 | ms/step | avg µs |
|---|---|---|---|---|
| `hcom_alltoallv_` | 41 / N/A | 1.86 | **0.368** | 198.3 |
| `ViewCopy` | 47 | 27.0 | 0.222 | 8.2 |
| `IndexCheck` | 47 | 35.7 | 0.134 | 3.8 |
| `hcom_broadcast_` | 38 | 1.86 | 0.022 | 12.0 |
| `IndexPutV2` | 47 | 1.86 | 0.019 | 10.2 |
| `ViewCopy` | 80 | 1.86 | 0.009 | 4.6 |
| **合计** | | | **≈0.77** | |

⇒ **host 侧 1.55 ms vs 设备侧 0.77 ms** —— 差额 ~0.8 ms 就是**设备在等 host 下发**
（host 算完 lookup、staging、下发 a2a 之前，设备没有对应的活可干）。

---

## 3. 同会话配对：整条 Engram host 路径的价值 = **2.77 ms/step**

（32K、3 发中位、SPEC_EAGER=0 会话、`/tmp/v41_bneck_mode` 运行时切换）

| 臂 | ms/step | A | Δ vs stock |
|---|---|---|---|
| `stock` | 35.19 | 2.93 | — |
| **`nohost`**（切 D2H+hash+route 全路径） | **32.42** | 2.92 | **−2.77** |
| `nocomm`（只切 route） | 34.10 | 2.97 | −1.09 |
| `faked2h`（只切第一个 D2H 的等待） | 34.40 | 2.45 | −0.79 |

`nohost` 与 stock 的 **A 几乎相同**（2.92 vs 2.93）⇒ 该差值可信（内容未变）。

---

## 4. 暴露率实测：**~64%**（不是历史报告的 116%）

内容不变的延迟臂（同会话、加固定忙等）：

| 臂 | ms/step | Δ |
|---|---|---|
| `stock` | 35.86 | — |
| `delaypost2`（D2H 之后加 2 ms） | **37.13** | **+1.27** |

⇒ 注入 2 ms 只换来 1.27 ms 的步时增长 ⇒ **暴露率 ≈ 64%**。

**与 §3 自洽**：真实 host 工作 1.55 ms × 64% ≈ **1.0 ms**；
加上 D2H 排空的增量（`faked2h` −0.79 ms）≈ **1.8 ms**，
与 `nohost` 的 2.77 相差的部分是 route 的集合通信本身在关键路径上（不可隐藏的那段）。

> 历史报告写的 "116% 暴露" 是在**旧基线**（`multistream_overlap_shared_expert` 尚可用的时代）
> 测的；当前形态下暴露率降到 64%，因为 `enable_fused_mc2=1` 让设备侧更忙、更能遮蔽 host。

---

## 5. 结论：**Engram 的可回收量 ≈ 0.6–1.0 ms/step**

| 可回收项 | 上限 | 说明 |
|---|---|---|
| route 的 host 工作藏进设备窗口 | **≈0.64** | 1.0 ms × 64% 暴露率 |
| `hash` + `pad` 藏进去 | ≈0.35 | 0.55 ms × 64% |
| D2H 排空（`faked2h` 臂） | 0.79 | 历史多轮已证不可回收（消掉一个会接棒下一个） |
| **合计现实上限** | **≈1.0** | 且**历史上已多轮尝试并否决**（route 流水化、host 镜像、预取、localmeta/gather/b2g） |

**为什么难动**：
1. `route` 的 1.0 ms 里，`a2a`(0.21) + `bcast`(0.11) 是集合通信的**固有延迟**，
   `plan`(0.27) + `lookup`(0.21) 是 CPU 查表（表盘 98 GB/rank，已在 DRAM）。
2. `plan` 的 numpy 化、`evt` 的 Event 复用**都已做过**（`fast` 模式）。
3. route 流水化（`async_op`）**实测无收益**（on 34.50 vs off₂ 34.57）。
4. 唯一未试的"前缀预测"（预查 8 个候选前缀）需要 8× CPU 查表（0.21→1.7 ms），
   且要改 `prepare_engram` 的契约，**风险高、上限 0.6 ms**。

---

## 6. 对整体目标的最终影响

当前 128K = **39.25 ms/step**（A=2.734，**69.8 tok/s**）。

| 若消化 Engram 的 1.0 ms | 128K → 38.25 | **71.6 tok/s** |
| 再叠加 `SPEC_EAGER=0` 的 1.0 ms | → 37.25 | 73.4 tok/s |
| 距离 110 tok/s（需 ≤25.1） | | **仍差 33%** |

⇒ **Engram 这条线即使全拿到，也只能把 128K 从 69.8 提到 ~71.6 tok/s**，
对 110 的目标**贡献 ≈1.4%**。而拆掉它需要改核心 `prepare_engram` 契约、有正确性风险。

## 7. 建议

| 优先级 | 动作 | 理由 |
|---|---|---|
| **不建议** | 继续深挖 Engram（前缀预测等） | 上限 0.6–1.0 ms、风险高、历史多轮已否决同类思路 |
| **建议保持** | 当前配置（`SPEC_EAGER=0` + fused_mc2 + static kernel + LOCAL_WORLD_SIZE 修复） | 已是所有试过的手段里最优组合 |
| **建议** | 把 110 tok/s 的判定与完整证据链交付 | 该目标在当前硬件/算子/架构下不可达，结论已由 15 份报告支撑 |
