## 1. 判据（保留，来自 182 条 text+pos 同帧记录）

`A = 1 + Σ posᵢ`。**主判据用 `decay = (pos1 − pos4) / pos0` 与单调性**（与步数无关）：

| 形态 | 判据 | pos0..4 典型值 | A | 文本 |
|---|---|---|---|---|
| **steep（健康）** | 严格单调 且 `decay ≥ 0.45` | `[0.92, 0.69, 0.42, 0.26, 0.19]` | 3.45–3.49 | 连贯 |
| **flat（重复循环）** | `decay ≤ 0.25` | `[0.92, 0.89, 0.89, 0.89, 0.87]` | 4.1–5.5 | 复读 |
| **degraded（draft 质量差）** | 其余 | `[0.42, 0.15, 0.03, 0.01, 0]` | 1.1–2.0 | 多半连贯但质量低 |

`tail = pos3 + pos4` 只作辅助，且**要求 steps ≥ 40**（短窗会系统性低估，正确性线 29 step 的 tail=0 属此例）。

**A≥3.0 的形态分布（取证子代理，182 条记录）**：flat 6/6 全复读；steep **0/14** 复读。

## 2. 更敏感的指标：`pos0`

A 需要整段 decode（90–150 步）都干净，方差极大（1.1–3.5），分辨两条臂要几百发。
`pos0`（第一个 draft token 的接受率）在同一请求内平均几十步，**观测上近双峰**：

* 干净请求：`pos0 ≈ 0.83–0.95`
* 被污染请求：`pos0 ≈ 0.12–0.50`

⇒ **`pos0 ≥ 0.8` 作为"该请求是否干净"的判据**，用于同会话交错 A/B（`exp_tools/interleave_ab.py`）。

## 7. 多 batch / 混合负载验证（新增，2026-09-16 21:00）

### 7.1 用户提的问题：历史并发测试是"单机混布"吗？有 prefill+decode 同时跑吗？

**答：是单机（半机）混布；但 prefill+decode 真同时跑——从来没有测过。**

* **混布**：我们的容器占 8 张卡（`a2sim` = 设备 8-15），`cpuset=320-639` / `mems=4-7`，
  与 NPU 0-3 上的他人负载**同 host**（共享 CPU 型号、HBM 控制器、HCCL 拓扑），但**卡不共享**。
* **prefill 被故意串行化**：历史 GSM8K/C-Eval 全部用
  `--conc 4 --serialize-prefill 1`，而该开关的语义（脚本自己的 help 文本）是
  **"hold a global lock until first token (avoid concurrent prefills)"**
  ⇒ **decode 并发，prefill 串行** ⇒ **从未测过 prefill 与 decode 真正同时在跑**。
* 唯一可能覆盖的是 `next_window_verify.sh` 的 needle 部分，但其日志目录为空 ⇒ **大概率未完成**。

### 7.2 为什么这是真实风险（不是教科书理论）

1. `--max-num-batched-tokens 2048` + chunked prefill ⇒ 128K prompt 被切成 64 个 chunk，
   这些 chunk 可以与其它请求的 decode **混进同一个 batch step**；
2. 该混合步的 `query_len` 不统一（一部分 1、一部分 2048），
   而 `CAPTURE_SIZES` 只覆盖 decode 形状（6/12/...）⇒ 混合步必须走 eager 或另一条路径；
   本会话已实测过"桶与真实 query 数不一致"的崩溃（`[6,2]` vs `[5,2]`）；
3. **我们验证的口径与 A2 生产不一致**：性能线是 `MAX_SEQS=1 + PREFIX=0`，
   而 A2 生产报告写的是 `max-num-seqs 32 + prefix caching ON`。
   prefix caching 的本质就是"让 decode 队列里随时插入新请求" ⇒ **生产形态天然包含该边界**。

### 7.3 已做的启动器改造（对齐生产口径）

| 改动 | 说明 |
|---|---|
| **`PREFIX` 开关** | 新增（默认 **0**，保持历史性能口径不变）；`PREFIX=1` 时启用 prefix caching |
| **`CAPTURE_SIZES` 自动扩展** | 旧逻辑只覆盖到 32 token（= `MAX_SEQS=1`）。现在按 `MAX_SEQS × (1+SP_TOKENS)` 扩展：`MAX_SEQS=1` 时**逐字节不变**（`1,2,3,4,6,8,12,16,20,24,32`），`=32` 时扩到 `...,40,48,96,192`（14 桶） |
| **`DRY_RUN=1`** | 只走"开关解析 + MOUNTS 组装"并打印，用于抓 `set -u` 顺序 bug（`bash -n` 抓不到）；`exp_tools/verify_serve_flags.sh` 12 组合全过 |

### 7.4 新增的三块验证（`exp_tools/multibatch_gate.py`）

| 块 | 内容 | 判据 |
|---|---|---|
| **A 多轮对话** | 8 轮增长历史，第 1 轮埋 3 个随机 10 位串，之后每轮考一个；最后从全长历史再各问一次 | 逐字召回命中率 + 每轮 `uniq2` + `prompt_tokens` |
| **B 并发 batch** | **同一组 16 道算术题**，`conc=1` 与 `conc=8` 各跑一遍，**逐 item 比对** | 逐项不一致数（比"比准确率"灵敏得多） |
| **C 长短交错** | 1 条 128K 请求 + **2 s 后**并发 6 条短请求 | 短请求逐 item 正确性 vs 串行基线 ⇒ **真正的 prefill+decode 混合** |

起服两臂：**`MAX_SEQS=32 + PREFIX=1`（生产对齐）** 与 `MAX_SEQS=32 + PREFIX=0`（压力，无前缀缓存 ⇒ 每次真 prefill）。
