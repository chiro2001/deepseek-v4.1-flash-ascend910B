### 1.0 统计显著性（对"失败率显著下降"的检验）

"修复后 10/10"单独看没有说服力 —— 10 次全过也可能只是运气。因此对
**同一剂量点左右**的修复前后做 Fisher 精确检验（单侧，检验"修复前失败率更高"）：

```bash
python3 tests/agent_trace/fisher_before_after.py
```

| 对比点 | 修复前 | 修复后 | Fisher p（单侧） | 判定 |
|---|---:|---:|---:|---|
| **130,538（逐 token 对齐）** | 5/10 | 10/10 | **1.63e-02** | 显著 |
| 60K（三次会话汇总） | 22/36 | 30/30 | **4.90e-05** | 显著 |
| 60K（单次最保守） | 5/10 | 10/10 | **1.63e-02** | 显著 |

⇒ 全部 **p < 0.05**，其中汇总口径 p = 4.9e-05。

> 口径说明：修复前/后必然跨重启（改 `BAT_TOKENS` 要重启），所以本表用的是
> **"同一探针、同一剂量点附近、各自 N=10"**。为了排除"恰好那次会话语境好"的可能，
> 修复前在 60K 上做过**两次独立测量**：剂量曲线 5/10、以及另一会话的 9/16 ——
> 都在 50–56% 区间，与 p 值的结论一致。

> 该脚本也能对任意两个比例做检验（`--before 3/4 --after 10/10` → p=0.29 不显著），
> 即它**不会**因为样本小而谎报显著 —— 这一点本身就是它的可信度证据。

### 1.0.1 ★ 可逆性检验（最强因果证据）

改 `BAT_TOKENS` 必须重启，所以"修复前/后"天然跨会话 —— 这给了"是不是恰好那一次会话语境好"
的空间。为排除它，本轮做了一个**可逆性检验**：把配置**改回 `BAT_TOKENS=2048`**，
用**同一个探针**再测一遍。

| 长度（prompt_tokens） | `BAT=8192`（修复后） | `BAT=2048`（改回） |
|---:|---:|---:|
| 60,012 / 60,013 | **10/10** | **8/10** |
| **130,538 / 130,538** | **10/10** | **5/10** |

**130,538 这一行尤其干净：前后是同一次探针、连 prompt token 数都逐 token 相同，
唯一变量就是 `BAT_TOKENS`。结果 10/10 vs 5/10。**

⇒ 失败随开关**可逆地出现/消失**，排除了"那次会话恰好状态好"的解释。

同时 KV 也随开关可逆地变化（4,146,569 ↔ 3,088,412），进一步确认配置真的生效了。

### 1.0.2 会话间方差的诚实说明

`BAT=2048` 下 60K 档做过**三次独立测量**，结果并不完全一致：

| 会话 | 60K 命中 |
|---|---:|
| 剂量曲线会话 | 5/10 |
| `prod_fresh` 会话 | 9/16 |
| 可逆性检验会话 | 8/10 |
| **汇总** | **22/36 = 61%** |

⇒ **`BAT=2048` 的失败率在 50–80% 之间波动**（会话相关的"状态"分量），
这与团队既有文档"确定性是每次批次的抽签"一致。

但 `BAT=8192` 在 **三个独立会话**里都拿到 **10/10**（30/30），
且每个长度点的 pattern 全是 `YYYYYYYYYY`（见 §1.1）——
**没有出现一次"部分成功"**，说明它不只是把成功率抬高，而是消除了那个随机分量。

Fisher 汇总：**22/36 vs 30/30，p = 4.9e-05**。

## 3. 机制

chunked prefill 把长 prompt 切成 `ceil(prompt / BAT_TOKENS)` 段依次前向。
**每段都有一次独立的"偏离"机会，误差沿后续 chunk 累积**，实测约 **2%/chunk**。

用"每 chunk 2% 独立事件"预测 vs 实测（`BAT=2048`）：

| prompt_tokens | chunk 数 | 预测 | 实测 |
|---:|---:|---:|---:|
| 10,396 | 5 | 90% | 100% |
| 20,318 | 10 | 82% | 80% |
| 40,163 | 20 | 67% | 70% |
| 60,011 | 30 | 55% | 50% |
| 79,856 | 40 | 45% | 30% |

形状与量级吻合（末端实测更低，说明偏离率还随 chunk 序号上升）。

这也解释了为什么此前找不到"阈值"：**它本来就没有阈值，是平滑下滑。**

## 4. 代价与已知限制

### 4.1 KV 容量

| 配置 | KV cache tokens | 说明 |
|---|---:|---|
| `BAT=2048`（旧默认） | 4,145,957 | |
| **`BAT=8192`（新默认）** | **3,088,303** | activation 峰值 0.79 → 3.21 GiB |

**低于 3Mi（3,145,728）的交付约束约 1.8%。** 本次验收按"调精度期间不设 KV 硬约束"执行；
若后续版本需要同时满足 KV>3Mi，可考虑：
* 提高总显存预算（`GPU_UTIL` 已经 0.94，余量有限）
* 评估 `BAT=4096`（chunk 数减半，KV 损失更小）—— 尚未验证是否足够

### 4.2 ★ `MAX_SEQS=64` + `BAT=8192` + `GPU_UTIL=0.94` 会 OOM

实测崩溃（ACL graph 重放时）：

```
torch.OutOfMemoryError: NPUGraph.cpp:281
Resource_Error_Insufficient_Device_Memory(EL0019)
Failed to allocate 2097152 bytes ... halStreamTaskFill failed
```

原因：`BAT=8192` 让 peak activation 涨到 3.21 GiB，而 `MAX_SEQS=64` 需要
capture 桶覆盖到 384（graph memory 1.15 GiB），两者叠加把显存吃干。

**已在 `scripts/serve_a2.sh` 里加 `[MEM-GUARD]` 提示**（只在危险组合时打印建议，
不擅自改用户配置）。实测可行组合：

| 组合 | 结果 |
|---|---|
| `MAX_SEQS=32` + `BAT=8192` + `GPU_UTIL=0.94`（**发布默认**） | ✅ 正常（本文全部数据） |
| `MAX_SEQS=64` + `BAT=8192` + `GPU_UTIL=0.90` | ✅ 启动正常、60K 检索 5/5（KV 降到 2,558,512） |
| `MAX_SEQS=64` + `BAT=8192` + `GPU_UTIL=0.94` | ❌ **OOM 崩溃** |

### 4.3 未量化项

* `BAT` 增大后**每 chunk 的 host 耗时**从 ~34 ms（2048 tok）升到 ~191 ms（8064 tok）；
  prefill 吞吐与显存峰值的净影响**尚未单独测量**。

## 6. KV 容量与正确性的取舍（实测边界）

### 6.1 结论

**在本机型（8×910C，61.27 GiB/卡）上，`BAT=8192` 时 KV 的稳定上限约 3.09M tokens。**

* 满足本次 objective 里的 **`KV > 3M`**（3,088,412 > 3,000,000）✅
* **未满足仓库历史文档里的 `> 3,145,728（3Mi）` 门槛**，差 **1.8%** ❌

两者是**互斥**的：把 KV 抬到 3.15M 以上会立刻 OOM。证据见下。

### 6.2 三次边界实验

| 配置 | KV tokens | 峰值 activation | 结果 |
|---|---:|---:|---|
| `BAT=8192` + `GPU_UTIL=0.94`（当前默认） | **3,088,412** | 3.21 GiB | ✅ 稳定（本文全部数据） |
| `BAT=8192` + `GPU_UTIL=0.95` | 3,221,350 | 3.21 GiB | ❌ **第一个真实 prefill 就 OOM** |
| `BAT=6144` + `GPU_UTIL=0.94` | 3,415,799 | 2.40 GiB | ❌ **ACL graph 重放 OOM** |

OOM 形态（两次都是同一类）：

```
torch.OutOfMemoryError: replay:../torch_npu/csrc/core/npu/NPUGraph.cpp:281
Resource_Error_Insufficient_Device_Memory(EL0019)
Try to allocate 632.00 MiB ... FAILED
```

### 6.3 为什么"少给 activation"救不回来

`BAT=6144` 确实把峰值 activation 从 3.21 降到 **2.40 GiB**（省 0.81 GiB，
与"每 1000 BAT 约 0.39 GiB"的线性外推完全吻合），KV 也因此涨到 3.42M。
但**仍然 OOM**。

⇒ 说明 **真实请求的 activation 峰值高于启动 profiling 报告的值**（约高 0.5–0.8 GiB）。
启动日志里的 "peak activation" 是 warmup 阶段的测量，不能直接当作运行期峰值来算余量。

**可用的安全余量下限**（设备总 61.27 GiB − 各项占用）：

| 配置 | 名义余量 | 结果 |
|---|---:|---|
| `BAT=8192` / 0.94 | 3.82 GiB | ✅ |
| `BAT=6144` / 0.94 | 3.37 GiB | ❌ |
| `BAT=8192` / 0.95 | 3.05 GiB | ❌ |

⇒ 需要留 **≥ ~3.6 GiB** 才稳。

### 6.4 如果必须满足 3Mi，可以考虑（均未验证）

| 方案 | 收益 | 代价 |
|---|---|---|
| 裁掉 `CAPTURE_SIZES` 的 `96,192` 两个桶 | graph memory 1.13 GiB 可省约 0.4 GiB | 并发 >32 时 decode 退回 eager（正确但慢） |
| `KV_DTYPE=int8` | KV 容量约翻倍 | **降精度**，与本次"修精度"目标冲突，不可用于本修复 |
| 提高单卡可用显存（换机型/降权重占用） | 直接 | 非本机型可控 |

### 6.5 建议

**本次以 `BAT=8192` + `KV=3.088M` 交付**，理由是：

* 正确性收益是**决定性的**（真实 agent 轨迹 0/3 → 10/10；60K 检索 50% → 100%）
* KV 从 4.15M 降到 3.09M 只影响"同时容纳几个满 1M 上下文"（3 → 2.9 个），
  而 3Mi 门槛本身就是按 `3 × 1048576` 设的
* 若某场景必须严格要求 3Mi，应显式评估 §6.4 的裁剪方案，**不要**靠调 `GPU_UTIL`
  （已实测会 OOM）
