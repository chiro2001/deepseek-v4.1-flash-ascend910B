# 061 — 把「容量倍数」换算成**并发 × 上下文**的边界（「32×128K 从不可能变可行」到底是什么意思）

> 2026-09-22 14:0x CST。执行：**主代理**（纯算术，**不占卡**）。
> 起因：`DELIVERY.md` 补上「档 C / 档 D」之后，**「×1.1356 / ×1.3146」这些倍率没有人能直接感知** ——
> 需要换成「**这台机器能开多少会话、开多长**」。
> 标记：【实测】/【算术】/【推断】/【未确认】。

---

## 0. 一句话

★★ **「32 × 128K 从不可能变可行」是 档 C 带来的**（档 B 要 421 GiB = 余量的 95%，紧到不可用；
档 C 只要 280 GiB = 63%）；**档 D 让它变宽松**（227 GiB = 51%）。
★ 但 **64 × 128K 在任何档下都不可能**（最少 ≈383 GiB 宿主）——
**别把「×1.91」读成「并发能翻好几倍」**：它翻的是**单请求 KV 的账**。

---

## 1. 口径（必须先钉死，否则数字没意义）

| 量 | 值 | 来源 |
|---|---|---|
| `cpu_bytes_to_use`（池的记账值） | **56 GiB** = 60,129,542,144 B | `logs/042` 的 8 卡臂；`serve_a2_offload.sh` 的默认 |
| 真实 `avail`（模型用的） | **4 GiB**（`--kv-cache-memory-bytes 4294967296`） | ★ **`050 §1.6` 的 9 个实测点都是这个口径** |
| `max_len` / `max_seqs` | 131,072 / 16 | `logs/042` |
| `block` / `window` / `max_in_flight` | 128 / 128 / 2×8192 | 源码几何 |

⚠️ **两个 `avail` 不能混**：`050` 的模型用的是**引擎里给 KV 的 4 GiB**，
而 `logs/042` 的 **197.21 GiB 是宿主实占**（池的 24.65 GiB/worker × 8）。本日志分开算、再对齐。

## 2. 【算术】每请求的 KV 账（**这是新算的部分**）

模型（`050 §1.6`，9 个实测点逐字命中；`C2_draft64` 的 `c2_model.py` 是它的可复跑实现）：
```
Σslot_pages = 3 × max(kv+index(ratio2), state, swa, draft) + max(kv+index(ratio1), swa)
BPR         = cdiv(max_len, 128) + 1 + 10 × P(128) + P(draft_block)
P(b)        = cdiv(min(window−1 + max_in_flight, max_len), b) + 1
tokens      = int((avail // Σslot_pages − 1) / BPR × max_len)
```
**把 `avail = 4 GiB` 固定，问「每个请求占多少页」** ⇒ 直接读 `BPR` 与 `Σslot_pages`：

| 档 | Σslot_pages | BPR（每请求页数） | `avail=4GiB` 时的 tokens | **每请求宿主 KV**（算术） |
|---|---:|---:|---:|---:|
| 档 B | 540,928 | 2,471 | 427,643 | **13.16 GiB** |
| **★ 档 C** | 540,928（注） | 2,471 | 427,643（= 档 B） | ★ **8.76 GiB** |
| **★ 档 D** | 476,416 | 2,471 | 485,610 | ★ **7.10 GiB** |
| ②c（预测） | 282,880 | 2,600 | 777,318 | 6.29 GiB |
| ②a（预测） | 282,880 | 2,471 | 817,898 | 5.99 GiB |

> ★ **注（档 C 的 Σ 为什么也是 540,928）**：档 C 只把 **SWA 与 state** 压小，
> 而 slots 0–2 的 binding 是 **draft 组（BF16、131,072）** ⇒ Σ 不变 ⇒ **HBM 容量 ×1.0000**。
> 但 **宿主**账不同：档 C 的 20 张张量里 SWA 平面**真的缩了**（Σpage 910,208 → **832,128**）
> ⇒ 同样 `OFFLOAD_GB=56`，每 worker 的宿主实占从 24.65 GiB 降到 **18.75 GiB**（`logs/048` 实测）。
> **「每请求宿主 KV」列就是把这条实测按比例摊到 16 个请求上**（197.21/16 与 150.01/16）。

## 3. 【算术】换算成「并发 × 上下文」

| 档 | **16 × 128K** | **32 × 128K** | **64 × 128K** | 余量 442 GiB 的占比（32×128K） |
|---|---|---|---|---|
| 档 B | 210.6 GiB | **421.3 GiB** | 842.6 GiB ⛔ | **95%** ⚠️ 紧到不可用 |
| **★ 档 C** | 140.2 GiB | ★ **280.4 GiB** | 560.8 GiB ⛔ | ★ **63%** 可行 |
| **★ 档 D** | 113.6 GiB | ★ **227.3 GiB** | 454.6 GiB ⛔ | ★ **51%** 宽松 |
| ②c | 100.7 GiB | 201.4 GiB | 402.7 GiB ⛔ | 46% |
| ②a | 95.8 GiB | 191.6 GiB | 383.2 GiB ⛔ | 43% |

★★ **三条结论**：
1. **32 × 128K 是 档 C 的分水岭**：档 B 要 421 GiB（余量的 95% ⇒ 实际不可用），
   档 C 降到 **280 GiB（63%）**，档 D 再降到 **227 GiB（51%）**；
2. **64 × 128K 在任何档下都不可能** —— 即使 ②a（每请求 5.99 GiB）也要 **383 GiB**，
   再乘 1.15 的安全系数就是 **441 GiB ≈ 整个余量**，没有任何操作空间；
3. ★ **「×1.91」翻的是「单请求 KV 的账」，不是「并发数」** ——
   从 13.16 GiB/请求 降到 5.99 GiB/请求 是 **×2.2**，但能不能开 32 路还取决于
   **服务本身、宿主余量、以及真实 trace 的前缀唯一率**（见 `README.md` §4）。

---

## 4. ⚠️ 宿主口径的不确定度（**必须与数字一起看**）

上面的「每请求宿主 KV」是**算术外推**，而**实测只到「16×128K 的池总量」这一格**：
```
档 B 197.21 GiB【实测·8 卡】      档 C 150.01 GiB【实测·8 卡】
```
**没被计入的**：`torch` 分配器的碎片/对齐、`aclrtHostRegister` 的额外占用
（`030` 实测「**第一次注册一次多花 ~589 MiB**」）、以及 KV 之外的服务自身内存。
⇒ ★ **建议按 1.15× 留余量**：档 C 的 32×128K 实际按 **≈322 GiB** 规划，仍在 442 GiB 之内。

---

## 5. 诚实边界

1. ★ **本日志是纯算术 + 外推，没有任何新实测**；
2. ★ **只算到「池要多少宿主」**，**没算**「服务自身 + 余量」⇒ 上面那些「可行」是**必要条件不是充分条件**；
3. ⚠️ **`deliverable` 里的 16×128K 那两格是实测，其余（32/64 路）都是按比例外推**；
4. ⚠️ ②c / ②a 两行用的是**预测容量**（777k / 818k），端到端在验（`T_draftceiling` 的 c0 臂 / `D_draftINT8` 的 c1 臂）；
5. ★ **真实 agent 流量的前缀唯一率会显著改变这张表**（`README.md` §4 的「16 倍差」）——
   本表是**最坏口径**（每条请求前缀互不相同）。
