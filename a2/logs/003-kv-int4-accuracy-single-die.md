> 服务于内网 **A2 = 8×910B3** 的使能。
> 全部结论标 **【实测】/【推断】/【未确认】**；缺的格子写"未确认"，不用相邻数字顶替。

## 0. 口径（先读这一段，否则数字会被误读）

### 0.1 这是**量化-反量化 roundtrip 的软件仿真**，不是算子性能

**【实测】Ascend 上没有 4-bit KV 算子**。三条独立证据：

| 证据 | 结果 |
|---|---|
| `kv_quant_sparse_attn_sharedkv` | A5（ascend950）专属；A2/A3 不支持 |
| `kv_quant_sparse_flash_attention` | **INT8**（`key` 必须是 `.to(torch.int8)`，见 nightly 测试） |
| `grep -riE 'fp4\|float4' vllm_ascend/` | **零命中**（本代理复核，2026-09-21） |

所以本实验**不测任何 4-bit kernel 的性能**，只回答一个物理问题：

> **把 BF16 的 long-KV 压到 4-bit、再还原成 BF16 喂给现有算子，attention 输出错多少？**

方法：`K_bf16 → 分组对称/FP4 量化 → 反量化回 bf16 → torch.ops.npu.npu_sparse_flash_attention`。
**参考臂**用未量化的 BF16 KV，**同一个算子、同一批 Q、同一份 `sparse_indices`**。

### 0.2 ★ 量化点：卡在 **long-KV 平面**，不是 compressor 的 `latent`

**【实测，代码证据】** 我量化的是 `attn.long_kv_cache.kv_cache[0]` 那 4 个共享 512 维平面 ——
也就是 KV 账里定价 4096 B/token 的那个张量。**不是** compressor 输出的 `latent`。

这条区别是红线，代码上分得很清楚（`vllm_ascend/attention/dsa_v41.py:418-437`）：

```python
attn.indexer.update_keys(latent, index_slots, source_cos, source_sin)   # ← indexer 吃 latent
...
scatter_cache_sk(attn.long_kv_cache.kv_cache[0], long_slots, latent.squeeze(1))  # ← long-KV 也吃 latent
```

两条路在 `latent` 处分叉：**indexer 先拿、long-KV 后拿**。
如果在 `latent` 上量化，indexer 会一起吃到，误差里就混进"选错块"，不再是纯量化误差。
**本实验完全避开了这一点。**

### 0.3 数据是**合成但分布贴真实**（真实权重单层 = 未做，见 §7）

KV 的合成方式：逐通道对数正态 spread（σ=0.5）+ 2% outlier 通道（×4），
Rope 的 64 维真的做了 interleaved 旋转。幅度标定到 attention logits 的 std ≈ 1.3（softmax 不退化）。

**为什么加 per-channel spread**：真实 MLA latent 的逐通道方差差异很大，这正是"分组"能救回精度的原因。
不做这个，group 扫描会全部看起来一样。**这一点用 σ 扫描验证过（§3.5）**，
并给出了一个**不需要相信合成分布**的下界（σ=0 的纯 i.i.d. 高斯，§3.5 表 B）。

## 1. ★ 问题一：910B3 到底支不支持 4-bit 数据类型

**只读探测**。容器 `prbench-c1`（die 6），CANN 9.1.0，torch 2.10.0+cpu，torch_npu 2.10.0.post4。
原始输出：[`raw/003-probe1-fp4-dtype.txt`](raw/003-probe1-fp4-dtype.txt)、[`raw/003-probe2-fp4-ops.txt`](raw/003-probe2-fp4-ops.txt)。

### 1.1 分三层，答案不一样

| 层 | 结论 | 硬证据 |
|---|---|---|
| **dtype 符号** | ✅ **有**【实测】 | `torch.float4_e2m1fn_x2` 存在；`torch_npu.float4_e2m1fn_x2 = 296`；另有 `float4_e1m2fn_x2`；`torch.int4` / `torch.uint4` 也在 |
| **NPU 上分配** | ✅ **能**【实测】 | `torch.empty(64, dtype=torch.float4_e2m1fn_x2, device='npu')` → `torch.Size([64])`；`uint8.view(fp4)` 也成功 |
| **bf16 → fp4 转换** | ❌ **不能**【实测】 | `RuntimeError: copy_d2d_baseformat_opapi ... call aclnnInplaceCopy failed, error code is 161002`；反向 fp4 → bf16 同样失败 |
| **量化算子产出 fp4** | ❌ **不能**【实测】 | `npu_dynamic_mx_quant(..., dst_type=296)` → `aclnnDynamicMxQuantV2 failed, 161001`（**同一个调用改成 fp8 也失败**，说明是算子/驱动侧整体不可用，不是 fp4 单独被拒）<br>`npu_quantize` 直接报：`Param (dtype) must be Int8, UInt8, Int32, HiFloat8, Float8_e4m3fn, Float8_e5m2` —— **白名单里根本没有 fp4/int4** |
| **CANN 里有 fp4 算子** | ❌ **没有**【实测】 | `grep -rliE 'nvfp4\|float4_e2m1\|fp4' $ASCEND_OPP_PATH/built-in/op_impl/ai_core/tbe/op_info_cfg` → **0 个文件** |

### 1.2 口径澄清：`torch_npu.float4_e2m1fn_x2 = 296` **不等于**"910B3 支持 FP4"

**【实测】**`torch_npu` 暴露这个常量，`vllm_ascend/ops/fused_moe/moe_quant.py` 也确实在用它做 **W4A8 的 W4**。
但**权重侧走的是另一条路**（离线打包成 `int8` 张量 + scale，运行时按 int4 解包），
**不是**运行时的 fp4 dtype 转换。

**【实测】反证**：连 **fp8** 的运行时转换在本容器里都失败
（`bf16 → fp8_e4m3fn` 报 `aclnnInplaceCopy ... 561103`）。
所以"dtype 常量存在"**不能**推出"这条 datatype 通路可用"。

> **一句话**：910B3 上 **4-bit 只能是一个存储/打包格式，不能是一条计算通路**。
> 这恰好就是本实验做 roundtrip 仿真的理由，也是"要真做 4-bit KV 就得自己写 kernel"的根据。

**服务类型归属（非本次探测所得，仅记录坐标）**：容器内 `torch.npu.get_device_name(0) = "Ascend910_9382"`，
按 `vllm_ascend/device/hardware.py:39` 映射到 **`AscendDeviceType.A3`**；`npu-smi` 报 `IT22HMDA_2_S`（双 die 板）。
**【未确认】**A3 是 910C、A2 是 910B3，两者不是同一颗芯片。本实验回答了"**在 A3 上与 A2 同代的 CANN 9.1.0 / torch_npu 2.10 栈**上 4-bit 可不可用"，
**A2（910B3）上的同款探测本代理没跑过**。

## 2. 方法：形状与调用方式（全部来自代码/nightly，没有自己编）

| 项 | 值 | 出处 |
|---|---|---|
| `head_dim` | 512 | `config.json` `text_config.head_dim`；`model.py:693` `width = config.head_dim` |
| `rope_head_dim` | 64 | `config.json` `qk_rope_head_dim` |
| `nope` | 448 = 512−64 | `partial_slice=[nope_head_dim, head_dim]`（`dsa_v41_cp.py:169`） |
| query heads | 64 | `config.json` `num_attention_heads` |
| KV heads | 1 | `config.json` `num_key_value_heads`（共享 MLA latent） |
| `index_topk` | 512 | `config.json` `index_topk` |
| `block_size` | 256 | nightly 测试 `test_kv_quant_sparse_flash_attention.py` |
| `softmax_scale` | `512**-0.5` | `model.py:694` |
| layout | `BSND` / `PA_BSND`，`sparse_block_size=1`，`sparse_mode=3`，`attention_mode=2` | nightly 测试 + `device_op.py:452` |
| 算子 | `torch.ops.npu.npu_sparse_flash_attention`（**BF16**） | `sfa_v1.py:154` 的非-A5 分支，即 V4.1 实际走的那个 |

**★ 形状的重要更正（实测踩出来的）**：算子的 `query`/`key` 是 **512 维 nope**，
**rope 是独立的 64 维入参 `query_rope`/`key_rope`**（`device_op.py:452`）。
一开始我把 rope 拼在 512 里传，算子直接报 `Shape of tensor queryRope is nullptr`。
⇒ **512 里没有任何维用来放 rope**。这一点与 K8_int8 的观察（算子要求 576 = 512+64）一致，
**也说明 V4.1 与那个 INT8 算子在维度上确实对不上**。

**正确性自检**【实测】：在 64 query × 4096 kv 上把算子输出与纯 torch 参考实现对比，
`rel_l2 = 1.06e-3`、`max_abs = 0.25`（bf16 级）⇒ **harness 测的是它该测的东西**。

### 量化方案

- **INT4/INT8**：**对称**、per-(token, head, **group 通道数**) 一个 fp16 scale，
  `scale = amax/2^(b-1)`，round-to-nearest，clamp 后反量化。group = 16 / 32 / 64 / 128 / 512（512 = 整条 head，即"不分组"）。
- **FP4 E2M1**（论文的格式）：非均匀电平 `{0,.5,1,1.5,2,3,4,6}`，逐 group 缩放到 amax→6.0。
  容量按论文口径算：**payload 0.5 B + 每 16 通道 1 个 E4M3（1 B）scale**。
- 所有臂**共用同一份 `sparse_indices`** ⇒ 差异**只**来自 KV 量化。

### 3.2 三条发现

**① 分组粒度是主线，而且收益是单调的**【实测】

```
prefill 4K · B1   rel_L2:  g512 41.2%  →  g128 23.6%  →  g64 17.6%  →  g32 13.0%  →  g16 9.11%
cos_p50:                   .9223       →   .9726      →   .9855     →   .9920     →   .9958
```

每细化一档 group，**rel_L2 大约降 0.74×**（g128→g64 0.745、g64→g32 0.739、g32→g16 0.702）。
⇒ **"per-token-head 不分组"（g512，即 KV 账里的 4096 B→1024 B 那个最激进的版本）是不可接受的**：
`cos_p50 = 0.922`、`cos_min = −0.258`（**方向都反了**）、`rel_L2 = 41%`。

**② FP4 E2M1 显著好于同 group 的 INT4**【实测】

`FP4 g16 = 7.54%` vs `INT4 g16 = 9.11%`（同 group，flatter 更好）；
`FP4 g16 (7.54%)` 甚至**优于 group 大 2 倍的 `INT4 g32 (13.0%)`**，
而 FP4 g16 的容量（0.5625 B/elem）只比 INT4 g32 的 0.5625 B/elem **完全一样**。

⇒ **在同样的字节预算下，E2M1 的非均匀电平比均匀 INT4 更划算**（4/6 这两档替 outlier 兜了底）。
**这是"要省字节就省在电平设计上，不要省在分组上"的直接量化证据。**

**③ 序列长度和 batch 几乎不影响结果**【实测】

把每个臂在**全部 13 个 case**（4K / 32K / 128K × B1 / B8 × prefill / decode）上扫一遍，
`rel_L2` 的**极差**是：

| 臂 | 最小 | 最大 | 极差 / 最小 |
|---|---:|---:|---:|
| INT8 g128 | 2.18% | 2.34% | **7.3%** |
| INT4 g16 | 8.68% | 10.1% | 16% |
| INT4 g32 | 12.6% | 13.2% | **4.8%** |
| INT4 g64 | 16.1% | 18.1% | 12% |
| INT4 g128 | 22.1% | 24.2% | 9.5% |

`cos_p50` 的极差 < 0.004。**没有单调趋势**（decode 4K·B1 反而总是最差的一格）。

⇒ **【推断，不是实测】** 误差曲线在整个长度/batch 域上近似**平移不变**，
所以**同一档位的结论可以外推**。⚠️ 注意这只在**测过的模板**（同一套合成 σ=0.5 分布）内成立，
**不是**"真实模型上长度不影响误差"的意思。真实 KS 分布的**尺度**会平移整条曲线（见 §3.5b 的方向）。

### 3.3 尾部风险：均值会骗人

**【实测】**`rel_L2` 和 `cos_p50` 是**聚合量**。看尾部才看得出问题
（原始：[`raw/003-tailstats.json`](raw/003-tailstats.json)）：

| case = prefill 128K · B1 | rel_L2 | cos_p0.1 | cos_p1 | **cos_min** | **frac(cos<0.90)** | frac(cos<0.99) |
|---|---:|---:|---:|---:|---:|---:|
| INT8 g128 | 2.18% | .9990 | .9995 | **0.990** | 0 | 0 |
| FP4 E2M1 g16 | 7.54% | .9801 | .9901 | **0.823** | 1.3e-6 | 0.97% |
| INT4 g32 | 13.1% | .9294 | .9653 | **0.203** | **2.7e-4** | **30.5%** |
| INT4 g16 | 9.14% | .9702 | .9851 | 0.789 | 8.0e-6 | 3.3% |
| INT4 g128 | 23.7% | .8075 | .8997 | **0.013** | **1.0e-2** | **99.6%** |

**怎么读这套数字**：

* **INT8 g128**：`cos_min = 0.990` —— **没有尾部**，最差的向量也有 0.99。
* **FP4 g16**：p0.1 = 0.980，只有 **0.97%** 的向量低于 0.99，`cos_min = 0.823`。**可接受量级**。
* **INT4 g32**：p50 = 0.992 看着不错，但 **30.5% 的向量低于 0.99**，最差的到 **0.203**（等于完全失效的一路头）。

⇒ **结论**：**per-token-head（g512）和 g128 直接出局**；`g64` 也危险（30%+ 低于 0.99）。
只有 **FP4/E2M1 g16** 与 **INT4 g32/g16** 落在"尾部还讲得通"的区间。

### 3.5 合成分布敏感度 —— 兼一个"不需要相信合成分布"的下界【实测】

#### (a) 逐通道 spread σ（prefill 4K · B1，`--sigma`）

σ 是我加在 KV 上的逐通道对数正态 spread。**σ=0 是纯 i.i.d. 高斯** ——
这是**对分组量化最有利**的分布（没有离群通道可伤），因此它是**最乐观的下界**：

| 臂 | **σ=0.0（最有利）** | σ=0.25 | **σ=0.5（主表）** |
|---|---:|---:|---:|
| INT8 g128 | **1.32%** | 1.76% | **2.21%** |
| FP4 g16 | — | — | **7.56%** |
| INT4 g512（不分组） | **34.8%** | 46.1% | **41.2%** |
| INT4 g128 | **23.5%** | 28.3% | **23.6%** |
| INT4 g64 | **18.3%** | 21.1% | **17.6%** |
| INT4 g32 | **14.1%** | 15.7% | **13.0%** |
| INT4 g16 | **10.8%** | 11.7% | **9.11%** |

（原始：[`raw/003-sigma000.json`](raw/003-sigma000.json)、[`raw/003-sigma025.json`](raw/003-sigma025.json)。）

**两个结论**：

1. **spread 对最粗的两档影响明显**（g512：σ=0 时 34.8% → σ=0.5 时 41.2%），
   对细分组几乎不影响（g16：10.8% → 9.11%，**方向相反**，属于单次抽样的噪声）。
   ⇒ **对"g16/g32 够不够"这个问题，spread 不是主导因素。**
2. **不单调**：σ=0.25 的 g512（46.1%）比 σ=0.5（41.2%）**更差**。
   这是**单次通道抽样的随机性**，说明 **σ=0.25 那一列不该被当成趋势读**。

> ★ **所以"INT4 不分组 / g128 不够"这个结论不依赖于我对合成分布的假设**：
> 即便在**最有利**的 σ=0（完全没有离群通道）下，
> **INT4 g512 仍然是 34.8%、INT4 g128 仍然是 23.5%** —— 照样不可用。
> 这是整个 §3 最不需要信任合成分布的一格，也是它最值得写下来的原因。

#### (b) attention logits 尺度（`--sharp`，只改 query 幅度，不改 KV 分布）

| 臂 | sharp=0.5（平 softmax） | **sharp=1.0（主表）** | sharp=2.0（尖 softmax） |
|---|---:|---:|---:|
| INT8 g128 | 1.97% | **2.21%** | 2.45% |
| FP4 g16 | 6.41% | **7.56%** | 8.79% |
| INT4 g32 | 10.7% | **13.0%** | 15.4% |
| INT4 g16 | 7.66% | **9.11%** | 10.6% |

**【实测】** softmax 越尖，量化误差越大（`rel_L2` 涨 11–28% 相对），但**排序不变**。
⇒ 真实模型的 logits 分布如果比我们合成的更尖，**上述所有数字会整体变差，但档位排序（§3.2①）不会翻**。

### 3.6 4-bit 特有的额外一节：把 64 维 rope 也量化会怎样【实测】

**动机**：在 V4.1 里，rope 的 64 维**就在**那条 512 维向量里（原地旋转）。
上面所有主结果**都把 rope 当作独立的、未量化的一路**（像 V4 那样）。
如果真要按 long-KV 那 4096 B 整片存 4-bit，**rope 会被一起量化**。

**结果**：影响**很小**（prefill 4K · B1）：

| 臂 | rope 不量化 | **rope 也量化** | 变化 |
|---|---:|---:|---:|
| INT8 g128 | 2.212% | **2.212%** | 0 |
| INT4 g32 | 12.98% | **13.00%** | +0.02pp |
| INT4 g16 | 9.112% | **9.131%** | +0.02pp |

（这一轮只跑了这三档；`g64`/`g128`/`g512` 与 FP4 的"rope 也量化"**没测**。）

**原因**【推断】：rope 的 64 维**只参与 logits、不参与 value 加权**，
而 softmax 对 logits 的整体尺度有补偿；量化引入的是**近似随机的相位扰动**，
512 个已选 token 求和后自平均掉了（`softmax_scale = 0.0442` 把 logits 压得很平）。

⇒ **"rope 要不要单独留 BF16"不是这条路上的主要矛盾**，不必为它设计特例。
（原始：[`raw/003-quant_rope_4K.json`](raw/003-quant_rope_4K.json)）

## 5. ★ 问题四：容量收益（相对 4421 B/token/rank）

**口径**：只动 4 个共享 long-KV 平面（4096 B）；**4 个 indexer 平面 325 B 不动**
（K8_int8 已独立确认 indexer 走自己的 INT8 平面，且没有 4-bit 需求）。
scale 用 fp16（2 B）；FP4 那行按论文口径用每 16 通道 1 个 E4M3（1 B）。

| 方案 | long-KV | + indexer | **B/token/rank** | **相对 4421 节省** | 1M 上下文/rank | **同 14.40 GiB（HBM）能装** | 8 rank 1M 合计 |
|---|---:|---:|---:|---:|---:|---:|---:|
| BF16（现况） | 4096 | 325 | **4421** | — | 4.32 GiB | 3.50 M token | 34.5 GiB |
| INT8 g128 | 2080 | 325 | **2405** | **45.6%** | 2.35 GiB | 6.42 M | 18.8 GiB |
| ★ **FP4 E2M1 g16** | 1152 | 325 | **1477** | **66.6%** | 1.44 GiB | **10.46 M（×2.99）** | 11.5 GiB |
| INT4 g32 | 1152 | 325 | **1477** | **66.6%** | 1.44 GiB | **10.46 M（×2.99）** | 11.5 GiB |

> **容量的边际收益是递减的，而精度代价是陡增的。**

按本次实测，**那一档不可用**；能站住的 4-bit 档位是 **1152–1605 B（省 63.7–66.6%）**，
而不是 1024 B。**请把预期从"省 76%"下修到"省 64–67%"。**

## 6. ★ 关键假设验证：量化 long-KV 会不会影响 sparse index 选择？

### 6.1 【实测，代码证据】不会 —— 两条路在读端就是分开的

```
DeepseekV41Indexer.select(..., source_cache, ...)        # dsa_v41.py:448
    ↑ context[self.index_k_source_prefix]
    index_k_source_prefix = f"{source}.indexer.k_cache"   # model.py:729

indexer.k_cache = DeepseekV41CacheLayer(
    AscendMLAAttentionSpec(num_kv_heads=1, head_size=128,
                           dtype=torch.int8, scale_dim=1))  # indexer.py:73-84
```

* indexer 的 key 是**独立的 128 维 INT8 平面**（`index_head_dim=128`，`index_n_heads=32`，来自 config），
  由 `torch_npu.npu_dynamic_quant(key, dst_type=torch.int8)` 现场量化（`indexer.py:107`）后 scatter 进自己的 cache；
* long-KV 是**另一个** spec（`head_size=512, dtype=bfloat16`，`model.py:700-708`）；
* 两者在 `latent` 处分叉后**再无交集**：attention 读 `long_kv_cache`，
  indexer 读 `k_cache`（`cache_config.py:61-63` 把它们作为**两个不同的物理页**登记进同一个 layer tuple）。

⇒ **【实测】量化 `long_kv_cache` 不会改变 sparse index 选择。** 我们的理解**成立**。

### 6.2 【实测，反事实】如果 indexer 真读了 long-KV，会有多糟？

为了不把"代码上不可能"变成"我们没测"（也让本表能和 K8_int8 那张表并排），
做了一个反事实：**用同一份 K 既选 top-k 又算 attention**（= K8_int8 的保守口径），
量 BF16 选出的 top-512 与量化后选出的 top-512 的重合度（4K，64 个 query）：

| 臂 | **top-512 重合度（均值）** | 最差 query | p10 | KV rel_L2 |
|---|---:|---:|---:|---:|
| INT8 g128 | **99.81%** | 99.41% | — | 1.67% |
| INT4 g32 | **98.38%** | 93.16% | — | 15.4% |
| INT4 g128 | **97.28%** | 90.04% | — | 26.1% |

（原始：[`raw/003-topk_overlap.json`](raw/003-topk_overlap.json)）

**【实测】 上表三行**；**【推断】 由它出发的两条结论**：

1. **【实测】**即使**在反事实下**，14%–26% 量级的 KV 误差也只把 top-k 改变 **1.6–2.7%**。
2. **【推断】**选择本身对 KV 误差是鲁棒的：真实 indexer 读的是 1.67% 误差的 INT8 平面
   （由 §3 的 INT8 臂 KV rel_L2 推得，**不是**在 indexer 平面上直接测的），
   对应上表 `99.8%` 那一行 ⇒ **选择路径上几乎没有风险**。
3. **【实测，口径】**我的主表**没有**用这个机制 —— 主表把 `sparse_indices` 冻结，
   所以量到的是**纯 attention 侧误差**。**§3 的数字是"纯量化误差"；§6.2 的数字是"量化误差 + 选错块"**。
   两者必须分开读，**不能相加、也不能互相顶替**。

## 7. ★ 额外一节：4-bit 误差的锚点 —— 拿不到，如实写"缺锚点"

任务要求：给 4-bit KV 误差找一个"已知可接受"的锚点。**结论：本代理没能建立有效锚点。**

| 想要的锚点 | 状态 | 原因 |
|---|---|---|
| **W4A8 权重量化的模型级退化** | **【未确认】** | 主代理已在 `logs/005` 给出真实张量上的 **int4 per-channel SSZ rel_L2 = 15.5–16.4%**、端到端 GSM8K **197–199/200**。**但那是权重误差，不是 KV 误差，两者的传播路径完全不同**（权重误差作用于所有 token 的同一组固定通道；KV 误差是逐 token 的随机扰动）⇒ **不能当作 KV 的接受线。** |
| 论文 "FP4 main KV, only marginal degradation" | **【未确认】** | 只有定性描述，**没有给出任何误差数字**。不能反推阈值。 |
| 本模型的 KV 侧 QAT | **【实测，反方向】** | 模型是**按 FP4 global KV 做 QAT 训练的**（论文自述）。⇒ **对 FP4 格式它见过、对均匀 INT4 它没见过。** 这是**支持 FP4 E2M1 而不是 INT4** 的一条独立理由。 |
| 端到端对跑（4-bit KV × GSM8K / Vision） | **【未确认，且本代理做不了】** | 需要 4-bit KV 的**推理路径**；见 §1 —— 910B3 上**连 bf16→fp4 的转换都跑不通**，没有算子可跑，**这条路在本机不可能**。 |

**⚠️ 一条被作废的锚点**：主代理先前给的 `11.7%` 是他自己合成的**高斯矩阵**、不是真实权重，
**已作废**，不要引用。正确的真实张量数字是上面的 `15.5–16.4%`。

> **诚实的结论**：**4-bit KV 的"可接受线"在本机拿不到**。
> 能说的是：**FP4 E2M1 g16（rel 7.5%、cos_p50 0.997、128K 上只有 1.3e-6 的向量低于 0.90、0.97% 低于 0.99）
> 落在"看起来像一个正常近似"的区间**，而 **g128 / 不分组那两档落在"明显塌掉"的区间**。
> 中间那条线需要一次**端到端对跑**才能画出来，那需要先有 4-bit 的读路径。

## 8. 这对 A2 意味着什么

### 8.1 直接答案

| 问题 | 答案 |
|---|---|
| 910B3 支持 4-bit 数据类型吗？ | **只支持"存"，不支持"算"**：dtype 符号与 NPU 分配 √，bf16→fp4 转换 ✗（`161002`），量化算子产出 fp4 ✗（`npu_quantize` 白名单无 fp4），CANN 无 fp4 算子（0 命中）。**【实测，A3 同代栈】** |
| 4-bit KV 精度够不够？ | **取决于分组，差一个数量级**：不分组的 INT4（=任务书里省 76% 那一档）**明确不可用**（rel 41%、cos_min −0.56）；**FP4 E2M1 g16 是唯一同时"省得多 + 尾部干净"的档**（省 66.6%、rel 7.5%、128K 上 cos_min 0.823）。 |
| 量化会不会打乱 sparse index 选择？ | **不会**【实测，代码 + 反事实双重证据】。indexer 有独立的 128 维 INT8 平面，读路径在 `latent` 后就分开了。 |
| 容量能省多少？ | **B/token/rank 4421 → 1477（省 66.6%）**（FP4 g16）或 **→ 1605（省 63.7%）**（INT4 g16）。**不是 76%。** |

### 8.2 对 A2 路线的三个具体含义

**① 4-bit KV 的收益是真的，但门槛比 INT8 高一档，而 A2 连 INT8 都还没打通**

K8_int8 已实测：**V4.1 吃不到那个 INT8 算子**（要求 `q_head_dim=576`、nope/rope 分离；
V4.1 是 512、rope 原地旋转），最短的正解是换 `mixed_quant_sparse_flash_mla`。
**4-bit 的处境严格更差**：连接口都没有，`kv_quant_sparse_attn_sharedkv` 是 A5 专属。

⇒ **【推断】对 A2 而言，4-bit KV 的瓶颈不是"精度够不够"，而是"先有一条能跑 4-bit 的 kernel"。**
本次实验的作用是：**把"精度"这个变量从风险清单里划掉**（FP4 g16 是好档位），
让决策集中在"值不值得写/等一个 4-bit kernel"。

**② 要写 kernel，就写 FP4 E2M1 + group 16，不要写均匀 INT4**

理由（都是本次实测）：同字节数下 FP4 g16（7.54%）优于 INT4 g32（13.0%）；
模型是**按 FP4 KV 做过 QAT** 的，对 E2M1 见过、对均匀 INT4 没见过；
FP4 g16 的尾部（低于 0.99 的向量占 **0.97%**）比 INT4 g32（**30.5%**）干净 **31 倍**。
**硬件侧也刚好对齐**：`torch_npu` 暴露的正是 `float4_e2m1fn_x2`（E2M1），
以及 `float8_e8m0fnu`（E8M0 幂次 scale）—— **dtype 的命名就是朝着这个格式去的**。

**③ 容量账要改：预期从"省 76%"下修到"省 64–67%"**

按 §5，A2 的 HBM 容量从 3.50 M token 变成 **10.5 M token（×2.99）**；
若按 DRAM 卸载那本账（`cpu_bytes_to_use / (B_per_token × 8)`）推，
**同样的 260 GB DRAM 能覆盖的 token 也同步 ×2.99**。
**注意**：这与 DRAM 卸载是**正交**的两条线（一个省字节、一个换层级），**收益可以叠乘**。

### 8.3 与 DRAM 卸载的关系（不要混）

| | DRAM 卸载 | 4-bit KV |
|---|---|---|
| 动的是什么 | 把 KV 放到 host，**字节数不变**（仍是 4421） | **字节数变**（4421 → 1477） |
| 瓶颈 | `aclrtMallocHost` / `host_mem_pool`（A2 上 = 0，**未解决**） | **kernel 不存在**（**未解决**） |
| 本次实验的贡献 | —— | 证明**精度不是瓶颈**（FP4 g16） |
| 叠加方式 | 乘法：同样的 DRAM 配额能装 2.99× 的 token | |

## 11. 一句话结论

> **【实测】在 A3 上与 A2 同代的 CANN 9.1.0 / torch_npu 2.10 栈上，4-bit 只能当存储格式、不能当计算通路**
> （dtype 有、分配成功，但 bf16→fp4 转换 `161002`、量化算子白名单里没有 fp4、CANN 里 0 个 fp4 算子）。
> **【实测】用 roundtrip 软件仿真把"精度"这个变量测干净了：**
> **不分组 / g128 的均匀 INT4 明确不可用**（rel 41% / 24%，`cos_min` 甚至为负），
> **★ FP4 E2M1 + group 16 是唯一同时省得多又尾部干净的档**：
> **rel_L2 7.5%、cos_p50 0.9973、128K 上 cos_min 0.823、只有 0.97% 的向量低于 0.99（1.3e-6 低于 0.90）**，
> 而它是**同字节预算下**（0.5625 B/elem）比 INT4 g32 好近一倍的那个。
> **容量：4421 → 1477 B/token/rank（省 66.6%，HBM 3.50 M → 10.46 M token，×2.99）——
> 不是任务书里写的 76%，那个数字对应的是不分组，不可用。**
> **【实测】量化 long-KV 不会影响 sparse index 选择**（indexer 有独立的 128 维 INT8 平面），
> 反事实验证下 INT8 g128 的 top-512 重合度 **99.81%**。
> ⇒ **对 A2 而言，4-bit KV 的瓶颈是"没有 kernel"，不是"精度不够"。**
