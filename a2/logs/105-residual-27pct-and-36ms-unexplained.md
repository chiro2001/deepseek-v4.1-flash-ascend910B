### ★★ 教训（值得单独记）：`GPU KV cache size` **不能**用来反推 block 数
`kv_cache_utils.py:1877-1887 get_kv_cache_capacity` 返回的是 `int(max_concurrency × max_model_len)`，
其中 `max_concurrency = num_blocks / nbpr`，`nbpr = Σ_groups cdiv(M_g, P_g)` —— 它是**可服务 token 数**，
已经含了"混合布局下每个请求要从**每个组**各消费 block"这层折算。
⇒ 用它 ÷ block_size 得到的**不是** block 数。本卷先在这一点上栽了一次，**记此以防再次**。

## 1.1 ★★★ 第三次更正（**定案**）：生产页数 = **7938**

### 那个 `2.377×` 的真身 = **混合布局的按组记账比**，不是内存问题
`blocks×128 / tokens = 1,016,192 / 427,643 = **2.3763**` **= `nbpr / blocks_per_req(仅 long-KV 组)` = 2471/1040 = **2.3760**`**。
代码注释原文即此：*"a request at max_model_len consumes whole blocks from **each** group's block table … the per-request total is the **sum over groups**"*。
⇒ 混合架构下每请求按**各组之和**消费 block ⇒ 该比值是**记账折算**，不是浪费。

### 决定性的算术（精确到个位）
`427,643` 是 `int(max_concurrency × max_model_len)`（`kv_cache_utils.py:1877-1887`）。用 `max_model_len = 133120` 反解：

| 假设 | `num_blocks / nbpr` | `int(ratio × 133120)` | 与实测 `427,643` |
|---|---:|---:|:--:|
| **7938 / 2471** | 3.2124646 | **427,643** | ✅ **逐字吻合** |
| 3341 / 1040 | 3.2125000 | 427,648 | ❌ 差 5 |

且 `7938 × 540,928 B = 3.999 GiB` ↔ 日志 `reserved 4.00 GiB` ✓（`020 §2` 的 `4 GiB / Σ = 7939/7940` 也在同一量级）。
⇒ ★ **`SWA_COMPACT` 的 7938 页测点本来就是生产口径**，我上一版的"3341"是**错的**。

### 修订后的残差分解（三方收敛，同一斜率）
三条独立来源给出**同一个斜率**，反解都指向"**该 `index_select` 把整个平面读了一遍**"：

| 来源 | 反解得等效带宽 |
|---|---:|
| `PROF_int8` 池扫描拟合 `cost ≈ 84 µs + 0.115 µs/页` | `65,536 / 0.115 µs = **570 GB/s**` |
| `CHUNKVIEW` 补丁 docstring 原文 | "**~610 GB/s per 64 KiB page**" |
| `SWA_COMPACT` 7938 页实测 829.0 µs/层 | `7938×65,536 / 829 µs = **627 GB/s**` |

⇒ 7938 页 × 65,536 B = **520 MB/层**；40 层 = **20.8 GB/step** @600 GB/s = **≈34 ms/step**。
⇒ 而 **chunk（连续）视图是平的**（320/1024/4096/7938 页都 **13.0 µs**；7938 页 36.8 µs/层）。
⇒ **修复值 = 829 → 36.8 µs/层 ⇒ 31.7 ms/step = 残差的 64%**（`SWA_COMPACT` 那张真算子表按 1117→289 算得 33.1 ms，89%）。

| 残差 49.7 ms 的构成 | ms/step | 占比 |
|---|---:|---:|
| SWA int8 读侧页视图 gather | **31.7 – 44.7** | **64 – 90%** |
| 写侧 `kv8_store_rows` | 0.39 | 1% |
| 其余 38 个小算子 | ~2 | 4% |
| **未确认余量** | **8 – 15** | 16–30% |

★ 余量嫌疑：scale 平面的**同型扫描**、档 D 的 `_kv8_cmp_plane`、8 卡 EP 交互。

## 2. 【实测】修复：chunk 连续视图（零容量代价）

131,072/147,712，载荷仅 65,536 B）⇒ `index_select` 退化成散拷贝。
★ **触发条件 = "源视图是否连续"**，不是跨步距离（gap 512 → 422 µs、gap 65,536 → 421 µs 一样；
**66,560 的"紧凑页"仍 443.7**）。

| 真算子路径（7938 页 / 表宽 8192） | µs/层 |
|---|---:|
| `swa_bf16` | 26.29 |
| `swa_int8_current`（页视图） | **1117.06** |
| **`swa_int8_fast`（chunk 视图）** | **288.90** |
| **Δ** | **828.16 × 40 = 33.1 ms/step** |

★ **`chunk_vs_page_bit_equal = True`**（无损臂与**真量化器**臂端到端都是 `torch.equal`）；

★ 补丁 `chunk_page_gather.patch`：**1 个 hunk、基线 `94aeebb7` → `d84f087c`**，**只改 `kv8_gather_pages` 函数体**
（行 360–392），与 graphsafe（增量全在基线行 ≥382）**零重叠**；已在容器内对真原件 `patch -p1` 实打验证。

### 2.1 调用点地图（贵的那批被定位）
`dsa_v41.py:593` 的 `kv8_gather_pages(kv_i8, phys)` = **每层 1 次（40 次/步）、808.8 µs/次** ← 正是 `bf16_ab`

## 5. ★★ 诚实的算术：**离 ≤24 还差什么**（服务端 8K quote 口径，基线 75.911）

| 路线 | 逐步 | 结果 |
|---|---|---:|
| **A（保留 int8，修 read 路径）** | −13.4（chunk，**按 8 卡真页数 3341**）→ −10（融合，推断 5–13）→ −3.8（Engram host，历史实测） | **≈48.7** |
| **B（关掉 KV8_SWA）** | 实测 `p2g`/`p3b2` = **29.0–30.3**（**真读数**，非投影）→ −3.8（host） | **≈25.8** |

⇒ ★★ **路 A 现在离得更远（≈48.7，因为 chunk 只值 13.4 且有 36 ms 未解释）；只有路 B（关掉 `KV8_SWA`，实测 29.0–30.3）接近目标。**
⇒ **≤24 还需要 int8 之外的东西**，候选（按嫌疑）：

1. **Engram gate 的 64× padding 冗余**（`stage_perf/engram-bottleneck-decomposition.md §4` + `reports_build/gate-padding-opt.md`）：
   `V41_ENGRAM_GATE_MAX_TOKENS=2048` 按行 pad，而单流 decode 真实 n=8 ⇒ **256×**；量化 = 每步 **6.48 GFLOP / 8.55 GiB 访存**，
   真实只需 **101.3 MFLOP / 133 MiB**。候选实现 `roundup_n`（pad 改成 `ceil(n/chunk)*chunk`）**CPU 预检 13/13 PASS、逐位相等**，
   但 **NPU 图模式兼容性从未验证**（这是唯一卡点，也从未上卡测过）。
2. **Engram `route`**：5 次集合通信/步（1×all_gather + 4×all_to_all），历史实测 **2.7–3.0 ms**（`nocomm −2.99`）。
3. **`H_after`（同步点之后的 host 工作）**：`D2H_advance` 用合成循环测得 4–9 ms；但**真机上历史实测只有 ~3.8 ms**
   （`nohost −3.78`，其中 route 2.99 + D2H 0.87）⇒ **本卷采用 3.8，不采用 9**（口径更贴生产）。
4. ★ **口径本身待用户确认**：24 ms 出自 `draft_ab.py --seq-len 1032`（≈1K、**进程内**配对 A/B），
   与服务端 8K quote 基线（30.45/31.52/30.92）**不是同一把尺子**。

## 6. 另一条独立线索：宿主 OOM（不是配置错）

`r8-1m-bcd`（1M + 8 GiB KV + `OFFLOAD_GB=85`）起服失败，**根因 = 宿主内存 OOM**（dmesg 铁证）：
```
[Wed Sep 23 01:47:55 2026] Out of memory: Killed process 167861 (VLLM::Worker_TP)
   total-vm:9773997692kB, anon-rss:92017920kB        ← 单 worker 87.7 GiB
   constraint=CONSTRAINT_CPUSET ... global_oom, task=VLLM::Worker_TP
```
- 表现是 `Worker proc VllmWorker-5 died unexpectedly (exit code: None)` + `shm_broadcast: cancelled`（**都是下游症状**）；
  **`serve.log` 里所有已知错误码全 0**——因为 OOM 在**内核层**，容器日志看不到。
- ⇒ **纪律**：8 卡 + 1M 几何起臂前，**`serv.log` 之外必须看 `dmesg`**；且 **`MemAvailable` 要 ≥1200 GiB**
  （8×87.7 anon-rss + 91 GB 池 ≈ 1000+）。上次只有 ~750 GiB 就开跑 = 直接原因。
