## 二、★ 三条会改写 A2 计划的发现

### 2.1 根因是**两条独立机制叠加**，缺一条都修不好

| # | 机制 | 后果 |
|---|---|---|
| **①** | **`state` 组一票否决**：它在取回路径上被当 full-attention 参与命中判定，但存储路径上永远存不出 chunk（`1//8 = 0`）⇒ key 必然 MISS ⇒ `if num_hit_chunks == 0: return 0` 把**整轮**判死 | 命中恒 0 |
| **②** | **池子比一轮工作集小 6.4 倍，LRU 先吃掉前缀链的头**：`num_cpu_blocks = cpu_bytes_to_use / (worker_kv_bytes_per_block × blocks_per_chunk × world_size)`，而**每个 (group, chunk) 各占一块** ⇒ 12 个参与组把有效容量**除以 12**。32 GiB ⇒ ~963 块，16 请求一轮要 **6,144 块** | 即便修了 ①，16 请求仍"零取回" |

★ 机制 ② 是**新的**：`_maximal_prefix_lookup` 要求**从第 0 块起连续命中**（全有或全无），
而 `lru.py` 从插入序**前端**淘汰 ⇒ **池子不够时不是"命中率下降"，而是"命中率归零"**。

### 2.2 ★★ `ENGRAM=0` **也会**撞 `207001` —— 池子上限 4–8 GiB/worker

> ⛔ **2026-09-22 00:55 更正（`logs/014` P1_pinned 实测）：本节第 2.2 节的"单次上限"结论不成立。**
> 干净进程里**单次** `pin_memory` 逐档跑到 **24 GiB 全成功**，同进程累加 **128 GiB 也全成功**，
> 复刻真实形状（16 块、首块 97%、8 进程并发）**8/8 成功**。
> ⇒ `207001` **不是容量/单次大小问题**，更像**态问题**（该进程当时已用的驱动侧 host 资源 + 邻居容器），
> **没有拿到可复现的最小条件**。
> **⇒ 修法不是"分片 pin"（候选 α），而是候选 β：改用 `aclrtHostRegister` 绕开 pinned 路径。**
> 详见下方 §2.2b。

### 2.2b ★★★ 修正后的结论（`logs/014` P1_pinned，【实测】）

**（一）"单次上限"这个说法被推翻**

| 探测 | 结果 |
|---|---|
| 单次 `torch.zeros(..., pin_memory=True)` 2/4/5/6/7/8/10/12/14/**16/20/24 GiB** | ✅ **全成功** |
| 同进程累加 256 MiB × 512 = **128 GiB** | ✅ **全成功** |
| **复刻真实臂形状**（16 块、首块 ≈97%、**8 进程并发**、每进程 8/16 GiB） | ✅ **8/8 进程成功，合计 64 / 128 GiB** |
| 先占 **48 GiB HBM** 再 pin | ✅ 仍全成功（不是显存压力） |

⇒ **`207001` 不是"单次要得太大"，也不是"总量"或"形状/并发/HBM"**
—— 更像**该进程当时的驱动侧 host 资源 + 邻居容器**这类**态**问题。
**没拿到可复现的最小条件**（这点必须如实记）。

**（二）★ 但候选 β 的生死判据**通过**了**

| 判据 | 结果 |
|---|---|
| `aclrtHostRegister(ptr, size, flags=0)` 注册**普通 host 内存** | ✅ ret=0 |
| **注册的内存能不能被真实 KV 拷贝路径用** | ✅ **16 / 24 GiB 单块往返逐字节一致** |
| 带宽 | **H2D 58 GB/s / D2H 42.7 GB/s**（与 pinned 同级） |
| 是否经过 `aclrtMallocHost` | ❌ **不经过** |

**（三）⇒ A2 的可执行方案（已备好补丁）**

| 项 | 结论 |
|---|---|
| **API** | ✅ `aclrtHostRegister` + **普通 host 内存**（`pin_memory=False`） |
| ❌ 不要用 | `aclrtMallocHost` / `pin_memory=True` 去撑大池（那正是 `207001` 的出处） |
| **池子能到多大** | 由**宿主 RAM** 决定（A2 余量 442 GiB ⇒ `OFFLOAD_GB=256` 内存账安全）；注册是一次性开销 0.37 s/GiB |
| **要改的地方** | **只有一处**：`native/cpu_npu.py` 的池子分配（改成 `_allocate_npu_offload_cpu_tensor()`，按 `NPU_OFFLOAD_HOST_MEM=registered|pageable|pinned` 选后端，**注册失败自动回落 pinned**） |
| 产物 | `agents/P1_pinned/scripts/make_cpu_npu_hostmem_patch.py` + `patches/offload_dsv41/cpu_npu.py`（328→388 行，锚点唯一） |
| **A2 验证命令** | `agents/P1_pinned/scripts/a2_pinned_probe.sh`（**不占卡、不加载模型**，见 `logs/014` §5.3） |

【实测】D2 把池子逐档抬高，**与 Engram 无关**：

| 池子 | 每 worker | 结果 |
|---:|---:|---|
| 32 GiB | 4 GiB | ✅ 起服成功（但机制 ② 让它对 16 请求无效） |
| **64 GiB** | **8 GiB** | **✗ `207001`，8/8 worker 全中** |
| **128 GiB** | **16 GiB** | **✗ `207001`** |

失败原文：`Failed to allocate 17179869184 bytes host memory`（16 GiB **单次**分配）。

⇒ **触发条件是"单次 pinned 分配过大"，不是"总量不够"**
（这也解释了 D_off8 的探针为什么"逐 1 GiB pin 128 GiB 全通过"）。

**⇒ ⇒ 这一条直接否掉 A2 的 260 GB 计划。**

### 2.3 主代理的 `alignment_chunk_count` 线索**不成立**（再次纠正）

## 三、A2 计划怎么改

### 3.1 ⛔ 作废：`cpu_bytes_to_use ≈ 260 GB` 这个计划

原计划（`HANDOVER.md` §4）按"宿主余量 442 GiB ⇒ 建议 260 GB"。
**现在看这条路走不通**：单次 pinned 分配在 8 GiB 就被拒 ⇒ 即使 A2 的驱动池更大，
**也必须换分配形态**（多次小分配、或走 `mmap + aclrtHostRegister`）。

### 3.2 必须先验证的三件事（**A2 上，用户粘贴**）

在原来那三条探测（`a2_probe.sh`）基础上，**加一条关键的**：

| # | 探测 | 为什么 |
|---|---|---|
| 1 | `host_mem_pool` | A2 预期 0 |
| 2 | `aclrtMallocHost` **逐档**（4/64/256/**1024 MiB**） | ★ **A3 上 1 GiB 单次就失败**；要量出 A2 的上限 |
| 3 | `pin_memory` 逐档 | 卸载层实际走的路径 |
| **4** | ★ **`aclrtMallocHost` × 多次小分配累加**（如 128 × 256 MiB） | **判"是单次上限还是总量上限"** —— 这决定第 3.1 的修法 |

### 3.3 修法的两个候选（等 §3.2 的读数）

| 候选 | 内容 | 前提 |
|---|---|---|
| **α** | **分片 pin**：卸载层多次小分配（每次 ≤ 上限），池子由多个 segment 拼 | 探测 4 显示"总量可以、单次不行" |
| **β** | **改走普通 `mmap` + `aclrtHostRegister(MAPPED)`**（Engram 已验证的机制）：不占驱动 pinned 池 | 探测 2/4 显示 pinned 根本不可用 |

> β 的可行性在 A3 上已有旁证：Engram 的 device-index 就是这条路，
> **206 GiB 整表注册成功**（`logs/040`），而它**不经过** `aclrtMallocHost`。

### 3.4 ★ 迭代策略（L1 的成果直接受益）

**D2 后续任何修复，都先在单卡 tiny 上验（≈2 min/臂），8 卡只做最终确认。**
这条已经在 `logs/010` 实测成立（单卡 1:1 复现了"能存不能取"）。
