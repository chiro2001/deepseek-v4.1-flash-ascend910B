# 037 · A2 的**非确定性**：`temperature=0` 下首 token 会翻（与 KV 卸载**无关**的独立质量问题）

**日期**：2026-09-22 04:0x（A3 本地时钟）
**执行**：子代理 `L3_8card`（在做 `027` per-group bpc 终验时**顺带发现**）
**机器**：A3（A3-node1）Phy-ID 8–15，**8 卡真权重**（`v41-w4a8-engram-dr-vision-qrot-mtpq`）
**配置**：`ENGRAM=0`、`PREFIX_MATCH_UNIT=32`、`MAX_SEQS=32`、`BAT_TOKENS=8192`、
`speculative_config=SpeculativeConfig(method='dspark', num_spec_tokens=5)`、`cudagraph_mode=FULL_DECODE_ONLY`、
`enable_npugraph_ex=true`、`enable_static_kernel=true`（= 与 `016`/`022` 的 L2 终验**逐字相同**的服务配置）
**标记约定**：【实测】/【推断】/【未确认】（同 `027`）

## 0. 一句话结论

**【实测】`temperature=0` + 固定 prompt 下，这个服务本身不是确定的**：
同一 prompt、同一服务、**每次先 `/reset_prefix_cache`（清池子 + 清前缀缓存）**，连发 4 次
`max_tokens=1`，得到 **2 个不同的首 token**（`'。\n'` 与 `'_'`）。

⇒ 这不是 KV 卸载的错，也**不是**"prefill vs 前缀缓存命中"两条路径的问题（清了缓存照样抖）。
⇒ 它在 `027` 里被当成"判据失效"处理（`sha256` 判据整体不可用）；
本文把它单独成文，因为**它是 A2 用户能直接感知的质量问题**（"同样的输入，输出不一样"）。

## 1. 实验（【实测】原样）

工具：`agents/L3_8card/scripts/diag_determinism.py`（对**一个正在跑的服务**、**同一个 32K prompt**）。

### 1.1 三格（32K prompt，`max_tokens=1`）

```
① 每次先 /reset_prefix_cache 再发（4 次）：'。\n' | '_' | '。\n' | '_'    distinct sha = 2/4   ← ★★
② 不 reset，连发（4 次）：                '_' | '_' | ' ' | '_'           distinct sha = 2/4
③ 并发 2： round0 = '。\n' | '_'  （2/2 不同）
           round1 = '_'  | '_'    （1/2 不同）
```

**读法**：

| 观察 | 含义 |
|---|---|
| ① 每次都 `reset_prefix_cache`（返回 200）**仍然 2/4 不同** | ★ **决定性**：与"前缀缓存命中 vs 全量 prefill"**无关** |
| ② 不清缓存也是 2/4 | 与 ① 同量级 ⇒ 缓存路径不是主因 |
| ③ 并发 2 的 round1 两次相同、round0 不同 | 不是"必然抖"——抖动与**调度次序/批形状**相关，是**竞态级**的 |

### 1.2 同一服务上背靠背的直证（更早的一次，`l3-cold1-65536.diag.json`）

```
prompt = 65536 token
  mt1_a : text_repr=' '   sha=36a9e7f1…   finish_reason=length
  mt8   : text_repr=' ~~~~~_~_~_'
  mt1_b : text_repr='_'   sha=d2e2adf7…   finish_reason=length   ← ★ 同一 prompt，紧接第二次
```

* `finish_reason` 一律 `length`（**没有 EOS / stop**）⇒ **不是"EOS 被渲染成空字符串"的口径问题**；
* ⇒ **是真正的 token 不同**（`' '` → `'_'`）。

## 2. 量级（【实测】，`max_tokens=1`）

### 2.1 投机**开**（= 现状生产配置）

| 组 | 4 次的结果 | 不同 sha |
|---|---|---|
| 32K／清缓存 ×4 | `'。\n' _ '。\n' _` | **2 / 4** |
| 32K／不清 ×4 | `_ _ ' ' _` | **2 / 4** |
| 32K／并发 2 round0 / round1 | `'。\n' \| _` / `_ \| _` | **2/2** / 1/2 |

### 2.2 ★ 投机**关**（格 3，`SPEC_ON=0`；同一服务、同一 prompt）

| 组 | 结果 | 不同 sha | 读法 |
|---|---|---|---|
| **32K／清缓存 ×4** | `' ' _ ' ' ' '` | **2 / 4** | ★ **仍抖** ⇒ 投机**不是**唯一原因 |
| **32K／不清 ×4** | `' ' ' ' ' ' ' '` | **1 / 4（全同）** | 关投机后**重复同一请求稳定了** |
| 32K／并发 2 | round0 `' ' \| _`（2/2）；round1 `' ' \| ' '`（1/2） | 2/2, 1/2 | 并发仍抖 |
| **512／清缓存 ×4** | `',' ' ' '\n' ','` | **3 / 4** | ★★ **短 prompt 抖得更厉害**（3/4 > 2/4） |
| **512／不清 ×4** | `',' ',' ',' ','` | **1 / 4（全同）** | 同上，重复请求稳定 |
| 512／并发 2 | 两轮都 1/2 | 1/2 | |

⇒ **首 token 的翻转率 ≈ 25 %–100 %**（32K prompt；样本 n=4，只能给量级，不能给精确率）。

> **适用范围（必须一起引用）**：【实测】只覆盖 **32K / 64K prompt**、`max_tokens=1`、
> **TP8 真权重**、`dspark` 开、ACLGraph + npugraph_ex + static kernel 开。
> **短 prompt（512）已补测（§2.2）**；**"关图"那两格仍未跑**（§4）。

## 3. 来源（【推断】，按可能性排序）

| # | 候选 | 支持 | 反对/状态 |
|---|---|---|---|
| 1 | **`dspark` 投机解码的接受路径**：5 个 draft token 的接受数随 fp 抖动变化 ⇒ 每步的批形状变化 ⇒ **自激** | 关掉投机后**"重复同一请求"那一格从抖变稳**（32K/512 都 4/4 相同）⇒ 它对"缓存命中路径"的抖动**有贡献** | **【实测·部分成立但非唯一】**关投机后**清缓存路径仍抖 2/4（32K）、3/4（512）** |

| 5 | ~~EOS / 特殊 token 的文本渲染差异~~ | —— | **【实测·已排除】**`finish_reason=length`、两次都是 1 个 token、文本不同 |

## 6. 对判据的影响（为什么这很重要）

* **任何"比输出文本 sha256"的判据在本服务上失效**：
  `fill vs replay`、`cold vs replay`、**甚至 `cold vs cold`** 都不可用（§1.2 的两条 `' '` / `'_'` 就是同路径）。
* ⇒ `027` §8 里"DRAM 取回数值正确性【未确认】"的**根因就是这条**；
  要判它必须换判据（**KV 级逐字节**，见 `027` §8 的下一步）。
* ⇒ 本轮所有 `sha_mismatch=16/16` 的臂（B/C/D）**不构成"取回错误"的证据**，也不构成"取回正确"的证据。
