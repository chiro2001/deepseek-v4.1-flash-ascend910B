## 1. 接挂载链：`sitecustomize` → **`docker -v` 单文件挂载**

### 1.1 为什么不能照抄 030

`030` 的 L1 是**单卡 tiny 的 `sitecustomize`**（`PYTHONPATH` + `sys.meta_path` 三钩子）；
而 `027` 的 8 卡链走的是**影子包 `serve_a2.sh` 的 `docker -v` 单文件覆盖**
（D2 的 `scheduler.py`、P1 的 `cpu_npu.py` 都是这个机制）。
⇒ 030 的三个钩子必须**落成文件**才能进 8 卡链（`027 §1.1` 的同一手法）。

### 1.2 挂的 6 个文件（`agents/K_l1_8card/patched/`，由 `build_patch.py` 生成）

| 容器内路径 | 来源 | 作用 |
|---|---|---|
| `vllm/distributed/.../offloading/config.py` | **L5 现行件** + ① | dict bpc 解析（L5）+ **每组权重/分量注入**（L1） |
| `vllm/v1/kv_offload/cpu/spec.py` | **L5 现行件** + ② | 池日志（L5）+ **按组配额 manager 分支**（L1） |
| `vllm/v1/kv_offload/cpu/pgp_manager.py` | **L5 现行件（逐字节）** | `PerGroupBPCManager`（一个 key 占 `bpc_g` 个 unit）+ `resolve_per_group_bpc` |
| `vllm/v1/kv_offload/cpu/p2_pool.py` | **030 的 `p2_pool.py` 逐字节 + 追加** | 配额/行空间/分量算术 + `make_quota_manager` + 挂载版追加的 `compute_weights`/`worker_rows` |
| `vllm-ascend/.../native/npu.py` | **镜像原文** + ③ | `create_worker` 改成"先算每张张量的行数，再建 worker" |
| `vllm-ascend/.../native/p2_worker.py` | 本任务新写 | 按 `row_counts` 分配宿主池的 worker（基类 = P1 的 worker） |

**生成脚本的硬约束**（`patch/build_patch.py`）：对 **L3/P2/P1/镜像原文** 均有 **md5 指纹断言**
（`patch/expected_inputs.md5`），锚点不唯一即报错，产物 6/6 过 `py_compile`，并检查 24 个标记齐全。
★ **`pgp_manager.py` 必须与 L5 原件逐字节相同**（脚本里 assert 了这一条）——
L5 的 unit 池语义一行没动。

**为什么 L1 挂在 `npu.py`（而不是 `cpu_npu.py`）**：L1 只要给 worker 传一个 `row_counts`
列表，而 `create_worker()` 在 `npu.py` 里（镜像的 `cpu_npu.py` 里 `NPUOffloadingWorker.__init__`
签名中**没有**行数参数）⇒ **挂 `npu.py` 就够，P1 的 `cpu_npu.py` 一个字节都不用碰**，
`aclrtHostRegister(MAPPED)` 与 `ret=0` 日志原样保留。

### 1.3 容器内 env 怎么进去（踩过一次）

`serve_a2.sh` **只在它的 `inner.sh` 里 export 一批固定 env** ⇒ runner 里 `export` 了
但 `serve_a2.sh` 不消费的变量**根本不会进容器**。因此 `patch_serve_a2_l1.sh` 往 `inner.sh`
模板里插了 4 行（`P2_POOL_PATCH` / `P2_STRUCT_LOG` / `P2_POOL_LOG` / `P2_COMP_JSON`），
在**宿主**上展开成字面量。

★ **第一次起服踩的坑**：runner 里漏了 `SP_TOKENS` 默认值 ⇒ `line 143: SP_TOKENS: unbound variable`
⇒ 起服脚本**一行都没跑**、自检 0 行 ⇒ 判 `exit 9`。**自检门抓到了它**（花了 1 s，不是 20 min）。

### 1.4 ★★ 上线前必须分清：**"挂载机制"与"运行期开关"是同一条链的两半**（缺一即静默 no-op）

本轮两处的环境变量**不是两种做法、不能二选一**：

## 4. 预测 vs 实测：**预测被实测超出，且当场归因**

### 4.1 三档数字并排

| 口径 | 倍率 | 宿主（8 rank） | 来源 |
|---|---:|---:|---|
| `030` 单卡 **tiny**（12 组） | 1.960× | 1000 → 510.5 MiB（单卡） | 【实测·030】 |
| 本任务 07:31 的**预测**（13 组，误以为 g12 吃 4 张 alias 张量） | 1.927× | 392.35 → 203.6 GiB | 【推断】 |
| ★ **本轮 8 卡实测** | **1.9895×** | **392.35 → 197.21 GiB** | **【实测】** |

### 4.2 为什么真权重比 tiny 省（结构性差别只有一个）

`draft` 组（eagle）的 `weight`：

```
每 1024 token 的 unit 构成（Σw）：
  tiny（030）：  full 8 + 10 个 SWA × 1          = 18
  A2 真权重：    full 8 + 10 个 SWA × 1 + draft 2 = 20   ← ★ 多一个 draft 组
alias 分量（g1..g12）占的行数比例 = Σquota(comp1)/units = 12/20 = 0.600
```

### 4.3 ★ 为什么实测比预测还好（逐字节复核）

预测时**误以为 draft 组引用全部 4 张 alias 张量**；臂 A 的只读结构臂给出真值
**g12 = `[12,13,14]`（不含 15）** ⇒ 张量 15（页 147,712 B）只需装到 g11 的区间上界
**28,929** 行，而张量 12–14 要装到 g12 的上界 **34,714** 行：

```
23,142 × 369,280            （张量 0–11：g0 的区间上界 × 前 12 张的页和）
  + 34,714 × 131,072 × 3    （张量 12,13,14 = g12 的上界）
  + 28,929 × 147,712        （★ 张量 15 = g11 的上界）
= 8,546,341,120 + 13,653,220,608 + 4,272,857,088 = 26,472,418,816 B
日志实测                                       = 26,469,138,432 B（差 3,280,384 B = 0.012%）
```

**⇒ 倍率 = `52,660,994,048 / 26,469,138,432 = 1.9895×`**（日志里那行 `= 1.99× 缩小` 是同一个数）。
（0.012% 的差来自"分量 base 各自从 0 起"与日志口径的取整，不影响结论。）

**⇒ 8 卡真权重比 tiny 更省（1.9895× vs 1.960×），根因是 A2 的 draft 组只吃 3 张 alias 张量。**
