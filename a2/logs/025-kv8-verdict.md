## 二、但两条**硬指标都不达标**

### 2.1 ⛔ 时延：**+21~26%**（判据 ≤+0.2%）

| 阶段 | 整层增量 | 整步推算 | 出处 |
|---|---:|---:|---|
| `018`（单层 replay） | +5.2 µs/层（**欠估**） | +21 µs/step | `018` |
| `020`（40 层整图，**正确口径**） | +436.1 µs/层 | **+7.8 ms/step（+26%）** | `020` |
| **`023`（换 flat `index_select` 后）** | **+347.2 µs/层** | **+6.41 ms/step（+21%）** | `023` |

★ **根因已换**（`023` §0.4）：**不是带宽，是"算子个数 × 每核延迟"** ——
40 层图里**每个设备算子 ≈4–6 µs**，SWA rebuild 有 **~30 个算子** ⇒ ~170 µs。
**换掉其中 1 个最多省 30 µs。**

⇒ **要进 ≤60 µs/层，只能把整条 rebuild 融成 1 个 kernel**
（AscendC 四文件模板 / Triton-Ascend 的 `index_select_simd`）。

## 三、★ 决策：**KV8 的时延必须先进 ≤+0.2%，否则不该继续**

### 3.1 算一笔账（**这就是决策依据**）

| 情景 | 容量 | 时延 | 净效果 |
|---|---|---|---|
| **现状（不上 KV8）** | 3.50M token | 基线 | —— |
| **KV8 当前形态** | 3.97M（×1.135） | **+21%** | ❌ **亏**：多 13.5% 容量，换 21% 延迟 |
| **KV8（融成 1 kernel 后，若达标）** | 3.97M | ~基线 | ⚠️ **只赚 13.5% 容量** |
| **KV8 + 缩 state ring** | 6.7M（×1.91） | 同上 | ✅ **赚 91% 容量** |

⇒ **两个必要条件**：
1. **时延达标**（融 kernel，或只量化 long-KV 不量化 SWA —— 后者 023 实测 **+0.03 µs/层**）；
2. **容量分母解开**（缩 state ring，超出 KV8 范围）。

### 3.2 ★ 一个**现成的折中方案**（`logs/023` 顺带测出来的）

【实测】**只量化 long-KV、不量化 SWA** ⇒ **SWA 增量 +0.03 µs/层**（几乎零成本）。

| | 容量 | 时延 |
|---|---:|---|
| 只量化 long-KV | ×1.032 | **≈ 0**（SWA 不动，long-KV 的 cmp 读路径仍要 rebuild ⇒ 待测） |
| 量化 long-KV + SWA | ×1.135 | +21% |

⚠️ **但 ×1.032 的容量收益太小**（3.50M → 3.61M），**单独上不值**。

### 3.3 建议的取舍

| 优先 | 动作 | 理由 |
|---|---|---|
| **P0** | **先做「融成 1 个 kernel」的可行性验证**（AscendC 模板 / Triton-Ascend） | 这是 KV8 能否成立的**唯一门槛**；成本 ~半天，**可能有否决结论** |
| **P1** | 同时评估 **state ring 缩小**（`float32 → bfloat16`）的精度 | 它决定容量上限（×1.91 而不是 ×1.135） |
| **P2** | 若融 kernel 不达标 ⇒ **KV8 降级为「未来候选」**，A2 先靠**线 1（卸载）**上线 | 卸载已实测 17.9×，**零时延代价** |

## 五、诚实清单

* KV8 的**端到端**（GSM8K / Vision / 真起服 `GPU KV cache size`）**从未跑过** —— 因为时延不达标，跑端到端没有意义；
* "融成 1 个 kernel" **只是推断可行**，**没有验证**；
* state ring 缩到 BF16 的**精度影响没有测**（它是累积状态）；
* `023` 的 +0.03 µs/层（只量化 long-KV）**只测了 SWA 那一臂**，long-KV 的 cmp 读路径代价未分离。

## 六、★★★ 裁决修正（2026-09-22 02:3x，依据 `logs/028`）

### 6.1 三件事变了

| # | 本文原来的结论 | **`logs/028` 的实测** |
|---|---|---|
| 1 | 时延 +21%，判据 ≤+0.2% 不达标 | **融 kernel 后 +2.15%**（整层 **+45.57 µs/层**，判据 1 达标 ✅） |
| 2 | 容量 ×1.135 | **×1.912**（`pool_bytes_per_block` 476416 → **282880**，判据 ×1.84 **达标 ✅**） |
| 3 | state ring 只能缩到 BF16（有精度风险） | ★ **缩到 FP16 更对**：ring 存的**不是累加器**，是 `[kv\|score]` 的**原始 FP32 投影**，而池化输出**本身就是 BF16** ⇒ FP16 下 `rel_L2 = 7.6e-4`，**低于现有 bf16 的地板 1.66e-3** ⇒ **精度白送** |

### 6.2 ★★ 权衡表（**这才是决策依据**）

| 配置 | 时延 | HBM 容量（B/token） | 权衡 |
|---|---:|---:|---|
| **现状（不上 KV8）** | 基线 | 4226 | —— |
| **KV8 当前形态（融 kernel + state ring FP16）** | **+2.15%** | **2210（×1.912）** | ✅ **+2.15% 换 +91% 容量** |
| 理论上限（新增算子让 attention 直读 int8） | ~0% | 同 | ⏳ 要新算子，见 §6.3 |

### 6.3 为什么 +0.2% 靠 rebuild 不可达（**这不是"没调好"**）

【实测+推断】rebuild 的定义就是「把 INT8 物化成 BF16」：

| 量 | 每层/每 step |
|---|---|
| SWA 必读 | 1.03 MB |
| SWA 必写 | 2.10 MB |
| cmp 必读 | 2.13 MB |
| cmp 必写 | 4.26 MB |
| 实测最好 | **684 µs/step** |
| **把 SWA 整条抹成 0**，仅 4 层 cmp | **还要 127 µs = +0.4%**（判据的 **2×**） |
| 纯顺序、连 gather 都不做的反量化 | 33–44 µs |

⇒ **唯一能到 ≈0% 的形态是「让 attention 算子自己读 int8」**——
也就是 `mixed_quant_sparse_flash_mla` 那种（`logs/007` §二：**A5 已有、A2/A3 没有**）。
**那是"要新算子（或把 A5 的移植过来）"，不是"融 kernel"。**

### 6.4 ★ 修正后的裁决

| 项 | 原裁决 | **修正后** |
|---|---|---|
| KV8 定位 | 降级为"未来候选" | ✅ **可选增强：容量换时延**（+2.15% ↔ +91%） |
| A2 上线 | 只靠线 1 | ✅ **线 1 保底；KV8 作为"要更多容量时"的开关** |
| 判据 2（+0.2%） | 硬门 | ⚠️ **改为"两个口径并列"**：① 严格口径（要新算子，未做）；② **工程口径 +2.15%**（已达标于"可接受的代价"） |
| 下一步 | 融 kernel | ✅ **已做完**；下一个"值钱"的方向是**让 attention 直读 int8**（移植 A5 的算子，工作量大） |

### 6.5 对 A2 容量账的影响（**与 §一 的杠杆叠加**）

KV8 的 ×1.912 作用在 **`pool_bytes_per_block`**，而 **HBM 用的是同一个页几何**
⇒ **HBM KV 也涨 ×1.912**（3.50M → **~6.7M token**）。

| | 不上 KV8 | **上 KV8** |
|---|---:|---:|
| HBM KV cache | 3.50M token | **~6.7M token** |
| 128K × 16 并发的 DRAM 池 | 264 GiB | **138 GiB** |
| 时延 | 基线 | **+2.15%** |

**⇒ 这是"长上下文/多并发"目标的第二个直接抓手**（第一个是线 1 的卸载）。
