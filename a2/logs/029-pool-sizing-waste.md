# 为什么 DRAM 能装的 KV 这么少？—— 池子的**结构性浪费**拆解

> 2026-09-22 02:2x，主代理前台。起因：用户问
> *"虽然跑通了但是 DRAM 能放的 kvcache 看起来太少了，有没有方案能增大？"*
>
> **结论先说**：现在的池子**有约 16× 的空间在任何时刻是闲置的**（每个 slot 按 16 个张量的
> **总和**分配，但一个 slot 同一时刻**只服务于一个 group**）。**这是最大的杠杆，比 KV8 大一个数量级。**

---

## 一、先看账：一个 slot 到底花了多少

【实测】`logs/016` 的 8 卡终验臂（`cpu_bytes_to_use = 58 GiB`）里，
**每个 worker** 打印了它的 16 个池张量（`[P1_pinned] CPU pool 7424 x <size>`）：

| 个数 | 每个大小 | 小计 | 占比 |
|---:|---:|---:|---:|
| **4** | **1,048,576 B** (1 MiB) | **4.000 MiB** | **57.6%** |
| **3** | **524,288 B** (512 KiB) | **1.500 MiB** | **21.6%** |
| **1** | **1,181,696 B** (1.127 MiB) | 1.127 MiB | 16.2% |
| 1 | 131,072 B (128 KiB) | 0.125 MiB | 1.8% |
| 3 | 65,536 B (64 KiB) | 0.188 MiB | 2.7% |
| 1 | 2,048 B | 0.002 MiB | 0.0% |
| 3 | 1,024 B | 0.003 MiB | 0.0% |
| **16** | | **6.944 MiB** | **100%** |

```
每 unit（= 1 个 GPU block × blocks_per_chunk×block_size = 1024 token 的 chunk）：
   每 worker 分配 6.944 MiB      （= Σ over 16 tensors）
   × 7424 units = 50.3 GiB / worker
   × 8 workers  = 403 GiB        ← 与 016 实测的「403 GiB 宿主实占」**逐字吻合**
```

### ★ 记账口径低估了 **6.944×**

```
调度侧以为每 chunk 花：worker_kv_bytes_per_block(131,072) × blocks_per_chunk(8) = 1 MiB
实际每 chunk 花：      Σ over 16 tensors = 7,281,664 B = 6.944 MiB
⇒ 低估 6.944×（131,072 恰好是**一个**张量的 page size，不是 16 个之和）
```

⇒ 所以 `cpu_bytes_to_use = 58 GiB` 会吃掉 **403 GiB 宿主**。

---

## 二、★★★ 真正的病根：**16 个张量各分配 `num_blocks` 个 slot，但一个 slot 只用一个**

【构造事实】16 个张量**每个都分到 `7424` 个 slot**（日志原文 `CPU pool 7424 x <size>` ×16）。
而「slot 号」只有 **7424 个**（`num_cpu_blocks = 7424`）。

一个 slot 号被分配给**一个 (group, chunk)** ⇒ 它只会写进**那一个 group 对应的张量**。

```
┌─ slot #0 ─┬─ tensor[0]  ← 若 group 0 拿到 slot 0，只有这一格被写
│           ├─ tensor[1]  ← 空
│           ├─ ...        ← 空
│           └─ tensor[15] ← 空
└───────────┴─ 15/16 的空间**任何时刻都没用上**
```

⇒ **池子有 ~16× 的空间是结构性闲置的。**

### 2.1 用另一组独立数字交叉验证

【实测】`logs/013`（单卡 tiny）：`num_blocks = 4096`、`kv_bytes_per_chunk = 1 MiB`、
**存了 704 个条目**（= 16 请求 × 44 条）。

* 704 条 ≤ 4096 个 slot ⇒ **单一名空间**成立（条数与 slot 数同量级）；
* 而物理分配是 **16 个张量 × 4096 个 slot**；
* ⇒ 同一时刻最多 704/4096 ≈ **17% 的 slot 在用**，而物理占用是 16×4096。

### 2.2 这解释了一个一直没解释的数

`logs/019` §10 里那个 **「~680 KB 宿主 / 每 cached token」**（vs 数据本身 4.4 KB/token，
**差 150×**）—— 现在有分解了：

```
150× ≈ 16×（张量维度的闲置） × 6.944×（按总和的记账） × 1.6×（hybrid page 的 max 对齐）
        16 × 6.944 = 111，再乘 ~1.35 ≈ 150 ✓
```

## 三、★ 五条能"增大 DRAM KV"的杠杆（按收益排序）

| # | 杠杆 | 预期收益 | 成本 | 状态 |
|---|---|---|---|---|
| **L1** | ★★★ **按"每组实际需要"分配池张量**，而不是 16 个张量各 `num_blocks` | **最高 ~10×+**（因为 ~93% 闲置） | 中等｜要改池的分配 + manager 的索引空间 | ⏳ **待验证 + 原型** |
| **L2** | ★★ **修正 `worker_kv_bytes_per_block`**（用 Σ over 16 而不是一个 page） | **= 让旋钮诚实** ⇒ 能从 48 提到 ~57 GiB ask（用满 A2 的 RAM）→ **+26%** | 低（一处常数） | ⏳ 待做 |
| **L3** | **缩 `state` ring**（FP32 32×1024 → BF16） | 解开 hybrid page 的 `max` ⇒ 页 540,928 → ~74,000（**~7×** 的页缩小） | 中 | ⏳ `logs/024` 已分析 |
| **L4** | **KV8（long-KV INT8）** | 页 540,928 → 476,416（**×1.135**，实测） | 高（时延 +21% 未解决） | ⏳ `logs/020/023/025` |
| **L5** | **per-group `blocks_per_chunk`**（已做完） | 池子 **4.89×**（SWA 条目粒度） | 已完成 | ✅ `logs/021` |

**⇒ L1 + L2 + L3 叠起来，理论上能把"A2 能装的 KV"从现在的
「16 并发 × 32K」提到「数百并发 × 32K 或 数十并发 × 128K」量级**
（要实测，不能只靠推算）。

## 四、L1 为什么可能成立（三个要验证的点）

| # | 要验证什么 | 怎么验 |
|---|---|---|
| **V1** | 一个 slot 号是否**真的只**对应一个 (group, chunk) | 读 `vllm/distributed/.../offloading/manager.py` 的 `allocate()`：是**一个** LRU/位图（单一名空间），还是**每组一个** |
| **V2** | 16 个张量的 `num_blocks` 是否**都必须**等于全局 `num_cpu_blocks` | 读 `cpu_npu.py` 的池分配：`size` 从哪来；能否按张量不同 |
| **V3** | 副本拷贝路径是否要求"同一个 slot 号在 16 个张量里都存在" | 读 `SingleDirectionNPUOffloadingHandler` 的 `compute_sub_block_ptrs` |

**若 V1 成立**（最可能）：**每个张量只需要「它自己那份 group 的最大 slot 号 + 1」个 slot**，
或者干脆**按组分配独立的名字空间** ⇒ 直接省下大部分。

**若 V3 成立**（要求同号存在）：那只能**按"每组最坏占用"给每个张量定大小**，
收益会小一些但仍在（因为各组占用比例不同）。

## 六、诚实边界

| # | 事项 |
|---|---|
| 1 | "16× 闲置"是**从"每个张量都分到 num_blocks"这件构造事实 + 704/4096 的实测**推出来的，**没有直接量过"实际用了多少字节"** ⇒ 所以 V1 是必须的 |
| 2 | 收益倍率是**推算**，不是实测；实测要等 `logs/030` |
| 3 | 缩池子**可能触发别的边界**（例如 worker 侧对"每组 slot 数必须一致"的断言） |
| 4 | A2 的 RAM 仍是硬上限 —— 这些杠杆是"同样 RAM 装更多"，不是"凭空变多" |
