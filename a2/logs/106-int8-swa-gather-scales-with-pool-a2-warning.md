# 106 — ★★★ int8 SWA 的 gather 代价 **∝ 池总大小**：在 A2 的真实几何下是 **≈117 ms/step**（A3 探针的 3.6×）

> 2026-09-23 02:0x CST。**主代理**（外推/裁决）基于 `SWA_COMPACT` 的 `p8_selectsweep`（c2 实测）与 `PROF_int8` 的池扫描。

## 0. 一句话

那条 `kv8_gather_pages` 的 `index_select` **与"这次取多少页"无关，与"池里总共有多少页"成正比**
（斜 ≈ **0.102 µs/页**）⇒ 它把**整个 SWA 平面物化了一遍**。
⇒ **A2 的 14.40 GiB KV（28,577 blocks）会比 A3 探针的 4 GiB（7,938 blocks）严重 3.6×**：
**≈117 ms/step 的纯 gather 开销**（A3 探针实测 32–45 ms/step）。

## 1. 【实测】池大小律（`SWA_COMPACT/p8_selectsweep.json`，c2，stride=131072）

| 池大小 | 选 **3** 页 | 选 **24** 页 |
|---:|---:|---:|
| 320 页 | 7.5 µs | 10.5 µs |
| 1,024 页 | 20.2 µs | 24.1 µs |
| 4,096 页 | 417.4 µs | 420.3 µs |
| **7,938 页** | **808.8 µs** | **810.9 µs** |

★★ **选 3 页 vs 选 24 页几乎相同** ⇒ 代价**不随选择规模变化**，只随**池大小**变化
⇒ 机理 = **把整个平面物化（隐式连续化）**，不是"取几页"。
★ 与 candbot 的官方表述同构（`graph/torch-npugraph-ex-performance-diagnosis/references/case-001`）：
`*_SliceAiCore_Slice` = 「完成**非连续输入的隐式连续化**……不是模型显式表达的切片语义」。

★ 大池区间的斜率：`(808.8 − 417.4) / (7938 − 4096) = **0.1019 µs/页**`；
反解得等效带宽 `65,536 B / 0.102 µs = **643 GB/s**` —— 与 `CHUNKVIEW` docstring 的 "~610 GB/s per 64 KiB page"
和 `PROF_int8` 拟合的 570 GB/s **三条独立互证**（同一量级）⇒ 就是"按 HBM 带宽把平面整个读/写一遍"。

## 2. ★★ 【推断·强】外推到 A2：**≈117 ms/step**

用**已被验证的** block 数公式（`SWA_COMPACT` 的同一算式，与日志 `reserved 4.00 GiB` 吻合）：
`num_blocks = KV_budget / pool_bytes_per_block = KV_budget / 540,928 B`

| | KV 预算 | **blocks** | gather / 层 | **× 40 层** |
|---|---:|---:|---:|---:|
| A3 探针（实测口径） | 4 GiB | **7,938** | 808.8 µs【实测】 | **≈32 ms/step**（全链 44.7） |
| **A2 生产** | **14.40 GiB** | **28,577** | **≈2,915 µs** | **≈117 ms/step** |

（A2 的 14.40 GiB 有独立实测支撑：`GPU KV cache size = 3,498,354`；且 A2 与 A3 在**同配置**下的
`token/GiB` 换算率吻合到 **0.006%**（242,928 vs 242,941，见 `logs/104 §1`）⇒ 两边几何同源。）

### ★★★ 折扣已排除：池是**每 rank 一份**，外推**不除以 8**
我核了 8 卡臂的 `[K_l1_8card]` 行：**8 个 rank 的宿主实占逐字相同**（`新=15,441,817,600 B`，`sort | uniq -c` = **8**）
⇒ 每个 rank 有**自己的一份池**（TP 切的是 head，不是 block 数）。
⇒ **gather 是各 rank 并行做的，步代价 = 单 rank 值 ⇒ 116.5 ms/step 成立，不是 15 ms。**

★★ **独立佐证（`prof_int8` 四条 + 一份权威文档）**：
`prof_int8` 用四条只读证据独立判同一格：① `deepseek_v4/model.py:117-131` 的 `get_kv_cache_spec()` **硬编码 `num_kv_heads=1`**
（MLA 单 KV 头 ⇒ **按头分片在算术上不可能**）；② `core/deepseek_v41.py:225-226` 要求 worker 的 spec 集**恰好含 40 层 SWA**，
否则起服即 raise ⇒ 每 rank 完整；③ 日志 `tensors=20 pages=[…]` **八个 rank 逐字相同**（若分片页应是 8192 而非 65,536）；
④ 8 个 rank 各自 `reserved 4.00 GiB … as specified by kv_cache_memory_bytes` ⇒ 预算 **per-worker**。
★ **权威文档佐证**（`upstream-v41/docs/KV-CACHE-ACCOUNTING.md`，`prof_int8` 在 A3 上搜所以没找到；本机存在）：
「| A2（910B3，util=0.90） | **14.40 GiB** | 3,498,354 | **4419.8** |」列名即 **B/token/rank**；§7.2 原文：
「**num_kv_heads = 1**（MLA 的 latent 被所有头共享），每个 rank 都要有完整的 latent 才能算自己那部分 query
⇒ **1M 上下文的 DRAM 需求是 34.5 GiB（8 份副本），不是 4.32 GiB**」。
⇒ **14.40 GiB 是 per-rank 可用量** ⇒ §2 的 116.5 ms/step **成立**（误差带 ±10%）。

### ★★★ 机理闭合（精确到 **0.04%**）：`index_select` 把**整个平面**物化了一遍
读一遍就够：非连续视图上 `aclnnIndexSelect` 会先 `Contiguous` **整个输入**（= cannbot CASE-001 的"隐式连续化"），
再选出 3 页（192 KB）⇒ **浪费 2,646×**。

| 池页数 | 平面大小 | @643 GB/s 预测 | `SWA_COMPACT` 实测 | 偏差 |
|---:|---:|---:|---:|---:|
| 320 | 21.0 MB | 32.6 µs | 7.5 µs | 小池 = 延迟主导（不适用带宽模型） |
| 1,024 | 67.1 MB | 104.4 µs | 20.2 µs | 过渡区 |
| **4,096** | **268.4 MB** | **417.5 µs** | **417.4 µs** | **0.02%** ✓ |
| **7,938** | **520.2 MB** | **809.1 µs** | **808.8 µs** | **0.04%** ✓ |

⇒ **大池区间与"按 643 GB/s 读完整平面"逐字吻合** ⇒ 机理确定，不是拟合巧合。
⇒ 这也解释了为什么"选 3 页 vs 选 24 页"没差别（§1）—— **两者都在读同一个整平面**。

## 3. 这条发现改变了什么

1. **A2 上线裁决**：在 gather 修好之前，**int8 档 C 不能上 A2** —— 它会带来 ≈117 ms/step，
   而它买到的只是 **宿主 DRAM ×0.7607**（HBM 容量 **×1.000**，零收益）。
   ⇒ **代价与收益的数量级完全不成比例。**
2. **修复的价值在 A2 上被放大 3.6×**：chunk 视图把该项与池大小**解耦**
   （320/1024/4096/7938 页都 **13.0 µs**）⇒ A3 上值 ~33 ms、**A2 上值约 ~117 ms**。
   ⇒ 这使"chunk 视图/融合"从"优化项"升级为 **A2 上线的前置条件**。
3. **它同时解释了 A3 探针口径的误导性**：用 4 GiB 探针测 int8 的性能代价会**系统性低估 3.6×**
   ⇒ 后续任何"A2 同规模"的 int8 性能评估都应当用 **A2 的 KV 预算**（14.4 GiB）而不是探针的 4 GiB。
