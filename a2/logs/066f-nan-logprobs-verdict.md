## 1. ★★ 统一假说（【已证实】）：不是两条链，是**一处损坏的两种表现**

### 1.1 判决数据（`out17`，**同一个 server 进程、同一批 prompt、同一 `max_tokens=16`**）

```
阶段2（要 logprobs）：
  A_echo_logprobs  ok=3  nan400=5  failed=[0,3,4,5,7]
  B_logprobs       ok=3  nan400=5  failed=[0,3,4,5,7]   ← 与 A 失败集相同
★ C_plain（不要 logprobs） ok=8  nan400=0  failed=[]    ← ★ 唯一变量 = logprobs

阶段1（流式，不要 logprobs）三种判据：
  fill != replay    : [4, 5, 7]              ← 弱判据
  replay != replay2 : [0, 3]
  ★ 三轮任一不同     : [0, 3, 4, 5, 7]       ← ★★ 逐元素等于 NaN 失败集
```

★ **`C` 是在 `A`/`B` 之后跑的** —— 若只是"时间越久越坏"，`C` 应当更容易炸，**它却是 0**
⇒ **调用顺序不构成混淆**（这是同进程单变量对照的价值）。

### 1.2 正确表述

> ★★ **一批 prompt（`{0,3,4,5,7}`）在"前置负载之后"进入损坏状态**，损坏有**时点差异**：
```
  p4/p5/p7 ⇒ 第 2 轮就坏（fill != replay）
  p0/p3    ⇒ 第 3 轮才坏（fill == replay，只能靠 replay2 看见）
  p1/p2/p6 ⇒ 3 轮全同、且从不 NaN ⇒ 从未损坏
```
> 进入损坏后：
```
  要 logprobs   ⇒ **NaN**（服务端 400）
  不要 logprobs ⇒ **token 不同 / 文本变短**（★ 静默）
```
> ⇒ ★★★ **不是"logprobs 的序列化问题"，是 decode 输出本身被污染**；
> **logprobs 只是把它暴露成 400 的"显影剂"。**

### 1.3 ⛔ 这条推翻了我 066d 里的一句

```
✓ 生产不请求 logprobs ⇒ 不会看到 400/NaN（这点仍然对；发布包 tools/ 下无一处请求 logprobs）
⛔ 但 ★ 同一批 prompt 会【静默拿到错误 token】⇒
★★ 档 D 的风险性质：从"求 logprobs 会 400" 升级为"**会静默产错 token**"
```

## 2. ★★★ 判据强度教训（**单列**，对未来所有验证都适用）

```
同一个仪器的两种判据，抓到的是【不同子集】：
  fill != replay   （弱） ⇒ [4,5,7]        ← ★ 漏掉 40% 的损坏

```
⇒ ★★ **这解释了为什么我此前会得出"两条链独立"** ——
   **不是模型有两条链，是我的弱判据少看了 2 条**。

### 2.1 建议的硬规则（主代理 19:2x 已确认加进 `AGENTS.md §5b`）

> ★ **任何"同输入多次应当一致"的判据，必须跑 ≥3 轮并取"任一不同"** ——
> 2 轮（`fill vs replay`）会漏掉"**延迟到第 N 轮才显现**"的损坏。
> ★ 而"延迟显现"恰恰是**进程内累积型**缺陷的典型形态。

## 3. ⛔ **撤回 066e 的负面结论**：它被自己的阳性对照证伪

### 3.1 阳性对照**通过**（探针确实看得见 NaN）

```
[C2-NAN-INJ] 已人为注入 1 个 NaN 到 tag=cmp_plane_gs/deq
[C2-NAN] cmp_plane_gs/deq shape=(98304,512) n_nan=1 n_inf=0 bad_rows=1
         numel=50331648 n_nonzero=1 absmax=0 head=[nan, 0.0, 0.0, 0.0] path=graph-safe-spec inject_ok=True
```
⇒ ★ **判据有效**（人为注入的 NaN 被探针准确捕获：`n_nan=1 / bad_rows=1 / head` 首元素是 `nan`）。

### 3.2 ★★★ 但**所有缓冲 `n_nonzero = 0`、`absmax = 0`**——**包括源平面**

```
tag                          call    shape                 n_nonzero  absmax  head
ori_plane/deq                 4    (12288, 512)                0        0     [0,0,0,0]
ori_plane/deq              4000    (1152, 512)                 0        0     [0,0,0,-0.0]
ori_plane/sel_scale           5    (32,3,128,1,4)              0        0     [0,0,0,0]
ori_plane/sel_i8              6    (32,3,128,1,512)            0        0     [0,0,0,0]
★ ori_plane_flat/src_i8       3    (2253,128,1,512)            0        0     [0,0,0,0]   ← ★ 源平面也是 0
cmp_plane_gs/scales          20    (192,512,1,4)               0        0     [0,0,0,0]
```

⇒ ★★ **确证**：这些缓冲**根本没有被写过任何非零值**
（含 `src_i8` = **KV cache 本体**，形状 `(2253,128,1,512)`；连它在 `call=3` 与后期 `call=4000` 都是全 0）。

### 3.3 结论：`066e` 的"NaN 不在反量化路径里"**作废**

```
066e 的原表述：「NaN 不在 int8 反量化路径里」（4 组探针 + 心跳，0 命中）
★ 实际含义：这些张量**全是 0**（包含源平面）⇒ 零张量上永远不会有 NaN ⇒ **"clean" 是平凡的**
⇒ ⛔ 066e 那条结论【撤回】；正确表述是：
   「**反量化路径是否产 NaN —— 未测到**；在 `--load-format dummy` 的 tiny 几何下，
     KV 平面（含源）全为 0，**该路径无法用这套几何验证**」
```
★ 原因【推断】：`--load-format dummy` 下权重是占位值 ⇒ 投影输出 0 ⇒ 写进 KV 的也是 0。
—— ⚠️ 这条**不改变**统一假说（§1 的损坏集与 NaN 集重合是**客户端可见行为**，
与内部缓冲是否为 0 无关）；但它意味着**要验证反量化路径，必须换非 dummy 权重**。
