## 1. 方法与 provenance

### 1.1 harness：arms 只有一份实现

图内 harness **没有重抄**两个 verbatim 块，而是用 `importlib` 加载 `logs/41` 的 sweep 脚本
（`agents/T2_ceilings/bench/bench_engram_gate_head2head_sweep.py`，sha256 `66470619…`），直接用它导出的
`pr16925_engram_gate` / `engram_gate` / `our_arm()` / `ceiling_arms()` / `make_inputs()`。
这样**eager 表与图内表的臂是同一份代码、同一个 arm 名字**（`ours ceiling=2048 (CHUNK=512 MAX=2048)` …），
verbatim 块也不可能漂移；`--verify-verbatim` 转调 sweep 自己的检查器（块只有那一份拷贝）。

```text
[verify-verbatim] 上游 PR-16925 : MATCH  25 行，block sha256 233b41566cbcdc49…（与 logs/36/41 相同）
                  OURS         : MATCH 184 行，block sha256 62649435a5476773…（同上）
[verify-verbatim] PASS        （三次运行都跑，c0/c1/c2 各一次）
[verify-embedded-blocks] PASS （本机纯文本版，证明 sweep 里的块 == 原版 pr/bench 里的块）
```

图内 harness 新增的东西只有三件：`torch.npu.NPUGraph()` + `with torch.npu.graph(g)` 的捕获/回放
（骨架照 `pr/rope_edge_cases.py` 的 `phase_graph`）、`torch.equal` 校验、显存统计。

### 1.2 图内协议（每格都做）

1. **shape 固定**：一图一 (arm, n)，`n` 就是 **capture 时的 batch size**（ceiling 是编译期常量，这正是它存在的理由）；
2. `capture_warmup` 次图外 warmup（3 次）→ `torch.npu.synchronize()` → capture；
3. **抓完必须校验**：`replay()` 后把图输出 `clone()` 出来，与**同一臂的 eager 输出** `torch.equal`（126/126 True，max|d|=0）；
4. **活性检查**：就地改 `hidden[0,0,0]` → replay 输出必须变（证明图真读冻结的输入 buffer，不是回放陈旧值）→ 改回后逐位复原；
5. 计时：`reps=30` 次"一次 replay + 一次 sync"取中位，**除以图内调用数 L**；另记一次 `reps=30` 次背靠背 replay（无逐次 sync）作参考；
6. 显存：capture+replay 期间的 `max_memory_allocated` 增量（= 图私有池峰值）。

**L 的含义**：生产帧是"一张图里 40 层模型"，gate 调用只是其中一个节点，所以 per-call 成本应看**大图内的摊薄值**。
本任务跑 **L=1 / 4 / 16**（c0/c1 主跑）与 **L=40**（c2 对照）。L=1 与 L=16 的差是"每次 replay 的固定开销"（拟合见 §6），
**L=40 与 L=16 逐格相同 ⇒ 已经收敛**（生产帧由此被覆盖）。

## 5. ★ 与上游臂对比：eager 口径为什么会误导

§3.2.1 原文写"小 batch 图上 512 只比上游慢 **1.19–1.38×**"。图内同一格完全不是这个数。原因只有一个：
**上游臂的 eager 时间里有一大半是 host 下发，而它进图后就没了；我们的臂几乎没有 host 成分**。

| n | 上游 eager | 上游 graph L=16 | 上游 eager/graph | 我们 MAX=512 图内 | 512 / 上游（图内） | 2048 / 上游（图内） |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.546 | **0.099** | 5.5× | 0.679 | **6.84×** | 26.13× |
| 8 | 0.611 | **0.152** | 4.0× | 0.688 | **4.54×** | 17.34× |
| 32 | 0.553 | **0.180** | 3.1× | 0.690 | **3.83×** | 14.79× |
| 192 | 0.552 | **0.270** | 2.0× | 0.742 | **2.75×** | 10.21× |
| 512 | 0.610 | **0.558** | 1.1× | 0.787 | **1.41×** | 5.11× |
| 1024 | 1.342 | 1.319 | 1.02× | （1024 桶 1.548） | 1.17× | 2.23× |
| 2048 | 3.315 | 3.276 | 1.01× | （2048 桶 3.185） | 0.97× | 0.97× |
| 4096 | 6.753 | 6.698 | 1.008× | （4096 桶 6.365） | 0.95× | — |

（die 6 逐格同号同量级：n=1 6.88× / 26.36×，n=192 2.77× / 10.23×，n=512 1.43× / 5.11×。）

**读法**：

1. **上游臂只在 n≳512 时 eager ≈ 图内**；n≤192 时 eager 是图内的 2–5.5×，
   也就是说 `logs/41`、`logs/36` 里"上游 0.55–0.69 ms"这个平台**主要是 host 下发**，不是 device 工作。【实测】
2. 我们的臂相反：图内只比 eager 快 1–11%（§2.3）⇒ **eager 口径系统性低估上游、从而系统性高估我们的相对优势**。【实测】
3. 因此"比上游慢 1.2–1.4×"这句话的正确适用范围只有 **n≈512 的、ceiling 恰好取 512 的、eager 的**格子；
   图内该说：**最优 ceiling 下 1.41× (n=512) → 2.75× (192) → 4.54× (8) → 6.84× (1)**；
   **shipped 2048 下 5.11× → 26.1×**（而 eager 只写 4.12–4.78×）。【实测】
4. 物理含义：上游每次只算真实行数（device 时间 ∝ n），我们每次算 MAX 行（device 时间 ∝ MAX）。
   **padding 常数就是全部成本**这句话在图内更干净：n=192 时 0.742/0.270 = 2.75 ≈ 512/192 = 2.67。
   换句话说，图内口径把"按行收费"这件事实测成了两条过原点的直线（§3）。【实测】
5. **公平性边界（必须写明）**：上游臂的图是"为该 n 单独捕获"的（静态 shape），我们的一张图能覆盖 1…MAX 任意 n
   ——这正是 chunked gate 存在的理由。所以图内的比值不是"同一张图"的比较，而是
   "**一张覆盖 2048 的图** vs **一张只覆盖 192 的图**"；要消掉这个不公平，就得用 per-capture-size 分桶（§8）。【推断】

## 6. 每次 replay 的固定开销与 L=40 生产帧对照

把 per-call(L) 对 1/L 做最小二乘（L=1/4/16），得 `per-call(L) = 渐近值 + 固定开销 / L`（die 3，节选）：

| n | arm | L=1 | L=4 | L=16 | 渐近值 ms | 固定开销 ms |
|---:|---|---:|---:|---:|---:|---:|
| 1 | 上游 | 0.316 | 0.110 | 0.099 | 0.069 | **0.244** |
| 1 | MAX=512 | 0.729 | 0.678 | 0.679 | 0.671 | 0.057 |
| 1 | MAX=2048 | 2.657 | 2.620 | 2.597 | 2.598 | 0.060 |
| 192 | 上游 | 0.348 | 0.279 | 0.270 | 0.261 | 0.086 |
| 512 | 上游 | 0.555 | 0.553 | 0.558 | 0.556 | −0.001 |
| 512 | MAX=2048 | 2.813 | 2.861 | 2.853 | 2.863 | −0.049 |
| 4096 | MAX=4096 | 6.368 | 6.347 | 6.365 | 6.356 | 0.010 |

**读法**：图内 per-call 成本 = 一个与 L 无关的渐近值 + 一个被 L 摊薄的固定开销。
轻图上（上游 n≤32）固定开销 0.17–0.24 ms/replay 很显眼（L=1 与 L=16 差 2–3×）；重图上它 ≤0.07 ms（拟合里出现负值是噪声）。
**所以"图内每调用时间"必须声明 L**：本文一律以 **L=16** 为主口径，并对轻图臂给出 L=1 的数（§5 的第 3 条）。

## 10. 结论与建议：推荐值有没有变

**规则不变**：

```text
V41_ENGRAM_GATE_MAX_TOKENS = max(CHUNK, ceil(B_max / CHUNK) * CHUNK)
```

图内口径给出的**价格表**（取代 eager 价格表作为引用值；L=16，die 3/die 6）：

| 场景 | 推荐 ceiling | 图内每调用 | 图池峰值 | 相对上游（图内） |
|---|---:|---:|---:|---:|
| decode-only 图（`B_max ≤ 512`） | **512** | **0.679–0.816 ms** | **285–305 MB** | 1.41× (n=512) … 6.84× (n=1) |
| 生产 prefill 合同（BAT = 2048） | **2048（维持现状）** | 2.597–3.185 ms（n≤512）/ 3.185 ms（n=2048） | 420–500 MB | 5.11× (512) … 26.1× (1) / 0.97× (n=2048) |
| 零 padding（n=MAX） | `ceil(n/512)·512` | n=2048: 3.185；n=4096: 6.365 | 500 / 760 MB | **0.97× / 0.95×（比上游快）** |

1. **推荐值不变**，但 §3.2.1 引用时必须改成图内数：`MAX=512` vs `2048` 的差在图内是 **+1.92 ~ +2.10 ms（3.6–3.9×）**，
   与 eager 的 +2.02 ~ +2.18 ms（3.4–3.8×）同量级 —— **超配的代价是 device 时间，不会因为进图而变小**。【实测】
2. **per-capture-size 分桶的价值在图内更大**（不是更小）：eager 口径下"一张 2048 图服务 1–192 token"看起来只贵 4–5×，
   图内是 10–26×，因为对手（上游）的 host 成分在图内消失了。分桶后每桶取 `ceil(BUCKET/512)·512`，桶价目表就是 §2.1 的行/列。【实测 + 推断（真实 capturer 未验）】
3. **§3.2.1 的 "1.19–1.38× upstream" 必须收窄到 eager**；图内的诚实说法是 §5 第 3 条。
4. **`MAX=256` 的静默抬升坑在图内同样适用**（本次未单独再测该臂：`logs/41` 已实测它等于 `MAX=4096` 臂，

## 12. 【实测】/【推断】/【未确认】

**实测**

1. 图内 ceiling 曲线是直线：斜率 **0.646–0.686 ms/512 行（die 3）**、**0.639–0.691（die 6）**，与 eager（0.648–0.693 同批 / 0.660–0.710 `logs/41`）同值；截距 0.010–0.471 vs eager 0.101–0.627。
2. `MAX=512` vs `2048` 在图内：绝对差 **+1.918 ~ +2.065 ms**（均值 +1.981 die3 / +1.999 die6），比值 **3.62–3.86×**；eager 同批 +2.018~+2.181 / 3.44–3.80× ⇒ **优势几乎不变（绝对 −4%、比值 +6%）**。
3. 上游臂的 eager→图内塌陷：n=1 0.546 → 0.099 ms（5.5×）、n=192 0.552 → 0.270（2.0×）、n=512 0.610 → 0.558（1.1×）；我们的臂只快 1–11%。
4. 图内比值（最优 ceiling）：1.41× (512) / 2.75× (192) / 3.83× (32) / 4.54× (8) / 6.84× (1)；shipped 2048：5.11× / 10.21× / 14.79× / 17.34× / 26.13×。
5. 126/126 图内格 `torch.equal` 与活性/复原检查全通过；0 个捕获失败；非法格 6 个记 error。
6. 图池峰值 = eager + 0~160 MB，**L≥4 饱和**（L=16 与 L=40 同值）；L=40（die 7）与 L=16（die 3）逐格差 ≤4%。
7. 8K 小表：eager 213.70 → 83.90 µs（n=192）、152.75 → 58.50（40 层 burst/调用）、165.62 → 64.20（spec lookup）；**图内 148.71 → 18.73 µs（7.94×）**；27/27 checks。
8. 同会话 1M↔8K 对照：stock 图内 48.35 → 147.64 µs（3.05×）、PR 18.72 → 18.67 µs（不变）⇒ 与 §6.1 的 6→12 kernel 计数互相印证。
9. n>4096：n=8192 于 MAX=8192 图内 12.771 ms / 1440 MB vs 上游 13.255 ms / 3520.5 MB（0.96× / 0.41×）；MAX=4096 在 n=8192 报错。

**推断（有数字支撑，但没有直接测量）**

1. "图内 per-call = 渐近值 + 固定开销/L" 的分解是拟合出来的经验式（L=1/4/16 三点），不是器件模型；
   轻图上 0.17–0.24 ms 的"固定开销"到底是图 launch 还是小 kernel 的 device 侧调度，本任务没有区分。
2. per-capture-size 分桶能把 shipped 的 2 ms 拿回：机制成立（ceiling 是编译期常量，桶内取最小合法值即可），
   但**没有**在真实 capturer（vLLM-Ascend 的 ACLGraph 池）里验证；本次是函数级、单图独立捕获的代理。
3. 把"每次 gate 调用 2 ms"放大到整 step：本任务只到函数级、合成输入、单卡无并发，不构成端到端结论。
4. L=16 的 per-call 值是"吞吐/摊薄"值；若生产图里 gate 调用能与其它算子重叠，实际占比可能更低。
