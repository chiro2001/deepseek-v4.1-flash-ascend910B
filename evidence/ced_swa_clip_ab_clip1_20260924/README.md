## 三条硬结论

1. **裁剪确实执行了。** `[CED-SWA-CLIP]` 按层统计各 **80 行** = 10 请求 × 8 rank
   （layer 2 与 layer 20 各 80），`[CED-SWA-TRACE] phase=replay` 也是 80 行
   = 10 请求 × 8 rank。所以"没生效"不是"没跑到"。
2. **修复没有改善失败。** 失败相位与修复前逐位相同（都是 #4、#8），
   通过率同为 8/10（修复前 8 次里 6/8）。
3. **"块碎片化 ⇒ 失败"被推翻。**
   - #4 与 #10 的 g0 统计**完全相同**（`last=6136`、`descents=1854`），一个 FAIL 一个 PASS；
   - #7 与 #8 共享 `descents=6114`，一个 PASS 一个 FAIL；
   - #5/#6 的 `descents=7967`（比失败的两个都更碎）却都 PASS。

   因此 `descents` / `first` / `last` 这类摘要量**不能**作为判别量。
   之前 4 请求的小样本里"失败的那一个恰好是碎片的"是巧合。

## 后续追加实验（2026-09-25 00:xx，同一个 D 实例，未重启）

### A. 续发 6 次：失败点正好落在 #12、#16

接着再发 6 个同款 1M 请求（记作 c2_1…c2_6，全局第 11–16 个），结果：

| 全局 # | c2 序号 | 结果 |
|---:|---:|---|

| 13 | c2_3 | PASS |
| 14 | c2_4 | PASS |
| 15 | c2_5 | PASS |
| **16** | c2_6 | **FAIL** |

⇒ 连续 16 个 1M 请求里，失败恰为 **#4、#8、#12、#16**（全部 ≡ 0 mod 4），
通过 12/16。失败间隔 #4→#8 与 #12→#16 都是 **6 分 53 秒（413 s）**，
而每个请求耗时 103 s ⇒ 413 ≈ 4 × 103。

### B. 插入 3 个短请求**没有**改变失败相位

在 #16 之后依次发 3 个 22-token 短请求（s1/s2/s3，全部 PASS，耗时 2.3/0.6/0.6 s），
再发第 4 个请求（L1，1M）——**L1 PASS**。

若周期按"全部请求"计数，L1 是全局第 20 个、应当失败；它通过了 ⇒
**短请求（或 ≤128 token、无长 replay 的请求）不推动这个周期**，
周期只按"走完整 128-token replay 的长请求"推进。

### C. 寻址元数据在通过/失败之间**逐字段相同**（原假说出局）

`[CED-SWA-TRACE] phase=replay`（layer 20，rank 0）在 #1…#6 六条
（含失败的 #4、通过的 #5）**完全相同**：

```
layer=20 phase=replay n_queries=128 pos=1019718..1019845 seq_len=1019846
bt_shape=(1, 8192) row_len=8192 row_head=[0, 0, 0, 0]
row_nonzero=[7966, 7967] need_blocks=7965..7967
```

即算子在这一步收到的**地址与长度元数据一字不差**，却一个失败一个通过。
结合"块统计相同的两个请求结果相反"，可以断言：
**根因不在寻址元数据、也不在块布局，而在这些地址背后的内容/时序。**

### D. P 侧延迟释放的超时值

两个容器内 `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT = 480`（秒）。
P 全生命周期共 40 条 `Delaying free of 7979 blocks`、8 条 `Force freed`
（全部发生在同一时刻、同一个请求）。413 s 的失败间隔与该 480 s 超时**不等**，
但同为"分钟级"，需要用空闲插入实验区分"计数周期"与"时间周期"（见下）。

### E. 正在跑：空闲插入判别（本轮最后一个实验）

在 #17（L1）之后**先空转 8 分钟**（>480 s），再连发 4 个 1M 请求（i1…i4）：

- **计数假说**：下一个失败仍是第 4 个长请求 → i3（全局第 20 个）失败；
- **时间假说**（≈413–480 s 的定时器/超时）：空转期间定时器在无请求在飞时到期，
  相位被打断 → i1…i4 全部通过。

两者预测**互相矛盾**，因此这一次即可判定周期是"按长请求计数"还是"按墙钟/活跃时间"。

### E 结果：**计数假说成立**（2026-09-25 00:08–00:16）

```
[idle-test] sleep 480 start 2026-09-25T00:00:44+08:00
[idle-test] sleep done  2026-09-25T00:08:44+08:00
i1  PASS   completion=7   wall=103.0s
i2  PASS   completion=7   wall=103.1s
i3  FAIL   completion=1   wall=102.8s   ← 全局第 20 个长请求
```

空转 8 分钟（> `VLLM_MOONCAKE_ABORT_REQUEST_TIMEOUT=480 s`）**没有**重置相位：
第 20 个长请求照旧失败。⇒ **周期由"长请求的个数"推进，与墙钟/超时无关**，
480 s 超时假说出局。

至此已排除的候选（都有实测依据）：

| 候选 | 结论 |
|---|---|
| D 侧物理块布局（碎片度/首末页/整行） | 不是判别量（#4 与 #10 布局统计相同、结果相反） |
| 算子收到的寻址元数据 | 不是判别量（通过/失败逐字段相同） |
| P→D 传输内容（尾位置 long_kv/index_k） | 不是判别量（通过-失败配对 maxdiff=0） |
| Engram 4-gram / hash 值 | 不是判别量（含失败的 #4 在内逐位相同） |
| 墙钟/超时机制（480 s） | 空转 8 分钟后相位不变 ⇒ 排除 |
| 短请求（≤128 replay） | 不推进周期（插 3 个短请求后失败点仍按长请求计数） |

**剩余最强候选：D 的请求槽位/批内常驻状态**（周期 = `MAX_SEQS = 4`）。
下一步单变量：把 D 改成 `MAX_SEQS=1`，其余完全不变，跑 8 个长请求——
若失败消失 ⇒ 槽位/批内 buffer 相关；若仍每 4 个失败 ⇒ "4" 与 `MAX_SEQS` 无关。

### F. `MAX_SEQS=1` 单变量：**周期不变**（2026-09-25 00:22–00:36）

重启 D，只把 `MAX_SEQS` 从 4 改成 1（其余完全不变：同样的 `GRAPH=1 EAGER=0`、
prompt-tail eager、metadata inline、`V41_CED_SWA_CLIP=1`）。新实例、
`num_blocks: 30200`（标准臂是 30082）、`max-num-seqs 1` 已在容器命令行核对。

```

ms1_2  PASS  completion=7
ms1_3  PASS  completion=7
ms1_4  FAIL  completion=1   ← 仍是第 4 个
ms1_5  PASS  completion=7
ms1_6  PASS  completion=7
ms1_7  PASS  completion=7
ms1_8  FAIL  completion=1   ← 仍是第 8 个
```

⇒ **周期 4 与 `MAX_SEQS` 无关**（也不是某个具体 D 实例的残留状态：
这是全新实例）。前面把"周期 = MAX_SEQS"当成最强候选的判断被这次实验否掉。

同时要修正本文早先一处过强的表述：我们只证明了块布局的**摘要**
（`n`/`first`/`last`/`descents`）不判别，而**摘要相同的两个列表顺序可以完全不同**，
所以"回收/绕回"这一类机制**并未被排除**。
两个 D 实例的池/请求比都落在同一档：
`30082 / 7989 = 3.766`（标准臂）、`30200 / 7989 = 3.780`（MAX_SEQS=1）⇒
`ceil(比值) = 4`，与观测周期一致。

下一步单变量：**把 KV 池压到"约 2.4 个请求"的量**（`--kv-cache-memory-bytes`），
让比值落到 `ceil = 3`。若失败周期随之变成 3 ⇒ 与池的绕回/回收直接相关；
若仍是 4 ⇒ 与池无关，回到"按请求计数"的其他机制。

### G. 压小 KV 池：**4 个一循环的失败消失**（2026-09-25 00:46–00:57）

保持 `MAX_SEQS=1`，只把 D 的 KV 池显式压到 `--kv-cache-memory-bytes=10545000000`
（实测 `num_blocks: 19494`，`19494 / 7989 = 2.44`），其余完全不变。连发 6 个 1M：

```
sp_1 PASS 102.7s | sp_2 PASS 102.7s | sp_3 PASS 102.7s
sp_4 PASS 102.7s | sp_5 PASS 102.7s | sp_6 PASS 102.7s
```

**6/6 全过** —— 这是本次调查里第一次连续 6 个 1M 请求没有出现偶发失败
（标准臂最好成绩是连续 3 个）。另外注意 wall 时间也变得整齐（全部 102.7 s，
标准臂是 103.0–103.2 s）。

**但周期并没有变成 3**（`sp_3` 与 `sp_6` 都通过），所以"失败发生在绕回的那一个
请求上"这个具体形式**不成立**：按 FIFO 前进，这个池下第 3、5 个请求就会绕回，
而它们都通过了。⇒ 触发条件与**池几何**有关，但不是"绕回"这一简单事件。

三次单变量对照（全部同一 prompt、串行、`temperature=0`）：

| D 配置 | `num_blocks` | 池/请求 | 失败位置 |
|---|---:|---:|---|
| `MAX_SEQS=4`（标准臂） | 30082 | 3.77 | #4, #8, #12, #16 |
| `MAX_SEQS=1` | 30200 | 3.78 | #4, #8 |
| `MAX_SEQS=1` + 小池 | 19494 | 2.44 | **6 个里 0 个** |

这是目前**唯一**能稳定跑过 4 个连续 1M 请求的配置，因此既是重要线索，也是
一个（尚未验证充分、机制不明）的**候选缓解手段**。必须先用更多请求确认它不是
更长周期（例如 7 或 8）的假象，再谈缓解。

#### G-1. 追加 6 个请求：**12/12 全过**

紧接着再发 6 个同款 1M（`sp2_1…sp2_6`），全部通过：

```
sp2_1 PASS 102.6s | sp2_2 PASS 102.7s | sp2_3 PASS 102.6s
sp2_4 PASS 102.6s | sp2_5 PASS 102.8s | sp2_6 PASS 102.6s
```

累加第一轮，**小池配置连续 12 个 1M 请求全过**；而标准池在同一台机器、
同一 P、同一请求下是**每 4 个必失败**（16 个里失败 4 个，位置 4/8/12/16）。
这不是"更长周期的假象"——若周期是 7 或 8，12 个里至少会命中一次。

**注意当前可交付性边界**：这一轮小池实验同时改了 `MAX_SEQS=1`（因为它是紧接
上一节实验的继续）。因此"小池"与"`MAX_SEQS=1`"这两个变量还没有分开验证。
下一步必须做 **`MAX_SEQS=4` + 小池**：若同样 12/12 ⇒ 小池是决定性因素，
可以恢复标准臂的 `MAX_SEQS=4`；若又出现每 4 个失败 ⇒ 是两个变量的组合效应。
