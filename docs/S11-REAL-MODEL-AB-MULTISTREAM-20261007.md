## 1. 实验设计（A/B 只差一个开关）

| 臂 | `multistream_dsv4_dsa_overlap` | 代码路径 |
|---|---|---|
| **A（双流）** | `true` | `_mla_prolog_multistream`：Part1 q_quant[V]→q_a_down[C] ‖ kv_quant[V]；Part2 q_norm[V]+q_b_quant[V] ‖ kv_matmul[C]；Part3 q_b_matmul[C] ‖ kv_norm[V]+rope[V]+scatter[AIV] |
| **B（串行）** | `false` | `_mla_prolog_single_stream`：全部在主流 |

**这正是用户描述的形态**：两条流，每条都含 cube(C) + vector(V) + AIV，按 Part 交叉排布。

**测量**：`tools/bench_concurrency.py`，prompt=1024 tok、output=96 tok、4 个互不重叠的请求，**各跑 3 次重复**。

## 3. Profiler：为什么只有 1~2%

取 device 最忙的 **200 ms 窗口**（A 臂，20071 个 kernel）：

| 指标 | 值 |
|---|---|
| 有 kernel 在跑的时间 | **77.6%** |
| **≥2 kernel 同时（真并发）** | **4.3% of 窗口；5.5% of 活跃时间** |
| 峰值并发 | 4 |
| **AIC 忙** | **27.8%** |
| **AIV 忙** | **38.9%** |
| 两者之和 | **66.7%** |

**并发时刻的 stream 组合**（Top）：

| stream 对 | 时长 |
|---|---:|
| (202, 204) | 4.8 ms |
| (201, 204) | 2.9 ms |
| (197, 199) | 0.4 ms |

⇒ **stream 204 是主流，202/201 是侧流**；两条流**确实在并发**，但只占 5.5%。

**三条推论**：

1. **设备绝大多数时间只在跑一个 kernel**（77.6% 活跃 vs 5.5% 并发）；
2. **AIC+AIV = 66.7%** ⇒ 有 ~33% 的时间是"gap"（kernel 之间没活）；
3. **如果 AIC 与 AIV 能完全重叠**，理论上限 = `max(27.8, 38.9) = 38.9%` ⇒ **~1.7× 空间** —— 但被**依赖链**卡住。

---

## 4. 为什么收益只有 1~2%（而定性方向是对的）

| 原因 | 证据 |
|---|---|
| **覆盖范围小** | `_mla_prolog_multistream` 只覆盖 attention 的 **q/kv 投影段**。按 trace 估算：prolog ≈ 90 µs/层 × 43 层 ≈ **3.9 ms / 28.1 ms = 13.8%** 的步长 |
| **其中只有一部分真重叠** | profiler 显示真并发 5.5% of 活跃 |
| **其余 86% 的步长仍是单流串行** | 主流 1624 个算子里的 MoE / HcPre / HcPost / SparseFlashMla 等仍是依赖链 |

**⇒ 1~2% 的端到端收益，与"14% 的覆盖 × 部分重叠"量级一致。**

---

## 5. 这次得到了什么、没得到什么

### 得到了（真机、真实依赖）

1. **方向验证**：两条流交叉排布在真实模型上**是正收益**，符号正确；
2. **量级锚定**：**当前只覆盖 14% 步长 ⇒ 端到端 +1~2%**；
3. **上限测量**：真并发只占活跃时间 **5.5%**，而 AIC+AIV 占 **66.7%** ⇒ **空间存在但被依赖链锁住**；
4. **一个可直接复用的开关与代码路径**（`multistream_dsv4_dsa_overlap` ↔ `_mla_prolog_multistream`）。

### 没得到

1. **没有做全模型的两流改造**（只在现有实现上做 A/B）；
2. **没有验证"把更多算子挪到侧流"能否扩大收益**——这是下一步；
3. **tiny 是 dummy 权重 + TP2/DCP2**，绝对数值不可直接外推到 TP8。
