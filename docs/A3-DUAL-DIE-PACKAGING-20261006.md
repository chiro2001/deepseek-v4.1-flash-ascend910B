# ★ A3（910C）单卡两 die 合封：实测特性与优化机会（2026-10-06）

> 问题来源：A3 一张卡是**两个 die 合封**，那这两个 die 之间的链路（SIO）
> 相比跨卡的 HCCS 是不是更快？有没有可以利用的机会？
> 全部为【实测】，工具 `tools/hccl_die_pair_bench.py`（图捕获剥掉主机下发开销）。

## 0. 一句话

**同卡两 die 只在"大消息带宽"上占优（+50%），在"小消息延迟"上没有任何优势。**
而我们的 decode（61 KB / 1.5 MB）恰好全在小消息区间 ⇒ **decode 不可能靠摆位变快**；
prefill（15.7–66 MB）在大消息区间，但**我们已经在用最优摆位**（4 个 SIO 跳 + 4 个跨卡跳，
是 8 rank / 4 卡下的上限）。

## 1. 硬件事实：链路类型（`npu-smi info -t topo`）

```
Phy-ID0-1 : SIO        （同卡两 die）
Phy-ID2-3 : SIO
...
其它所有组合 : HCCS_SW  （跨卡，经 HCCS 交换芯片）
```

⇒ A3 的 16 个 Phy-ID = **8 张卡 × 2 die**；同卡内 SIO，跨卡走 HCCS 交换芯片。
（我们此前在 README 里强调过"说卡会有歧义"，这里给出量化版本。）

## 2. 同卡 vs 跨卡（2 rank，图捕获）

| 消息 | SIO（同卡） | HCCS_SW（跨卡） | 谁赢 |
|---:|---:|---:|---|
| 61 KB | 113.3 µs | 111.0 µs | 平（差 2%，在噪声内） |
| 1.5 MB | 107.8 µs | 103.9 µs | 平 |
| 6 MB | 121.2 µs | 108.1 µs | 平 |
| 24 MB | 251.7 µs（100.0 GB/s） | 281.3 µs（89.5 GB/s） | **SIO +12%** |
| 64 MB | 609.8 µs（110.0） | 688.4 µs（97.5） | **SIO +13%** |
| 128 MB | 1195.1 µs（112.3） | 1334.1 µs（100.6） | **SIO +12%** |

**结论**：交叉点在 **6–24 MB** 之间。
* **< ~6 MB：完全无差别**（都被 ~105–115 µs 的固定成本主导）；
* **≥ 24 MB：SIO 领先 ~12%**。
* 【注意】2-rank 时两者的固定成本都是 ~110 µs，**说明 HCCS 交换芯片的逐跳延迟并不比 SIO 差**。

## 3. 4 rank 对照：含 SIO 跳 vs 全跨卡

| 消息 | C：4 die / 2 卡（2 个 SIO 跳） | D：4 die / 4 卡（全跨卡） | 谁赢 |
|---:|---:|---:|---|
| 61 KB | 94.5 µs | 88.7 µs | 平 |
| 6 MB | 246.3 µs（25.5 GB/s） | 154.7 µs（40.7） | D |
| 24 MB | 317.5 µs（79.3） | 373.2 µs（67.4） | **C +18%** |
| 128 MB | 1075.1 µs（**124.8**） | 1622.5 µs（82.7） | **C +51%** |

⇒ 大消息下**含 SIO 跳的拓扑明显更强**（+51%），这也说明 SIO 的单跳带宽/效率高于 HCCS_SW。

## 4. ★★ 最有价值的一条：**rank 摆位**（8 rank / 4 卡）

容器内 8 个 die，只改 `DEVS` 的**顺序**（= 第 i 个 rank 用哪个 die），硬件不动：

| 配置 | 同卡两 die 落在哪些 rank | 61 KB | 6 MB | 24 MB | 128 MB |
|---|---|---:|---:|---:|---:|
| **A 自然** `0,1,2,3,4,5,6,7` | 相邻：(0,1)(2,3)(4,5)(6,7) | **98.9** | 307.2 | **404.2** | **1218.1（110.2 GB/s）** |
| E 打乱卡序 `0,1,4,5,2,3,6,7` | 仍是相邻 | 168.7 | 270.1 | 431.6 | 1243.5（107.9） |
| **B 交错** `0,2,4,6,1,3,5,7` | 相隔 4：(0,4)(1,5)… | **258.9** | 343.6 | 484.8 | **1935.1（69.4 GB/s）** |

* **A ≈ E ≫ B**（128 MB：110.2 / 107.9 / **69.4** GB/s）⇒ 决定性变量是
  **「同卡两 die 是否相邻 rank」**，与"具体是哪张卡"无关；
* **B 比 A 慢 59%（大消息）/ 2.6×（61 KB）** —— 这正是"想当然地把 rank 交错开"会踩的坑；
* 【实测】**我们现役的 `DEVS="8 9 10 11 12 13 14 15"` 就是 A（最优）**。
  8 rank / 4 卡下，一个简单环最多只能有 **4 个 SIO 跳**，A 正好用满 ⇒ **没有进一步摆位空间**。

## 5. 代价曲线：为什么"消息越大越划算"

8 rank 自然摆位的实测（图捕获）：

| 消息 | per_call | 有效带宽 |
|---:|---:|---:|
| 384 KB | 90.4 µs | 8.7 GB/s |
| 768 KB | 109.2 µs | 14.4 |
| 1.5 MB | 121.9 µs | 25.8 |
| **4.5 MB** | **272.9 µs** | 17.3 |
| 6 MB | 263.2 µs | 23.9 |
| 12 MB | 302.8 µs | 41.6 |
| 24 MB | 414.9 µs | 60.7 |
| 48 MB | 610.4 µs | 82.5 |

**1.5 MB → 4.5 MB 之间有一个台阶（~120 µs → ~270 µs）**，之后进入"~250 µs 固定 + 129 GB/s"
的线性段 ⇒ 大消息的**边际带宽很高**（4.5→48 MB 的增量 ≈ 129 GB/s），但每次调用要付 ~250 µs。

【推论】同一个 allreduce，**M 越大越划算**：

| 场景 | 张量（o_proj allreduce，TP8） | 估计 per_call | **每 token 摊销** |
|---|---:|---:|---:|
| 解码 M=6 | 49 KB | ~99 µs（延迟段，且被 multistream 部分掩盖） | — |
| **prefill M=1920（BAT=2048）** | 15.7 MB | ~250 + 122 = **372 µs** | **0.194 µs/tok** |
| **prefill M=8064（BAT=8192）** | 66 MB | ~250 + 512 = **762 µs** | **0.0945 µs/tok** |

⇒ **把 BAT 从 8192 降到 2048，会让 allreduce 的每 token 成本翻 2.05×**
（40 层 × 2 次/层；60K prompt 下估算 +0.46 s）。
这解释了我们实测 prefill 6.5K→5.8K tok/s（−12%）里的**相当一部分** ——
它**不是** SIO/HCCS 的问题，而是"每刀消息变小、固定成本摊不薄"。

## 6. 优化机会（按可操作性排序）

| # | 机会 | 依据 | 预期 | 状态 |
|---|---|---|---|---|
| 1 | **保持 `DEVS` 自然顺序**（同卡两 die 相邻 rank） | §4：交错会掉 59% 带宽 | 避免 −40~60% | ✅ **已是最优** |
| 2 | **prefill 别把 M 压太小**（BAT 2048 → allreduce 每 token 翻倍） | §5 | 每 token −0.10 µs×80 次 | ⚠️ 与"容量 +34%"是**权衡**：容量要 BAT=2048，prefill 要 BAT=8192 |
| 3 | **减少小消息集合通信的"次数"**（解码侧） | §2：<6 MB 时链路无差别 ⇒ 只能靠"更少的调用" | 80 次/步 × ~29–99 µs | 已知靶点：`fuse_allreduce_rms` 本栈未实现、`enable_sp` 实测更慢 |
| 4 | 大消息走 SIO 的**摆位**已到上限（4/8 跳） | §4 环论 | — | 无空间 |
| 5 | 用 DP 把 TP 组关进单卡（TP2×DP4） | 理论上 TP allreduce 全走 SIO | 实测**更慢**（低并发 −18%），因为 TP2 让非专家权重多复制 3.24 GiB/rank | ❌ 已否（`docs/DP-TP-TRADEOFF-20260929.md`） |
| 6 | 分层 allreduce（卡内 SIO 先归约，再跨卡） | 手算：15.7 MB 下 200 µs + 300 µs ≈ 500 µs **> 372 µs** | 更差 | ❌ 不划算 |

**核心结论**：这个合封装带来的**唯一**结构性优势是"大消息的卡内带宽"，
而它恰好**不是**我们解码的关键路径（解码是小消息、延迟受限）。
真正能动的杠杆仍然是**减少集合通信次数**与**把 prefill 的消息做大**，
两者都与 die 合封无关 —— 也就是说，**别指望靠摆位解决解码性能**。

## 7. 复现

```bash
# 1) 建一个只占目标 die 的容器（必须挂 driver，否则 aclInit 507008）
sudo docker run -d --rm --name dsv41-pairtest --net=host --shm-size=32g --privileged=true \
  --device /dev/davinci4 --device /dev/davinci5 --device /dev/davinci6 --device /dev/davinci7 \
  --device /dev/davinci_manager --device /dev/devmm_svm --device /dev/hisi_hdc \
  -v /usr/local/Ascend/driver:/usr/local/Ascend/driver \
  -v $HOME/tmp:/work:ro -e ASCEND_RT_VISIBLE_DEVICES=4,5,6,7 \
  quay.nju.edu.cn/ascend/vllm-ascend:deepseek-v4.1-flash-a3 sleep infinity

# 2) 同卡 vs 跨卡（容器内逻辑 0,1 = 物理 4,5 同卡；0,2 = 跨卡）
docker exec dsv41-pairtest bash -lc "cd /work && DEVS=0,1 PAIR_LABEL=SIO \
  SIZES=30,768,3072,12288,65536 CAP=50 REPLAY=5 \
  torchrun --nproc_per_node=2 --nnodes=1 --node_rank=0 --master_addr=127.0.0.1 \
           --master_port=29591 hccl_die_pair_bench.py"

# 3) rank 摆位对照（8 rank，只改 DEVS 顺序）
DEVS=0,1,2,3,4,5,6,7   # A 自然（最优）
DEVS=0,2,4,6,1,3,5,7   # B 交错（大消息 −59%）
```

产物：`tools/hccl_die_pair_bench.py`；本页数据来自 2026-10-06 在 a3-21 的实测
（die 4–7 做 2/4-rank，die 8–15 做 8-rank；测试期间 `dsv41-tp8k5` 已停、测完恢复）。
