# ★★ 关键发现：算子级收益会被"步内松弛"吸收 —— 步时由关键链决定，不由工作量决定（2026-10-04）

> 本文记录本轮最重要的一个**结构性发现**，它推翻了"削减设备工作量就能降步时"这个
> 隐含假设，并解释了为什么多个已在算子层被证明有效的改动在端到端上毫无反应。

## 1. 判决数据：armF 算子变快 7.56µs，但步时不动

**算子级（同一服务、同一份 profile 口径，msprof `Task Duration` 中位）**：

| 指标 | stock（`k6full` N=1） | **armF**（`armF_meta2` sleep=0） | Δ |
|---|---:|---:|---:|
| `GroupedMatmulSwigluQuantV2` Duration | 73.64 µs | **66.08 µs** | **−7.56** |
| `aicore_time` | 63.11 | 57.06 | −6.05 |
| `aic_scalar` | 30.79 | 27.11 | −3.68 |
| `aic_mte1` | 11.21 | 11.21 | 0 |
| `aic_mte2` | 15.51 | 12.35 | −3.16 |
| `aic_mac` | 2.01 | 2.01 | 0 |

⇒ **armF 在真实服务里确实生效**（这同时验证了"`[OPP-OVERRIDE]` + 复制覆盖镜像 vendor + 符号指纹
`_2_mix_aic=37328`"这条交付链完整可用）。

**端到端（`tools/ab_gate.py`，同口径 `[bneck] hp` 按 batch size 分组取中位）**：

| n（batch tokens） | stock（`final_1004_1815`） | **armF** | Δ |
|---:|---:|---:|---:|
| 6 | 25.27 ms | **25.21** | −0.06 |
| 12 | 28.18 | **27.85** | −0.33 |
| 18 | 32.23 | 32.27 | +0.04 |
| 24 | 32.99 | 32.62 | −0.37 |
| 36 | 39.09 | 41.61 | +2.52 |
| 48 | 41.67 | 41.92 | +0.25 |

**配对差中位 = +0.038 ms**（9 个档位）⇒ **端到端无改善**。

按算子级 Δ 折算应得 **−7.56 µs × 43 次/步 = −0.325 ms/step（−1.3%）** ⇒ **被完全吸收**。

## 2. 这个吸收不是孤例

| 改动 | 算子级收益 | 端到端 | 结论 |
|---|---:|---:|---|
| **armF**（SyncAll 4→2、Reset 5→2） | −7.56 µs/op（服务实测） | **+0.04 ms** | 吸收 |
| **HcPre A1**（自适应 K_L0） | −2.61 µs/op | 待测 | （同族，预期也会被吸收） |
| **HcPre+RMSNorm 融合** | 算子级 −2.67 µs（M=96） | 融合版**更慢** | 反向 |
| **Engram 设备索引** | 去掉整条 host lookup | **−2~3.6%** | **未被吸收** ✅ |

**区别在哪**：`ENGRAM_DEVICE_INDEX` 去掉的是 **AI core 主动等待的依赖**（host lookup 完成才能继续），
而 armF/A1 只是让**某个算子本身更快**。

## 3. 机理：步内有 8.4–14.9% 的松弛，吸收了"非关键链"上的加速

修正后的占空比（`scripts/duty_fix.py`；此前"100%"是把 AICPU 混入"设备"的测量错误）：

| 场景 | AI core 占空比 | 空闲 |
|---|---:|---:|
| `ENGRAM_DEVICE_INDEX=0`（host lookup） | 85.1% | 14.9% |
| `ENGRAM_DEVICE_INDEX=1`（设备索引） | **91.6%** | **8.4%** |

而且空闲**均匀散布**（`scripts/idle_hist.py`：100ms 桶 p10–p90 只差 3 个百分点）、
**由 ~1591 个平均 1.5µs 的微小间隙构成**（`scripts/idle_full.py`）——
这是"AI core 等下一个 kernel"的**图内调度/依赖松弛**。

⇒ 一个算子快 7.5µs，只要它**不在当前的关键链上**，那 7.5µs 就落进已有的间隙里，
**步时不缩**。这与"设备占空比 100%、只能削工作量"的旧认识**方向相反**：
**在 91.6% 占空下，能吸收 ~8% 的算子级加速。**

## 4. 对后续策略的三条改写

| 旧策略 | **改写后** |
|---|---|
| 继续找"最贵的算子"并加速它 | **先判该算子是否在关键链上**；不在关键链上的加速会被吸收 ⇒ 白做 |
| 用"独占贡献"排序靶点 | 独占贡献（并集差）仍可用，但**必须叠加"吸收检验"**：算子变快后步时要跟着降，才算真收益 |
| 把 8.4% 空闲当"可填的气泡" | 它是**松弛**，不是浪费 —— 减少非关键链工作量不会自动转化为步时下降 |

**关键链怎么找**（下一步的具体做法）：
1. 对**每一个候选算子**，用 `[OPP-OVERRIDE]` 或等价手段造一个**更快的版本**，
   再看 `ab_gate.py` 的配对差是否 < 0 —— **这就是"吸收检验"**（armF 就是反例）；
2. 或者反过来：**人为把某个算子变慢**（sleep 注入的同款思路，但注入到设备侧），
   若步时**跟着涨**，则该算子在关键链上。这比"加速看是否变快"更灵敏
   （加速可能被吸收，而变慢无法被吸收）。
