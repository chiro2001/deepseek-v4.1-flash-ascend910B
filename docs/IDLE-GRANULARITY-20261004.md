# AI core 空闲的粒度：每步 ~21 个 50–300 µs 的洞（2026-10-04）

> 承接 `DUTY-CORRECTION-20261004.md`：AI core 占空比 85.1%，空闲 14.9%
> （其中 4.6% 被 AICPU metadata 占用，**10.6% 纯空闲**）。
> 本文回答"那 10.6% 长什么样"，因为它的形状决定改法。

## 1. 空间分布：**完全均匀**（`scripts/idle_hist.py`，100 ms 桶，124 个桶）

| 分位 | 每桶 AI core 空闲率 |
|---|---:|
| p10 | 13.30% |
| p25 | 13.95% |
| **p50** | **15.39%** |
| p75 | 15.75% |
| p90 | 16.31% |

* **完全无空闲（<1%）的桶：0.0%**
* **空闲 >50% 的桶：0.0%**

⇒ 空闲**均匀散布在整个 decode 窗口**，**不是**集中在阶段切换/爬升/回落处。
按 27.4 ms/步算，**每步固定有 ≈4.1 ms 的 AI core 空闲**。

## 2. 时间粒度：**每步约 21 个中等大小的洞**（`scripts/idle_gaps.py`）

| 量 | 值 |
|---|---:|
| AI core 忙区间数 | 715,153 |
| **空闲洞数** | **9,644** |
| 空闲合计 | 1,254.0 ms（窗口的 **10.13%**） |
| p50 洞 | **0.069 ms** |
| p75 / p90 洞 | 0.170 / 0.284 ms |
| p95 / p99 洞 | 0.539 / 0.921 ms |
| max 洞 | 2.745 ms |

分布侧重：

| 阈值 | 个数 | 合计 | 占空闲 |
|---|---:|---:|---:|
| ≥ 0.05 ms | 5,028 | 1,196.2 ms | **95.4%** |
| ≥ 0.20 ms | 1,965 | 864.2 ms | 68.9% |
| ≥ 0.50 ms | 533 | 442.0 ms | 35.2% |
| ≥ 1.00 ms | 9 | 11.7 ms | 0.9% |
| ≥ 2.00 ms | 1 | 2.7 ms | 0.2% |

⇒ **没有"一个大洞"**（≥1 ms 的只占 0.9%）。空闲是**大量 50–300 µs 的中等洞**。

## 3. 解读

稳态窗口 12.38 s ÷ 27.4 ms/步 ≈ **452 步** ⇒
**9,644 / 452 ≈ 21 个洞/步**，每洞中位 69 µs。

这个形状（每步 20+ 个几十到几百 µs 的洞、分散在整步、无大洞）是
**图内 kernel 依赖链的流水气泡**的典型特征：
每个 kernel 要等前驱完成、再从图内调度器取下一个 ⇒ 累积约 4 ms/步。

它**不是**：
* 阶段切换（那会集中在少数桶里 ⇒ 已否证，§1）；
* 单个长阻塞（那会有大洞 ⇒ 已否证，§2）；
* allreduce 等待（`hcom_allReduce_` / `AivKernel` 属 AI core 任务，已计入"忙"）。

## 4. 可做的事（按可行性）

| # | 方向 | 上限 | 说明 |
|---|---|---:|---|
| 1 | **减少 kernel 数**（融合） | 与"洞数"成正比 | 21 个洞/步对应约 1590 个 AI core 忙区间/步。融合能同时减少 kernel 数和洞数 ⇒ **这是唯一已证有效的方向**（gmm1 的 armF 就是在减 SyncAll/Reset） |
| 2 | metadata 与设备重叠 | **4.6%** | 三类 metadata 目前串行在 AI core 空闲段里（子代理在攻） |
| 3 | 提高图内调度密度 | 未知 | 若能确认洞来自"图内相邻 kernel 的依赖等待"，则无解（物理依赖）；若来自 host 侧图调度，则可能有解。**需要更细的取证**（例如看同一 stream 内相邻 kernel 的 gap 分布） |

## 5. 教训（补充到 `DUTY-CORRECTION`）

**"设备占空比"必须同时看"空间分布"和"时间粒度"**：
只看总数（14.9%）会以为"有个大洞可以填"，实际是 21 个/步的弥散气泡 ⇒
改法完全不同（融合 vs 调度）。
