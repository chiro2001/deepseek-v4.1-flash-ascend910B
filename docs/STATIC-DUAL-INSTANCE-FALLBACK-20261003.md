# 备用路线：静态双实例 + 按并发选端口（2026-10-03）

> 目标里写明：「**若查不出根因，则用"静态双实例 + 按并发选择端口"拿到同样包络，并记录负结果**」。
> 本文把这条路线**落到可执行的形态**，并记录一个**之前没注意到的硬前提**。

---

## 0. 为什么需要它

【实测】同机、同脚本、地火 1024/256：

| 并发 | 静态 `SPEC=0` | 静态 `SPEC=1 K=5` | 谁赢 |
|---:|---:|---:|---|
| 1 | 51.6 | **109.5** | SPEC=1（2.12×） |
| 2 | 92.6 | **142.9** | SPEC=1 |
| 4 | 166.2 | **225.4** | SPEC=1 |
| 8 | 277.4 | **315.3** | SPEC=1（1.14×） |
| **16** | **434.1** | 398.6 | **SPEC=0（1.09×）** |

⇒ **交叉点 N≈12**：低并发要 `SPEC=1 K=5`，高并发要 `SPEC=0`。
一个静态实例只能选一边；动态 K 就是想用一个实例吃到两条曲线。

**而动态 K 目前只做到 0.80×**（K=0 的 N=2 = 73.9 vs 静态 SPEC=0 的 92.6，仅 1 个采样点）。
所以备用路线是必要的。

## 1. ★ 硬前提：这条路线需要 **16 个 die**

单实例 TP8 要占 **8 个 die**（A3 一块卡 = 2 个 die）。双实例要 **16 个 die = 整台 A3**。

【实测】a3-21 长期是多租户共用：`hlz-dsv4-dp2`（die 0,1）、我们自己的 `dsv41-tinyspark`（die 2,3）、
`vllm-ascend-0.23.0-a3-s50057815`（die 4-7）等。**8-15 这 8 个 die 才是我们常态化可用的**。

⇒ **这条路线不能"随时起"，必须先拿到整机 16 个 die。** 两条子路线：

| 子路线 | 做法 | 前提 |
|---|---|---|
| **A. 真双实例** | 实例1 = dies 0-7（`SPEC=1 K=5`）、实例2 = dies 8-15（`SPEC=0`）；前面加一个极简按并发选端口的转发 | 需要**整机 16 die 同时空闲**（要与 hlz 等协调） |
| **B. 单实例轮换** | 保留动态 K 的表，但把"N≥12 关 spec"实现成**配置文件级**：高并发时段由人/脚本切到 `SPEC=0` 实例 | 只需 8 die，但**切换要重启**（约 12 分钟），做不到"同一时刻两种负载都最优" |

**子路线 B 不是等价替代**（不满足"同时服务"），所以目标里的"拿到同样包络"实际指 **A**。

---

## 2. 子路线 A 的具体设计（**不是**鉴权/配额那一层）

用户明确说过"在线量测类的、鉴权的不做，主要关注性能"。所以这里**只做一个按并发选端口的
极简转发**，不做任何鉴权/配额/多模型路由：

```
                ┌──────────────────────────────┐
  客户端 ──────►│ 极简端口选择器 (127.0.0.1:19200) │
                │  当前在飞请求数 < 12 → 19210  │  ← SPEC=1 K=5 实例
                │  否则            → 19211      │  ← SPEC=0 实例
                └──────────────────────────────┘
```

**判据/纪律**：
1. 选择器**只看当前并发**，不做限流、不排队、不改请求体（流式直通）；
2. 必须能给出"路由到哪个实例"的可观测痕迹（一行日志含 `req_id → port`）；
3. **两个实例的模型名/上下文/`MAX_SEQS` 必须逐项一致**，否则客户端看到的行为会不一致；
4. 这个选择器**不进交付默认路径** —— 它是"够不到动态 K 时"的替代品，一旦动态 K 修好就退役。

## 3. 两条实例的启动命令（a3-21，`serve_a3.sh`）

```bash
# 实例1：低并发档（dies 0-7）—— SPEC=1 + K=5
MODEL=/home/l00886679/models/out/v41-flat-verify3 \
DEVS="0 1 2 3 4 5 6 7" TP=8 DP=1 NAME=dsv41-lo PORT=19210 \
SPEC=1 SP_TOKENS=5 DRAFT_GRAPH=1 MAX_SEQS=32 BAT_TOKENS=8192 PREFIX=1 \
ENGRAM=1 ENGRAM_DEVICE_INDEX=0 GPU_UTIL=0.92 PATCH_MODE=mount PROFILE=1 \
VLLM_ENGINE_READY_TIMEOUT_S=7200 \
bash scripts/serve_a3.sh

# 实例2：高并发档（dies 8-15）—— SPEC=0
MODEL=/home/l00886679/models/out/v41-flat-verify3 \
DEVS="8 9 10 11 12 13 14 15" TP=8 DP=1 NAME=dsv41-hi PORT=19211 \
SPEC=0 DRAFT_GRAPH=0 MAX_SEQS=32 BAT_TOKENS=8192 PREFIX=1 \
ENGRAM=1 ENGRAM_DEVICE_INDEX=0 GPU_UTIL=0.92 PATCH_MODE=mount PROFILE=1 \
VLLM_ENGINE_READY_TIMEOUT_S=7200 KV_CACHE_MEMORY_BYTES=15728022528 \
bash scripts/serve_a3.sh
```

**两处必须注意**：
- 实例2 必须带 `KV_CACHE_MEMORY_BYTES=15728022528`，否则会撞 **KV32 池守卫**
  （已实测：不带它起服到最后会被 fail-closed 拒绝，见
  `results/tp8spec0_1003_000442/serve.log` 的 `[KV32] 拒绝以越界池起服`）。
- `VLLM_ENGINE_READY_TIMEOUT_S` 目前**必须靠我们加的透传**（原脚本不透传，见
  `fixes/20261003-dynspec/serve_a2.dynspec.patch`）；不带它时冷编译 >600 s 会被默认超时杀掉。

## 4. 验收判据（与目标一致）

| 项 | 判据 | 当前证据 |
|---|---|---|
| 低并发档 | N=1 ≥105 tok/s | ✅ 静态 K=5 实测 **109.0–109.5** |
| 高并发档 | N=16 ≥430 tok/s | ✅ 静态 SPEC=0 实测 **434.1**（3 rep：429.6/434.1/435.5） |
| 包络 | 每档都取两实例的较优者 | ✅ 由 §0 的表可直接算出：109.5 / 142.9 / 225.4 / 315.3 / 434.1 |
| 正确性 | 两条路径各自的探针 | ⚠️ 两档都是**已验收过的静态配置**（不是新组合），但**仍需各跑一次 `regress2.py`** |

**⇒ 这条路线在数字上是"已达标"的**（每一档都取到了实测的最优），
代价是**要 16 个 die** + 一个极简转发。

## 5. 与动态 K 的关系（不要搞混）

| | 动态 K（Track A 主线） | 静态双实例（本文） |
|---|---|---|
| die 需求 | **8** | **16** |
| 切换粒度 | 每步（按当时请求数） | 每请求（按入站并发） |
| 实测包络 | N=2 只有 73.9（0.80×，**待修**） | 每档取最优，**已达标** |
| 状态 | 根因已修，第二个缺陷待修 | **随时可起（前提是 16 die 空闲）** |

**决策规则**：动态 K 的第二个缺陷修好并跑出完整曲线之后，
若 N=16 仍 <430，则**两手都留**：
- 8 die 场景 → 动态 K（或干脆静态 K=5，接受 N=16 只有 398.6）；
- 16 die 场景 → 静态双实例。
两条都写进交付文档（本仓纪律：负结果与替代路线都留档）。
