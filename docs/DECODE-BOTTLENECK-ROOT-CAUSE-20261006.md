# ★ decode 瓶颈根因：**2,900 个算子的串行链**，不是带宽、不是算力、不是空闲

> 起因：用户追问 ——「已经是图下发了、`free` 占比也不高，为什么带宽仍然只有 11%？」
> 数据：`results/armF_r6_base/prof/...rank0.../kernel_details.csv`（交付口径、纯 decode）
> + `npu-smi` 带宽采样。全部为【实测】。
> 新工具：`tools/prof_cp{2,3,4}.py`、`tools/prof_find_step.py`。

## 0. 一句话

**这个步是 2,888 个算子的串行链**：时间加权**并发度只有 1.19**、**73% 的时间只有 1 个算子在跑**、
几乎没有算子间重叠。所以步长 = Σ(单算子耗时)，而每个算子都**远远**小于带宽饱和所需的规模
（例如 `HcPre` 搬 117 KB 花 37.8 µs，满带宽只需 **0.1 µs**）。
⇒ 把"带宽利用率"当指标天然就低：**分母（步长）由算子数量决定，分子（字节）由模型权重决定。**

## 1. 先纠正三个容易误导的观测量

| 观测量 | 实测值 | 为什么不能直接当结论 |
|---|---:|---|
| `Free` 占比 | **4.9%** | 它统计的是**整机真空闲**。96% 的时间"至少有一个核在忙"，但**不代表核被用满** |
| `union`（至少一个算子在跑）/ 步长 | **96%** | 同上：一个 kernel 占 2 个核也算"忙" |
| `AICore%`（npu-smi） | 79%（conc=1）/ 100%（conc=8） | "busy" 包含**等数据/等指令**的时间，不等于在做 MAC |

**真正有判别力的是两个数**：

| 指标 | 实测 | 含义 |
|---|---:|---|
| **算子并发度**（同时运行的算子数，时间加权） | **1.19**（峰值 4；**73% 的时间 = 1**） | 基本**没有算子间重叠** |
| **Σ算子时长 / 步长** | **1.20** | 同上，串行度 ≈ 1 |

### 1.1 怎么找到"步"的（方法说明）

profile 里没有步标记，但有个天然标志：**`allgatherAicpuKernel`**（engram 的 wkv all_gather）
每步恰好出现一次 —— 实测 **77 次、间隔中位 40.63 ms、变异系数 0.08** ⇒ 干净步边界。
切出 **76 步**，稳态取 72 步（去掉首尾各 2 步）。

> profile 步长 **40.02 ms** vs 服务里 `[bneck] hp = 24.59 ms` ⇒ msprof 膨胀 **1.63×**。
> 下文**默认给 profile 口径**，需要时折真实值除以 1.63。

## 4. 为什么"图下发"没解决这件事

图下发（NPUGraph）消除的是**主机侧**下发开销 —— 这一点**确实生效了**：
服务内 allreduce 只要 32–73 µs，而 standalone 微基准同消息要 88–110 µs（省掉主机往返）。

但图下发**不能**消除：

1. **设备侧每个 kernel 的启动/收尾**：tiling 计算与设置、L1/L0 buffer 分配、
   标量参数装载、`SetFlag/WaitFlag` 同步；
2. **同一条流上的算子间依赖**：残差链是严格串行的，下一个算子必须等上一个写完；
3. **小张量本身的低效**：M=6 的 GEMM 在 16×16 的 cube 上只用了 **6/16 = 37.5%** 的 M 维；
   权重按 NZ 格式搬运时，小块很难打满访存流水。

**所以 `free` 低 + 图下发 ≠ 时间花在有用的地方。** 判别方法是**并发度**（1.19）与
**逐算子离带宽的距离**（85% 超额），这两条都指向"算子数量"而不是"带宽"。

## 5. 可优化空间（按实测超额排序）

| # | 靶点 | profile 超额 | **折真实 ms/步** | 手段 |
|---|---|---:|---:|---|
| 1 | **小张量 elementwise 群**：`AivKernel` + `HcPre` + `HcPost` + `RmsNorm` + `RoPE` | 10.76 | **6.6** | **融合**（把 per-token 的多次小算子合成一次） |
| 2 | **attention 投影**：`QuantBatchMatmulV3` + `MatMulV2` + `MatMulV3` | 7.82 | **4.8** | 合并/消除冗余投影、更大 tiling |
| 3 | **`SparseFlashMla`** | 2.19 | **1.3** | 算子内（KV 读取路径） |
| 4 | MoE 两个 grouped GEMM 的超额 | 5.05 | **3.1** | M=6 的 M 维利用率（37.5%）是主因 |
| 5 | `ScatterNdUpdate` / `DynamicQuant` / routing 等元数据类 | 5.3 | **3.3** | 减少调用或融进邻居 |
| 6 | allreduce（`allreduceAicpuKernel` 39.7 ms/72 步 ≈ 0.55/步） | — | ~1.4 | 只能减次数（MC2/enable_sp 已试过，负结果） |

**注意排序与上一份文档的差别**：本轮用**逐算子超额**（而不是 stream 空隙）归因，
发现**最大的单体靶点是"小张量 elementwise 群"（6.6 ms 真实）**，
而不是之前以为的"尾部 5.5 ms"—— 因为在这份 profile 里**尾部是 0**
（末算子比步末只早 0.01 ms、首算子 0.00 ms）⇒ 该 profile 的步是**背靠背**的，
上一份文档的"尾部 5.5 ms"来自**另一份** profile（且口径是"主图流内空隙"）。

> 【口径说明】"尾部"在两种口径下含义不同：
> * `stream_gap_attrib` 的"主图流内空隙" = 主图在等别的流（别的流在跑，不是真空闲）；
> * 本文的"步尾无任务"= 全机都没任务。
> 本文这份 profile 里**后者是 0**，前者（主图流空隙）待补测。

## 6. 复现

```bash
PROF=~/cedpd-repo/results/armF_r6_base/prof/dp0_pp0_tp0_dcp0_ep0_rank0_1434_20261004195431495_ascend_pt
# ① 找步标志（allgatherAicpuKernel，每步一次）
python3 tools/prof_find_step.py $PROF/ASCEND_PROFILER_OUTPUT
# ② 步长/占用/头尾
python3 tools/prof_cp2.py $PROF/ASCEND_PROFILER_OUTPUT
# ③ 算子时长分布 + **并发度**（核心指标）
python3 tools/prof_cp3.py $PROF/ASCEND_PROFILER_OUTPUT
# ④ 逐算子"离带宽多远"
python3 tools/prof_cp4.py $PROF/ASCEND_PROFILER_OUTPUT 1180e9
```

> 需要 pandas / numpy：用交付镜像跑（`docker run --rm --entrypoint python3 -v ... `），
> 宿主 `python3` 没有 pandas。
