# ★ A3 交付实例实测结论：KV32 slot 重排拿到 4,010,585 tokens（+34.2%）

> 2026-10-06 08:50，`dsv41-tp8k5`（a3-21 chips 8-15，TP8 / DCP1 / 1M / DRAFT入图 / prefix cache）。
> 全部为**真机实测**；配方推导见 `docs/KV32-SLOT-REPACK-PROPOSAL-20261006.md`。
> 交付配置已在实测后**恢复并核验**（镜像 / 挂载 / BAT / 容量四项，见 §6）。

## 1. 一句话

**容量 2,987,836 → 4,010,585 tokens（+34.2%）**，长文针 **24/24 全过**，decode 吞吐
同日同机受控对比为 **−0.6% ~ −6.2%**（接受长度差异可解释其中大部分）。

## 2. 配方

```bash
V41_KV32_REPACK=1                  # 挂 patches/files/deepseek_v41.repack.py 覆盖 core/deepseek_v41.py
BAT_TOKENS=2048
KV_CACHE_MEMORY_BYTES=17179869184  # = 32768 × 524288（恰好顶到 32 位上界）
```

* 池 stride `540,928 → 524,288`（四槽页步长全 131,072），块上限 `29,076 → 32,768`；
* `32768 × 131,072 = 2³²` **恰好取等**（页尾落进 32 位空间）；
* 不重排而硬压到 32768 块是**带风险**的做法：tiny 受控 A/B 里旧几何同容量 68 轮出现
  7 轮非零偏差（新几何 0/68，见提案文档 §13）。

## 3. 容量与几何证据

| 量 | 实测 |
|---|---|
| 几何（重排生效的**间接证据**） | 不重排时 16 GiB 只能给 ⌊17179869184/540928⌋ = **31,759 块** ⇒ 容量约 3.89M；实测 **4,010,585** ⇒ 只可能来自 524,288 的 stride |
| `GPU KV cache size` | **4,010,585 tokens**（预测 4,010,708，差 123 = 0.003%） |
| `Maximum concurrency` | 3.82×（1,048,576 tokens/请求） |
| 现役基线 | 2,987,836（同日重测）/ 2,988,163（原值） |
| **增幅** | **+34.2%** |

> 【口径说明】交付镜像**没有** `[V41-DCP-DIAG]` 探针（那是 tiny 工作副本独有的埋点），
> 所以窗口脚本的"断言 C"（读 `pool_bytes_per_block`）在交付侧拿不到数据、只打印 ⚠️。
> 几何由**容量反证**：两套 stride 在同一 KV 预算下给出的块数相差 1,009 块（31,759 vs 32,768），
> 容量差 3.1%，不可能混淆。

## 5. 性能：同日同机受控 A/B

口径 `tools/bench_concurrency.py`，地火 1024/256，每档 2 rep 取中位，**同一天、同一台机、
同一个脚本**先后测得（新配置 08:26 起服 / 基线 08:47 起服）：

| 并发 | 新配置 单流/总吞吐 | 基线 单流/总吞吐 | Δ单流 | Δ总吞吐 | 新配置接受长度 | 基线接受长度 |
|---:|---|---|---:|---:|---:|---:|
| 1 | 116.2 / 110.4 | 114.7 / 111.1 | **+1.3%** | **−0.6%** | 3.37 | 3.41 |
| 2 | 92.2 / 151.0 | 98.7 / 154.1 | −6.6% | −2.0% | 3.35 | 3.40 |
| 4 | 83.3 / 256.6 | 86.8 / 273.7 | −4.0% | −6.2% | **3.31** | **3.62** |
| 8 | 55.6 / 339.5 | 57.7 / 344.5 | −3.6% | −1.5% | 3.38 | 3.48 |

* **单流（并发 1）不变**（+1.3% / −0.6%），这是最干净的一档；
* 并发 4 的总吞吐差 −6.2%，但该档**接受长度低了 8.6%**（3.31 vs 3.62）——
  推测解码的接受长度依赖被解码的 token 序列，直接按比例影响 token/s ⇒ 该档差额基本由它解释；
* 每档的 rep1/rep2 离散度很大（如并发 8：41.7 vs 69.4、42.5 vs 73.0）⇒ 单档中位的
  不确定度就在 ±10% 量级，**3~6% 的差落在噪声带内**；
* 【结论】容量 +34.2% 的代价是**解码吞吐 0~6%**（单流无损）；若要把这个区间压紧，
  需要多次重复的专门 A/B。

prefill（`ced_pd_bench`，128 token 输出）：

| 上下文 | prompt | TTFT | prefill |
|---:|---:|---:|---:|
| 8,192 | 8,279 | 1.28 s | **6,478 tok/s** |
| 65,536 | 65,442 | 11.36 s | **5,761 tok/s** |

> `BAT=2048` 对 prefill 的影响集中在**分块粒度**（每步最多 1920 token）：300K prompt 实测
> 分 79 个 prefill-only step，端到端仍在分钟级；这是拿容量的代价之一。
