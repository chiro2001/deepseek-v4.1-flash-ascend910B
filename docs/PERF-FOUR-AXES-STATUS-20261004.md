## 2. ★ prefill 维度的真相：**我们没退化，缺的是 CED 架构**

| 来源 | 32K | 144K |
|---|---:|---:|
| **本机 TP8（全 40 层）** | **7,200** | — |
| CED 文档里的**「全 40 层基线」** | **7,219** | 6,599 |
| **CED-PD（P 只跑 20 层）** | **12,536** | **13,676** |

⇒ **我们的 7,200 与 CED 自己的"全 40 层基线" 7,219 几乎相同** ——
**prefill 没有退化**；那 1.5–1.7× 的差距**完全是"CED 的 P 只跑一半层"这个架构性收益**。

### 2.1 为什么现在上不了 CED【实测】

CED-PD 要**整机 16 个 die**（P 8 + D 8）。2026-10-04 逐 die 实测：

| die | 归属 |
|---|---|
| **0, 1** | **`hlz-dsv4-dp2`（别人）** |
| 2, 3 | 我们（`dsv41-tinyspark`，可停） |
| 4–7 | 空闲 |
| 8–15 | 我们（Track A 实例） |

⇒ **只差 dies 0,1**。一旦那两张空出来，CED-PD 的交付件是现成的
（GitHub release tag `a3-ced-pd-v3`，`deploy/a3-ced-pd/`）。

### 2.2 在 8 die 上能优化 prefill 的空间

对 32K prefill 的 profile 做**独占贡献**分析（`tools/excl_time.py`）：

| 算子 | sum 占比 | **独占占比** |
|---|---:|---:|
| SparseFlashMla | 12% | **3.3%** |
| QuantLightningIndexerV2 | 7% | 3.1% |
| `allreduceAicpuKernel` | **42%** | **≈0（完全被重叠）** |
| HcPre / HcPost | 6% / 4% | 2.0% / 1.2% |
| **top-14 合计** | — | **≈16%** |

而且**设备 98.1% 忙**（idle 仅 1.9%）⇒ **没有气泡可填**，必须真的削减设备工作量；
**但最大的单项独占也只有 3.3%** ⇒ 工作量是**弥散**的，要靠一批 kernel 优化累积。

> ⚠️ 我先前在 prefill 那节写"把 top-14 全优化掉也只能到 ~8,600"是**误用**了独占指标：
> `excl(op) = union(全部) − union(去掉 op)` 是**单算子**的边际贡献，
> 把它们相加得到的是"同时移除它们"的**下界**（彼此重叠，一起移除会省更多），**不是天花板**。
> **正确的说法**：8 die 上**没有一条改动能显著改善 prefill**，
> 要 12,536 这个量级只能靠 CED（P 只跑 20 层）；
> 但**没有证据表明 7,200 已到 8 die 的设备极限**。

## 8. ★★★ 2026-10-04 下午续：admission gate **多-prefill** 采纳为默认（N=8 282→324）

见 [`GATE-MULTIPREFILL-RESULT-20261004.md`](GATE-MULTIPREFILL-RESULT-20261004.md)、
[`N8-SCALING-DEEPDIVE-20261004.md`](N8-SCALING-DEEPDIVE-20261004.md)。

**根因（子代理独立量化）**：8 流 bench 的 13.15s 窗口里，ramp（prefill-only 独占步 +
单流 decode）占 **39.6%**、tail 占 28.8%、**满并发相位只占 30.7%**；按 token 缺口算是
**ramp 63% / tail-B 26% / tail-A 8% / full 仅 2%**。而原 gate 写死
「一个 prefill-only 步只放 **1** 个 prefill」，8 条请求 → 至少 8 个独占步。

**改动**：`V41_GATE_MAX_PREFILL`（默认 **8**），仍保持「prefill-only 步不含任何 decode」
的硬不变量。`patches/admission_gate.patch` + `scripts/serve_a2.sh`。

| N | 基线 | **多-prefill** | Δ |
|---:|---:|---:|---:|
| 1 | 107.0 | 107.2（5 rep 中位） | 0%（噪声内） |
| 4 | 197.0 | **210.0** | **+6.6%** |
| 8 | 282.1（3 rep 中位）/ 321.2（历史会话） | **324.2（5 rep 全 ≥319）** | **+11.0% ~ +14.9%** |
| TTFT(N=8) | 0.80 s | **0.48 s** | **−40%** |

**正确性**：`ced_pd_acceptance --mode all` **21/21 通过**（144K 四针 A/B/C/D、1M 四针、
流式 144K/1M、多轮）；`multibatch_gate` [A] 7/7+3/3、[B] 并发逐项 16/16 不一致 0、
**[C] 128K 长请求 + 8 短请求真并发 6/6 不一致 0**；`regress2` 5/6（与基线同）。
⇒ 「多 prefill 同一步」**不触碰** 2026-09-17 加 gate 的原始风险（同一步混 prefill+decode）。

**方法学**：稳态 decode 的**设备占空比 100.0%**（gap p50 = 0.00ms，N=8 稳态 271 步，
用 43 次 gmm1/步切步）⇒ **没有 host 气泡可填**，任何优化必须真实削减设备工作量。
另：bench 的 rep1 是冷 prefill、rep2+ 命中前缀缓存，**报数必须分开**。

**负结果（同日留档）**：
* **HcPre+RMSNorm 融合**：算子级（M=96）省 2.67 µs/次，但**真实 decode（M=6）**下
  `HcPreNorm` 40.9 µs vs `HcPre`+`RmsNorm` 33.5 µs ⇒ **净亏 672 µs/步**，端到端
  N=1 98.4 / N=4 195.2 / N=8 285.0（全面低于基线）⇒ 不采纳，默认 0。
  教训：**单算子基准的 M 必须取真实 decode 的 M = 1 + SP_TOKENS**。
* **CED-PD 卡数预算**：P=4/D=8（12 die）与 P=6/D=8（14 die）均**不可行** ——
  ① 连接器硬门 `prefill_tp_size ≥ decode_tp_size`；② rank 映射不支持 P:D ≠ 1:1；
  ③ TP=6 对本模型结构性非法（`num_attention_heads=64`）；④ P 侧权重实测 37.4 GB/rank，
  但 routed experts 259.19 GiB/EP 切分 ⇒ **单引擎最少 8 die**；⑤ 降 `MAX_LEN` 不改变池上界。
  ⇒ **16 die 是最小可行集**，CED-PD 维持搁置。

## 9. ★★ 2026-10-04 傍晚：Engram 设备侧索引设为 A3 默认（步时 −2~3.6%，两次独立复现）

见 [`ENGRAM-DEVICE-INDEX-A3-20261004.md`](ENGRAM-DEVICE-INDEX-A3-20261004.md)。

**审计发现**：交付一直用 `ENGRAM_DEVICE_INDEX=0`（强制 host lookup），而 `[bneck]` 显示
host 路径的 **`d2h` p50 = 10.10 ms/步**（`serve_a2.sh` 的默认本是 `auto`，A3 上会开启）。

**改成 `=1` 后**（设备侧索引：两张 engram 表映射成设备可寻址，HBM 占用 0，整条替换 host 路径）：

| n（batch tokens） | `=0`（基线） | `=1` run#1 | `=1` run#2 | Δ |
|---:|---:|---:|---:|---:|
| 6 | 26.15 ms | 25.34 | **25.37** | **−3.0%** |
| 12 | 29.24 | 28.17 | **28.20** | **−3.6%** |
| 18 | 32.92 | 31.68 | **32.24** | **−2.1%** |
| 24 | 33.73 | 33.02 | **33.08** | **−2.0%** |
| 48 | 42.60 | 41.54 | **41.75** | **−2.0%** |

**两次独立运行几乎逐位相同**（25.34/25.37、28.17/28.20）⇒ 效应真实可复现。

* **端到端**：N=8 **374.0 tok/s**（本工程迄今最好；此前的交付记录是 321.2，同口径 3 rep 中位）、
  N=16 537.4、N=4 247.3、N=1 108.7（同批 A=3.56/3.36/3.56/3.47）。
* **正确性**：144K 四针 + 流式 + 多轮 + prefix **11/11 PASS**；`regress2` 5/6（与基线同）。
* **容量**：KV 2,821,446 vs 2,823,080 tokens（−0.06%，噪声内）。
* 落地：只改 A3 入口 `serve_a3.sh` 默认；`serve_a2.sh` 保持 `auto`（A2 无 `host_mem_pool`）、
  CED-PD 显式 `0` 不动（未验证）。回退 `ENGRAM_DEVICE_INDEX=0`。

**为什么 `d2h` 10.1 ms 只换来 2~3.6%**：那 10.1 ms 大部分与其它流**重叠**，
只有约 1 ms 在关键路径上 —— 审计一开始就警告"不要按 38% 记账"，实测证实这条纪律是对的。
⇒ **判据必须用"步时"（`[bneck] hp` 中位数，按 batch size 分组），不能用 `tok/s`**：
`tok/s = A / 步时`，而 `A` 在 run 间摆动 2.79–3.63，足以掩盖 3% 的真实改进。

### 9.1 同轮的另一条负结果：gmm1 armD 自定义 kernel 真机无效果

见 [`GMM1-ARMD-VERDICT-20261004.md`](GMM1-ARMD-VERDICT-20261004.md)。
单算子层 −4.5%（`aic_scalar` 34.4→26.4，11 轮配对 10/11 为负）、图捕获 200 次 replay 通过、
bitwise 相等；但容器内 `.o` 已确认为 armD（md5 `f93d96d1`）时，
**服务里该算子的设备时间毫无变化**（Duration 73.64→72.98、`aic_scalar` 30.79→30.46，噪声内）。
⇒ 最可能是**服务命中的是另一个 tiling key 的 `.o`**（该 op 目录下 14 个 `.o`；补丁只改 Base/idx-4，
而 op 还注册 `FusionTiling(0)` 且优先）。
**教训已固化进 `tools/verify_opp_vendor.sh` 步骤 0.5**：验证自定义 kernel 必须证明
①容器内 `.o` 与宿主一致 **且** ②该 `.o` 真的被调用（指标确实变了）——只做 ① 会得出
"改动无效"的错误结论。

### 9.2 同轮修掉的两个静默问题
