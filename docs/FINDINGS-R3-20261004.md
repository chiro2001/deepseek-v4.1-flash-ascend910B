## 3. ★ armD 补丁**确实进了服务的 kernel**，但效应从 eager 的 −3.5µs 缩到 −0.66µs

上一轮我怀疑"改错了算子"，本轮用两条独立证据**否证**了该怀疑：

| 证据 | 内容 |
|---|---|
| **kernel 名**（msprof `task_time` 的 `kernel_name` 列） | `GroupedMatmulSwigluQuantV2_fa3d6d3de6e1f32e170e39d2ddd3a20e_2` ⇒ 服务跑的就是子代理改的那个 bundle 里的 **`_2`** 子 kernel |
| **符号段大小**（`nm`） | armD `_2_mix_aic` = 0x0→0x5210（**21008** B）；stock = 0x0→0x5188（**20872** B）⇒ **+136 B**，代码真的变了；`_3` 段两者完全相同 |

**但设备时间只降 0.66µs**（73.64 → 72.98，中位），而 eager bench 是 **−3.5µs**。

**两个候选原因**（子代理正在验证）：
1. **图模式下控制流被固化**：服务用 aclgraph，`loopCount == 1` 的早返回分支可能被编译器
   按捕获期的代表值消除 ⇒ 优化失效。子代理此前只验证了图模式下的**正确性**，
   **没有测图模式下的时长** —— 这是缺口。
2. **真实 M 分布不同**：子代理 bench 用 `M=48, E=48`（均匀填充），
   而服务 decode 是 `M=36, E=48`（**大量空组**）。空组比例不同会让 `while` 扫描的
   迭代次数差很多 ⇒ 早返回省下的工作量变小。

## 4. 独立容器 bench **不能代表服务**（重要方法学）

在 die5 独立容器里跑 wo_a 形状（`[M,4096]×[4096,1024]` bf16 纯 matmul）：

| M | 时长 | 等效带宽 |
|---:|---:|---:|
| 6 | 54.13 µs | 155 GB/s |
| 48 | 56.06 µs | 150 GB/s |
| 96 | 48.89 µs | 172 GB/s |

而**服务里同一个算子只有 23.16 µs**（2.3× 更快）、`aic_mte2_ratio` 达 0.90。
⇒ 服务路径有 aclgraph/融合带来的额外优化，**任何算子级结论都必须回到服务里验证**。
