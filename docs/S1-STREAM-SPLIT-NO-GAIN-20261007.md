# S1：为什么"把 AIC/AIV 分到两条流"不会有收益 —— 解析证明 + 实测（2026-10-07）

> ⚠️ **本文 §2.3 的"被 HBM 争用压到 1.30×"归因已作废**，实测证明与 HBM 无关
> （HBM 足迹 672MB 反而略好）。真正的限制是 **AI Core 执行资源池争用**，
> 见 `S1-CORRECTION-NOT-HBM-CORE-POOL-20261007.md`。**§1 的解析恒等式与 §3 的两条实现规则不受影响。**

> 环境：a3-21 **chip 5**（`dsv41-op-hcfuse`，全程未动 tp8k5 / tiny）。
> 解析臂用**真实 trace**（`armF_r6_base`，主流 stream 109，3 步窗口）；
> 实测臂用**真实算子**（`MatMulV2` / `RmsNorm`）在 NPUGraph 内回放。全部【实测】。

---

## 0. 一句话

**把算子按 AIC/AIV 分到两条流上，如果依赖边一条都不删，makespan 与串行严格相等（1.000×）——
这不是"没测出收益"，而是数学恒等式。**
收益**只可能**来自"删掉依赖边"（即找到不是硬前驱的工作），而删边后的上界也不是 1.95×：
**实测被 HBM 争用压到 1.30×**。

---

## 1. 解析臂：保留依赖 ⇒ 与串行恒等

从真实 trace 取主流 1528 算子/步，按 `Accelerator Core` 分类，用同一套时长做三种调度：

| 调度 | makespan | 相对 |
|---|---:|---:|
| ① **serial**（单流原序） | **77.957 ms** / 3 步 | 1.000× |
| ② **split_dep**（两流 + 保留相邻依赖） | **77.957 ms** | **1.000×** |
| ③ **split_nodep**（两流 + 无任何依赖，数学上界） | **53.198 ms** | **1.465×** |

```
主流构成：AIC 17.733 ms/步（68.2%，439 个）| AIV 8.253 ms/步（31.8%，1089 个）
各流负载：AIC 侧 53.198 ms | 非 AIC 侧 24.759 ms
AIC<->非AIC 切换 711.7 次/步  ⇒  711.7 条依赖边必须跨流
```

**为什么 ② 恒等于 ①**：若每个算子的输出都被下一个算子消费，那么无论它跑在哪条流上，
后继都必须等它完成 ⇒ 关键路径 = 算子序列本身 ⇒ makespan = Σ时长。**换成几条流都一样。**

⇒ **"仅切流"是恒等式，不存在"切了但没测出来"的可能。**
⇒ 唯一的问题是：**这 711.7 条边里，有多少是假的（即后继并不真的需要前驱）？**
　 那正是 §4 的 S2 依赖审计要回答的，也是"删边"的收益来源。

## 2. 实测臂：真实算子在图内的时序与争用

### 2.1 先纠正一个 3.6× 的测量陷阱

| 口径 | `MatMulV2` | `RmsNorm` |
|---|---:|---:|
| **eager 单算子**（循环 + sync） | 9.45 µs | **26.78 µs** |
| **图内真实设备时长** | **7.81 µs** | **7.45 µs** |

eager 口径把 host 派发（每算子 ~7~10 µs）当成了设备时间，**`RmsNorm` 虚高 3.6×**。
⇒ **任何"单算子时长"必须图内测**，否则整个经济账都是错的。
（与 `DBO-RUNTIME-VERDICT` 同源：eager 下 84% 时间在 Python 侧。）

### 2.2 依赖密度 → 收益曲线（K=128 个 AIC/AIV 单元）

| 臂 | makespan | µs/单元 | 加速比 | 理论预测 |
|---|---:|---:|---:|---:|
| join=1（每条边都保留 = 现状） | 2.086 ms | 16.30 | **1.000×** | 1.000× |
| join=2 | 1.777 ms | 13.88 | 1.174× | 1.323× |
| join=4 | 1.627 ms | 12.71 | 1.282× | 1.578× |
| join=8 | 1.547 ms | 12.08 | 1.349× | 1.746× |
| join=16 | 1.502 ms | 11.73 | 1.389× | 1.844× |
| join=32 | 1.484 ms | 11.59 | 1.406× | 1.897× |
| **join=0（全删，上界）** | **1.471 ms** | **11.49** | **1.419×** | ~~1.954×~~ |

第一行再次确认 §1：**每条边都保留 ⇒ 严格 1.000×**。
最后一行说明：**即使把依赖全删，也到不了理论 max(a,v) = 1.954×，只到 1.419×。**

### 2.3 ★ 差额去哪了：AIC 与 AIV 抢 HBM

固定 AIV 工作量，只改 AIC 算子是否打满带宽：

| AIC 权重规模 | `aic_only` | `aiv_only` | serial | **two_stream** | 实测/理论 | **vs serial** |
|---|---:|---:|---:|---:|---:|---:|
| **big（10.5 MB/算子，打满带宽）** | 7.80 | 7.29 | 15.83 | **12.21** | **1.57×** | **1.30×** |
| **small（1.0 MB/算子，可驻留）** | 5.58 | 7.60 | 13.81 | **9.07** | 1.19× | **1.52×** |

**读法**：AIC 算子越吃带宽，两流越兑不出并行 —— 离理论 max(a,v) 从 1.19× 拉开到 **1.57×**。
根因是 **AIC 与 AIV 共享 HBM**：另一条流并不能凭空多出带宽。

> 而本项目的 decode 主流恰恰是**带宽重**的（`MATH-IS-7PCT`：搬运 43%、数学 8%）
> ⇒ **应按最差列（1.30×）定预期，不能按 small 列的 1.52×。**

## 3. 两条实现规则（本轮实测得到，直接可用）

### 3.1 所有侧流必须在 `capture_end` 前 join 回根流

```
rtStreamEndCapture failed:
  capture model contains a stream that was not joined to the original stream
```

补上末尾 `s2.record(ejoin); root.wait_event(ejoin)` 后捕获成功。
（与既有规则"**fork event 必须 record 在捕获根流上**"是同一族约束。）

### 3.2 分段 fork/join vs 逐算子 fork/join：差别只有 3.5%

K=128，分段长度 2/4/8/16/32：

| 结构 | µs/单元 | 相对逐算子 |
|---|---:|---:|
| 逐算子 fork/join | 12.86 | 1.000× |
| seg=2 | 12.38 | 1.039× |
| seg=4 | 12.43 | 1.035× |
| seg=8 | 12.52 | 1.027× |
| seg=32 | 12.48 | 1.030× |

⇒ **同步开销不是瓶颈**（分段只值 3%），瓶颈是**带宽争用**（值 57%）。
　 这与 `SHUNT-MICROBENCH` 的 event 代价测量（0.64 µs/对）一致。

## 4. 对 Shunt 路线的影响（诚实修正）

| 项 | 原估计 | **S1 修正后** |
|---|---|---|
| 保留依赖的收益 | "可能很小" | **严格 0（1.000×，数学恒等）** |
| 全删依赖的上界 | 1.465×（真实 trace） | 仍成立，但**不可达** |
| 叠加带宽争用后的现实上界 | — | **≈ 1.15 ~ 1.30×** |
| Shunt-A/B/C 的 4~8 ms（10~20%） | "乐观合计" | **下调**：按 1.30× 折算，主流 25.4 ms 的可回收上限约 **5.9 ms**，且需**真删边** |

**结论不是"Shunt 死了"，而是它的价值被重新定位**：

1. **S2 依赖审计从"挠痒"升级为唯一决定性步骤** —— 只有它能回答"711.7 条边里有多少是假的"；
2. **门槛要重设**：审计若产出可删边对应的 AIV 工作量 < 2 ms，则**不值得投入实现**；
3. **优先级应让位给"不依赖删边"的项**：Shunt-C（尾部 7.7 ms 空洞里与采样无关的元数据）
   之所以仍值得做，是因为它是**跨步**独立工作——不涉及删本步依赖边，也就不受 §2.3 争用折扣的同等影响。
