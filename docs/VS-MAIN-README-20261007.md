## 4. KV 容量与正确性：最大的一项

### 4.1 主分支的两难（README §2.5 / §5）

| 配置 | 容量 | 长文正确性 |
|---|---:|---|
| `BAT=8192`（默认，0.92） | **2,823,080** | 10/10 ~ 6/6 ✅ |
| `BAT=2048` | **4,145,957** | ❌ **10K 10/10 → 20K 8/10 → 40K 7/10 → 60K 5/10 → 80K 3/10 → 150K ~0%** |
| `GPU_UTIL=0.94` | 3,088,412 | ✅ 但 **prefill 慢 6~7×**（8 s 级首 token） |

主分支 README 自己写着：**"KV 门槛 3Mi 默认配置不再满足"**，并把责任归为
**"chunked prefill 的 chunk 数决定偏离率（~2%/chunk）"**。

### 4.2 现在：两难被解开

| 配置 | 容量 | 长文针 60K/74K/150K |
|---|---:|---|
| `BAT=8192`（默认） | **2,987,727**（+5.8%，来自 engram `wkv` 分片） | **24/24** |
| **`BAT=2048` + KV32 slot 重排** | **4,010,585** | **24/24** ✅ |

**净效果**：

```
可用容量（在长文可用的前提下）：2,823,080 → 4,010,585 = +42.1%
```

**根因更正**（`KV32-OVERFLOW-DOSE-RESPONSE-20261006`，走查实验）：

> `BAT=2048` 的长文退化**不是** chunk 数导致的数值偏离，而是它带来的容量增益
> **把 KV 池推过了 32 位块号边界 ⇒ 块号回绕 ⇒ 静默读错**。
> 剂量-反应实测：池 **≤29,079 块**时 87 条请求**全部逐位相同**；
> 池 = **30,000 块**（越界 924）时 **24% 的请求出现输出级偏离**（max|Δ| 最高 2.04）。

**修复**：slot 重排把块上限 **29,076 → 32,768**（+12.7%），
连同 `[V41-KV32-CAP]` 自动夹上限 ⇒ `BAT=2048` 从**"不可交付"变成"可交付"**。
重排本身**逐位相同**（同块数下 30 轮 × 63,998 位 `max|Δ|=0`）。

## 7. 结论：这 16 天优化了什么、没优化什么

### 7.1 有实质提升

| # | 项 | 量级 |
|---:|---|---:|
| 1 | **高并发步长**（conc 8/16） | **−23% / −27%** |
| 2 | **高并发聚合吞吐**（conc 8/16） | **+15% / +30%** |
| 3 | **可用 KV 容量**（长文可用的前提下） | **+42.1%**（2.82M → 4.01M） |
| 4 | **prefill** | **+10%**（7.2K → 7.9K tok/s） |
| 5 | **PD 分离 + CED**（prefill 加速） | **1.74× / 2.07× / 2.78×**（32K/144K/1M） |
| 6 | **长上下文正确性的根因修正** | 从"chunk 数 2% 偏离"更正为"32 位块号回绕"，并修复 |

### 7.2 没提升（诚实记录）

| 项 | 状态 |
|---|---|
| **单流 ms/step** | **持平**（24.19~24.9 vs 23.9~24.9）；最好的 24.19 只比主分支好 ~1%，且要付 prefill −11% 的代价 |
| **单流上限 110 tok/s** | 未突破，且已被证明是设备侧限制 |
| kernel 级数学优化 | 全部实测收益 <3%（`RmsNorm` 融合、`Scatter` 换算子、`HcPre` 迭代…） |

**单流没有提升不是"没努力"，而是结构性**：24.6 ms 里 45% 是 AIC 白等，
而**填掉它必须引入"独立工作"**——我们试遍了跨 batch（拆批 ×1.7 代价）、
层内控核（+0.8%）、通信重叠（结构上无独立工作）、metadata 提前（暴露仅 0.032 ms）。
剩下唯一未测的大项是**跨层软件流水**（上界 1.39×），但它同样需要拆批。
