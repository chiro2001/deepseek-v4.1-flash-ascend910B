# ★★ 重大修正：撤回"算子级收益被步内松弛吸收"的结论（2026-10-04 晚）

> 本文**撤回** `ABSORPTION-FINDING-20261004.md` 的核心结论。
> 该结论建立在**被污染的数据**上；用干净数据重测后**结论反转**：
> **armF 确实降低步时，且幅度与算子级预测一致。**

## 1. 错在哪：armF 那次 run 的日志里混入了我自己的 sleep 实验

`armF_meta2_1004_2010` 这个 run **同时承载了两件事**：
1. armF 内核的部署验证；
2. metadata 线的 **sleep 三档/多档扫描**（sleep = 0 / 300 / 1000 / **5000** / **50000** µs 全部在同一服务实例内反复切换）。

于是 `serve.log` 里的 `[bneck] hp` 样本**混入了 sleep>0 的分段**。证据（旧分析的离散度）：

| n | armF 旧数据 p10–p90 | stock |
|---:|---:|---:|
| 6 | **120.9%** | 7.5% |
| 36 | **285.5%** | 9.5% |
| 42 | **284.3%** | 8.2% |
| 48 | **286.6%** | 16.2% |

**285% 的离散度**说明样本是双峰/多峰的（sleep=50000 档的 ~41.7ms 与正常 ~25ms 混在一起）。
我在旧分析里用"配对差中位"跨过了这个双峰分布 ⇒ 得到 **+0.038 ms** 的错误中位。

## 2. 修正方法：按**行号**取干净样本

新工具 `tools/ab_lines.py`（`<run> [start_line]`）：只取指定行号之后的 `[bneck]` 样本。
在 `armF_meta2` 的日志里先记下行号 `17252`（sleep 全部复位为 0 之后），再跑一次
**干净的同 N 档扫描**（N=1,2,4,8 × 6 rep），只统计这批新样本。

## 4. ★ 同内核对照：证明这不是跨实例漂移

用**两个都是 stock 内核**的 run 做漂移基线（`devidx_1004_170852` vs `final_1004_1815`，
配置完全相同、只差运行时刻）：

| 统计 | **同内核（对照）** | **armF（实测）** | 倍数 |
|---|---:|---:|---:|
| 配对差中位 | **−0.029 ms** | **−0.666 ms** | **23×** |
| 低离散档中位 | **−0.082 ms** | **−1.086 ms** | **13×** |

⇒ 跨实例漂移只有 **0.03–0.08 ms**，而 armF 效应是 **0.67–1.09 ms**。

**并且与算子级预测吻合**：armF 在服务里省 **7.56 µs/op** × 40–43 次/步
= **−0.30 ~ −0.33 ms/step** ⇒ 实测 n=6/12 的 −0.28/−0.40 **正好落在这个区间**。

## 5. 修正后的系统模型

| 旧（错误） | **修正后** |
|---|---|
| "步时由关键链决定，与工作量无关；算子级加速会被 8.4% 的松弛吸收" | **步时 ≈ 关键 stream 上的串行工作量 + 少量跨 stream 等待**；**在该 stream 上减少工作量会 1:1 转化为步时** |
| "armF 端到端无收益" | **armF 端到端 −0.28 ~ −1.09 ms/step（−1.1% ~ −4.3%）** |
| "不要再追求更快的内核" | **继续追求更快的内核，但要落在正确的位置** |

**为什么旧模型看起来自洽**：armF 的算子级收益（−7.56 µs）确实存在，端到端也**确实**有收益 ——
只是被 sleep 污染的数据把它盖住了。我把"测量不出"误读成了"物理上被吸收"。

## 6. 保留有效的部分

旧文档里的**这条**仍然成立、且是正的证据：
* 主导 stream = **146**（主模型 40 层），步内 busy **17.61 ms/步**（68% 窗口），
  构成：`HcPre` 3.42 ms（80 次/步）> `gmm1` 2.66 ms（40 次）> `MatMulV2` 2.34 ms（97 次）>
  `gmm2` 1.61 ms > `SparseFlashMla` 1.35 ms > `QBMV3` 1.05 ms > `MatMulV3` 0.70 ms > `MoeInitRoutingV3` 0.69 ms。
* 每步有**恰好 1 个 ~5.5 ms 的间隙**（251 步 × 5.5 ms = 1368 ms = 21.9% 窗口），
  位置固定在 `RmsNorm → Cast`，其间其它 stream 在跑：**stream 142（draft 3 层）38.4%**、
  stream 47（verify/采样路径）31.2%、stream 35（AICPU metadata）18.4%、stream 147（rejection 采样）14.7%。

⇒ **这两个事实仍然指向"减少关键 stream 上的工作量"和"压缩那 5.5 ms 的串行段"**，
只是**不再**有"会被吸收"的免责条款 —— 收益是可以拿到的。

## 7. 方法学（最重要的教训）

**不要把互相干扰的实验放进同一个服务实例的日志里**，尤其是当判据来自该日志时。
本轮把"Kernel A/B"与"sleep 剂量扫描"混在同一个 run，直接导致：
* 一个**错误的核心结论**（吸收效应）；
* 我把这个错误结论写进了文档，并据此给子代理派了方向。

**加固措施（已做/待做）**：
1. 新增 `tools/ab_lines.py`：按行号隔离样本段 —— **任何在同一实例内做过多种配置的 run，
   都必须用行号过滤后才能用于对比**；
2. 判据前先看**离散度**：p10–p90 相对值 >20% 就说明样本混了分布，中位数不可信；
3. **必须做同内核对照**（两个同配置 run 之间的漂移基线）才能声称"某改动有/无效果"。
   —— 这一条本轮做了，也正是它把错误结论翻了过来。
