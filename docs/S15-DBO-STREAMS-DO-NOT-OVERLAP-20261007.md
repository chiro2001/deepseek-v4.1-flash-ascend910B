# 第3步实测：DBO 的两条 ubatch 流**不并行**，CBP 需要换载体（2026-10-07）

> 承接 `S14-CORRECTION`。本文用 **decode-only profiler** 回答一个关键问题：
> **DBO 的双流到底有没有并行？** 结论是没有。全部【实测】。

---

## 0. 一页纸

| 项 | 结果 |
|---|---|
| DBO 两条 ubatch 流并行吗 | ❌ **不并行**（decode 稳态 600ms 内，两主流之间几乎无重叠） |
| DBO @ conc=2 吞吐 | **38.4 tok/s vs 基线 67.0 ⇒ 0.573×** |
| 实测 tax | **1.984** |
| 需要 tax | **< 1.137** |
| 差距 | **超门槛 75%** |
| 相位配平有救吗 | ❌ 试了 40µs / 2000µs 位移，吞吐**完全不变**（38.3 / 38.1 vs 38.4） |
| 疑似根因 | **TP allreduce 串行化**（每 ubatch 91 次/步，两个 ubatch 在同一通信域上交替） |

## 1. Decode-only profiler（关键证据）

**采集方法**：prompt=**64** token（< 512 ⇒ **prefill 不 ubatch**）+ output=320 token
⇒ 窗口几乎全是 decode。conc=2，`dbo_decode_token_threshold=8`（强制 decode ubatch）。

**分析**：全程 19.9 s、231.6 万 kernel；取 kernel 率稳定的**最后 3 个 200ms 桶 = 600ms 稳态段**（7.2 万 kernel）。

| 指标 | 值 |
|---|---|
| 有 kernel 在跑 | **95.4%** |
| **≥2 kernel 同时** | **10.0% of 窗口 / 10.5% of 活跃** |
| 峰值并发 | 5 |

**流分布**：

| stream | kernel 数 | 活跃时长 |
|---|---:|---:|
| **188** | 21564 | **226.2 ms（37.7%）** |
| **187** | 20955 | **220.5 ms（36.7%）** |
| 184 | 10417 | 31.3 ms（5.2%） |
| 47 | 6348 | 41.4 ms（6.9%） |
| 183 | 3852 | 38.3 ms（6.4%） |

**并发流组合 Top6**：

| 组合 | 时长 |
|---|---:|
| (186, N/A) | 16.90 ms |
| (185, 188) | 11.07 ms |
| (185, 187) | 10.79 ms |
| (184, 188) | 6.82 ms |
| (184, 187) | 6.51 ms |
| (12, 187) | 2.26 ms |

### ★ 读法

1. **187 与 188 是两条 ubatch 的主链**（各 ~220ms 活跃，体量对称）；
2. **（187,188）这一对甚至进不了 Top6** ⇒ **两条主链之间几乎零重叠**；
3. 并发全部来自**辅助流（184/185/186）与主链**的重叠 —— 那是本来就有的 MULTISTREAM/DSA 侧流；
4. 187 + 188 = 446.7 ms 活跃，而窗口只有 600 ms ⇒ **两条链基本是"串着跑"的**。

## 2. 相位配平无效（第 3 步的实验结论）

给 ubatch1 的图内分支插入可控延迟（`V41_DBO_PHASE_US`），扫描：

| 相位位移 | conc=2 吞吐 |
|---:|---:|
| 0 µs（对齐） | **38.4** |
| 40 µs | **38.3** |
| **2000 µs**（判别性大延迟） | **38.1** |

**⇒ 完全无变化。** 2000 µs 的延迟若真的进入每步执行，应造成 ~4% 的吞吐下降（38.4 → ~36.9）；
实测只差 0.8%（在噪声内）⇒ **该补丁对运行期没有影响**。

【推断】运行期要么不走 `_run_ubatches_graph`（走 threading 路径，所有 ubatch 共用一条 `compute_stream`），
要么图内延迟被优化掉。无论哪种，**"人工相位配平"在这条实现路径上无法生效**。

> 附带：本轮实现 per-ubatch 独立 `compute_stream` 的补丁（`V41_DBO_PER_UBATCH_STREAM`）
> 在**捕获期创建新流 ⇒ 破坏 ACL graph 捕获 ⇒ 启动期 MTE 越界**（`MTE accesses an invalid GM address`）。
> 已修为"只在非捕获期建流"，但**仍无法启动** ⇒ 该补丁保留但**默认关闭**，不可用于交付。

## 3. 疑似根因：TP allreduce 把两条流串起来

**数量级**：每个 ubatch 每步 **91 次 allreduce**（`COMM-STRUCTURE-AND-DBO-REGIME` 实测）。
两个 ubatch = **182 次集合通信/步**，全部走**同一个 TP 通信域**。

**机制【推断】**：
* TP 集合通信要求各 rank 按**相同顺序**提交，否则死锁
  ⇒ ubatching 的协作式让渡协议保证了顺序，但代价是**两个 ubatch 的通信点必须交替**；
* 每个通信点都是**同步点** ⇒ 两条流在通信点处被"锁在一起"，无法长距离并行；
* 而通信点之间只有很短的纯计算段（91 次/步 ⇒ 平均每段很短），**可重叠的窗口极小**。

**这解释了三件事**：① 为何两主链几乎不重叠；② 为何相位配平无效；③ 为何历史 DBO 一直 −42%。

## 4. 对 CBP 结论的修正（重要）

| 载体 | 是否真并行 | tax@2 | 判定 |
|---|---|---:|---|
| **DBO / ubatching（TP2 + 共享通信域）** | ❌ | **1.98** | ❌ 超门槛 75%，不可用 |
| 两条**独立实例**（无共享集合通信） | 待测 | — | **下一个必测项** |

**⇒ 关键推论：跨 batch 真并行的前提是"两条流之间没有共享的同步点"。**
　 TP 集合通信恰好是这样一个同步点。
　 因此 **CBP 的天然实现形态是 DP（数据并行）**：
　 每个实例各有一个请求，各自跑完整前向，**互不共享集合通信**。

**这与目标里的判据一致**：`P(M) ≥ B(M)`。
DBO 的 P 实测 ≈ 1.0（无并行），所以必然输给 B=1.137。
