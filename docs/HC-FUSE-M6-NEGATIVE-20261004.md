# HcPre+RMSNorm 融合：真实 decode 形状下的**负结果**（2026-10-04）

> 结论：融合算子在**真实 decode 形状（M=6）**下比 `HcPre + input_layernorm` 两个算子之和**更慢**，
> 端到端净亏 ≈ **0.67 ms/步**。算子级基准（M=96）的"省 2.67 µs/次"结论**不能外推到 decode**。

## 3. 为什么与算子级基准相反（【推断】，有实测支撑）

| 场景 | `HcPre` | 融合 `HcPreNorm` | 差 |
|---|---:|---:|---:|
| **M=96**（Track B 单算子基准） | 57.0（+ RmsNormCast 13.1 = 70.1） | 67.4 | **融合快 2.7 µs** |
| **M=6**（真实 decode，本报告反推） | **31.1** | **40.9** | **融合慢 9.8 µs** |

* `HcPre` 本身是 M 弱相关的（31.1 → 57.0 µs，M 涨 16× 只涨 1.8×）⇒ 它主要是**固定开销**；
* 融合算子在**小 M 时固定开销更大**（多一个 reduce 分支 + 输出写回 + 同步）。
* ⇒ **"融合省一次 kernel 往返"的收益只在 kernel 时间占主导的大 M 下成立**；
  decode 的 M=6 下，两次 kernel 的固定开销之和反而低于融合的一次。

## 4. 结论与动作

1. **不采纳**：`V41_HC_FUSE_NORM` 保持默认 **0**（交付配置不动）。
2. 产物留档（不删）：OPP 包 `~/cedpd-repo/patches/hcfuse_opp`（= `opstageFIX4`）、overlay `patches/hcfuse_overlay`、启动器 `~/tmp/launch_hcfuse.sh`。
3. **方法学教训**（已入本文件）：单算子基准的 **M 必须取真实 decode 的 M**（= 1 + SP_TOKENS），
   否则结论会反向。Track B 的 M=96 来自 tiny 实例，与本实例 decode 差 16×。
4. 融合算子的**正确性**不受质疑：`regress2` 5/6（与基线同）、四针全过。问题纯粹是性能。

## 5. 附带发现（可复用的正结果）

融合臂的 profile 顺带确认：
* `HcPre` 在 decode 形状下是**固定开销主导**（31.1 µs @ M=6 vs 57.0 @ M=96）⇒
  **任何"减少 HcPre 次数/固定开销"的改动在 decode 上都是 1:1 的收益**（79.9 次/步 × 31 µs = 2.49 ms/步 = 9.5% 墙钟）。
* `hcom_allReduce_` 在两次 profile 间波动 ±8%（4.23–4.59 ms/步），属于宿主/网络噪声，不宜作为单变量判据。
