# ★ 决定性：图模式下**每算子边际成本 3.05 µs**（与 eager 几乎相同）⇒ 减算子数**确实有效**

> 本文回答一个此前悬着的问题：**"融合省下的 launch 开销"在图模式下是否还存在？**
> 之所以关键：`hc_pre_norm` 的 2:1 融合在 E2E 上无可测收益（`HCPRE-FUSE-E2E-NEGATIVE`），
> 如果图模式摊平了每算子开销，那么"减少算子数"这条路就是死的；
> 如果不是，那么它是唯一通往目标的路。
> 方法：**串行依赖链**的 N 个同 footprint 小算子，eager 与 NPUGraph 两种模式各扫 N，
> profiler 取设备总时长，用斜率求边际成本。全部为【实测】。

---

## 0. 结论

| M | footprint | **eager 边际** | **graph 边际** | 带宽所需 | **净开销** |
|---:|---:|---:|---:|---:|---:|
| **6** | 0.12 MB | 2.43 µs | **2.18 µs** | 0.15 µs | **≈2.0 µs** |
| **48** | 0.98 MB | 3.29 µs | **3.05 µs** | 1.16 µs | **≈1.9 µs** |

**两条读法**：

1. **图模式没有摊平每算子开销**（2.18 vs 2.43、3.05 vs 3.29，差异 <12%）
   ⇒ **"减少算子数"这条路是有效的**，与"通信/带宽"无关；
2. **每算子净开销 ≈ 1.9~2.0 µs**（扣掉带宽所需后）—— 这是**融合能回收的单位价格**。

### 0.1 这正好解释了 `hc_pre_norm` 为什么测不出收益

```
86 次调用（43 attn + 43 FFN）→ 2:1 融合 → 43 次
省 = 43 × 2.0 µs = 86 µs = 步长的 0.34%
判据下限 = 1%   ⇒  <判据下限，必然测不出
```

**⇒ 上一个"融合无收益"的结论不是否定融合，而是"2:1 的规模太小"。**

## 2. ★ 各融合族里"在主流上"的算子数（只有这些能被融合省掉）

不在主流上的算子落在侧流上，会被主流的等待窗口吸收（已实测：尾链仅超出主流 0.128 ms）
⇒ **融合它们不会缩短步长**。

| 融合族 | 总次数/步 | **主流上次数/步** | 总 ms | **主流上 ms** | 主流占比 |
|---|---:|---:|---:|---:|---:|
| F1 位置/槽位链 | 470.0 | **215.9** | 0.833 | 0.293 | 46% |
| F2 dtype/搬运链 | 418.0 | **180.9** | 0.974 | 0.327 | 43% |
| **F3 norm+quant** | 370.0 | **220.9** | 1.780 | **0.852** | **60%** |
| **F4 MoE 路由链** | 129.0 | **119.9** | 0.929 | **0.858** | **93%** |
| **F6 indexer 小 kernel** | 24.0 | **24.0** | 0.576 | **0.575** | **100%** |
| F7 RoPE/取表链 | 197.0 | **96.9** | 0.715 | 0.323 | 49% |
| F8 归约/逐元素杂项 | 160.0 | **93.9** | 0.623 | 0.427 | 59% |
| **合计** | **1,768** | **952.5** | **6.431** | **3.656** | **54%** |

## 3. ★ 融合的现实预期（只算主流上的 952.5 个算子）

```
省 = (主流上算子数 − 主流上算子数/k) × 每算子净开销
```

| 每算子开销 | 融合比例 | **可省** | **占步长** |
|---:|---:|---:|---:|
| 2.0 µs | 4:1 | 1.429 ms | **5.6%** |
| 2.0 µs | 8:1 | 1.667 ms | **6.5%** |
| **3.0 µs** | **4:1** | **2.143 ms** | **8.4%** |
| **3.0 µs** | **8:1** | **2.500 ms** | **9.8%** |

### 3.1 与目标（−12% = −3.0 ms）的关系

| | 值 |
|---|---|
| 融合上界（8:1、3 µs 口径） | **2.50 ms = 9.8%** |
| 目标 | 3.00 ms = 12% |
| **差距** | **0.5 ms** |

⇒ **多合 1 融合是唯一能拿到接近两位数的路，但单靠它也差 0.5 ms。**

**要补上最后的 0.5 ms，只能是**：
* F1/F2 里那 **811 个不在主流上的算子**（占 46%）—— 如果能把它们**移到主流之外彻底隐藏**，
  可再省一部分主流的等待；
* 或者把融合比例做得更激进（16:1）——但受限于"同一条链上相邻"的可融合粒度。

## 4. 为什么会"差 0.5 ms"：F1/F2 有一半在侧流上

| 族 | 主流占比 | 说明 |
|---|---:|---|
| F6 indexer | **100%** | 全在主流（可能是 AICPU metadata 提交点） |
| F4 MoE 路由 | **93%** | 几乎全在主流 |
| F3 norm+quant | 60% | |
| F8 逐元素 | 59% | |
| F7 RoPE | 49% | ⚠️ 一半在侧流（draft 的 RoPE） |
| F1 位置/槽位 | 46% | ⚠️ 一半在侧流（s47 的采样/槽位链） |
| F2 dtype/搬运 | 43% | ⚠️ 一半在侧流 |

⇒ **F1/F2 之所以"不可判定"，正是因为它们多数不在关键路径上**——
这与 `prof_tail_critical` 的结论（尾链超出主流仅 0.128 ms）互相印证。

## 5. 修正后的执行计划（按"每算子开销 × 主流占比"排序）

| 序 | 目标 | 主流上算子/步 | 主流上 ms | 4:1 融合预期（3 µs 口径） | 难度 |
|---:|---|---:|---:|---:|---|
| **1** | **F3 norm+quant**（`RmsNorm`+`DynamicQuant`+`RmsNormCast`+`DequantSwigluQuant`） | 220.9 | 0.852 | **0.50 ms（2.0%）** | 中（官方有 `npu_rms_norm_dynamic_quant`） |
| **2** | **F1 位置/槽位链**（主流上的那 216 个） | 215.9 | 0.293 | **0.49 ms（1.9%）** | 中（已有 `_compute_slot_mapping_kernel` 先例） |
| **3** | **F4 MoE 路由**（gating + routing 合 1） | 119.9 | 0.858 | **0.27 ms（1.1%）** | 中 |
| **4** | F2 dtype/搬运（主流上的 181 个） | 180.9 | 0.327 | 0.41 ms（1.6%） | 低（纯 Python 侧） |
| **5** | F7 RoPE 并入 F3 链 | 96.9 | 0.323 | 0.22 ms（0.9%） | 中 |
| **6** | F8 逐元素杂项 | 93.9 | 0.427 | 0.21 ms（0.8%） | 待查 |
| **7** | F6 indexer 三件套 | 24.0 | 0.575 | 0.05 ms（0.2%） | 中 |
| | **合计** | **952.5** | **3.656** | **≈2.14 ms（8.4%）** | |

**注意**：单看每一项都只有 1~2%，**但它们加起来是 8.4%**；
而**每一项单独做都无法用现在的判据验证**（<1%）—— 所以必须**批量做、用累计值验证**。

## 6. 方法学增量（本轮学到的新判据）

| # | 判据 | 用途 |
|---:|---|---|
| 1 | **串行链 N 扫描求斜率**（eager/graph 各一套） | 求"每算子边际成本"，判定减算子数是否有效 |
| 2 | **主流占比**（自动识别主流 = busy 最大流） | 只有主流上的算子才在关键路径 |
| 3 | **尾链超出量**（整步末任务 − 主流末任务） | 判定侧流是否延长步长（本 profile 仅 0.128 ms） |
| 4 | **判据下限 1%** | <1% 的效应必须批量累计验证 |
