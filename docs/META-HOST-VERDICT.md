# ★ 部署判决：metadata host 路径完全被隐藏，Task Duration 是干净设备时间（2026-10-04）

> 背景：metadata 线在 api_statistic 里发现 host 侧 GetWorkspaceSize 三件套合计
> **1013.3 ms**（4396 次、平均 209µs），比算子本体入队（21µs）贵 10 倍。两个待裁决假说：
> **H1**：msprof 的 AICPU Task Duration 被 host 延迟污染（⇒ 717ms「设备时间」是虚的）
> **H2**：内核在服务里真的跑得久。
> 本文用**同一台服务、同一份配置**的 sleep 注入实验裁决二者。

## 1. 实验设计与一个我自己先犯的错

子代理在 device_metadata.py 的 task.run() **之前**注入**文件驱动**的 maybe_sleep()
（/tmp/v41_meta_host_sleep_us，默认 0 = 与 stock 同行为），只延迟 host 提交、不触及设备执行。

**判据选择**：一开始我用 [bneck] 的 hp 作判据 ⇒ sleep 从 0 加到 1000µs（应 +7ms/step）**毫无变化**；
但把 sleep 拉到 **50000µs** 时吞吐从 **367 崩到 31 tok/s**，而 hp 仍是 41.7ms
⇒ **hp 只测 forward 内部，而 metadata 的 host 延迟发生在 forward 之外**（靠 ExternalEvent 阻塞主图）
⇒ **hp 对这类延迟是错判据**；改用**端到端吞吐**后立刻有分辨力。
**教训：判据必须与被测延迟的作用位置匹配。**

## 2. 结果一：host 路径的隐藏预算 ≥ 1 ms/task

同一服务、N=8、1024/256、3 rep（首尾各一次 0 档做漂移校准）：

| sleep/task | N=8 总吞吐 | A | 相对 0 档 |
|---:|---:|---:|---:|
| **0**（首） | **334.0** | 3.22 | — |
| 300 µs | 329.0 | 3.10 | −1.5%（噪声内） |
| **1000 µs** | **333.9** | 3.27 | **−0.0%** |
| **0**（尾） | 330.8 | 2.95 | −1.0%（漂移量级） |

若 7 次/步的 host 延迟**全在关键路径**，1000µs 档应 **+7.0 ms/step ⇒ 约 −15%** 吞吐。
**实测 0.0%** ⇒ **在真实成本量级（209–258µs/call）上 host 路径被完全吸收。**

再往上加才逐渐穿透（给出隐藏预算上界）：

| sleep/task | 每步注入（7 次） | N=8 吞吐 | Δ |
|---:|---:|---:|---:|
| 0 | 0 | 334.0 | — |
| 1000 µs | 7 ms | 333.9 | **0.0%** |
| **5000 µs** | **35 ms** | **229.9** | **−31%** |
| 50000 µs | 350 ms | 31 | −92% |

⇒ **隐藏预算在 1–5 ms/task 之间**（7–35 ms/step），实际成本 0.21–0.26 ms/task 落在预算内 ⇒ 余量 **4–5×**。

## 3. ★★ 结果二：Task Duration 不被 host 延迟污染（H1 被否证）

sleep=0 与 sleep=5000（吞吐已掉 54%）两档各采一份 profile，同口径对比（稳态 p50）：

| 算子 | sleep=0 p50 | sleep=5000 p50 | Δ |
|---|---:|---:|---:|
| SparseFlashMlaMetadata | 232.2 µs | **233.2 µs** | **+1.0** |
| SparseAttnSharedkvMetadata | 216.0 µs | **211.5 µs** | **−4.5** |
| QuantLightningIndexerV2Metadata | 194.0 µs | **193.3 µs** | **−0.7** |

两档分布整体重合（p5/p25/p75/p95 逐点一致）。**宿主每任务多睡 5ms、吞吐掉一半，
而 Task Duration 纹丝不动** ⇒ msprof 记的是"从 AICPU 取到任务到算完"的净时间。

**⇒ H1 否证、H2 成立**：服务里这三类 kernel 确实各自跑 190–230µs。

## 4. 三条可执行结论

| # | 结论 | 依据 |
|---|---|---|
| **1** | **不要优化 GetWorkspaceSize（209–258µs）** —— 完全被隐藏，改了拿不到吞吐 | §2 |
| **2** | **设备侧那 717ms 是真的**（4.6% 占空），不能当记账假象 | §3 |
| **3** | 但内核本体只值 9.5µs（Prep 4.6 + Sched 4.1 + Gen 0.8）⇒ **约 180–220µs 是 AICPU 框架开销**，不是我们的算法 | 子代理 [META-PHASE] 插桩 + §3 |

⇒ **唯一可动的杠杆是"减少调用次数"**（当前 **7 次/步**：628 簇×6 + 628 簇×1），
因为单次成本的大头在框架、不在我们的代码。

## 5. 顺带确认

* **AI-core 空闲洞与 metadata 的关系不变**：metadata 仍占 AI core 空闲 71.9%（92.3ms/128.3ms）；
  因为 Task Duration 是干净的，这 92.3ms **是真实等待**，不是记账伪影。

## 6. 方法学（追加到全局清单）

1. **判据必须与被测延迟的作用位置匹配**：hp 只覆盖 forward 内部；位于 forward 之外、
   靠 event 阻塞主图的延迟，**只有端到端吞吐/墙钟能反映**。
2. **用"极端档"验证注入是否真的生效**：0/300/1000 三档全平不能直接判"被隐藏"，
   也可能是"注入没挂上"。拉到 50000µs 看吞吐崩不崩，才能区分。
