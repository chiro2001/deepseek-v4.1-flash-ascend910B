# 更正：tp8k5 吞吐曲线（非退化 prompt 集）与两处判断修正（2026-10-06）

> 本文**更正**两处此前发布的错误结论，并给出可复现的权威数字。
> 全部为【实测】。

## 0. 更正清单

| 此前结论 | 更正 |
|---|---|
| `docs/TP8-AUTHORITATIVE-THROUGHPUT-20261006.md`：conc=32 → **2825 tok/s** | ❌ **被重复退化污染**。非退化 prompt 下是 **1413 tok/s**（§2） |
| `docs/MOE-WEIGHT-BOUND-VERIFIED-20261006.md` §4.1：高并发 MoE 有效带宽只有 **54%**，是最大杠杆 | ❌ **算错**。用权威计数反推，活跃专家只有 **~13 个/次**，MoE **已经跑在峰值带宽**（§3） |

## 1. 重复退化：是怎么被发现、怎么污染的

上一版探针（`tools/tp8_steady_probe.py`）对**所有请求使用同一条 prompt**。实测该 prompt 下
模型会**退化成逐字重复**：

```
rep(20-gram 最高频/总数) = 0.092
尾部: '用一句话概括上文。 请用一句话概括上文。 请用一句话概括上文。 …'（反复）
```

退化的文本对投机解码是"白送"——draft 模型每一步都能猜中，于是
**接受长度被虚高到 4.97/5**（≈ SP_TOKENS 上限），吞吐随之被高估约 2×。

**判别实验（决定性）**：conc=1、**完全相同的 prompt**，连续两次运行：

| 运行 | 接受长度 | 吞吐 |
|---|---:|---:|
| 第 1 次 | **4.97** | 236.7 tok/s |
| 第 2 次 | **1.95** | 119.6 tok/s |

同一输入、同一并发、同一 `temperature=0`，结果差 2× ⇒ **不是并发效应，是生成内容退化与否**。

## 2. 更正后的权威曲线（非退化 prompt 集）

prompt 集：**32 条互不重叠的正文切片 × 4 个任务后缀**（`data/hlm_local/` 的
continue / extract / qa / quote），与 `tools/bench_concurrency.py` 口径一致，但支持任意并发。
窗口法：稳态 `/metrics` 差分（`Δdrafts/并发 = 步数`）。

```bash
python3 ~/tmp/tp8_curve.py http://127.0.0.1:19210 1,8,32 20
```

| conc | **ms/step** | 每步 token | 接受长度 | **吞吐** |
|---:|---:|---:|---:|---:|
| 1 | **24.580** | 2.36 | 1.36 | **95.8 tok/s** |
| 8 | **41.510** | 25.54 | 2.19 | **615.3 tok/s** |
| 32 | **69.472** | 98.18 | 2.07 | **1413.2 tok/s** |

**接受长度稳定在 2.07~2.19**（不再随并发"上升"）。

**与既有基线的对比**：仓库文档里 `conc=8 总吞吐 344.7~374.7 tok/s`；
本次实测 **615.3 tok/s**（约 1.7× 高）。原因：`tools/bench_concurrency.py` 只有 **4 条 prompt**
⇒ `--concurrency > 4` 时实际并发仍为 4；且它用 64-token 的极短窗口，prefill/爬升占比过大。

## 3. 更正：MoE **已经跑在峰值带宽**，不存在"54% → 90%"的杠杆

用 `op_statistic.csv` 的**权威计数**（不是抽样）：

| 算子 | 次数 | 合计 µs | **均值/次** |
|---|---:|---:|---:|
| `GroupedMatmulSwigluQuantV2`（w1/w3） | 3655 | 434,277 | **118.8 µs** |
| `GroupedMatmul`（w2） | 3655 | 232,592 | **63.6 µs** |
| `HcPre` | 7310 | 294,538 | 40.3 µs |

（三者计数比 3655 : 3655 : 7310 = 1 : 1 : 2，与"每层 2 次 HcPre + 1 次 w1/w3 + 1 次 w2"吻合。）

每专家权重（int4）：`w1/w3 = 2·2304·5120·0.5 B = 11.8 MB`、`w2 = 5.9 MB`。
由"算子纯带宽受限"（`tools/moe_gmm_bench.py`：token 64× 只 +4%，g=48 打满 1292 GB/s）
反推活跃专家数：

| 假设带宽 | w1/w3 反推 | w2 反推 |
|---:|---:|---:|
| 1200 GB/s | 12.1 | 12.9 |
| 1300 GB/s | **13.1** | **14.0** |

⇒ **每次调用只读 ~13 个专家**（EP=8 下 routes/rank 本来就只有几十个），
且耗时与"13 个专家 × 每专家字节 ÷ 峰值带宽"**完全吻合**
⇒ **MoE 的权重流已经达到峰值带宽，没有可回收的效率损失。**

（此前"54%"的错误来源：我假设了"48 个本地专家全读 = 34 GB/步"，
而实际只有 ~13 个/次被读到，字节数被高估了 3~4×。）

## 4. 更正后的成本结构

用 §2 的曲线做线性拟合（ms/step vs 每步 token）：

```
斜率 = (69.472 − 24.580) / (98.18 − 2.36) = 0.4685 ms / token
截距 ≈ 23.5 ms（固定成本/步）
```

| 项 | conc=1 | conc=32 |
|---|---:|---:|
| 固定成本 | 23.5 ms（96%） | 23.5 ms（34%） |
| 与 token 成正比的部分 | 1.1 ms | 46.0 ms |
| 实测步长 | 24.58 | 69.47 |

⇒ **单流延迟几乎全是"每步固定成本"（23.5 ms）**；
**高并发端则已经进入"按 token 线性"的区间**，斜率 0.47 ms/token。

## 5. 这对优化方向意味着什么（修正后的结论）

1. **没有"MoE 带宽效率"这块肥肉**（已证 MoE 在峰值），
   `docs/MOE-WEIGHT-BOUND-VERIFIED-20261006.md` §4.1 的 1.6~1.8× 预期**撤回**。
2. 高并发端已经**按 token 线性**（0.47 ms/token），说明那条路径上没有明显浪费；
   要再提吞吐只能**让每步处理更多 token**（更高并发 / 更长接受长度）。
3. 低并发端 23.5 ms 的固定成本，其组成已被逐项测过并大多封顶：
   HcPre 1.99（官方设计点）、通信 2.50（单批内无可填）、
   MoE ~2、SparseFlashMla ~1.4、RmsNorm/HcPost/RoPE ~1.8、Scatter 0.72……
   ⇒ **单流延迟基本处于平台设计点**，剩余空间需要 kernel 级改动。
4. **验收口径必须固定**：报告任何吞吐/步长数字时，必须同时给出
   **prompt 集、接受长度、ms/step**；单条 prompt 反复使用会得到 2× 虚高。
