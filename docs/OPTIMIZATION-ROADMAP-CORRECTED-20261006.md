+## 0. 一句话
+
+**单流内"换算子/融合"的空间其实很小** —— 因为大部分算子**已经被别的资源盖住了**
+（换掉它也省不了 wall-clock）。真正暴露在关键路径上的，是
+**MoE GEMM（4.44 ms）+ 通信（2.50 ms）+ 一批本身就是模型数学的算子**。
+⇒ **必须把优先级从"线 A（单流换算子）"移到"线 B（micro-batch 并行）"。**

+## 1. 新增的方法论：**暴露度**（比"算子耗时"准得多）
+
+一个算子只有在**不被任何其它资源覆盖**的那部分时间里，才真的在关键路径上。
+`tools/prof_expo2.py` 对每个算子算：
+
+```
+暴露 = 该算子的 union 时长 − 与"其它所有算子并集"的重叠
+真实暴露 = 暴露 / K      (K = 40.02/24.59 = 1.6275，profile→服务)
+```

+## 5. 为什么单流空间这么小 —— 结构性原因
+
+```
+主流上的 AIC/AIV 是 272 组「AIC 块(37 µs) → AIV 块(21 µs)」严格交替
+AIC 连续块中位长度 = 1 个算子
+```
+
+⇒ 层内几乎每一步都是**真依赖**（AIV 吃 AIC 输出、AIC 吃 AIV 输出）。
+**能靠"融合/换算子"省掉的，只有那些"被别的资源盖住"的部分** ——
+而它们恰恰**已经不在关键路径上**了（如 DequantSwigluQuant 0.025、AivKernel 0.000）。
+
+**这是好消息也是坏消息**：
+* 坏消息：单流优化天花板约 +5%；
+* 好消息：**AIC 利用率 55% 的空间是真实存在的（45%）**，只是必须靠"引入独立工作流"来填 ——
+  这正是 micro-batch / pingpong 的用武之地，而微基准已证明它有效（1.37×，达上界 94%）。

### 7.1 线 B 为什么与预测相反（方法论）

微基准那 1.37× 是「**固定总工作量**切多流」——每个 kernel 的效率不随 shape 变化；
真实推理里「**拆 batch**」会改变 kernel 自身的效率：

* 每半批 token 数减半 ⇒ MoE/GEMM 算术强度与专家利用率下降；
* 每半批各自 allreduce ⇒ 通信次数翻倍且每次更小；
* 而收益上限只有 **~10%**（通信暴露 2.5 ms / 24.6 ms）。

⇒ **不能用合成微基准外推 ubatching 在真实模型上的收益。**
