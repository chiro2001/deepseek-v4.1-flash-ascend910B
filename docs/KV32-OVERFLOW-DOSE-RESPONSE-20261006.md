# 池超过 32 位块上界 ⇒ 间歇性**输出级**偏离（块号走查实验，2026-10-06）

> 目的：给 `[KV32-POOL-GUARD]` 的 29,076 块上界一个**独立于 CED 线**的实测支持，
> 并解释「为什么 `BAT_TOKENS=2048` 会让长文退化」。
> 方法：**同一条 64K prompt 重复 N 次**，每次记录**逐位置 logprob**，逐轮比对。
> 全部为【实测】。**未占用 A3 生产实例**（实验在 1+1 tiny 夹具上做）。

## 0. 一句话

**池 ≤ 29,079 块时，87 条请求全部逐位相同；池 = 30,000 块（越界 924 块）时，
24% 的请求出现输出级偏离（max|Δ| 最高 2.04，而信号本身 std 仅 0.99）。**

## 1. 仪器（可复用）

`walk_blocks.py`：同 prompt 重复 N 次，每次记 `prompt_logprobs=1` 的**逐位置**值。
`walk_cmp.py`：以第 0 轮为基线逐位比对，输出每轮 `max|Δ|`、非零位置占比、首个偏离位置。

**为什么不用 argmax**：`docs/CED-PD-BLOCK-BOUND-20260925.md` §0.4 曾记
"1+1 tiny 线不复现该故障，最可能的解释是 dummy 权重判据不够灵（基线 logprob −11.77，分布极平）"。
本轮把判据从"首 token 是否相同"换成"**逐位置 logprob**"后，
**同一个 tiny 能直接看到污染** ⇒ **那段"不复现"的结论应更正为"判据不够细"**。

## 2. 结果（同一配置，**只改池大小**）

配置：GRAPH=1 / SPEC=1 / DCP 见表 / PREFIX=0 / `V41_DUMMY_INIT=real`（真实尺度初始化）

| 池块数 | 越界块数（≥29,077） | DCP | 偏离轮数 / 总轮数 | 判定 |
|---:|---:|---:|---|---|
| 3,970（默认 2 GiB） | 0 | 2 | **0 / 29** | ✅ |
| 29,000 | 0 | 2 | **0 / 29** | ✅ |
| 29,079 | 3 | 2 | **0 / 29** | ✅ |
| **30,000** | **924** | 2 | **7 / 29** | ❌ |
| 30,000 | 924 | **1** | **7 / 29** | ❌ |
| **30,000**（eager） | 924 | 2 | **15 / 61** | ❌ |

⇒ **完全越界为 0 的三组共 87 条请求，全部逐位相同**；
**越界 924 块的两组（不同 DCP、不同 eager/graph）× 90 条请求，偏离率 24–25%**。

## 3. 偏离的形态

* **幅度是输出级的**：max|Δ| 最高 **2.04**（logprob 本身 std 仅 0.99），
  单轮最多 **93% 的位置**不同；不是浮点噪声（噪声底见 §4）；
* **偏离轮次是散落的**：30,000 块那两组分别落在
  `{5,10,16,21,22,26,27}` 与 `{5,10,15,16,20,25,26}` —— **都在开头就出现**，不是"走到高块号之后才开始"；
  两组的规律接近"每 ~4–5 轮一次"（与 DCP、eager/graph 无关）。

## 4. 噪声底（阴性对照）

同一配置连跑 4 轮：**max|Δ| = 0**（逐位相同）⇒ 仪器本身没有噪声，
§2 的偏离是真实差异。另：三组"0 越界"共 87 条请求全部 Δ=0，构成**大样本阴性对照**。

## 5. 阈值区间

已知硬件事实（`docs/CED-PD-BLOCK-BOUND-20260925.md` §3）：槽位 3 页步长 147,712 B，
`⌊2³²/147712⌋ = 29,076` 块。

本轮实测：**29,079 块（越界 3 块）干净、30,000 块（越界 924 块）脏**。
⇒ 阈值落在 **(29,079, 30,000]** 之间。这与"越界块数越多、损坏越明显"（剂量-反应）
一致：3 个块只占一条 64K 请求上下文的 **0.18%**，低于检测下限；
924 个块占 **55%**，于是 24% 的请求被改变。

⚠️ **诚实的边界**：偏离轮次散落这一点，**不能**用最简单的"块号顺序走查、走到高位才坏"解释。
可能存在"越界块 + 某个周期性状态"的耦合。本文件只主张**剂量-反应**这一层，
机制细节待后续（建议用 `V41_CED_BLOCK_DUMP_DIR` 抓每请求的真实块号验证）。

## 6. 对 `BAT_TOKENS=2048` 的直接意义（本轮的主要动机）

| 配置 | 池块数 | 越界块数 | 预期 |
|---|---:|---:|---|
| A3 现役（BAT=8192，13.81 GiB） | 23,341 | 0 | ✅ 干净（与 48 条长文针全过一致） |
| **BAT=2048 自动 profiling**（16.60 GiB） | **31,507** | **2,431** | ❌ 大面积越界 |
| **BAT=2048 + 压池 29,076** | **29,076** | **0** | ✅ **已实测**（见下） |

⇒ **"压池"不是可选的容量优化，而是让 `BAT=2048` 可用的前提**。
`[KV32-POOL-GUARD]` 拒绝 `BAT=2048` 的默认池**不是过度保守**；它给出的配方
`KV_CACHE_MEMORY_BYTES=15728022528`（= 29,076 × 540,928）正是把池拉回"恰好 0 越界"。

**并且这也解释了 2026-09-18 那次"`BAT=2048` 长文退化"**：
当时报告给出的池是 **4,145,957 tokens**，按其几何换算约 **33,874 块 ⇒ 越界 4,798 块**，
正是本文件里"污染最严重"的那一档。

## 7. 复现

```bash
# 1) 起服（tiny，chips 2/3）：把池设成想要的块数 × 540928
KV_CACHE_MEMORY_BYTES=$(( 30000 * 540928 ))  # 例：越界 924 块
# 2) 走查
python3 ~/tmp/walk_blocks.py --tokens 64000 --rounds 30 --out ~/tmp/plp/WALK.json
# 3) 比对
python3 ~/tmp/walk_cmp.py ~/tmp/plp/WALK.json
```

数据：`~/tmp/plp/WALK*.json`（6 组）。脚本：`~/tmp/walk_blocks.py`、`~/tmp/walk_cmp.py`。

### 6.1 ★ 方案形态已实测（2026-10-06）

把 A3 计划的形态在 tiny 上**照原样跑了一遍**：
`BAT_TOKENS=2048` + `KV_CACHE_MEMORY_BYTES=15728022528`（= 29,076 块，**0 越界**）
+ `GRAPH=1` + `SPEC=1` + **`DCP=1`**（与 A3 生产一致）。

| 项 | 值 |
|---|---|
| 池 | **29,076 块**（0 越界） |
| 每请求 prefill 刀数 | **33**（64000 / 1920，M=1920） |
| 容量 | 2,148,206 tokens |
| **走查 30 轮** | **0 / 29 偏离 —— 完全逐位相同** ✅ |
| 单轮耗时 | 11.8–12.0 s（比 BAT=8192 的 17.7 s **更快**） |

⇒ **即使把 M 降到 1920、刀数升到 33，"池不越界"时仍然完全确定**。
这与"退化主要来自越界污染、而不是刀数本身"一致（另见生产实例上 112 刀仍 100% 的记录）。

### 6.2 ★★★ 决定性对照：**同一个 `BAT=2048`，只修越界 ⇒ 从 12/12 FAIL 变成 24/24 PASS**

2026-09-23 在 A3 上留下的两份原始日志（`~/a3_bat2048.log` / `~/a3_bat8192.log`，
同一次部署序列、只差 `BAT_TOKENS`）现在可以把整条因果链闭合：

| run | `GPU KV cache size` | 换算块数（npr 8,567~9,493 两种口径） | 越界？ | 实测结果 |
|---|---:|---:|---|---|
| 09-18 A2 `BAT=2048` | 4,145,957 | 33,873 ~ 37,534 | **越界 4,797+** | 60K **5/10**、74K **3/10**、150K ~0% |
| **09-23 A3 `BAT=2048`** | **3,845,472** | **31,418 ~ 34,814** | **越界 2,342+** | **负控 12/12 FAIL**（空回复 `''`） |
| 09-23 A3 `BAT=8192` | 2,821,228 | 23,050 ~ 25,541 | 干净 | 长文针全过 |
| **10-06 A3 `BAT=2048` + 重排 + cap** | **4,010,585** | **32,767（= 32,768 上限，恰好 ≤）** | **0** | **24/24 PASS** ✅ |

**为什么这一组是决定性的**：第 2 行与第 4 行是**同一个 `BAT=2048`**，chunk 数完全相同
（60K → 30 刀）⇒ 若是"每刀 2% 偏离"作祟，第 4 行应当同样塌掉；实际它 24/24 全过。
唯一变化是**把池从"越界 2,342 块"改成"恰好 0 越界"**。
⇒ **chunk 数不是原因，越界才是**。

**旧机制为什么看起来也成立**：`失败率 ≈ 1−0.98^(prompt/BAT)` 这条曲线是在
**同一批变长 prompt** 上拟合的，而 prompt 越长 ⇒ 该请求占用的块越多 ⇒ 越可能踩到越界区
⇒ 失败率随 prompt 上升。两条机制在**那批数据上不可分辨**；能分辨的是本节的"同 BAT 对照"。

> 注：`docs/BAT-TOKENS-TRADEOFF-20261005.md` 的"实例在图捕获中途静默退出"也已在
> `docs/KV32-SLOT-REPACK-A3-VERDICT-20261006.md` §2/§6 更正为"我们自己的守卫拒绝 + 快照误读"。

**累计样本**：**0 越界 = 116 条请求（87 + 29）全部逐位相同**；
**924 越界 = 90 条请求，偏离率 24–25%**。

## 8. 内存是否装得下（用 A3 实测数字精确核算）

数据来源：`results/armC_bat2048/serve.log`（BAT=2048）与 `results/armIMG_v3_restore6/serve.log`（BAT=8192）
的 `worker.py:826` 行（`Actual usage: … for weights / peak activation / non-torch memory / NPU graph memory`）。

| 配置 | weights | peak act | non-torch | graph | **固定项合计** | 预算(0.92) | **KV 上限** |
|---|---:|---:|---:|---:|---:|---:|---:|
| BAT=8192（现役） | 38.71 | 3.21 | 0.63 | 0.77 | **43.32** | 56.37 | **13.05 GiB** |
| **BAT=2048** | 38.35 | 0.79 | 0.63 | 0.77 | **40.54** | 56.38 | **15.84 GiB** |

**计划需要的 KV = 14.648 GiB**（29,076 块 × 540,928 B）：

| | 总占用 | 预算 | 余量 | 判定 |
|---|---:|---:|---:|---|
| BAT=8192 + 压池 | 57.97 | 56.37 | **−1.60** | ❌ **装不下** |
| **BAT=2048 + 压池** | **55.19** | 56.38 | **+1.19** | ✅ **装得下** |

**vLLM 自己的判据**（armC 日志原文）：
> `Replace gpu_memory_utilization with --kv-cache-memory=16849797980 (15.69 GiB) to fit into requested memory`

⇒ 计划用 **14.648 < 15.69 GiB**，**在 vLLM 认为"装得下"的范围内还留 1.04 GiB**。

### 8.1 附带结论：`BAT=2048` 的**真实**内存余量也更宽

`docs/prefill-memory-headroom.md` 记录：BAT=8192 时**真实** prefill 峰值 **5.5–6.0 GiB**，
而 vLLM 只按 **3.21 GiB** 预留 ⇒ **缺口 2.4–2.8 GiB**（这就是 0.94 那次断崖、以及
2026-10-05 那次 OOM 的根源）。

按 chunk 线性外推 BAT=2048（1920 vs 8064 token，4.2×）：真实峰值 ≈ **1.3–1.4 GiB**，
预留 0.79 ⇒ **缺口只有 0.5–0.6 GiB**。

⇒ **`BAT=2048` 的"预留缺口"比 `BAT=8192` 小 4–5 倍** ⇒ 不仅容量更大，
**长跑时的内存风险也更低**（OOM 事故的教训正是"跑久后 reserved 漂到预算之上"）。

## 9. 结论：`BAT=2048` 与"压池"是**互相依赖**的一对

| 单独做 | 结果 |
|---|---|
| 只压池、不动 BAT（8192） | ❌ 内存装不下（需 13.05 GiB 上限，计划要 14.648） |
| 只降 BAT（2048）、不压池 | ❌ 池 31,507 块 > 29,076 ⇒ 越界 ⇒ §2 的间歇污染 |
| **两者一起** | ✅ 内存够（余 1.19 GiB）+ 池 0 越界 + 真实余量更宽 |

⇒ 这不是"两个可选项"，而是**一个必须成对执行的动作**。
