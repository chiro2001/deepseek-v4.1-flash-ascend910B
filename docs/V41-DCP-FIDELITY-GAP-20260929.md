# V4.1 DCP8 的**保真度差距**（2026-09-29 深夜定位）

**一句话**：DCP8 在**功能层面**正确（长上下文多选针 6/6、容量 6.95×、性能 1.14×），
但在**分布层面**与 DCP1 有系统性差距（首 token |Δlogprob| 0.37~0.68，
短 prompt 甚至 11.77）⇒ **任务目标②的"与 DCP1 基线对齐"尚未完全达成**。
本文记录证据、已排除项与根因候选，供接手者继续。

**约定**：【实测】= 真机跑出来的；【推断】= 由代码/公式推出；【未确认】= 没验。

## 3. 已排除项（都有实测证据）

| 假设 | 判决 | 证据 |
|---|---|---|
| **空 rank 返回 kernel 写死的 `LSE=0.0`**（交接文档 §2.2 警告过的坑） | ❌ 已排除 | 权重级诊断（真实 1093-token 请求）：**8 个 rank 的 `lse` 全部 `finite=69952/69952`、`zero=0`** |
| **`ori_lse`（零通信参考点）在各 rank 不同** | ❌ 已排除 | 同上：8 个 rank 的 `ori_lse` **逐位相同**（`min=0.190644 max=10.241326 mean=4.847902`） |
| **权重出现 0/NaN** | ❌ 已排除 | `w ∈ [1.00007, 910.9]`，`n>0 = 69952/69952` —— 全部为正、有限 |
| **短 prompt 走错分支** | ❌ 已排除 | T=16 请求：rank 0 `w ∈ [1.18, 28.8]`、rank 1-7 `w ≡ 1.0`；`ori` 与 `lse` 在 rank1-7 上逐位相等 —— 与设计**完全一致** |
| **合并公式** | ✅ 数学上精确 | 真值对拍：old/new vs 真值均 `6.3e-16`；离线推导见 `RELEASE.md` §3 |

⇒ 合并的**输入**与**公式**都对，所以差距来自**"喂进去的键集不同"**或**首调用的数值**。

## 4. 根因候选（两个，尚未判别完）

### 候选 A：indexer 分片 ⇒ DCP8 实际attend 的键远多于 DCP1 **【推断，主嫌】**

`patch_v41_dcp.py::replicate_indexer()` 的默认是 **关闭**（`V41_DCP_REPLICATE_INDEXER=0`），
即 indexer K cache 按序列分片。于是**每个 rank 只在自己那 1/8 分片里选 top-512**：

| 上下文 | DCP1 attend 的压缩键 | DCP8 attend 的压缩键 | 比值 |
|---|---|---|---|
| L=16（短 prompt） | 8（全部） | 8（全在 rank 0） | **1×**（应等价） |
| L=2000 | 512（全局 top-512，实际取满 1000 中的 512） | 每 rank 125 < 512 ⇒ 取全部 ⇒ **1000** | **~2×** |
| L=16000 | 512 | 每 rank 1000 > 512 ⇒ 各取 512 ⇒ 并集 **~4096** | **~8×** |

⇒ 模型是按「全局 top-512」训练的，DCP8 让它看 **2~8 倍的键** ⇒ 出分布 ⇒ 保真度下降。
**这解释了 L=2000（0.375）与 L=16000（0.675）的差距，但解释不了短 prompt（1× 键集却 Δ=11.77）**。

**为什么难修**：算子 `npu_quant_lightning_indexer_v2` 的第二个返回值（本应是 top-k 分数）
实测是**空张量**（`assert values.numel() == 0`，官方 UT 原文）⇒ 拿不到分数，
「分布式 top-k（本地 top-k → all-gather 索引+分数 → 全局归并）」这条路缺一半输入。
另一条路（打开 `V41_DCP_REPLICATE_INDEXER=1`）在文档里记为**有两个障碍**：
容量代价 22%，以及 compressor state ring 与槽位等长的硬断言。

### 候选 B：短 prompt 的**首调用数值**（q 从 8 head 变 64 head）【未确认】

短 prompt（16 token）的键集与 DCP1 **完全相同**（8 个压缩行全在 rank 0），
合并公式也精确，却仍然 Δ=11.77 ⇒ 差异只能来自**首调用的注意力输出**本身。
唯一的结构差异是：DCP8 的 `q` 是 **64 head**（gather 后）、DCP1 是 **8 head**（TP 分片）。
kernel 在不同 head 数下的 tiling/归约顺序不同 ⇒ 输出有微小差异。
**但 11.77 nats 太大，不像是纯舍入** ⇒ 候选 A 无法解释的这部分仍需定位。

**判别实验（已做完）**：`rank0_only=1`（文件驱动；我把它接到 `/tmp/v41_perf_flags`，
**prefill 是 eager ⇒ 文件开关在 prefill 生效**，这样无需重启就能 A/B）：

| 实验 | 17×23 短 prompt | ~1200 token 请求 |
|---|---|---|
| 基线（正常合并） | `# 使用` | `大观园里` |
| `rank0_only=1`（只保留 rank0 的 partial） | **`# 使用`（仍错）** | `#.`（不同，但同样错） |

⇒ **不是 rank 1-7 贡献的问题**。短 prompt 的键集本来就全在 rank 0
（16 token ⇒ 8 个压缩行，`owner(pos)=(pos//32)%8` 全为 0），
所以 `rank0_only` 对它本来就无差别 —— 这反过来把嫌疑**集中在两处**：
① rank 0 自己的首调用（64 head vs DCP1 的 8 head）；
② **根本不过合并路径的层**（ratio=0 的层 0/1）。

第②条有**历史实测线索**（先前未查清，见 `a2sim-ref/dcp2tiny/REPORT_2.md` §5）：
ratio=0 的层 0/1（纯滑窗、不走 DCP）输出**也差 19%**，且层 0 的**最后一个 token 逐位相同**、
越往前差得越多（t0 19% → t7 0%）。当时推断是"复制态 SWA 的写侧寻址 /
同算子在不同 pool 布局下的归约顺序"，**从未定位**。
若层 0/1 就已分叉，后面的差距是**被放大的**而不是新增的。

**下一步**：已派专职子代理 `/root/dcp_fidelity` 用 2-chip 逐层夹具定位
（判据必须是**张量级**，因为 tiny 的 token 级判据是死的）。

## 5. 对目标的结论

* ① 容量 ✅（6.95× 同配置对照 / 7.88× 对任务书给的 1,096,072 基线）
* ② 正确性 ⚠️ **功能达标、保真度未对齐**：长针 6/6 答对，但分布层面与 DCP1 有
  0.37~0.68 nats 的系统性差距；短 prompt 有 1/5 的答案翻转
* ③ 性能 ✅（1.14×，无数量级退化）

**②的收口路径**（按代价排序）：
1. 先做候选 B 的判别（`rank0_only`，无需重启，几分钟）
2. 若确认是键集问题 ⇒ 优先做**分布式 top-k**（需先解决"算子不返回分数"，
   例如用已选中的索引在 torch 侧重算分数：候选集 ≤4096 行 × 128 维，T=1 时可忽略）
3. 备选：打开 `V41_DCP_REPLICATE_INDEXER=1` 并解决 ring/槽位布局（容量降到 ~6.45×，仍接近 8×）
