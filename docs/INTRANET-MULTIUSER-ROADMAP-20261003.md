## 1. 缺口一：接入层（今天是"把 IP:port 告诉人"）

### 现状与证据

| 观察到的事实 | 说明什么 |
|---|---|
| a3-21 上是裸端口 `19210`，无鉴权、无限流、无配额 | 只能服务"我们认识的人"，且一个人打满就全体受影响 |
| GitHub issue #2 的报告者**自己搭了 GPUStack** 来托管 | 真实用户需要这层，官方没提供 |
| 他的 `/v1/models` 里 `data[0]` 是 **bge-embedding** | 多模型聚合网关是**真实场景**，不是假想 |
| 我们的 `bench_concurrency.py` 曾被 `data[0]` 覆盖 `--model` 而**静默压错模型** | 这个坑在聚合网关下必踩，我们自己也踩过 |

### 要补的三件事

1. **统一入口 + 鉴权**：域名（或固定入口）+ token 校验。判据：无 token 请求返回 401，
   且能从 token 反查到人。
2. **per-user 限流与配额**：至少 `并发上限` + `每分钟请求数` + `每日 token`。
   判据：单用户打满时其他用户 p95 延迟不劣化 2×。
3. **多模型路由**：一个入口后面挂多个模型（chat / embedding / VL）。
   判据：客户端显式指定 `model` 时必须命中该模型，**不允许被列表首项覆盖**
   （这正是 issue #2 §7.2 那条，我们仓库里已经修过一次同类问题）。

> **需要你输入的部分**：内网是否已有统一网关/账号体系（SSO、网关白名单）？
> 如果有，这一层就是"接进去"而不是"自己造"，工作量差一个数量级。

## 2. 缺口二：容量（"更多人"= 更多并发 + 更多长上下文）

### 2.1 先把两个账算清楚

**KV 容量账**（单实例 TP8 = 2,823,516 tokens）：

| 人均上下文 | 可同时"在场"的请求数 |
|---:|---:|
| 8K | ~345 |
| 32K | ~86 |
| 128K | ~21 |
| **1M** | **~2.8** |

⇒ **短上下文场景，单实例完全够"几十人"用；长上下文场景，单实例只能服务个位数。**
这就是选形态的唯一判据（README §1.1 那张表背后的真实含义）。

**吞吐账**（地火 1024/256，单实例 TP8）：

| 并发 | 8 | 16 |
|---|---:|---:|
| SPEC=1 K=5 | 315.3 | 398.6 |
| SPEC=0 | 277.4 | **434.1** |

### 2.2 三条扩容路线（都有底数，按性价比排序）

| 路线 | 买到什么 | 代价 | 状态 |
|---|---|---|---|
| **① 动态 K 按并发切** | 16 并发 **398.6 → 434.1（+8.9%）** | 无，纯配置 | ⚠️ **未接**：`SP_SCHEDULE` 目前只对 `V41_CED_ROLE=decode` 生效，独立 TP8 形态没接线 |
| **② DCP8** | KV 容量 **×3.0**（2.82M → 8.51M） | decode **+8.23 ms/step** | 已实现（`feat/v41-dcp8`） |
| **③ CED PD 分离** | prefill **2.07×**（144K）、TTFT 21.8 → 10.95 s | 需要 16 个 device；decode 不退化 | 已发布 `a3-ced-pd-v3` |
| （备选）DP2TP4 / DP4TP2 | 高并发抗压 +5%，低并发略省 | 容量与单流各有取舍 | 已实测（`docs/DP-TP-TRADEOFF-20260929.md`） |

**⇒ 最高性价比的一条是 ①**：零硬件成本，而且它同时解决了用户已经观察到的
"spec 一开、高并发反而变慢"（交叉点 N≈12，N=16 时 SPEC=0 反超）。

## 3. 缺口三：静默错误（这是信任风险，不是性能风险）

### 为什么单列一层

性能差用户会抱怨；**答错用户会离开，而且不会告诉你**。三类静默失效我们都遇到过：

| 族 | 指纹 | 今天还撞到过吗 |
|---|---|---|
| A 长上下文静默空答 | HTTP 200 + `completion_tokens=1` + `content=null` | KV32 池越界会触发，已 fail-closed |
| B 图模式乱码 | 打满 `max_tokens` + 无 `finish_reason` + 含 `<｜box｜>` | 已在 A3 定位到多流开关，**A2 生产仍在用** |
| C 草稿静默失效 | 文本对的，但 `A≈1.0` | `DRAFT_GRAPH` 文件没装入时会静默发生 |

### 现状：判据齐全，但**全靠手动跑**

今天这一轮我自己就遇到两次需要人工判断的情况：
1. 服务刚起完的首批请求，并发一致性掉到 **0/8**（其实是冷启动预热）；
2. 稳态下并发一致性 **6–7/8**，逐条比对才知道**差异只在空白/换行**。

这两次如果没人盯着看，就会被误判成"精度坏了"或"其实没事"。

### 要补的一件事：**常驻在线探针**

```
每 N 分钟（或每 M 个请求）跑一遍固定用例集：
  17×23 / count 2000 / count 16000 / needle 904 / needle 8000
  + 一条并发一致性（warmup 后）
→ 任一项失败 ⇒ ① 告警  ②（可选）自动降级到保守档：关 SPEC → 关图 → 只留 TP8
```

- **判据**：探针失败到告警的延迟 < 2× 探测周期；降级动作可回滚且留痕。
- **必须遵守的两条纪律**（今天实测得来）：探针要在 **warmup 之后**跑；
  一致性判据要看**内容**而不是空白。
- **已有基础**：`regress2.py`、`concchk.py`、`conc_detail.py`（都在 a3-21 `~/tmp/`）。

## 4. 缺口四：A2 生产上的两个已知硬伤

这两条不是"新功能"，是**已经在生产上的**风险，而且都不需要新硬件。

### 4.1 DRAM 池满 ⇒ 请求卡住

**已复现的现象**：`DRAM offload pinned 99.9%` 之后，新请求（或旧请求的长 prompt）
会卡在某个阶段不进入 decode；表现为 NPU 利用率在 `{0, 100, 0, 68}` 之间每秒跳变、
**prefix cache hit 一路掉到 0%**、external prefix cache hit 拉升。

**为什么要紧**：池满在生产里是**必然发生的稳态**，不是边界条件。

### 4.2 A2 生产在跑 `MULTISTREAM=1 + DSA_OVERLAP=1`，而我们在 A3 定位的乱码成因正是这组开关

**证据**：`docs/ISSUE-TRIAGE-20260926.md` §6 我们自己列的「🔴 未验证项」第一条
就是这一条 —— A2 生产**正在用**，但**没在 A2 上隔离过**。

**⇒ 这是"让更多人用"之前最该关掉的一个不确定性**：一个单变量 A/B
（同实例、只切这组开关）就能把"A2 到底会不会乱码"从猜测变成结论。

## 5. 建议的优先级（我的判断）

| 序 | 做什么 | 为什么排这个位置 | 需要什么 |
|---:|---|---|---|
| **1** | **在线正确性探针 + 可选自动降级** | 是"多人用"的**前置**：没有它，任何一次静默错误都要靠人发现 | 只需工程，不需要新硬件 |
| **2** | **动态 K 接线到独立 TP8** | 零成本 **+8.9%**，且直接治"高并发 spec 反亏" | 只需工程 |
| **3** | **A2 单变量 A/B：`MULTISTREAM/DSA_OVERLAP`** | 把生产上最大的未知关掉 | 一次重启窗口 |
| **4** | **接入层（鉴权 + 配额 + 多模型路由）** | 决定能不能服务"不认识的人" | **需要你确认内网现有网关/账号体系** |
| **5** | **A2 DRAM 池满卡死** | 生产稳态风险，但定位成本高 | 需要 A2 的复现窗口 |
| **6** | **DCP8 / CED-PD 按规模选型** | 容量决定的，等 1–4 落地后再按实际流量选 | 需要内网的规模假设 |

### 需要你回答的两个问题（这两个答案会改变上面的排序）

1. **"更多人"是多少人、什么用法？** 具体想知道：峰值并发、人均上下文长度、
   是否有人传图/传长文档。按 §2.1 的账，这个答案直接决定要不要 DCP8。
2. **内网有没有现成的统一网关 / 账号体系？** 有 ⇒ 第 4 项变成"接进去"；
   没有 ⇒ 需要先做一个最小可用版（token + 配额 + 路由）。
