# 24ms→17ms 的拆解 + 跨层软件流水的思路/收益/代价（2026-10-07）

> 回答两个问题：① 主干步长降下来的那几毫秒具体是什么；② 跨层软件流水要怎么做、为什么能做、收益落在哪。
> 全部为【实测】；推断处标注。

## 0. 先更正一处口径：24.35 ms **不是同一拓扑**

| 数字 | 出处 | 机器/拓扑 | 配置 |
|---|---|---|---|
| **24.35 ms** | `CED-PD-DYNAMIC-SPEC-20260926` §11.4 | **A3 单机 8+8 PD 分离（CED）的 D 节点** | `SPEC=0` |
| 22.22 ms | `tp8s0_1003_020311` | **A3 TP8 单体** | `SPEC=0`，原镜像，`ENGRAM_DEVICE_INDEX=0` |
| **17.79 ms** | `armNOSPEC2_1006_231507` | **A3 TP8 单体** | `SPEC=0`，我们的镜像，`ENGRAM_DEVICE_INDEX=1` |

⇒ **"24.35 → 17.79"跨了拓扑**（PD 分离的 D 节点 vs TP8 单体），不能直接相减。

**同拓扑、同模型、同 die 的干净对照是**：

```
tp8s0_1003_020311  (10-03, 原镜像)            hp p50 = 22.22 ms   n=1960
armNOSPEC2_1006_231507 (10-06, 我们的镜像)     hp p50 = 17.79 ms   n=168
⇒ 降低 4.43 ms（−19.9%）
```

## 1. ★ 降低了什么：四项机制 + 证据

### 1.1 最直观的一份现场证据（两次 run 的 `[bneck]` 正文）

```
# 10-03（ENGRAM_DEVICE_INDEX=0，host 路径）
[bneck] mode=stock steps=4940 dec=20 d2h=17.395 hash=0.281 hp=28.492 meta=0.002 pad=0.127 route=0.890 total=19.408
                                         ^^^^^^^^^^^^ 每步 17.4 ms 的 D2H

# 10-06（ENGRAM_DEVICE_INDEX=1，设备路径）
[bneck] mode=stock steps=440 dec=20 hp=17.729 pad=0.124 route=0.056 total=0.242
                                        ^^^^ d2h / meta 字段**整个消失**
```

⇒ **engram 的 host 往返（D2H + CPU 查表 + H2D）被整条搬走了**，这是那几毫秒的主体。

### 1.2 四项逐项账（每项都有独立 A/B）

| # | 项 | 机制（**去掉了什么**） | 实测收益 | 证据 |
|---:|---|---|---|---|
| **①** | **`ENGRAM_DEVICE_INDEX` 0→1** | 去掉 **D2H**（实测 `d2h` p50 **10.1 ms**，本 run 单步 17.4 ms 级）+ CPU hash + `hcom_broadcast_`/`hcom_alltoallv_` 回程 | **−2.1 ms/步**（同配置 A/B：27.42 → 25.26~25.37）；**AI core 空闲 10.6% → 5.9%** | `ENGRAM-IDLE-ELIMINATED-20261004`、`ENGRAM-DEVICE-INDEX-A3-20261004` |
| **②** | **gmm1 armF 内核** | 去掉 `GroupedMatmulSwigluQuantV2` 里的**冗余跨核同步**（`SyncAll 4→2`、`Reset 5→2`） | 算子 **−7.56 µs/次** ⇒ 端到端 **−0.67 ~ −1.09 ms/步（≈3%）** | `DELIVERY-KERNEL-GAP-20261005`、`FINAL-R5` |
| **③** | **`ENGRAM_WKV_TP=1`** | 去掉 **315 MB 权重 × 8 卡重复读**（engram `wkv` 投影原先每卡复制），改按输出维分片 + all_gather | **−0.57 ms/步（−2.2%）**；四个稳定桶全部更快；**外加 KV 容量 +5.9%** | `ENGRAM-WKV-TP-20261005` |
| **④** | **`ENGRAM_PAD_SKIP=1`** | 去掉每步 1.86 次 `ZerosLike`（padding 底噪） | **−58 µs/步** | `R6-SUMMARY` §4.9 |
| | **小计** | | **−3.4 ~ −3.8 ms** | |
| | **实测总变化** | | **−4.43 ms** | |
| | 残差 | 镜像重建 / 静态内核编译缓存 / 运行间漂移 | ~0.6 ~ 1.0 ms | 【推断】 |

### 1.3 一句话总结

**降下来的不是"算得更快了"，而是四件"本来就不该做的事"被删掉**：
engram 的 host 往返、gmm1 的冗余同步、wkv 权重的跨卡重复读、padding 的 ZerosLike。
**主干模型本身的算子结构没有变**（这也是为什么后面的 kernel 级优化收效有限）。

## 2. 跨层软件流水：思路 / 为什么 / 收益

### 2.1 要解决的问题（实测的账）

| 资源 | 忙 | 空闲 | 与 AIC 的重叠 |
|---|---:|---:|---:|
| **AIC**（24 cube/die） | 22.05 ms（profile，55%） | **17.97 ms** | — |
| AIV（48 vector/die） | 14.75 ms（37%） | — | **仅 3.50 ms** |
| 通信 | 4.21 ms | — | **0.000** |
| AICPU | 2.07 ms | — | 0.06 |

```
AIC 闲 17.97 = 等 AIV 11.25（未重叠） + 通信 4.21 + AICPU 2.07 + 噪声 0.43
```

⇒ **AIC 有 45% 的时间在"白等"**，其中最大一块是**等 AIV 的 11.25 ms（profile）= 6.9 ms（真实口径）**。

### 2.2 思路：让"另一份独立工作的 AIC 相位"去填这段白等

**关键不是"多流"，而是"相位错开"。**

```
没有错开（当前 DBO 的形态）：
  A: [AIC][AIV]…[AIC][AIV]
  B: [AIC][AIV]…[AIC][AIV]      ← 两条链同相位 ⇒ A 做 AIC 时 B 也在做 AIC ⇒ 互抢，0 重叠

错开一层（软件流水）：
  时刻 t:  A 在层 L 的 AIV   ‖   B 在层 L−1 的 AIC
  时刻 t+1:A 在层 L+1 的 AIC ‖   B 在层 L 的 AIV
  ⇒ A 的 AIV 等待被 B 的 AIC 填满，反之亦然
```

**实现要素**（三条，缺一不可）：

1. **两条（或更多）真正独立的工作链**，各自一条 `compute_stream`；
2. **层偏移**：让链 B 相对链 A 慢 k 层（k=1 起步），而不是同时起步；
3. **层间栅栏**：用 event 把两条链的相位锁住（不锁的话队列会漂移回同相位）。
   - 已有可行写法：`MULTISTREAM-GRAPH-CAPTURE-BREAKTHROUGH` 实测
     **fork event 必须在"捕获根流"上 record**，否则捕获就失败（这是当时卡住的根因）。

### 2.3 为什么"能做"：设备层面的证据

| 证据 | 数值 | 含义 |
|---|---|---|
| **pingpong 微基准**（图内，同工作量切 k 条独立链） | **6 流 1.37×**，上界 1.46× ⇒ **达 94%** | **设备确实有 AIC‖AIV 并行的能力** |
| 单流是"零 ILP 的调度" | 串行下界 3.075 ms vs 实测 3.082 ms（差 0.2%） | 一条流里没有任何空档被自动填 |
| `MIX_AIC ∩ MIX_AIV = 0.000` | — | 连同一个 MIX 核内部的 cube/vector 相位也是**先后**执行 |
| `AivKernel` 4.11 ms | **已 100% 与 HCCL 并行** | 本栈已有"把 vector 工作藏进别处"的成功先例 |

### 2.4 ★★ 但有一个**决定性的结构性障碍**（必须先知道）

**要拿到"独立工作"，就必须把工作拆成两份（micro-batch）。而拆分本身有代价。**

**实测代价**（`DBO-GRAPH-VERDICT-NEGATIVE`，图模式、同配置只切"串行/并发"）：

| conc | 基线（不拆批） | **拆 2 micro-batch（图内同流串行）** | 拆批的净代价 |
|---:|---:|---:|---:|
| 1 | 38.3 | 36.0 | — |
| 4 | **98.9** | **58.0** | **×0.59（慢 1.70×）** |
| 8 | **130.6** | 75.1 | **×0.58（慢 1.72×）** |

**根因（我们的步长性质决定）**：

> **我们的 decode 步长 = Σ(算子耗时)，而不是 Σ(字节)/带宽。**
> 一小批（M=6）时，**算子数几乎不随 M 变化**（它是模型的结构决定的）——
> 实测 conc=1 有 **3,349 个算子/步**，conc=8（M=48）才降到 **1,603 个**。
> ⇒ **把 M=6 拆成 2×3，算子数≈翻倍 ⇒ 步长≈翻倍。**

**于是账就是**：

```
收益上限（藏掉 AIV）        ≤ 6.9 ms（真实口径） ⇒ 24.59 → 17.7 ms（1.39×）
拆批结构代价（算子数翻倍）   ≈ ×1.7
额外代价：allreduce 次数翻倍（81 → 162，每次固定延迟 32~73 µs）⇒ +2.6 ~ 5.9 ms
⇒ 1.39× 的收益**远不能**补偿 1.7× 的代价
```

**并且 DBO 的实验已经把这一点钉死了**：拆批后的"图内串行"与"图内并发"**曲线完全重合**
（58.0 vs 57.7、75.1 vs 73.9）⇒ **那 −42% 全部是"拆批代价"，不是"并行没生效"**。

### 2.5 那还有没有"不拆批"的跨层流水？—— **没有（同层/相邻层是真依赖）**

| 想重叠的两者 | 能否 | 原因 |
|---|---|---|
| 层 L 的 AIV ‖ 层 L 的 AIC | ❌ | 实测 272 对 AIC↔AIV 是**直接依赖**交替，且 **AIC 连续块中位只有 1 个算子** |
| 层 L 的 AIV ‖ 层 L+1 的 AIC | ❌ | `HcPost(L)`（AIV）→ `HcPre(L+1)`（AIC）是 4070 次/窗口的**相邻依赖对** |
| MoE(L) ‖ attention(L+1) | ❌ | attention(L+1) 吃 MoE(L) 的残差输出 |
| draft(L+1) ‖ verify | ❌ | draft 依赖 verify 的接受/拒绝结果 |
| 官方那两组"层内互不依赖支路" | ✅ 但空间小 | 已实测 **+0.8%**（`limit_core_num`，kv‖q_b，最优 kv=8 核） |

### 2.6 ★ 唯一"不拆批就能拿到独立工作"的路：**prefill 与 decode 混步**

**独立工作不一定要来自"同一个请求的另一半"，也可以来自"另一个请求的另一种工作"。**

`N8-SCALING-DEEPDIVE` 的相位表（8 流 × 512 token 的完整一轮）：

| 相位 | 应产出 | 实际 | 缺口 | 占总缺口 |
|---|---:|---:|---:|---:|
| **ramp**（prefill 独占步 + 单流 decode，7.6 s） | 3764 | ~130 | **−3634** | **63%** |
| tail-B（剩 2 流） | 1783 | ~260 | −1523 | 26% |
| tail-A（5–7 流） | 990 | ~550 | −440 | 8% |
| **full（8 流稳态）** | 2872 | ~2730 | −142 | **2%** |

**机制（日志实证）**：`admission_gate` 把每个 prefill 变成**独占步**，
其间 decode 被推迟（`deferred_decode_reqs` 累计到 28，16 个 prefill-only 步跨了 **8.0 秒**）。

⇒ **"取消 prefill 独占步、让 prefill 的 AIC 去填 decode 的 AIV 空档"**
是一条**不需要拆批**的独立工作来源，且量级（63%）远大于跨层流水的上限（1.39×）。

### 2.7 收益落在哪（汇总）

| 维度 | 跨层软件流水（若拆批可行） | 备注 |
|---|---|---|
| **单流 ms/step** | **主要受益**：理论上界 24.59 → **17.7 ms（1.39×）**；连通信一起藏 → 15.1 ms（1.63×） | 这是用户的主指标 |
| 每 token 延迟 | 同比例改善 | |
| **高并发总吞吐** | **收益被摊薄**：conc=8 步长 41.9 ms 里固定成本只占 ~50~59% ⇒ 相对收益约砍半（+12~15%） | 固定成本 = 24.6 ms |
| 预填质量 | 无直接改善 | |
| **代价（必须一起看）** | 拆批 ×1.7、allreduce 翻倍 +2.6~5.9 ms、精度（DBO 实测长 prompt 仅 26.1% token-identical） | |

### 2.8 结论与建议顺序

| 优先 | 做什么 | 理由 |
|---:|---|---|
| **1** | **先做归因实验**，把"拆批代价"与"重叠收益"分离（判据用设备时间轴上的重叠系数 ρ，不用端到端时间） | 否则无从判断跨层流水是否可能转正 |
| **2** | **优先考察"prefill∥decode 混步"**（取消 prefill 独占步） | **不拆批** ⇒ 无 ×1.7 代价；量级 63% ≫ 跨层流水上限 |
| **3** | 跨层软件流水（拆 micro-batch + 层偏移 + 层间栅栏） | 只有当第 1 步证明"拆批代价可降到 1.39× 以下"时才值得投入 |
| **4** | 补完 A1（`limit_core_num` 真正落代码） | 已测 +0.8%，改动小，作为顺带 |
