# 「独占贡献」分析：为什么 prefill 与 decode 的瓶颈结构完全不同（2026-10-04）

> 本文引入一个比"算子 sum 占比"更正确的指标，并用它把两个维度的优化方向**分开**。
> 工具：`~/tmp/excl.py`（区间并集 + 逐个算子求"去掉它之后并集少多少"）。

---

## 0. 为什么"sum 占比"会把人带偏

我们一直用 `op_summary` 的**时间总和占比**排序（比如"allreduce 占 42%"）。
但在**多流并行**的引擎里，一个算子即使 sum 很大，**也可能完全被别的流盖住**
⇒ 砍掉它**一点墙钟都不省**。

正确的指标是**独占贡献**：

```
excl(op) = union(全部算子) − union(去掉 op 之后的算子)
```

它直接回答"**砍掉它，墙钟能少多少**"。被重叠掉的部分贡献为 **0**。

（实现细节：`hcom_*` 与 `AivKernel` 是同一份工作的两次记账，必须按 `(start,end)` 去重，
否则会把通信算两遍 —— 本仓已记录过这个坑。）

## 2. 两条**完全不同**的优化结论

| 维度 | 结论 | 该做什么 | 不该做什么 |
|---|---|---|---|
| **decode（N=4–8）** | 通信**在关键路径上**（22.7%） | **把 allreduce 与 matmul 融合/重叠** ⇒ `FUSED_MC2`（`enable_fused_mc2`，我们当前=0） | — |
| **prefill** | 通信**已被隐藏**；瓶颈是弥散的设备工作量 | **减少总工作量**（kernel 融合、减少算子数） | ❌ **不要**再往"重叠/填气泡"方向投入 |

### 2.1 这条结论解释了此前两个"看起来矛盾"的实验

| 实验 | 结果 | 现在能解释了吗 |
|---|---|---|
| `MC2=1`（=`enable_prefill_mc2`）对 **prefill** 无收益 | 负结果 | ✅ 因为 prefill 的 allreduce **本来就被隐藏了**，没有可重叠的空隙 |
| `MC2=1` 对 **decode** 也几乎无变化 | 负结果 | ✅ 因为**这个开关只作用于 prefill**（名字就是 `enable_prefill_mc2`）；decode 要用 `FUSED_MC2` |

## 3. 验证结果：`FUSED_MC2=1` —— **也是负结果**【实测 2026-10-04 04:xx】

⇒ **`FUSED_MC2=1` 全面略差，不应开启**（保持在默认 0）。

### 3.1 这否证了什么、还剩下什么

| 命题 | 状态 |
|---|---|
| "把通信与 matmul 融合（`FUSED_MC2` / `MC2`）能拿回那 22.7%" | ❌ **两个开关都试过，都不行** |
| "`AivKernel` 的 22.7% 独占是真的" | ✅ 仍然成立（独占贡献是**实测的并集差**） |
| ⇒ 结论 | 那 22.7% **不是"重叠不足"**，而是"**通信本身就在串行等待**"—— 融合开关改不了它 |

**下一步的正确方向**（本轮没时间做，留给下一轮）：
1. **减少集合通信的「次数」**：decode 每步 **88 次** allreduce（40 层 × 2 + 8）。
   把 attention 出口与 MoE 出口的两次归约**合并成一次**（层内合并）⇒ 理论上砍掉一半；
2. **减少「体积」**：TP 域内先 reduce-scatter 再 allgather（等于 sequence parallel），
   把 per-rank 流量从 O(T) 降到 O(T/TP)；
3. 查清那 22.7% 里**attention 出口与 MoE 出口各占多少**（用 `gid` 拆），
   只对真正贵的那一半动手。

## 3.9 原假设（保留备查）

**假设**：decode 的 `AivKernel` 独占 22.7%，若把它与 matmul 融合 ⇒ 理论上限 **~22% 的墙钟**。

**实验（单变量）**：

| 臂 | 配置 |
|---|---|
| A（已有） | `BT_PERSIST=1 + SKIP_K0=1`（N=1/2/4/8/16 = 103.4 / 77.6 / 144.3 / 262.8 / 404.0） |
| **B** | A + **`FUSED_MC2=1`**（已起服，`enable_fused_mc2":1` 已确认进容器） |

**判据**：
1. **decode N=4/8/16** 必须**显著**变快（这是目标里点名的弱点）；
2. N=1 不得回退；
3. **prefill 不得回退**（FUSED_MC2 也可能改变 prefill 路径）；
4. 正确性探针（144K/1M 四针 + 并发 2 不同针）必须过。

## 4. 方法学改进（留给后来者）

1. **排序看 `excl_ms`，不要看 `sum_ms`** —— 尤其在这套多流引擎上，两者可以差到无穷大
   （prefill 的 allreduce：sum 占 42%，excl ≈ 0）。
2. **同一份 profile 里，prefill 与 decode 的结论不可互推**（本文就是反例）。
3. `hcom_*` 与 `AivKernel` 必须去重（按 start/end），否则通信被算两遍。
4. 工具在 `~/tmp/excl.py`，用法 `python3 excl.py <op_summary.csv> [topN]`。

## 6. ⚠️ 对 §5 假设的**否证**（2026-10-04 05:0x 实测）

§5 我推断"步尾的慢 allreduce 是 draft 段没进图（dispatcher 静默回落 eager）"。
为验证，我把守卫**从"只对显式开启多 ql 的 dispatcher"扩展到所有 dispatcher**
（原守卫带 `_v41_dynamic_sd_enabled` 条件，而 **draft proposer 用的是自己的
dispatcher 实例、没有这个标记** ⇒ 若 draft 也回落，原守卫**照样静默**），
改成按 `(num_tokens, step_ql)` 去重、每键最多报 3 次。

**结果**：起服 + 打真实流量（N=1 与 N=8 各一整轮）后——

```
GUARD 命中 = 0
```

⇒ **没有任何 dispatcher（主或 draft）在回落 eager**。**§5 的"draft 退 eager"假设被否证。**

### 6.1 那步尾的慢 allreduce 是什么？两个候选（**均未确认**）

| # | 候选 | 支持 | 反证/缺证 |
|---|---|---|---|
| 1 | **那是 prefill 步**（不是 decode）—— prefill 的 allreduce payload 大（T≤8192 ⇒ 82 MB），走 AICPU 回落，单次 10.5 ms 量级；采集窗口里混进了 warmup 的 prefill | 量级接近（我们量到的 1.5–10 ms） | 时长分布里 >1000 µs 的只有 3.8 次/步、均值 1.6 ms，**比 prefill 的 10.5 ms 小一个量级** ⇒ 不像纯 prefill |

## 6. ★★ 重大纠正：**必须剔除 warmup 才能算独占**（2026-10-04 11:2x）

### 6.1 我发现的问题

上面 §5 用的那份 decode profile，**采集窗口的前 20% 里混了大量 warmup/JIT 期**。
把 allreduce 的慢调用按**时间十分位**统计，结果极其干净：

```
慢调用(>=1ms) 按时间十分位:
  00-10%:  176
  10-20%:  162
  20-30%:    0
  …（后 8 个十分位全是 0）

全部 allreduce 按十分位的中位时长:
  00-10%: n= 298 median=1204.9 µs
  10-20%: n= 224 median=1229.4 µs
  30-40%: n= 811 median= 39.1 µs   ← 稳态
  40-50%: n= 999 median= 40.6 µs
  …
  90-100%:n=1404 median= 27.4 µs
```

⇒ **338 次慢 allreduce 全部落在窗口的前 20%**，之后一次都没有。
**§5 那条"22.7% 独占"是把 warmup 期算进去了**。

> 顺带**撤回 §5 的一个子结论**：我当时用"(tN−t0)/steps"估步长，得到的 65.7 ms
> 与实际不符，于是"慢调用出现在步内第 67–86 次（步尾）"那个结论是**步长估错的产物**。
> 按时间十分位看，它们是**时间上的开头**，不是**步内的尾部**。

### 6.4 方法学教训（更新 §4 的清单）

5. **算独占贡献前必须先剔除 warmup**：JIT/首步会让少数算子异常慢，
   在"独占"这种**取最大值**的统计里会被**放大**（本例把 11.9% 放大成 22.7%）。
   做法：按时间十分位看慢调用分布，或直接只取窗口尾部（本工具加了
   `~/tmp/excl_ss.py`，支持 `tail_frac` 参数）。
6. **不要用"(总跨度 ÷ 步数)"估步长**去定位"步内位置"——它与真实步长可以差 20% 以上，
   会得出看似合理其实错误的结论（本轮踩过）。
