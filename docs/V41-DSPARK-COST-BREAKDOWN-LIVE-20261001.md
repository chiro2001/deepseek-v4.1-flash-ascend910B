# DSpark 入图开销拆解（2026-10-01 实测，TP8+DCP8）

> 目标：找出 DSpark 入图后 decode `ms/step` 增量落在哪，找可优化项。
> 方法：同配置 SPEC=0 / SPEC=1 各采一次 `op_summary`，归一化到 per-step 差分。

## 0. 参照基线：A2 生产的历史数字

| 项 | 值 | 出处 |
|---|---|---|
| `SPEC=0` | 24.35 ms/step（A=1，41.06 tok/s） | `docs/CED-PD-DYNAMIC-SPEC-20260926.md` §11.4 |
| `SPEC=1 DRAFT_GRAPH=1` | 32.68 ms/step（A=3.10，**94.79 tok/s**） | 同上 |
| ⇒ DSpark 代价 | **ms/step +34.2%（+8.33）**，换来 ms/token ÷2.31 | |

⚠️ 那是 **CED-PD 拓扑（无 DCP）**。本轮在 **DCP8** 上重测。

端到端墙钟（另测）：SPEC=0 **29.35 ms/step**、SPEC=1 **43.2 ms/step**（+47%）。

### 2.1 ★★ 反直觉结论 1：target 的 M 从 1→8 **几乎不花钱**

`HcPre` 的 Input Shapes（决定性证据）：

| | SPEC=0 | SPEC=1 |
|---|---|---|
| decode 行数 | **1** | **8**（= 1+K = 1+7） |
| 单次耗时 | **28.14 µs** | **32.26 µs** |
| 涨幅 | | **仅 +14.6%** |

同理 `SparseFlashMla` 只涨 **1.08×**。

⇒ **M=8 是"权重带宽 bound"的，多 7 行几乎免费。**
⇒ "target M=1→8 是主要开销" 这个假设**被证伪**，它不是优化重点。

### 2.2 ★★ 反直觉结论 2：主要增量来自**通信**与**元素级小算子**

- `hcom_allReduce` **+1767 µs/step 是最大单项**（占增量的 16%）。次数从 316→330/step，**但单次从 25.67→29.96 µs（+17%）**。
- 一批元素级算子涨幅 **1.6–1.9×**（远超层数比 1.075×）：`DynamicQuant` 1.93×、`DequantSwigluQuant` 1.90×、`ScatterNdUpdateSk` 1.86×、`ViewCopy` 1.76×、`Sub` 1.72×、`Cast` 1.70×、`Mul` 1.69×。
- **两个全新算子**：`Transpose`（+463）与 `Add`（+382）在 SPEC=0 下**完全不存在**。

⇒ 说明 DSpark 引入的**不只是"多 3 层"**，而是一整套额外的元素级流水线 + 通信相位。

### 2.3 通信分流的发现

`hcom_` 分布在 **6 条 stream**：

| stream | count | avg_us | wait_total_us |
|---|---:|---:|---:|
| N/A | 17921 | 29.91 | 19044 |
| 217 | 6966 | 29.17 | 2936 |
| 214 | 9804 | 19.36 | 5525 |
| **38** | **348** | **172.13** | **9970** |
| 212 | 688 | 28.90 | 235 |
| 32 | 38 | 15.58 | 32 |

**stream 38 的 348 次单次平均 172 µs**（是其它流的 6–9 倍），且 wait 合计 9970 µs
⇒ 这是**被序列化/等依赖**的那部分通信，是最可能的优化靶点。

## 4. 已证伪的方向

- ❌ **"target M=1→8 是主要开销"** —— 实测 HcPre 只 +14.6%、SparseFlashMla +8%。
- ❌ **"draft 3 层 = +7.5% 就够"** —— 实测 +38.3%，差额来自通信与元素级算子。


## 6. ★★★ 通信模式拆解（本轮最关键发现）

用 `hcom_allReduce__<gid>_<seq>_<k>` 的 **`k` 值** 做模式归并（`k` 是通信 buffer/位置的标识）。

### 6.1 模式数量：SPEC=0 有 198 个，SPEC=1 只有 85 个

| | SPEC=0 | SPEC=1 |
|---|---:|---:|
| `hcom_allReduce` distinct patterns | **398** | **172** |
| 其中「每步一次」的层内模式 | **198 × 81 次** + **198 × 76 次** | **85 × 88 次** + **85 × 76 次** |

`198 = 40 层 × ~5`；`85 ≈ 43 层 × 2`（40 target + 3 draft）。

⇒ **入图把通信模式从 198 压到 85（−57%）**，这是入图的正向收益（减少 launch/调度开销）。

### 6.2 但每个模式的**耗时上升了**

| 模式 | SPEC=0 us/step | SPEC=1 us/step | Δ |
|---|---:|---:|---:|
| 层内模式 A（81→88 次） | **2287.2** | **2512.4** | **+225.2** |
| 层内模式 B（76 次） | **910.8** | **1520.7** | **+609.9** |
| 骨干 `gid=503_k=1`（TP 组） | 748.0 | 659.9 | **−88.1** |
| 骨干 `gid=097_k=1`（**DCP merge 组**） | 206.0 | **461.1** | **+255.1** |
| | **4152.0** | **5154.1** | **+1002** |

### 6.3 三条可操作的结论

**① `gid=097`（DCP merge 组）次数/step 从 0.76 → 1.75**
`gid=097` 是 **DCP 的 merge 通信**。次数翻倍说明 **draft 的 attention 也走了一次 DCP merge**
⇒ 每步多出约 1 次 264 µs 的 merge ⇒ **+255 µs/step**。

**② 层内模式 B 的耗时 +610 µs/step（+67%）是最大单项**
次数/步没变（76/200=0.38 vs 76/87=0.87，注意这是"每模式次数"，需按模式数归一）。
真正要看的是 **总耗时/step**：911 → 1521。

**③ 骨干通信反而变便宜**（503_k=1：748→660）
说明 DSpark 让 TP 组的大通信更高效（可能因为 M=8 的矩阵更大、摊薄了固定开销）。

### 6.4 优化靶点（按预期收益）

| # | 靶点 | 预期 | 依据 |
|---|---|---|---|
| **1** | **DCP merge 的 draft 部分能否与 target 共享/跳过** | **−255 µs/step** | gid=097 次数 0.76→1.75 |
| **2** | 层内模式 B 的 +610 µs/step | 未知 | 需查它的数据量是否随 M=8 变大 |
| **3** | 元素级算子 1.6–1.9× 涨幅 | ~1 ms/step | §2 表 |
| **4** | `Transpose` + `Add` 新增（+845 µs/step） | ~0.8 ms/step | 查来源 |


## 8. ★★★★ gid=097（DCP merge 组）的精确拆解

用 `hcom_allReduce__097_<seq>_<k>` 的 `k` 值做 buffer 级归并。

| 项目 | SPEC=0 | SPEC=1 | Δ |
|---|---:|---:|---:|
| distinct k 个数 | **199** | **86** | **−113（−57%）** |
| **总耗时 us/step** | **1116.8** | **1981.7** | **+864.9** |

### 8.1 k=1（大 buffer）——次数翻倍

| | SPEC=0 | SPEC=1 |
|---|---:|---:|
| 次数/step | 0.76 | **1.75** |
| 单次 us | 271.06 | 263.91 |
| **us/step** | **206.0** | **461.1**（**+255.1**） |

⇒ **每步多出约 1 次 264 µs 的大 merge**。这是明确的可优化项。

### 8.2 其它 k（每层小 buffer）——单次变慢

| | SPEC=0 | SPEC=1 |
|---|---:|---:|
| k 个数 | 198 | 85 |
| 合计 us/step | 910.8 | **1520.6**（+609.8） |
| **平均单个 k us/step** | **4.60** | **17.89**（**3.89×**） |
| 单次耗时 | ~13.0 µs | **~21.7 µs**（+67%） |

### 8.3 两条优化靶点

| # | 靶点 | 预期收益 | 需要查什么 |
|---|---|---:|---|
| **(a)** | 让 `097_k=1` 每步只做 **1** 次（现在 1.75） | **~255 µs/step** | 为什么 draft 那一步也触发了这个大 merge？是 draft 的 attention 也走 DCP 合并，还是 buffer 复用导致重复？ |
| **(b)** | 单次从 13.0 → 21.7 µs（+67%） | **~610 µs/step** | 该 buffer 的数据量是否随 M=8 变大？若只是 `[T,H]` 且 T 从 1→8，那是**真实数据量增长**，可考虑用 reduce_scatter 或降低精度 |

### 8.4 与其它组的关系

`gid=503`（MoE/TP 组）同样有"每步一次"的层内模式（SPEC=0: 198×81 + 198×76；SPEC=1: 85×88 + 85×76），
其耗时/step 也从 2287→2512（A）与 911→1521（B）。

⇒ **两个组呈现同一个模式**：**buffer 数被入图合并（−57%），但每个 buffer 的单次耗时上升**。
优化必须针对"单次耗时上升"的根因，而不是再减 buffer 数。
