# Track B：HcPre+RmsNorm 融合 —— 实测结论与目标纠偏（2026-10-03）

> 目标原文（我 2026-10-03 定的）：「实现 HcPre+RmsNorm 融合 kernel（数值需逐元素对齐），
> 最后接到 overlay 在独立 TP8 上验证**收益 ≥3 ms/step**」。
> **本文纠正这个目标：3 ms/step 不可达，实际上限约 1–2 ms/step。**

---

## 0. 一句话

融合**做成了**（数值对齐到半个 bf16 ULP、设备侧省 **11.92 µs/次**、kernel 1:1 接管已验证），
但 **3 ms/step 这个目标从一开始就算错了**：86 次/步 × 11.92 µs = **1.02 ms/step**（attn 路径一半）。
即使把 FFN 路径也融合，合计也只有 **~2 ms/step**。

---

## 1. 我错在哪（目标定错的口径）

我当时看到设备画像里 `HcPre 4.1 ms/step + HcPost 1.7 ms/step = 5.8 ms/step`，
就写了「≥3 ms/step」。**但 5.8 是这两者的"总设备时间"，不是"可省量"**：

| 项 | 值 | 说明 |
|---|---|---|
| HcPre 设备时间（86 次/步） | 48 µs/次 | 这部分**必须照做**，融合不会消掉它 |
| 相邻 RmsNorm | ~16 µs/次 | 融合把它并进来 |
| **融合后单次** | **61.4 µs** | vs 原 `hc_pre + rmsnorm = 73.3 µs` |
| **真正省下的** | **11.9 µs/次** | = 省掉的那次 launch + 中间张量的读写 |
| **× 86 次/步** | **1.02 ms/step** | **这才是上限** |

⇒ 我把"总时间"当成了"可省量"，差了约 5 倍。**这是计划文档里的一个真错误，不是执行问题。**

---

## 2. 实际做到了什么【实测】

### 2.1 数值（**未放松任何容差**）

| 项 | 结果 |
|---|---|
| `y` vs 参考 `rms_norm(hc_pre(x).y)` | `max|Δ|=0.015625`（`|y|max=5.594` ⇒ **半个 bf16 ULP**，相对 0.28%）、`mean|Δ|=2.5e-5`、`cos=0.99999994` |
| `post` / `comb_frag` / `pre` 三个输出 | **逐元素完全相同（max|Δ|=0）** |
| 无 gamma 的退化路径（4 输出） | **逐元素 0** |
| 多 T 回归 T=1…256 | 全过（`y` ≤1 ULP，其余 0） |

### 2.2 设备侧单算子（M=96，20 次 profile）

| 臂 | µs/次 |
|---|---:|
| `hc_pre` | 57.0 |
| `hc_pre + rmsnorm`（基线） | 73.29 |
| **fused（`hc_pre_norm`）** | **61.37** |
| **省** | **−11.92 µs（−16%）** |

### 2.3 端到端（tiny，dies 6-7 / 19320，M≈8）

| 臂 | ms/step | A | 单流 tok/s |
|---|---:|---:|---:|
| base | 36.20 / 36.315 | 2.000 | 55.25 / 55.07 |
| fuse | 36.111 / 36.441 | 2.000 | 55.38 / 54.88 |

**差异在噪声内（|Δ|<0.4 ms/step）**。内核级取证证明融合**确实生效**
（`HcPreNorm n=6923 ↔ HcPre n=6923` 1:1；`RmsNorm` 少 6923），但每次调用的设备时间打平
（base 39.2+6.2≈45.4 µs vs fuse 46.1 µs），只少了一次 launch。

**三条最可能原因**（【推断】，按可能性排序）：
1. **tiny 单请求 M≈8** —— 11.92 µs 那笔收益是在 **M=96** 上测出来的；
   M 小时两次调用本身就更便宜，能被省掉的部分也更少；
2. tiny 是 `MULTISTREAM=1 / DSA_OVERLAP=1`，6 µs 级的 layernorm 落进流水线**被掩盖**；
3. 本次只融合 **attn 路径**，覆盖面只有一半（FFN 路径是 `hc_pre + rms_norm_cast`，
   两算子各 6923 次 1:1）。

⇒ **tiny 不是收益口径**，`M≈8` + 多流重叠会把 <12 µs/次 的收益抹平。

## 3. 顺带解掉的两条硬骨头（本来会反复坑人）

| # | 坑 | 真相 | 处置 |
|---|---|---|---|
| 1 | **CANN custom op 内核不会因改源码而重编** —— 前一位的 6 版二分对照**全部失效**（跑的都是陈旧内核） | 真正触发重编的是 `build/binary/ascend910_93/gen/hc_pre_norm_ascend910_93_{0,1}.done`（**小写 op 名**）+ `bin/hc_pre_norm/*.o`；清 `gen/HcPreNorm-*.sh` / `src_copy.done` **都不算** | 固化成 `~/tmp/trackB/rebuild_hc_op.sh`：清缓存 → 构建 → **断言 `.o` md5 变化** → 装 opstage |
| 2 | vLLM 编译产物缓存 key **不含** `V41_HC_FUSE_NORM` | 同一份 `model.py` 只翻 env ⇒ **命中旧图** ⇒ `AttributeError: dsv41_ops has no attribute hc_pre_norm` 起不来 | 各臂用**内容不同**的 overlay 副本，或清 `~/.cache/vllm`；已写进 `apply_overlay_hcfuse.py` 头部 |

另外：自定义 op 必须注册 **Meta（fake tensor）** 实现，否则启动即
`Operator does not support running with fake tensors`（已按 `npu_hc_pre_meta` 的写法补上）。

## 4. 修正后的收益预期（诚实版）

| 路径 | 状态 | 潜在收益 |
|---|---|---|
| **attn 路径**（`hc_pre` + `input_layernorm`） | **已实现、数值已对齐、设备侧已证 −11.9 µs/次** | **~1.0 ms/step**（86 次/步） |
| FFN 路径（`hc_pre` + `rms_norm_cast`） | **未做** | **~1.0 ms/step**（另一半调用） |
| **合计上限** | | **~2.0 ms/step** |
| ~~目标里的 3 ms/step~~ | **不可达**（见 §1） | — |

**⇒ 决策：FFN 路径值得做**（成本是把 `hc_pre_norm` 的输出契约扩一个 fp32 的 `y`，
属改动交付面所以先前挂着等批），因为它是把这 2 ms 拿满的另一半。
