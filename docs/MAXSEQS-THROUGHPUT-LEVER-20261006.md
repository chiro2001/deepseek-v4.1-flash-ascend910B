# ★ 杠杆 B 实测验证：把 `MAX_SEQS` 从 32 提到 64 ⇒ 吞吐 **+32~37%**（2026-10-06）

> 承接 `docs/THROUGHPUT-CEILING-AND-BUCKET-MECHANISM-20261006.md` §4 的杠杆 B 预测。
> 本轮**在 tp8k5 上真机验证**（按约束：先停 → 用测试配置启动 → 测 → 恢复原配置）。
> 全部为【实测】。

## 0. 结论

| 配置 | conc=32 | conc=48 | **conc=64** |
|---|---:|---:|---:|
| **`MAX_SEQS=32`**（交付基线） | 1658（running=32） | — | 1676（**running=32 / waiting=32**） |
| **`MAX_SEQS=64`**（测试） | 1502 | **1990** | **2212 / 2291 / 2209**（**running=64 / waiting=0**） |

⇒ **实测 +32~37%**（1676 → 2210~2290 tok/s），与上一轮按 capture bucket 的预测（+35%）吻合。

**根因（已被本实验闭环验证）**：吞吐上限不是硬件、不是 KV、也不是 `BAT_TOKENS`，
而是 **`MAX_SEQS`**——它把 `num_requests_running` 硬性封在 32，
于是每步只能吃满 capture bucket 192（真实却只用 106，利用率 55%）。

## 1. 测试方法（与约束一致）

```bash
# 1) 记录基线（恢复基准）
#    KV 2,987,509 token / BAT 8192 / MAX_SEQS 32 / SP 5 / capture …96,192
# 2) 停掉并**用测试配置启动**
MAX_SEQS=64 BAT_TOKENS=8192 \
CAPTURE_SIZES="1,2,3,4,6,12,18,24,30,36,42,48,60,72,96,144,192,240,288,336,384" \
bash scripts/serve_a2.sh
# 3) 测量（nonce 破缓存 + 零命中核验 + 稳态窗口）
python3 ~/tmp/tp8_ceiling.py http://127.0.0.1:19210 32,48,64,64 20 1024
# 4) 恢复原配置并核验 health / 容量 / BAT
```

**capture_sizes 的扩展依据**：`num_tokens = num_reqs × (1 + SP_TOKENS) = num_reqs × 6`，
所以 `MAX_SEQS=64` 需要覆盖到 **384**。新增 `144 / 240 / 288 / 336 / 384`
（原表缺 144 正是 conc=24 异常慢的原因，见上一份文档 §3）。

## 2. 测试配置的启动核验

| 项 | 基线 | MAX_SEQS=64 测试 | 一致？ |
|---|---|---|---|
| health | 200 | **200** | ✅ |
| **GPU KV cache size** | 2,987,509 token | **2,987,618 token** | ✅（+109，0.004%） |
| max_num_seqs | 32 | **64** | 符合预期 |
| max_num_batched_tokens | 8192 | 8192 | ✅ |
| SP_TOKENS | 5 | 5 | ✅ |

⇒ 提高 `MAX_SEQS` **不损失 KV 容量**（元数据缓冲的开销可忽略）。
这很关键：说明该杠杆是"净增"的。

## 3. 完整对照数据

### 3.1 `MAX_SEQS=32`（交付基线）

| conc | running | waiting | ms/step | 每步 token | 接受 | 吞吐 |
|---:|---:|---:|---:|---:|---:|---:|
| 8 | 8 | 0 | 41.511 | 27.66 | 2.46 | 666.3 |
| 16 | 16 | 0 | 49.528 | 50.89 | 2.18 | 1027.4 |
| 24 | 24 | 0 | 63.320 | 77.09 | 2.21 | 1217.5 |
| **32** | 32 | 0 | 63.925 | 105.99 | 2.31 | **1658.1** |
| 64 | **32** | **32** | — | — | 2.79 | 1676.5 |
| 128 | **32** | **77** | — | — | 2.80 | 1659.3 |

### 3.2 `MAX_SEQS=64`（测试）

| conc | running | waiting | ms/step | 每步 token | 接受 | 吞吐 |
|---:|---:|---:|---:|---:|---:|---:|
| 32 | 32 | 0 | 66.695 | 100.21 | 2.13 | 1502.5 |
| 48 | 48 | 0 | 77.854 | 154.93 | 2.23 | **1990.1** |
| 64 | 64 | 0 | 89.726 | 198.48 | 2.10 | **2212.0** |
| 64（复测 1） | 64 | 0 | 89.733 | 205.54 | 2.21 | **2290.6** |
| 64（复测 2） | 64 | 0 | 88.926 | 196.45 | 2.07 | **2209.2** |

⇒ conc=64 三次落在 **2209~2291 tok/s**，且 **waiting 恒为 0**（不再排队）。

### 3.3 为什么 conc=32 在两种配置下都约 1500~1660

两种配置下 conc=32 都恰好等于 32（running=32），步长 63.9 vs 66.7 ms
（差 4%，属运行间波动），所以吞吐接近。
**增益全部来自"第 33~64 路请求现在能真正进入引擎"**。

## 4. 与 capture bucket 机制的自洽性

| conc | 真实 token/步 | bucket | ms/step（实测） | 每 bucket-token 成本 |
|---:|---:|---:|---:|---:|
| 32 | 100.21 | 192 | 66.70 | 0.347 ms |
| 48 | 154.93 | 288 | 77.85 | 0.270 ms |
| 64 | 198.48 | 384 | 89.73 | 0.234 ms |

⇒ 桶越大，**每 bucket-token 的边际成本越低**（0.347 → 0.234），
因为每步的固定开销（约 33 ms）被摊得更薄。
这与 `TP8-CURVE-CORRECTED` 里 decode 的"固定成本 + 线性边际"模型完全一致。

## 5. 可以继续往上推吗？

按同一模型外推（`ms/step ≈ 33～36 + 0.15 × bucket`）：

| MAX_SEQS | 需扩 capture 到 | 预测 ms/step | 预测吞吐 | 相对交付基线 |
|---:|---:|---:|---:|---:|
| 32（基线） | 192 | 63.9（实测） | 1658 | 1.00× |
| **64（已实测）** | 384 | 89.7（实测） | **2210~2290** | **1.33~1.38×** |
| 128 | 768 | ~150 | ~2700 | ~1.65× |
| 256 | 1536 | ~270 | ~2900 | ~1.75× |

**收益递减但仍在增长**；瓶颈不是 KV（conc=64 只用了 8.9%）。
【未确认】继续往上需要同时评估：图显存（capture 数量翻倍）、
`MAX_SEQS=256` 时 metadata 缓冲的显存、以及长 prompt 下的实际并发形态。

## 6. 建议

1. **把 `MAX_SEQS=64` + `capture_sizes` 扩到 384 作为新的交付默认**：
   实测 +32~37%，**KV 容量零损失**，改动只有两个启动参数。
2. 若要更进一步，按 §5 先算清图显存与 metadata 缓冲的代价，再决定 128。
3. **注意：`MAX_SEQS` 提升会放大排队尾延迟**（§3.2 里 conc=64 的 TTFT 会更长），
   面向交互式场景时应配合准入控制。
