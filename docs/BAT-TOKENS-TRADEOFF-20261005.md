# `BAT_TOKENS` 权衡实验：容量 **+35%**，但实例在**图捕获中途静默死亡**（2026-10-05）

> 动机：`BAT_TOKENS`（= `max_num_batched_tokens`，prefill chunk 大小）同时决定
> **激活峰值**与 **engram 缓冲**（`_engram_max_tokens = max(BAT, capture_max)`，
> 2 层 × rows × 6144 × 2 B：8192 行 = 201 MB、2048 行 = 50 MB）
> ⇒ 它把 ③ prefill 与 ④ 容量绑在一起，而这个权衡**从未测过**。
> 标注：【实测】。

## 0. 结论

| | BAT=8192（当前交付） | **BAT=2048** |
|---|---|---|
| **KV 容量** | 2,987,727 tokens | **4,032,862 tokens（+35.0%）** ✅ |
| 冷 prefill N=1/2/4 | **7,135 / 7,389 / 7,498 tok/s** | **未测到**（实例崩溃） |
| 起服 | ✅ 正常（16/16 捕获桶） | ❌ **仅捕获 10/16 桶后容器静默退出** |
| 可用性 | 交付默认 | **不可交付**（需先定位崩溃） |

⇒ **不能只为了容量把 `BAT_TOKENS` 降到 2048**；但它暴露了一条**容量与 prefill 的强耦合**，
值得作为后续"容量优先模式"的候选（先定位崩溃）。

## 1. 容量：+1,045,135 tokens（+35%）来自哪里

| 项 | 8192 | 2048 | 差 |
|---|---:|---:|---:|
| engram 缓冲（2 层） | 201 MB | 50 MB | −151 MB |
| **激活峰值**（log：`Actual usage: 3.15 GiB for peak activation`） | ~3.15 GiB | 未单独打印 | **大幅下降** |

实测容量差 = 1,045,135 tokens = **8,165 块**；按交付实例的
`13.05 GiB / 22,042 块 ≈ 636 KB/块` 折算 ⇒ 净释放 **≈5.1 GiB**。
即：**激活峰值随 `BAT_TOKENS` 线性下降**，它比 engram 缓冲更值钱（151 MB vs ~4.9 GiB）。

> 推论：任何"给激活留更多余量"的配置（更小的 chunk）都会显著抬高 KV 容量。
> 这与 `GPU_UTIL`（0.92）是**两条独立的容量杠杆**。

## 2. 崩溃现场（这是本轮最有价值的诊断信息）

臂 C（`armC_bat2048`，发布镜像 + 仅改 `BAT_TOKENS=2048`）：

```
[serve_a2] 就绪（用时 1039s）          ← serve_a2 的 readiness 只看 /health
(APIServer) GET /health 200 OK        ← 唯一一次成功探测
[serve_a2][FAIL] 容器退出
[serve_a2] 清理容器 dsv41-tp8k5
```

* **没有 traceback**（`grep -c ERROR|Traceback` = **0**）；
* **dmesg 无 segfault/OOM**（近期条目只有 9 月的旧记录）；
* 崩溃前的唯一线索是最后一条 `[bneck]`：

```
graphs=10 replays=19 captures=10 eager_fallbacks=0
keys=[(18,3,8192),(24,4,8192),(30,5,8192),(36,6,8192),(42,7,8192),
      (48,8,8192),(60,10,8192),(72,12,8192),(96,16,8192),(192,32,8192)]
```

**16 个捕获桶只完成了 10 个，且恰好是"从大到小"的前 10 个**（192, 96, 72, 60, 48, 42, 36, 30, 24, 18）
⇒【推断】**它死在捕获第 11 个桶（12 token）时**。
交付配置（BAT=8192）在同一位置能顺利捕完 16 个 ⇒ 崩溃与 `BAT_TOKENS` 直接相关。

**已排除的解释**：engram 缓冲尺寸不够 —— `[bneck]` 显示 `max=2048 lookup=(2048, 6144)`，
所有观测样本 `n=18 padded=18`，**没有越界**。

**还注意到一处副作用**：BAT=2048 时 vLLM 提示
`max_num_scheduled_tokens is set to 1920 based on the speculative decoding settings`，
并且**小桶（1,2,3,4,6）根本没有进入捕获列表**（列表里最小是 18）
⇒ 即便不崩，**单流 decode 也会退化到 eager**（①会变差）。

## 3. 顺带修一个测量口径错误：**prefill 必须先热身**

第一轮按 N=1→2→4 顺序测时得到：

| | 首轮（无热身） |
|---|---|
| N=2 | **4,133 tok/s**（TTFT 15.85 s！） |
| N=4 | 7,426 tok/s |

同一实例、同一协议，**N=2 比 N=4 慢 44%** —— 不合物理。加一次热身（1×32K）后重测：

| | 热身后 |
|---|---|
| N=1 | **7,135** |
| N=2 | **7,389** |
| N=4 | **7,498** |

⇒ 结论：**空闲后的第一次 prefill 有 1.7–1.8× 的冷效应**（可能是权重/页表/page-cache 预热）。
**任何 prefill 对比都必须先打一发热身**，否则会把冷效应当成配置差异
（我第一轮就差点把"BAT=8192 的 N=2 = 4,133"记成基线）。

## 4. 处置

* **保持 `BAT_TOKENS=8192` 为交付默认**（可用性优先）；
* 把"容量优先模式（BAT=2048 / 更小 chunk）"记为**待定位崩溃后的候选**，
  预期收益 **+35% 容量**，代价是 ① 可能退化（小桶丢失）与未测的 ③；
* 复现：`sed 's|BAT_TOKENS=8192|BAT_TOKENS=2048|' ~/tmp/launch_armF.sh > ~/tmp/launch_armC.sh`，
  `bash tools/run_arm_suite.sh ~/tmp/launch_armC.sh armC_bat2048 0 0 0`。
