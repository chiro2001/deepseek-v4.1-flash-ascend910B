## 3. 三个臂的判决

### 3.1 armH（`IDS64_HOIST=1` + `ENGRAM_PAD_SKIP=1`）：**弱正，未超噪声**

两个开关此前"已实现但启动器不可达"，本轮接线（commit `2049615`）。

| 判据 | 结果 |
|---|---|
| 环境确认 | 容器内 `V41_IDS64_HOIST=1`、`V41_ENGRAM_PAD_SKIP=1`、`ENGRAM_DEVICE_INDEX=1` ✅ |
| **`[bneck] hp`（步时，按 batch 归一）** | **配对差中位 −0.165 ms**（n=6..48 共 6 档；逐档 −0.37/−0.29/−1.04/−0.25/**+0.67**/−0.05） |
| 聚合吞吐 | 无一致变化（N=1 −1.2%、N=4 −0.5%、N=8 −3.1%、N=16 **+2.0%**） |
| 验收 | 144K 11/11 通过 |

**判决**：机制清楚（每步少 ~37 个 cast / 少 63 µs memset），实测 **≈ −0.2 ms/步（−0.6%）**，
**落在单跑噪声（±5%）之内**；聚合层面看不到收益。
⇒ **保留（低风险、方向正确），但不计入"已兑现收益"**；要坐实需 3 轮交替 A/B（成本 3 h，收益 0.6%）。

### 3.2 armP（`PYTHON_PGO=1`，本机重编 libpython）：**中性偏负**

背景：`optim/pgo/` 里没有 A3 的产物（A2 的 md5 与 A3 镜像不同），本轮用 **A3 镜像**做编译容器
重编（910 s），并先做**加载烟测**（`PYOK 3.12.13` + `import vllm` 成功）才起臂。

| 判据 | 结果 |
|---|---|
| `[bneck] hp` 配对差中位 | **−0.115 ms**（n=6..48：−0.22/−0.11/−0.41/−0.17/**+2.03**/+0.49） |
| 聚合吞吐 | **每一档都下降**：−1.0% / −5.6% / −0.8% / −3.5% / −0.5% |
| 验收 144K | **11/11 通过** |

**判决**：PGO 只加速 **host Python**，而本工作负载的 host 侧早已被设备工作隐藏
（见 `META-HOST-VERDICT`：host 注入 1 ms/任务仍 0.0% 影响）⇒ **预期内无收益**；
实测也中性偏负。**不采纳**（不写进交付默认）。

> 第一次编译用的编译容器镜像是 **openEuler**，产物 glibc 2.38 与 A3 运行镜像（Ubuntu 2.35）
> 不兼容 —— 加载直接报 `GLIBC_2.38 not found`。**必须用 A3 镜像做编译容器**
> （`PGO_FORCE=1 PGO_BUILD_IMAGE=<a3 image> bash build_scripts/00_ensure_pgo.sh`），
> 且**先做加载烟测**再起臂。

### 3.2.1 一次编排事故（已修）

给 `run_arm_suite.sh` 加"补跑 msprof 导出"时，我在导出命令里引用了 `$IMAGE`，
但该脚本**自己并不定义** IMAGE（由各 launcher export）⇒ `set -u` 下
`IMAGE: unbound variable` **直接中止脚本**，症状是
**"基准与 profile 都跑完、验收被静默跳过"**（armH 与 armP 各中一次）。

* 影响面：只有**验收**与**导出**被跳过；**基准数据（主 KPI）与其后的自动对比不受影响**。
* 修补：脚本内加 `IMAGE=${IMAGE:-<a3 镜像>}`（commit 在 `tools/run_arm_suite.sh`）；
  armP 的验收已在容器仍存活时**手工补跑**（11/11 PASS），两个臂的 profile 也**手工补导出**。
* 教训：编排脚本里每一个变量都要有默认值，且**关键阶段之后要有"到达"断言**
  （下一步给 run_arm_suite 加：每阶段结束打印 `STAGE_OK <name>`，缺任何一个即判失败）。

### 3.3 ★ 一条被否掉的旧结论

`[bneck] hp` 是**步周期**（中位 26.2 ms），不是 host 开销 —— 早前按"÷20 累计"读过一次，
已修正（`DECODE-EXCLUSIVE-HOST-20261005.md` §4.2）。

## 4. 剩余杠杆（按"可动的量 × 可信度"排序，全部 <2%）

| # | 靶点 | 量 | 依据 | 成本/风险 |
|---|---|---:|---|---|
| 1 | **HcPre 小 M 的跨核规约/屏障**（tiling 里 K 被切成 20 块 × 24 核） | **0.5–1.0 ms** | HcPre AIV 同步 1.527 ms/步（83%） | 改 host tiling + 重编 + 重验数值（**中高**） |
| 2 | `hc_sinkhorn_iters` 20 → 少量 | **0.30 ms** | tiny 实测 33.76→29.98 µs/次 | 需**真实权重**数值验证（风险：语义） |
| 3 | s47 的 **24× `Fill+ViewCopy(16384)`** | **0.19 ms** | 交付口径仍在、与 engram 无关、严格交替 | 未定位源码（`find_op_context.py` 已备） |
| 4 | draft 的 **5× `[1,256]×[129280,256]`** 合成 1 次 | **0.12 ms** | 每次重读 66 MB 权重；vllm `vocab_mapping.py` 有源码 | 中 |
| 5 | gmm1 的 group_list 标量扫描（2 读点 × 48） | ~0.4 ms | `REPORT-FLOOR-20261004B.md` | 被 gmm2 的 type=0 内核缺失堵死 |
| 6 | 主图若干"norm+quant"融合（F2/F6） | 各 ~0.12 ms | `LEVERS-R5` | 中 |

**合计可及上限 ≈ 1.5–2.0 ms/步（6–8%）**，且每一项都要独立的重编/验证周期
（每轮 A/B ≈ 1 h）。**没有更大的结构性杠杆**：单流 decode 的算术占比只有 8%，
其余是"每层 37 个算子的串行开销 + 权重载入"，而这两者已被图捕获与 armF 内核吃掉大半。

## 4.5 prefill：首份画像（本轮新增，此前完全没有）

详见 `PREFILL-PROFILE-20261005.md`。要点：

| 项 | 实测 |
|---|---|
| **冷前缀 prefill 吞吐** | **7,204 tok/s**（2 x 32,772 tok，TTFT 9.04/9.09 s） |
| 并发扫描（冷） | N=1/2/4/8 = 6,869 / 7,204 / **7,456** / 6,789 tok/s，8 die 已饱和 |
| 每 die 效率 | **932 tok/s/die**（CED 参考 13,676/16 = 855，我们高 9%） |
| 窗口忙碌度 | 全任务并集 **8,996 / 9,022 ms = 99.7%**（无空闲） |
| 绑定资源 | **AIV（向量单元）占主流任务时长 88%**，`aic_mac` 仅 **17.7%** |
| 主计算流构成 | `SparseFlashMla` 26% + `QLI` 16% + `HcPre` 14% + `HcPost` 8% |
| `allreduceAicpuKernel` | busy 7118 ms 但**独占仅 9.6 ms**，完全被隐藏，不要动 |

**为什么是 AIV 而不是算力**：`SparseFlashMla` 的 AIC 与 AIV 都 99% 占用，
但其 AIC 的 MAC 只占自身 15%（其余是 scalar 寻址/载入），AIV 的 4.38 ms 里
真正向量算术只有 0.24 ms，即这个内核是「标量 + 两单元紧耦合」，不是算力不够。
`QLI` 才是真向量受限（vec 占 87%）。

**结论**：prefill 没有配置级旋钮可用（4 个并发档都打在 99.7% 忙）。要再快只能自研
attention 内核（把 `SparseFlashMla` 的每 token 标量寻址向量化），属多日工程。

## 4.6 一条影响口径的发现：贪心输出**依赖批大小**

详见 `BATCH-DEPENDENT-OUTPUT-20261005.md`。8 条 prompt 在 N=1 与 N=8 下，
**7 条生成了不同的文本**（最早在第 0 个字符就分叉）。
即 bench 各并发档之间 **A 的差异不是纯性能信号**（有「文本变了」的成分）；
跨档比较必须看 `ms/step = 1000*A/单流吞吐`（`bench_delta.py` 已按此给数），
**不能把 A 的下降当成 draft 的性能 bug 去修**。

## 4.7 本轮的**负结果**（避免下一轮重走）

| 假说 | 判定 | 依据 |
|---|---|---|
| HcPre 的 K 分核数（20 块）是固定开销主因 | **否** | trackB 实测 `kDimNum 24->4` **反而慢 35-45%**（M=1 33.8->45.6 µs） |
| `hc_sinkhorn_iters` 20->1 可省 0.3 ms/步 | **不可等价** | trackB 判为数值参数；本仓 tiny 复测 33.76->29.98 µs（-3.8 µs），但会改数值 |
| 多请求下 draft 变差（可修 bug） | **否** | 输出文本本身就不同（7/8），见 §4.6 |
| metadata 7 次 AICPU 是杠杆 | **否** | 交付口径 exclusive 仅 0.163（N=1）/0.088 ms（N=8） |
| host 太慢（acl 33.9 ms/步） | **否** | 65% 是同步阻塞；`[bneck] hp` 是步周期不是 host 开销 |
| prefill 受 chunk 大小的调度限制 | **否** | 4 个并发档全部 99.7% 忙，吞吐对并发不敏感 |

## 4.8 HcPre A1 复测：机制已生效，但效应低于采纳门槛

详见 `HCPRE-A1-RETEST-20261005.md`。要点：

| 项 | 结果 |
|---|---|
| 单变量条件 | 两臂 gmm1 内核**相同**（`5dab79be`），只有 HcPre 不同；两臂都清 skcache |
| `hp` 配对差 | **−0.104 ms**（vs 同期对照）；≈ **0**（vs 旧基线） |
| 聚合吞吐 | N=1 +4.7% / N=2 +6.0% / N=4 +1.0% / N=8 **−2.8%**（方向不一致） |
| 验收 144K | **11/11 通过** |
| **执行指纹** | A1 臂新编译的 HcPre 静态内核 **12 个唯一 sha**，与 stock 累计 **790 个 sha 交集 = 0** ⇒ **内核确实换上了** |
| 判决 | **不采纳为默认**（效应 0.4% < 噪声底 0.16 ms）；与 armH 同处置，保留可选包 |

**本轮的方法论收益**：`V41_OPP_CLEAR_SKCACHE=1` 端到端**已被证明可用**
（R5 的"内核从未执行"不再是障碍），后续所有 kernel A/B 都建立在这一点上。
