## 2. 测量与两个必须记录的坑

### 2.1 坑 1：请求在窗口内**结束**会严重污染读数

第一版探针用 `max_tokens=8192`。竞态：

* 60 s 窗口 × 124 tok/s = **7.4 K token ≈ 上限** ⇒ 请求在窗口内**结束**；
* 结算 `Δrequest_success_total=1`，窗口里混进收尾段 ⇒ `ms/step` 虚高到 **52.5 ms**，
  且 `A` 冲到 **4.999**（**重复退化**的典型征兆——模型退化成逐字复读，draft 免费命中）。

⇒ **修正**：`max_tokens=100000` 保证不结束，并**逐轮校验 `A ∈ [1.2, 3.2]` 且 `Δsuccess=0`**，
不满足的轮次标记为污染并丢弃。

### 2.2 坑 2：首窗有预热污染

服务刚 ready 后的**第一个** 30 s 窗口给出 28.282 ms（+13%），
**复测就回到 25.34**。⇒ **必须丢弃 ready 后的第一个窗口**。

### 2.3 最终采用的口径

**主指标 = `[bneck] hp` 的 p50（大样本）**，因为它
① 不依赖 `A`（不受内容/退化影响）；② 样本量大（数千条）；③ 与 `/metrics` 在**基线**上交叉验证一致（24.996 vs 25.029，差 0.13%）。

## 4. 为什么"算子级 −1.8%"没有兑现（三条假设，未逐一验证）

| # | 假设 | 依据 |
|---:|---|---|
| **1** | **图模式把 launch 开销吃掉了** | 邻居的口径是 **eager 单算子**（M=96、die5、60 样本中位），省下的是"一次 kernel 启停 + 一次全张量读"。图重放里启停本来就便宜 ⇒ 收益缩水 |
| **2** | **M=48 ≠ M=96** | 邻居在 **T=96** 测；真实 decode 是 **M=48**（1+5 tokens × 8 reqs）。融合算子要把 fp32 输出"加宽已舍入的 bf16"，这个额外动作在 M 更小时**相对占比更大** |
| **3** | **FFN 路径的 fp32 写回不划算** | 邻居实测 `want_fp32=True` 比 `False` **快 3.75 µs**（反直觉），但那是 standalone；在真实图里多写一份 fp32 输出（48×5120×4 B = **983 KB/次** × 43 次 = **42 MB/步**）是实打实的额外流量 |

### 4.1 一个自洽的估算（【推断】）

```
省下的：attn 路径少一次 RmsNorm（~21.4 µs 里的部分）+ 少一次 launch
付出的：FFN 路径多写 983 KB fp32 × 43 = 42 MB/步
        按 HBM ~845 GB/s（MoE 实测达峰的档位）⇒ 42 MB / 845 GB/s ≈ 0.05 ms
        但 decode 的 HBM 利用率只有 11% ⇒ 这点流量不该是主要成本
⇒ 更可能是假设 1（图模式）+ 融合内核在 M=48 下的 tiling/同步不如两个小内核
```

**这一条需要 profile 才能定论**（对比 `RmsNormCast` 是否消失、`HcPreNorm` 的单次时长）。
本轮未做（profile 导出约 50 min，而结论已足以判定方向）。

## 5. ★ E2E 过程中发现的 OPP 覆盖陷阱（重要，供后续复用）

### 5.1 `opp_override_block.sh` 是 `cp -a` **覆盖**，不是并列

```bash
cp -a /opt/dsv41/hcfuse_opp/vendors/custom_transformer/. "$_imgv/"   # 覆盖进镜像 vendor
export ASCEND_CUSTOM_OPP_PATH="$_imgv"
```

⇒ **同路径文件会被我们的包替换掉**。

### 5.2 因此新包必须"补回"镜像原版内核，否则混淆真实存在

实测对比（归一化到"末 3 段路径"后）：

| 文件 | 新包 | 镜像 | 处置 |
|---|---|---|---|
| `hc_pre/HcPre_6c9f0fa7….o` | `0e4c3e5c…` | **`5aa7b15c…`** | ✅ **已拷回镜像版** |
| `grouped_matmul_swiglu_quant_v2/…_05bce438….o` | `2300ffa0…` | **`318571d1…`** | ✅ **已拷回镜像版** |
| `grouped_matmul_swiglu_quant_v2/…_fa3d6d3d….o`（**armF**） | `18ad8067…` ❌ | **`01f600d2…`** ✅ | ✅ **已用仓库 armF 覆盖** |

⇒ 若不处理这三组，**启用 OPP 会同时换掉 `HcPre` 与 gmm1 的 armF 内核**，
把"融合的收益"与"内核回退的损失"混在一起 —— 会得到**看似有收益**的假象（或掩盖真收益）。

另外：新包里还夹带着邻居实验留下的 **68 个 `.bak*` 文件**，已清掉。

### 5.3 安全性：overlay 是**容器内临时**的

`_cann_ops_custom` **不在 tp8k5 的挂载清单里**（37 个挂载中无此项）⇒ `cp -a` 只改容器层，
**容器重启即还原**，交付 vendor 不受影响。已核对。

### 5.4 `V41_HCFUSE_MOUNT`：不改交付 `model.py`

`serve_a2.sh` 新增该 env（见 commit `885d31a`）：传一份打过 overlay 的 `model.py` 副本覆盖，
**交付文件保持原样**，随时可切回基线。本轮两臂的 `model.py` 因此是可控的单变量。

## 6. 对目标的影响（诚实评估）

| 项 | 变化 |
|---|---|
| **HcPre 融合（原最大单项候补，0.459 ms）** | ❌ **转为负结果**（+0.36 ms） |
| 融合 program 的现实可回收（1.6~2.5 ms） | ⚠️ **需要重估**：原估算把它当"另一条独立线"，现在少了一条 |
| 目标 24.59 → ≤22.0（−12%，即 −2.59 ms） | ⚠️ **本轮之后更不可能达到** |

**这一条的教训**：
> **算子级 standalone 的收益（eager、固定 M、单算子）不能外推到图模式 E2E。**
> 本仓此前已有同类教训（"微基准 1.37× 不能外推 ubatching"），这是第二次。
> ⇒ 后续任何"融合/换算子"项，**必须先在 E2E 上验证方向**，再投入工程量。
