# 容量上限的物理账：为什么是 3.57M / 4.03M / 6.7M（2026-10-06）

> 回答一个具体问题：目标里的 **"容量 4.03M tokens（+35%）"** 到底能不能拿到、需要什么条件。
> 全部为**解析计算 + 既有实测校准**，未占卡。
>
> 校准源：① `[V41-DCP-DIAG] pool_bytes_per_block=540928 (slots=[131072,131072,131072,147712])`（真机）；
> ② A3 两个实测容量点（BAT=8192 → 2,987,618 / BAT=2048 → 4,032,862）反解出的 `num_blocks_per_request`；
> ③ `docs/CED-PD-BLOCK-BOUND-20260925.md` 的 32 位页偏移上界。

## 0. 三个公式

```
① 池块数上限        nb_max = floor(2³² / max_slot_stride)          ← 32 位页偏移
② 从字节数得块数    nb     = KV_CACHE_MEMORY_BYTES / pool_bytes_per_block
③ 容量（tokens）    tokens = nb × max_model_len / num_blocks_per_request(BAT)
```

三个数都是**实测**的：

| 量 | 值 | 来源 |
|---|---|---|
| `max_slot_stride` | **147,712 B** | slot3 = C1 KV 131,072（bf16 128×1×512）+ INT8 index K 16,384（128×1×128）+ FP16 scales 256 |
| `pool_bytes_per_block` | **540,928 B** | = 131,072×3 + 147,712 |
| `num_blocks_per_request` | BAT=2048 → **8,533**；BAT=8192 → **9,621** | 由 A3 两个容量点反解，与仓库 `v41_capacity_sweep.py`（含两个真机自检）一致 |

## 1. 三档容量，各自的前提

| 档 | 绑定线（`max_slot_stride`） | 池块上限 | **容量（BAT=2048）** | vs 现役 2,987,618 | 前提 |
|---|---:|---:|---:|---:|---|
| **① 现状几何 + 压池** | slot3 = **147,712** | **29,076** | **3,572,998** | **+19.6%** | 只改配置（`BAT=2048` + `KV_CACHE_MEMORY_BYTES=15728022528`） |
| **② 主线 C1 KV 转 int8**（draft 仍 bf16） | **draft = 131,072** ← 新绑定线 | **32,768** | **4,026,689** | **+34.8%** | 需要 int8 主线 KV 移植 |
| ③ 若 draft 也能压（代码禁止） | slot3 = 82,176 | 52,265 | 6,423,000 | +115% | 需改 `DeepseekV41DraftSWASpec` 的 bf16 硬约束 |

## 2. ★ 目标的「4.03M / +35%」= 第 ③ 档

`vLLM` 自动 profiling 在 BAT=2048 下报的 **4,032,862 tokens** 来自
`16.60 GiB / 540,928 = 32,950 块`。而：

* **draft SWA 线的 32 位上限恰好是 `2³²/131,072 = 32,768` 块** ⇒ 容量 **4,026,689 tokens**；
* 两者相差 **0.15%**。

⇒ **「4.03M」不是随便来的数——它几乎正好是"把主线 KV 压到 draft 那一档"的物理上限。**
⇒ 但它**不是当前几何能达到的**：当前几何的绑定线是 147,712 B ⇒ 只有 29,076 块 ⇒ **3.57M**。

**要拿到 4.03M 需要把四条 KV 线的 stride 全部压到 ≤ 131,072 B。**

## 3. 每条线的现状与可压缩空间

| 线 | 每块字节（128 token） | 每 token | 能否压 | 说明 |
|---|---:|---:|---|---|
| slot0/1/2 的 C1 KV 等 | 131,072 | 1,024 | ⚠️ int8 → 65,536 | bf16 `[128,1,512]` |
| **slot3 的 C1 long-KV** | **131,072** | 1,024 | ⚠️ int8 → 65,536 | 同上的另一份 |
| slot3 的 **index K** | **16,384** | 128 | ❌ **已经是 int8** | `[128,1,128]` int8 ⇒ 16,384 B，已是 1 byte/elem |
| slot3 的 FP16 scales | 256 | 2 | ❌ | 已最小 |
| **draft SWA**（`DeepseekV41DraftSWASpec`） | **131,072** | **1,024** | ❌ **代码强制 bf16** | `__post_init__`：`"Aurora DSpark requires one uncompressed BF16 KV plane"` |

⇒ **索引 K 无法再压**（本来就 int8）；**唯一能压的是主线 C1 KV**（bf16 → int8）；
**draft 线被代码锁死** ⇒ 它成为压到 131,072 之后的**新绑定线**，给出 32,768 块。

## 4. 内存也够（第 ③ 档）

若 C1 KV 转 int8，每块字节数同步下降：

```
pool_bytes_per_block(新) = 540,928 − 65,536 = 475,392 B
32,768 块 × 475,392 = 15.58 GiB  ≤  BAT=2048 可用 16.60 GiB  ✅（余 1.02 GiB）
```

## 5. 结论（三句话）

1. **只改配置能拿到的上限是 3,572,998 tokens（+19.6%）** —— 受限于 `slot3` 的 147,712 B stride；
2. **目标的 4.03M（+35%）几乎正好是"主线 KV 压到 draft 那一档"的上限（4,026,689）**，
   但**必须做 int8 主线 KV**，且 draft 线（代码强制 bf16）会成为新的绑定项；
3. **再往上（6.4M / +115%）** 需要动 `DeepseekV41DraftSWASpec` 的 bf16 硬约束 ——
   那是改模型契约，风险显著更高。

## 6. 复现

```bash
python3 - <<'PY'
U32=2**32; MML=1048576; NPR_2048=8533     # NPR 由 A3 两实测点反解
for name, stride in [("现状 slot3",131072+16384+256), ("C1 int8",65536+16384+256),
                     ("draft 绑定",131072)]:
    nb = U32//stride
    print(name, stride, nb, int(nb*MML/NPR_2048))
PY
```
