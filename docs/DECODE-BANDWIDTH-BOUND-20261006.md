# 交付基线权威测量 + decode 是带宽受限（2026-10-06）

> 本轮做了三件把"优化方向"钉死的事：
> ① 无侵入测出 **tp8k5 交付配置的真实 ms/step**；
> ② 实测 **A3 的 HBM 带宽真实上限**（不再沿用假设的 1182 GB/s）；
> ③ 算出**每步必须搬运的权重字节**，判定 decode 的性质。
> 全部为【实测】，除非标注【推断】。

## 1. tp8k5 交付基线的权威数字（无侵入，不重启服务）

手法：对空闲的 tp8k5 施 20 s 定点负载，用 `/metrics` 的
`spec_decode_num_drafts_total` 差分求步数（**每步 +1/请求 ⇒ Δdrafts/Δt = 步/秒**）。

```
conc=1  窗口 20.0s
  drafts(步数)        Δ=807.0   40.33/s
  draft_tokens        Δ=4035.0  201.67/s
  accepted            Δ=1487.0  74.32/s
  gen_tokens          Δ=2294.0  114.65/s

  ⇒ ms/step       = 24.793
  ⇒ 每步产出 token = 2.84
  ⇒ 接受长度       = 1.84
  ⇒ 生成吞吐       = 114.7 tok/s（**真实权重**）
```

**两个交叉验证**：

1. 这个 24.793 与 tp8k5 自己 bneck 日志里的 **`hp=24.592` 完全一致**
   ⇒ ① 目标里的"真实步长 24.59 ms"就是这条口径；② 我的 metrics 方法可信。
2. `draft_tokens/步 = 5.0` ⇔ SP_TOKENS=5 ✓。

**⚠️ 重要口径修正**：此前用 `bench_concurrency.py` 在 tp8k5 上量到的
"conc=1 = 38.3 tok/s" 是**混合语料**下的数字；用真实长文 prompt 复测是 **114.7 tok/s**。
差异全部来自**接受长度**（这里 1.84）。⇒ **报吞吐必须同时给接受长度或 ms/step**，
否则不同语料的数字不可比。

## 2. A3 的 HBM 带宽实测（目标里 1182 GB/s 的来源需要验证）

`~/tmp/hbm_bw.py`（native torch 算子，非我们自己的 kernel）：

| 口径 | 尺寸 | 实测 |
|---|---:|---:|
| **纯读**（大张量 sum） | 0.5 / 1 / 2 GiB | 1200 / 1263 / **1299 GB/s** |
| 读+写（`copy_`） | 0.25 / 0.5 / 1 GiB | 1147 / 1210 / 1237 GB/s |
| 读+写（`mul_` 原地） | 1 GiB | 1172 GB/s |

设备：`Ascend910_9382`（即 A3 / 910C）。

⇒ **纯读上限约 1300 GB/s**（目标里的 1182 GB/s 偏保守 9%，结论方向不受影响）。
⇒ decode 以**读权重**为主，应该拿 1300 GB/s 当分母。

## 3. 每步必须搬多少权重

从 checkpoint 的 `quant_model_description.json` 读出（**不是估算**）：

| 项 | 值 |
|---|---|
| MoE 专家量化类型 | **W4A8_DYNAMIC**（int4 权重） |
| 专家相关键数 | 190,476（≈ 40 层 × 385 专家 × 12 键） |
| `quant_model_weights-*.safetensors` 总大小 | **273 GB** |

配置：hidden 5120 / moe_intermediate 2304 / 384 routed experts / top-6 / 40 层 / EP=8。

⇒ 每个专家 `(w1+w3+w2) = 3 × 2304 × 5120 × 0.5 B = 17.7 MB`
⇒ 每 rank 每层（若 48 个本地专家全读）= 849 MB ⇒ **40 层 = 34 GB/步**
⇒ 纯流式下界 = 34 GB / 1300 GB/s = **26.2 ms/步**

**而实测 tp8k5 conc=1 的步长就是 24.79 ms。**

## 4. ★ 结论：decode 是**带宽受限**的，重叠类优化不可能有效

把上面三个数放在一起：

```
实测步长          24.79 ms
纯权重流式下界     26.2 ms   （读全部 48 个本地专家）
实测带宽上限       1300 GB/s
```

⇒ 步长**已经落在"必须搬运的权重字节 ÷ HBM 带宽"这个下界的同量级（约 1.0×）**。

这解释了本轮之前所有重叠类优化的失败，而且**是从原理上解释**：

| 失败项 | 原先的解释 | **真正的解释（本轮）** |
|---|---|---|
| DBO / pingpong | 拆批降低 kernel 效率 | 拆批**不减少权重字节**，反而让两路各自再读一遍专家权重 ⇒ 净亏 42% ✓ |
| 通信与计算重叠（A2） | 单批内无独立工作 | 即使有，**带宽已被权重流占满**，藏进去也不缩短步长 |
| A1/A3/A4 微融合 | 暴露度本来就小 | 同上，省下的是**非带宽**的时间，占比本来就低 |

**这与官方 v4.1 技术报告的表述完全一致**（原文）：

> "**Decode**：带宽密集型。每 token 主要开销为**搬运一轮权重**，受带宽限制"

⇒ 目标开头"**AIC 只忙 55%，完美重叠上界 1.81×**"的框架**对 decode 不成立**：
AIC 空闲是在**等权重**，不是在等可重叠的计算。**1.81× 不可能靠重叠拿到。**

## 5. 因此，decode 上真正剩下的杠杆只有三条

| 杠杆 | 说明 | 量级 |
|---|---|---|
| **① 提高权重流式带宽利用率** | 若当前 ~56~95%（取决于专家命中数，见 §6），提到 ~95% 有 **1.05~1.8×** | 大 |
| **② 减少每步要读的权重字节** | 只读**被路由命中的专家**；命中率越高、每字节服务的 token 越多 | 大 |
| **③ 增大批** | 同一专家被更多 token 共享 ⇒ **每 token 权重成本下降**（与 §1 的步长探针实测曲线一致：8→64 token 只涨 1.72× 步长） | 中（吞吐向） |

### 5.1 与已有实测的一致性检验（这就是最好的一致性证据）

tiny 步长探针（`docs/STEP-PROBE-AND-BATCH-SCALING-20261006.md`）：

| conc | tok/step | ms/step | 每 token |
|---:|---:|---:|---:|
| 1 | 8 | 38.9 | 4.86 ms |
| 8 | 64 | 66.9 | **1.05 ms** |

token 数 ×8、步长只 ×1.72 ⇒ **每 token 权重成本降 4.6×** ——
正是"更多 token 共享同一批被读出的专家权重"的预期形状。**两条独立实验互相印证。**

## 6. 仍未确定的一环（诚实标注）

【未确认】**每步实际读到多少个不同的专家**。这决定 §5 杠杆①的剩余空间：

| 假设 | 每步字节 | 折算利用率（24.79 ms × 1300 GB/s = 32.2 GB） |
