# 方向翻转：把「只占 AIC」和「只占 AIV」的算子融合/并行，能拿到多少？（2026-10-07）

> 问题（用户提出）：不拆 MIX，反过来看——那些**只占 AIC** 或**只占 AIV** 的算子，
> 能不能把前后相邻的配对起来，让它同时占用 AIC 和 AIV？
> 数据源：`armF_r6_base` 交付口径 profile（引擎级计时列 `aicore_time` / `aiv_time`）。全部【实测】。

---

## 0. 一页纸

| 项 | 结果 |
|---|---|
| 这个方向成立吗？ | ✅ **成立**，而且是 S5 那条 1.301× 的**同一条机制的不同实现** |
| 机会总量 | 纯 AIC 段 **3741 µs**（13.3% 步长）、纯 AIV 段 **8299.7 µs**（29.5%） |
| **本方向的天花板** | **1.095×**（把 3741 µs 全部藏进 AIC 闲置窗口） |
| 位置邻近性 | ✅ **152/152** 个纯 AIC 算子都有纯 AIV 邻居（±1 位置内） |
| 微基准实测（合成层） | **1.439×**（理论 1.53×） |
| 生态里有没有现成融合算子？ | ⚠️ 有（`npu_rms_norm_quant`、`npu_kv_rmsnorm_rope_cache` 等），**但都不匹配我们的算子对** |
| 关键约束 | **依赖**。`MatMulV2 → HcPost` 之类的相邻对是**真依赖**，必须跨层错开 |

## 1. 机会量化：谁在占着引擎、谁在闲置

| 类别 | 个数/步 | Duration | aicore | aiv | 占步长 |
|---|---:|---:|---:|---:|---:|
| **MIX**（同时用两个引擎） | 317 | 15541.6 | 12323.5 | 13996.3 | 55.3% |
| **AIC_ONLY** | 152 | 3741.2 | 3374.4 | **0.0** | 13.3% |
| **AIV_ONLY** | 758 | 8299.7 | **0.0** | 5799.4 | 29.5% |
| OTHER（都<1µs） | 397 | 522.3 | 0.0 | 298.9 | 1.9% |

```
纯 AIC 段 3741.2 µs —— 此时 AIV 100% 闲置
纯 AIV 段 8299.7 µs —— 此时 AIC 100% 闲置
⇒ 互相填坑的天花板 = min(两者) = 3741.2 µs = 步长的 13.3%
⇒ 理想加速 = 43242.4 / (43242.4 − 3741.2) = 1.095×
```

**为什么天花板是 min 而不是 max**：容器（AIV 段 8300 µs）远大于要藏的东西（AIC 段 3741 µs），
所以瓶颈是**"有多少工作可以被藏"**，不是"有没有地方藏"。

---

## 2. 位置邻近性：152/152 —— 但位置近 ≠ 无依赖

| 搜索半径 | 有纯 AIV 邻居的纯 AIC 算子 | 覆盖时长 |
|---|---:|---:|
| ±1 位置 | **152/152** | 3741.2/3741.2 µs |
| ±2 / ±3 / ±5 / ±10 | 152/152 | 3741.2/3741.2 µs |

**纯 AIV 段的长度分布**（可容纳 AIC 工作的容器）：

| 项 | 值 |
|---|---|
| 段数 | 442 个 |
| 时长中位 / 均值 / 最大 | **16.3 / 18.8 / 100.0 µs** |
| ≥20 µs 的段 | **162 个，合计 4788.7 µs** |

**但位置近不代表能配对。** 真实序列里最典型的纯 AIC 对是：

```
 11  AIC  MatMulV2  (48,4096)@(4096,1024) → 48x1024   28.0 µs   ← wo_a
 12  AIC  MatMulV2  (48,1024)@(5120,1024) → 48x5120   16.5 µs   ← wo_b（吃 11 的输出）
 13  AIV  TensorMove                                   5.1 µs
 14  AIV  HcPost                                      17.2 µs   ← **吃 12 的输出**
```

**`12 → 14` 是真依赖**（`HcPost` 的输入就是 `MatMulV2` 的输出 `48x5120`），
**不能把 14 和 12 并行**。可行的只有**跨层错开**：把层 L 的 `HcPost` 与层 L+1 的 `MatMulV2` 并置。

**但这里有个硬约束**（`STEPTIME-DECOMP` 已记录）：层 L+1 的第①个算子 `HcPre` 吃的是层 L 的**最后一个**输出
⇒ 跨层错开需要**跨越该边界**，而边界处是 `HcPre(MIX)` 而非纯 AIC ⇒ 可错开的窗口比想象的小。

## 3. 微基准实测（合成层，比例取自真实）

每层：**2 个纯 cube（24blk，30.6 µs）+ 5 组纯 AIV（58 µs）**，比例 1 : 1.9（真实 1 : 2.2）

| 臂 | makespan | **vs 串行** |
|---|---:|---:|
| ① 串行交替（= 现状形态） | 2.025 ms | 1.000× |
| **② 两流（= 内核融合上界）** | **1.407 ms** | **1.439×** |
| ③ 跨层延后 | 1.408 ms | 1.438× |

**理论**：纯 cube 占总时长 34.5% ⇒ 完美隐藏 = 1/(1−0.345) = **1.53×**；实测 **1.439×（拿到 94%）**。

> ⚠️ 注意这是**合成比例**（纯 cube 占 34.5%）。真实主流里纯 AIC 只占 **13.3%**，
> 所以真实天花板按 §1 算 = **1.095×**。

## 4. 生态里有没有现成的融合算子？

`torch.ops.npu` 里与「融合」相关的候选（A3 可用）：

| 算子 | 融合了什么 | 匹配我们的需求？ |
|---|---|---|
| `npu_rms_norm_quant` / `_v2` | RmsNorm + 量化 | ⚠️ 部分（我们的 `RmsNorm` 后紧跟 `DynamicQuant`） |
| `npu_rms_norm_dynamic_mx_quant` | RmsNorm + MX 量化 | ❌ 非 MX 场景 |
| `npu_kv_rmsnorm_rope_cache` / `_v2` | RmsNorm + RoPE + KV cache | ⚠️ 但那是 KV 侧，不是 hidden 侧 |
| `npu_qkv_rms_norm_rope_cache` | QKV + RmsNorm + RoPE + cache | ❌ 形状不符 |
| `npu_moe_distribute_combine_add_rms_norm` | MoE combine + Add + RmsNorm | ⚠️ 需要分布式 MoE 上下文 |
| `npu_swiglu` / `npu_swiglu_quant` | SwiGLU（+ 量化） | 已在用 |
| `npu_quant_gmm_alltoallv` | GMM + AllToAllV | ❌ EP 通信场景 |

**⇒ 关键的每一条都不直接匹配**：
* 我们要融的是 **`MatMulV2`(纯AIC) + `HcPost`(纯AIV)**，这类「cube 算子 + vector 算子」的通用配对**没有现成算子**；
* 生态里的融合都是**特定模式**（RMSNorm+量化、RoPE+KV cache），不是通用配对。

**⇒ 要做到"同时占 AIC 和 AIV"，只有两条路**：
1. **依靠双流**（不用写内核，S5 已验证 1.301×）；
2. **写自定义融合内核**（`KERNEL_TYPE_MIX_AIC_1_2`，像 `HcPre` 那样）——
   把 `MatMulV2` 放 cube 部分、`HcPost` 放 vector 部分。**但两者有真依赖，这样融没有意义**；
   有意义的融合必须选**互相独立**的算子对。

## 5. 结论：这个方向对，但它不是新杠杆

| 判定 | 内容 |
|---|---|
| 方向上 | ✅ 正确，与 S5 的 1.301× **同源**（都是"把工作挪进闲置引擎的窗口"） |
| 天花板 | **1.095×**（纯 AIC 13.3% 全部隐藏）——**比 S5 的 1.301× 小** |
| 为什么更小 | S5 能同时利用 **AIV 段（8300µs）+ MIX 段里的 AIC 空档**；本方向只利用前者 |
| 实现方式 | **双流即可，不需要写新内核**；写内核的收益只是省掉同步（实测差异 <1%） |
| 真正的瓶颈 | **依赖**：可配对的独立算子对有多少，仍未审计 |
