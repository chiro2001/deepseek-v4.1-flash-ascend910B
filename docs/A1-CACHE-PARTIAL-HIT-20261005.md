# A1 静态缓存"部分命中"考古：M=5 已换成新内核、M=6 没有（2026-10-05 晚）

> **本文是对 10-04 晚旧 profile（armF_meta2 vs armF_A1，未清 skcache）的事后取证**，
> 逐条回答 `KERNEL-REALIZATION-STUDY-20260404.md` §4 的 5 列取证请求（trackB 线）。
> 结论修正 `KERNEL-CACHE-STALE-20261004.md` 里"服务里两臂跑的是同一个内核"的表述：
> **该结论只对 decode 主形状 M=6 成立；同一份镜像在 M=5 形状上跑的是新内核，且 100% 兑现。**
>
> 关系说明：10-05 凌晨的规范复测（`HCPRE-A1-RETEST-20261005.md`，两臂各清 skcache、
> sha 集合交集=0、效应 −0.10 ms/步低于噪声底）**不依赖本文**，判决维持"不采纳"。
> 本文的价值在机制层：**static kernel 缓存的命中/失效是按 op×形状/图"部分"发生的，
> 不是"要么全新、要么全旧"** —— 这直接影响所有 kernel 部署的验证方法。

## 0. 摘要

| 形状（Input Shapes 前缀） | stream | 样本 | stock `aic_mac_time` | A1 `aic_mac_time` | 判定 |
|---|---|---:|---:|---:|---|
| `6,4,5120;…`（decode 主形状） | 146 | 26800 / 15280 | **1.282** | **1.282** | ❌ 旧内核（缓存命中） |
| `5,4,5120;…` | 142 | 2022 / 1158 | **1.282** | **0.605** | ✅ 新内核在跑 |
| `256,4,5120;…` | 47 | 160 / 160 | 6.504 | 6.503 | —（A1 本不改 M>64 档，符合预期） |

* `aic_mac_time 1.282 → 0.605 = −0.68 µs` 正是 trackB 在隔离环境建立的 A1 零噪声指纹
  （"11/11 轮恒为 −0.68"）；stock 的两个独立采集批次都是 1.282，排除"漂移"解释。
* M=5 的 **`Task Duration` 36.10 → 34.38 µs（−1.72/次）**，与隔离侧效应（−1.5~−1.7 µs/次）
  吻合 ⇒ 服务侧该形状**兑现率 ≈100%**（不是"不可兑现"，详见 §3 修正）。

## 2. 附带的悬案线索：`aic_scalar_time` 的口径差

trackB 曾观察到"服务 stock 的 `aic_scalar_time=4.66`、而本地任何档位都是 11–14"。
本次按形状拆开后：

| 服务 stock 形状 | `aic_scalar_time` |
|---|---:|
| M=6 | **4.615**（p10 4.29 / p90 7.04） |
| M=5 | **11.277**（p10 10.1 / p90 14.6） |
| M=256 | 13.646 |

⇒ 本地 11–14 的观测值**精确落在 M=5（及更大 M）档**，而不在 M=6 档。
【推断】trackB 本地复现的标量耗时对应的是**另一档位的内核路径**（或另一 M 组合），
而不是"服务与本地同档不同口径"。对齐口径时请以"整串 Input Shapes + 档位"为单位，
不要把不同 M 的记录聚合到一起。

## 3. 对既有结论的修正（重要）

| 文档 | 原文 | 修正 |
|---|---|---|
| `KERNEL-CACHE-STALE-20261004.md` §1 | "服务里两臂跑的是同一个内核" | **只对 M=6 成立**。M=5 上 A1 内核已生效且 100% 兑现 ⇒ 缓存复用是**部分**的 |
| `A1-IN-SERVICE-NEGATIVE-20261004.md` §4 | 猜想"L0 压力被掩盖/口径不同/漂移" | 主因是**M=6 走了旧内核**（缓存命中）；其"M=6 无收益"的测量本身没错，但归因改为"没换上" |
| `KERNEL-REALIZATION-STUDY` §5.1 判据 | "若两边 mac 相同 ⇒ 跑的不是同一个内核" | 判据方向正确，但**必须逐形状核验**：只看一个形状会得出"整体没换"的错误总判 |

【推断·机制】M=6 与 M=5 分属不同 stream/图（146 vs 142），static kernel 的"复用"以
图/编译会话为单位发生：M=6 的产物命中了更早的 stock 缓存，M=5 的产物在 A1 会话里
被重新编译 ⇒ 出现"同一 `.o`、两种命运"。这解释了为什么"同一个包"在不同形状上
表现不同，且**不需要**假设任何时间上的测量漂移。

## 4. 对交付纪律的更新（写进流程）

1. **换 kernel 后，资源计数指纹要"逐形状"核验**：至少覆盖 decode 主形状（M=6）、
   次形状（M=5）、大 M（M=256）。只核验一个形状 = 可能漏掉"部分命中"。
2. 清缓存三件套（`npugraph` / `skcache/compile_outputs` / `skcache/install`）仍然必要；
   本文的"部分命中"说明**没有清干净时的行为是不可预测的半新半旧**，比"全旧"更危险
   （收益减半且难以察觉）。
3. `ab_gate` 类的端到端配对判据仍是最终门槛：M=5 的 100% 兑现只在单算子层可见，
   折算到步时（该形状出现频次低）对总时长贡献 <1%，与规范复测的 −0.10 ms/步一致。

## 5. 附：当前交付实例（tp8k5）gmm1 内核血缘抽查

背景：`restore6`（15:35 启动）日志显示 `skcache: static_kernel_cache/ 命中（1 个缓存文件）`
——需要确认它运行的 gmm1 静态内核是不是 armF 版（而不是 stock 旧产物）。

| 检查 | 结果 |
|---|---|
| 本次会话 install 目录 | `install/20261005073415657510_1434/…/GroupedMatmulSwigluQuantV2/*.o`，**57800 B，文件 mtime = 10-05 09:50:21** |
| 0735 编译批次（8 rank 全量） | 每个 rank 的 `opcompile_gathered/` 均含 `GroupedMatmulSwigluQuantV2_*` 与 `HcPre_*` 条目 |
| 09:50 包的来源 | 09:32–09:53 是 **armF_r8_base / armF_r8_final** 的运行窗口，两者启动日志均确认挂载 `pkg_armF`（`[V41-HC-FUSE] opp pkg: …/pkg_armF`） |
| 发布镜像 | `local/dsv41-a3-tp8:20261005-1001` 构建于 **10:01:41**，即把同一 `pkg_armF` 内核烘入镜像层 |
| 后续复用 | armIMG_v3_final（10:25）→ restore1–6 全部复用 09:4x–09:50 这批静态包 |

⇒ 【高置信】tp8k5 上实际生效的 gmm1 静态内核 = **armF 内核**（编译源与发布镜像一致）。
【未闭环】严格证明"运行时加载的就是这批产物"仍需服务侧资源计数指纹（gmm1 的
`aic_*` 对照），可作为下次重启时的验收项之一（重启时带 `V41_OPP_CLEAR_SKCACHE=1` 更干净）。

### 5.1 顺带发现的脚本问题：SKCACHE-GC 报数 ≠ 删净

`serve_a2.sh` 的 GC 在 15:34 打印"清掉 1680 个 ts*_outputs 临时目录"，但事后核查
10-04 22:38 UTC 的 `ts202610042238…_outputs`（root:root 700）**仍然存在**。
【推断】GC 以 `l00886679` 身份运行，`rm -rf` 对 root 私有子目录失败被 `|| true` 吞掉，
计数（`wc -l`）与删除结果无关。影响：ts 目录只增不减（磁盘占用）；**但本次血缘核查
恰好因此保住了旧产物可追溯**。修复方向：GC 后重新计数比对（或在有 sudo 的场景清理）。
