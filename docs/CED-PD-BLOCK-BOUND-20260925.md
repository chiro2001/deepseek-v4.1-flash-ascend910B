## 0. 结论先行（2026-09-25 16:30 版）

1. **故障判据**：D 侧请求的 g0 最高物理块号一旦 ≥ **T ∈ (29077, 29084]**，该请求就
   静默变成"HTTP 200 + 1 token（EOS）"。与池大小、与请求长度 c、与 P 侧块号都无关。
2. **T 与 `2³² / 147712 = 29076.44` 对齐**（147712 B = 128 行 × 512 维 BF16 + 64 维 rope
   + 256 B scale 的实测块步长）⇒ 机理最可能是**每块 147712 B 的 32 位偏移量回绕**。
3. **可用缓解（已验证）**：把 D 池钳到 **C ≤ 29077**（池顶 29076）时，同一 1M 请求
   4/4 全过；C=29128/29129 时必挂。容量代价相对 29600 只有 1.8%。

4. **1+1 tiny 线不复现该故障**（几何逐字节相同但它 29599 也全过）⇒ 该故障的真判据只能
   在 8+8 真权重上取；1+1 的价值在几何、工具与"1M 可行性"。

## 3. 主假说：**B = 29077 = ⌈2^32 / 147712⌉**

### 3.1 每块的真正字节数：147712 B（不是 147456 B）

`[CED-KVGEOM]` 在 a3-22 tiny 线（同一份 40 层 / 12 组几何）上实测：

```
[CED-KVGEOM] swa_cache layer0  shape=(29129,128,1,512) stride=(65536,512,512,1) bf16
             block_stride_bytes=131072  page_content_bytes=131072  limit_2^32=32768
[CED-KVGEOM] swa_cache layer3/20 / long_kv_cache
             block_stride_bytes=147712  limit_2^32_on_stride=29076
[CED-KVGEOM] n_addr=4 block_len=[131072,131072,131072,147712]
             lengths=[3817996288,3817996288,3817996288,4302702848]
```

即：512 维 BF16 = 131072 B，加上 64 维 rope（16384 B）与 256 B 的 scale，
每个块槽位实际占 **147712 B**。三个 131072 B 的对象上限是 32768，池内永远
不会越界；**只有 147712 B 这条线落在观测区间内**。

### 3.2 边界

147712 B/块 ⇒

| 口径 | 首个越界块号 |
|---|---|
| 块**起始**字节 ≥ 2^32 | ⌈2^32/147712⌉ = **29077** |
| 块**末**字节 ≥ 2^32 | 29076 |

（等价地：元素偏移 `block_id × 73856` 首次越过 2^31 也是块号 **29077**。）

两个候选都落在实测区间 **(29023, 29559]** 内。

### 3.3 被排除的版本

打包（packed）slab 的块步长是 **540928 B**（实测 3×131072 + 147712；
旧文档写的 540932 是标定点反推的上界，两者相差 4 B，不影响块数换算）。
若 32 位回绕发生在"块号 × 540928"这一步，边界会落在 ⌊2^32/540928⌋ ≈ 7938；
而实测有**通过**的请求使用了块号 7968、15957、21610 等，故该版本被排除。
回绕必须发生在 **147712 B 这个步长所对应的那个量**上。

## 4. 在飞的刀锋实验（a3-21 8+8）

脚本：`arm_knife_edge_a321.sh`（a3-21 上 `/home/l00886679/tmp/20260924/ced_numeric/`），
由它删掉旧 D、等 chip8–15 的 `VLLMWorker` 归零、用
`V41_CED_KVGEOM=1` 起新的 D，再串行发 4 个 1M 请求。

每请求消耗块数 `R = ceil((N-1)/128) + 21 = 7989`，新鲜池按顺序发块，因此
第 k 个请求的**新鲜块号**是 `[(k-1)·7989+1, k·7989]`，第 4 个请求会顶到池尾。

| 臂 | D 池块数 C | 池内最大块号 = C-1 | 若 B=29077 的预期 |
|---|---|---|---|
| A1 | 29077 | 29076 | 全过 |
| B1 | **29078** | **29077** | 落点请求失败 |

`KV_CACHE_MEMORY_BYTES = C × 540928`（实测每块 540928 B）。既有的四个标定点
（16146820200→29850、16011587200→29600、15700000000→29024、10545000000→19494）
反推每块字节数 ∈ (540915.05, 540931.63]，540928 落在该区间内。

**落点方法**（避免"靠运气碰池尾"）：用 R≈500 的短请求逐条推进，每条请求后读
D 侧 blockdump 的最大块号，最后一条取 `R_last = (C-1) - cursor`，
使它的最大块号**恰好**等于 C-1；前后各留对照请求。

同一实验在 **a3-22 的 1+1 tiny 线**（chip0/chip1，用户本轮划出）并行复核，
那里起服与请求都快 1–2 个数量级，用于把 B 夹到 ±1 并做两臂对照。

### 4.1 实测结果（真权重 8+8，a3-21）

每个臂都是"新 D + 4 个 1M 请求"，第 4 个请求因为装不下而绕回，
其 max 块号**恰好等于 C-1**（前三臂实测逐点吻合）：

| 臂 | C | 各请求 max 块号 | 判决 |
|---|---|---|---|
| b1 | 29129 | 7968 / 15957 / 23946 / **29128** | PASS / PASS / PASS / **FAIL（1 token、content=null）** |
| a1 | **29077** | 7968 / 15957 / 23946 / **29076** | **全 PASS（4/4）** |

⇒ **B ≥ 29077 且 B ≤ 29128**。旧候选 29128 与 29077 都还在区间内；
b2 臂（C=29078，max 块号 29077）正在跑，用于把二者分开。

注意 a1 臂还顺带否掉了一条假说：C=29077 时注册长度
`lengths = [3811180544, 3811180544, 3811180544, 4295021824]` 已经超过 2^32，
但请求全部通过 ⇒ **"TE 注册窗口长度用 32 位"这条不成立**（否则 a1 臂应当整体失败）。

`2³² / 147712 = 29076.44`：块 **29076** 的起始字节 4,294,874,112 < 2³²，

对照：stride = 131072 的三个平面给出的上界是 32768，池内永远到不了；

新增的 `[CED-KVGEOM]` 会打印每个平面的 `ptr_mod_4g`。在 `ced_kvbase_d1`

`T = ⌈(2³² − ptr_mod_4g) / block_stride⌉` 推算的阈值是：

| 平面 | stride | ptr_mod_4g | 推算 T |
|---|---|---|---|
| layers.2 long_kv_cache / indexer | 131072 | 2782920704 | **11536** |
| layers.20 long_kv_cache / indexer | 147712 | 1543503872 | **18627 / 18628** |

而该实例上连发 3 条 1M（g0 max = 7966 / 15953 / 23940）**全部通过**，
即 g0 max 已远超 11536 与 18628。⇒ 用张量基址算出的绝对地址回绕**不是**判据。

### 5.3 目前能站得住的结论

1. **存在一个与池大小无关、与请求长度 c 无关的块号上界 T ∈ (29077, 29084]**（a3-21 真权重）；
   同一实例里 c=7966（1M）与 c=236（30K）两批请求都在 max≈29084 处失败。
2. **T 的数值与 2³²/147712 = 29076.44 对齐**：块 29077 的起始字节首次越过 4 GiB。
   即机理最可能是"每块 147712 B 的 32 位**偏移量**回绕"，而不是绝对地址回绕、也不是
   packed slab 的 540928 步长（后者早已被 7968 通过样本否掉）。
3. **可控的安全区**：D 池 C ≤ 29077（池顶 ≤ 29076）时，1M 请求 4/4 全过
   （a1 臂 C=29077 与 b2 臂 C=29078 均为 4/4 PASS）。C=29128/29129 时同一请求必挂。
4. 失败形态不变：HTTP 200、`completion_tokens=1`、`token_ids=[1]`（EOS），
   首 token logprob ≈ −1.6 / −2.3，而通过时正确答案 logprob ≈ −0.0002。
5. **P 侧块号与失败无关**（P 的 g0 在 29721 池里近乎铺满，仍有大量请求通过）。
6. **1+1 tiny 线不复现**：几何逐字节相同（`n_addr=4`、页 `[131072,131072,131072,147712]`、
   540928 B/块），但 tiny 在 C=29600 的 max=29599 与 C=29129 的 max=29128 处**全部通过**。
   ⇒ 触发条件还与"真权重 / 8+8 拓扑"有关，1+1 只能提供几何与工具，不能作为该故障的判据。

## 6. 为什么"清空请求"不能复位游标：vLLM 的空闲块队列是 FIFO

`vllm/v1/core/kv_cache_utils.py::FreeKVCacheBlockQueue`：

* 初始化时队列**按块号排序**（0,1,2,…,N-1）；
* 分配从**队首**取；
* 请求结束时释放的块用 `append()` 放回**队尾**，排在所有"从未用过"的块之后。

因此：

1. D 的分配游标会**单调向前扫过从未使用过的块号**，直到整池用尽才开始复用；
2. **把请求跑完并不能复位游标** —— 释放只把块挂到队尾，下一次分配仍然拿新块；
3. 只有**进程重启**才把队列恢复成"从 0 开始的顺序"，这也解释了为什么每次换臂
   （新容器）第一条 1M 请求拿到的都是 1..7966 这种低块号；
4. 上界 T 的判定因此是"本次进程生命周期内 D 用过的最高块号"的函数，
   与"当前是否有请求在跑"无关。

这条同时解释了 §5.1 的 9 条数据为什么块号逐条递增、以及为什么
`ced_kvbase_d1` 里第三条 1M 之后接一段 c=236 的短请求就能把游标推到池顶。

## 7. 复位/重启的成本与可选方案（2026-09-25 实测）

D 容器重启的实测分解（`ced_mitig_c29077`）：

| 阶段 | 时刻 | 耗时 |
|---|---|---|
| 脚本/容器启动 → 引擎 init 开始 | 16:19:04 → 16:20:47 | 103 s |
| 加载权重（86 分片） | 16:20:47 → 16:23:39 | 64 s |
| KV 分配 + 连接器注册 | → 16:24:01 | 22 s |
| API server 就绪（health=200） | → 16:24:56 | 55 s |
| **合计** | | **≈5 min 52 s** |

三种"复位"手段的实际效果：

| 手段 | 能否复位块号游标 | 能否改池大小 | 成本 |
|---|---|---|---|
| 跑完/排空所有请求 | **不能**（FIFO 队尾，见 §6） | 不能 | 0 |
| `/sleep` + `/wake_up`（需 `VLLM_SERVER_DEV_MODE=1`） | **不能**（allocator 原地恢复同一批地址） | 不能 | ~30 s |
| `/reset_prefix_cache` | 不适用（CED 口径 `PREFIX=0`，无前缀缓存） | 不能 | 0 |
| **D 容器重启** | **能** | **能**（`KV_CACHE_MEMORY_BYTES` 只在 init 读一次） | ≈6 min |

结论：

1. **池大小与游标复位都只能靠重启**；`/sleep`/`/wake_up` 一类 dev 端点帮不上忙。
2. **P 侧不需要跟着重启**：失败是 D 侧块号的纯函数（§2.1 已排除 P），
   且 P 的容器已经连续运行 21 h、状态健康。P+D 同时复位只会更慢。
3. 既然安全值已经确定（C ≤ 29077），**验收阶段只需要重启一次 D** 就能跑完
   144K/1M 四针、流式、多轮 —— 不再需要每臂重启。
