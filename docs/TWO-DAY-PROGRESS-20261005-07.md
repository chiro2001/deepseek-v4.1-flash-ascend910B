## 0. 一句话

**这两天没有把单流 decode 步长（24.59 ms）推动一分** —— 单流侧的换算子、控核、融合、
重叠四条路全部被实测证否。真正的净收益在**吞吐与容量**两条线上：

| 维度 | 起点（10-05 R6） | 现在（10-07） | 净变化 |
|---|---|---|---|
| decode 聚合吞吐 | conc=32 封顶 **1658~1740** tok/s | conc=128 **2768~2853** tok/s | **+60~72%** |

这部分的价值是**止损**——避免继续往已经证明无效的方向投人。

## 2. 实测为负、可以停止投入的

这一节是这两天**最主要的产出**——把"预估有收益"的方向逐个用实测关掉。

### 2.1 单流：换算子 / 融合 / 控核 —— 全部关闭【实测】

| 项 | 原预估 | 实测结论 | 为什么 |
|---|---:|---|---|
| 层内控核 `limit_core_num`（A1） | +4~9% | **+0.8%**（最优 kv=8 核） | 原估计用的是"整个主流 AIV 全藏进 AIC"，那是跨 micro-batch 的事，不是层内控核 |
| `ScatterNdUpdateSk` → 官方算子 | +2.9% | **三条路径全否** | 换 `_asc` 无效（同为 aclnn 启动路径）；换 PA 写算子形状不兼容；合并调用被"同层先写后读"挡住 |
| metadata 提前到步首 | +2~3% | **暴露仅 0.032 ms（0.1%）** | 它落在步尾，但**同时别的流在跑** ⇒ 不在关键路径 |
| `DequantSwigluQuant` 融合 | +0.5~1% | **暴露仅 0.025 ms（0.1%）** | 几乎完全被盖住 |
| `RmsNorm + DynamicQuant` 融合 | +1~2% | **暴露 ≤0.200 ms** | 受 w8a8 门控；上限本身很小 |
| `HcPre` 减 Sinkhorn 迭代 | — | **不可减** | 101 次/步 × ~40 µs，固定开销主导；eps 下限使 12 次迭代仍差 8e-2；原生实现慢 35× |

**方法论教训（本仓已第三次踩）**：**"算子耗时" ≠ "可回收时间"**。
必须用**暴露度**（`union − 与其它 kernel 的重叠`）判断，否则会把"等待"算成"工作"。

### 2.2 重叠类优化 —— 全部关闭【实测】

| 项 | 结论 | 关键数据 |
|---|---|---|
| A2 通信与计算重叠 | **单批内不可做** | `通信 ∩ AIC = 0.000`，但紧跟随的消费者立即依赖 allreduce 结果 ⇒ 没有可填的独立工作 |
| 线 B ubatching / DBO（图模式） | **净亏 42%** | conc=4：98.9 → 59.3；conc=8：130.6 → 75.7 |
| ↑ 图内"并发"vs"串行" | **两者曲线完全重合** ⇒ 重叠收益 = 0 | 拆 batch 的损失（MoE/GEMM 效率下降 + 通信次数翻倍）远大于收益上限（~10%） |
| pingpong 微基准 1.37× | **不能外推** | 微基准是"固定总工作量切多流"，真实推理是"拆 batch"——会改变 kernel 自身效率 |

> DBO 的技术进展仍然记录在案：**一张 NPU 图可以捕获双流并行分支**（要求 fork event 在捕获根流上 record），
> 根因也定位到"捕获期 metadata 张量被回收"（上游 `ubatch_utils.py:125` 自己标注了 *This will break cudagraph compatibility*）。
> 但结论是：修好也只是"**正确地慢 42%**"。

### 2.3 prefill 杠杆 —— 全部封堵【实测】

| 项 | 结论 |
|---|---|
| `MC2=1`（把 MoE 通信从 ALLTOALL 切到 MC2） | **明确负结果**：prefill conc=1 慢 **8.2×**、conc=8 慢 **2.2×**，decode 中性 ⇒ 当前 ALLTOALL 已是最优 |
| MegaMoE | **双重封堵**：`=1` 已被上游回退；`=2` 被 `moe_intermediate_size=2304 % 512 ≠ 0` 静默关闭 |
| PCP（prefill CP） | vllm-ascend 已实现，但**硬性要求 V2 runner**；Ascend 侧 `use_v2_model_runner` 只认环境变量，未设置则 V1 ⇒ 我们开不了，需 runner 迁移 |
| `BAT_TOKENS` 是 prefill 杠杆的假设 | **被证伪**（2K prompt 仍 1.16×） |
| `admission_gate` 默认值 | 非元凶 |

### 2.4 其他负结果【实测】

| 项 | 结论 |
|---|---|
| `enable_force_eplb` | **不是可交付开关**：它只换 `topk_ids` 不换 `topk_weights` ⇒ 绕过门控路由、**输出算错**。且并发 N=4 +12.9%、N=8 +27.6% 退化 |
| 动态 EPLB | 结构性受阻（适配器假定层同构） |
| HCCL allreduce 三个旋钮 | **全负**；且消息 60 KB → 2 MB 耗时几乎不变 ⇒ 是**每次调用的固定延迟**，只能靠减少调用次数（81 次/步，结构性） |
| F2（`RmsNorm+DynamicQuant` 融合） | 不做：非逐位等价（4~5% 元素差 1 LSB）且 prefill 反而更慢 |
| armP（Python PGO） | 中性偏负，不采纳 |
| `DSPARK_SWA_ONCE` | 候选已实现（默认关 + 自校验），未转默认 |

## 3. 瓶颈的最终画像（这两天最重要的认知产出）

### 3.1 decode：**2,888 个算子的串行链**

| 指标 | 实测值 | 含义 |
|---|---:|---|
| 时间加权**算子并发度** | **1.19**（峰值 4；**73% 的时间 = 1**） | 几乎没有算子间重叠 |
| `Σ算子时长 / 步长` | **1.20** | 串行度 ≈ 1 |
| HBM 带宽利用率 | **11%（conc=1）~ 17%（conc=8）** | 远未饱和 |
| FLOPs | ≈ 2% of peak | 不是算力受限 |
| 每步算子数 | **约 2,878 个**，平均 8.5 µs/个 | 步长由**算子数量**决定 |

⇒ **既不是带宽受限、也不是算力受限，而是"算子数 × 依赖延迟"的限制。**
这解释了为什么"图已下发、`Free` 只有 4.9%"却仍慢：`Free` 统计的是整机真空闲，
96% 的时间"至少有一个核在忙"，但不代表核被用满。

唯一例外是 MoE：**`grouped_matmul` 是权重带宽受限**，g=48 时跑到 **1,292 GB/s ≈ HBM 上限**；
token 数涨 64× 耗时只涨 4% ⇒ **融合、算力优化、重叠对它都没有意义**，只有"少读字节"和"提带宽"有意义。

### 3.2 prefill：**算力饱和，通信已重叠**

同一份 profile 经历过三代结论，最终以**暴露度**定案：

| 代 | 口径 | 结论 | 对否 |
|---|---|---|---|
| ① | 并发不伸缩 + 墙钟整除 | compute-bound（~8K tok/s，合批不帮） | ✅ 最终成立 |
| ② | `op_statistic.csv` **求和** | allreduce 占 **45.5%** ⇒ 通信受限 | ❌ **求和假象** |
| ③ | **暴露度** | allreduce 实际搬运只占 **11%**，其余是算力 | ✅ 最终结论 |

`allreduceAicpuKernel` 的 6.93 s 里有 **87.5% 与其它 kernel 重叠**——等待不是工作。
剔除采集脚本自身的 sleep artifact（5.7 s）后：**设备 98.5% 忙、真实空闲 1.5%**。
另外 prefill **几乎不随并发伸缩**（conc 1→32 仅 1.06~1.22×）。

### 3.3 步长的构成：**固定成本 + 按 token 线性**

| conc | 真实 token/步 | capture bucket | ms/step | 每 bucket-token |
|---:|---:|---:|---:|---:|
| 32 | 100 | 192 | 64.3 | 0.335 ms |
| 64 | 202 | 384 | 88.9 | 0.232 ms |
| 128 | 394 | 768 | 138.0 | **0.180 ms** |

⇒ **步长由 capture bucket 决定，与真实 token 数无关**（conc=24 时 144→192 的补白实测证实）。
⇒ 两个杠杆：**提高接受长度**（填满 bucket）、**提高 `MAX_SEQS`**（用更大 bucket）。

### 3.4 非确定性：源头 1e-7~1e-4，被解码放大

| 层面 | 实测 |
|---|---|
| prefill | **逐位确定**（T=32/1024/1240 三档 `max\|Δ\|=0.000`） |
| decode 源头抖动 | **1e-7 ~ 1e-4** |
| 可见性 | 取决于输出分布是否饱和：饱和（续写）⇒ 观察为 0；平坦（问答）⇒ 放大到 0.3~0.4 |
| 已排除 | 投机解码（`SPEC=0` 判别）、小 T 的 TP allreduce、`npu_scatter_nd_update_sk`（4 用法 × 100 次逐位相同） |

**结构化任务（抽取/事实/算术）10/10 逐字一致且 100% 正确**，
只有开放生成的措辞不同 ⇒ 不影响交付质量。
