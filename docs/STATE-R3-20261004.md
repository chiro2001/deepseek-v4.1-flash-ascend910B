## 2. ★★ 方法学陷阱（本轮踩到，必须记录）

**`bench_concurrency.py` 的 prompt 集由「传入列表里的最大并发」决定**
（`prepare_prompts(tok_base, model, max_conc, prompt_tokens)`，
`max_conc = max(concs)`，切片步长 = 语料长度 / max_conc）。

后果：**用 `--concurrency 1` 单跑，与用 `--concurrency 1,2,4,8,16` 跑，N=1 用的是完全不同的文本**。
实测同配置下：
* `--concurrency 1` ⇒ 单流 **58.5 tok/s**、A=**1.66**
* `--concurrency 1,2,4,8,16` ⇒ 单流 **106.7 tok/s**、A=**3.42**

差 **1.8×**，全部来自"文本不同 ⇒ 投机解码接受长度不同"。
⇒ **报数必须固定并发列表**；跨 run 比较必须用同一列表。我曾因此误判"服务退化 45%"。

**推论**：任何 N 档的 tok/s 都强依赖该档所用文本，而文本又依赖 `max_conc`。
所以**"N=1 单流多少"这个问题在有 `max_conc` 依赖时没有唯一答案** —— 报数必须写明并发列表。
