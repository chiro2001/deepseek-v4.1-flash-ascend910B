# V4.1 DCP8 保真度缺陷 —— 根因定位报告（2026-09-30）

**一句话**：DCP8 的"短 prompt 硬故障"（logits 全相同 ⇒ 均匀分布）根因是
**HCCL 的 `all_reduce` 对未对齐的最后一维把 buffer 弄坏了**；
而"长针 Δlogprob 0.37~0.68"是**另一个独立现象**（见 §5）。

**约定**：【实测】= 真机跑出来的；【推断】= 由代码/公式推出；【未确认】= 没验。

---

## 1. 现象（端到端，同机同 overlay 对照）

| | DCP1 | DCP8 |
|---|---|---|
| 容量（5 GiB 池） | 1,242,687 token | **8,634,871**（6.95×） |
| ms/step | 28.54 | 35.00 |
| tok/s | 35.04 | 28.57 |
| 长针 2K/8K/16K × 2 | 6/6，回答**干净** | 6/6，回答**带噪声** |
| 短问答 | 5/6 | 4/6 |

**硬故障的精确签名**【实测】：失败时首 token 的 top-5 是
`BOS:−11.7697, EOS:−11.7697, PAD:−11.7697, '!':−11.7697, '"':−11.7697`
—— 5 个**不同** token 概率完全相同，而 `−11.7697 = −ln(129280)` 逐位等于
**词表大小的均匀分布** ⇒ **logits 全相同**（不是"答错"，是分布退化）。

## 2. 触发条件【实测】

**服务端 `prompt_tokens` ∈ {8, 12, 16}**（4 的倍数且 ≤16）失败；
`9,10,11,13,14,15,17…24` 全部通过。**20、24 也是 4 的倍数却通过。**

⚠️ 服务端长度 = 离线 tokenizer 数 **+ 4**（chat template）⇒ **做长度类实验必须用
`usage.prompt_tokens` 校准**，踩过一次。

## 3. 逐层快照定位【实测】

用仓库自带的 `V41_CED_LAYER_SNAPSHOT_*`（我们的 overlay
`models/deepseek_v41/model.py::_maybe_snapshot_ced_layer`），给 `POS=-1`
（本批最后一个位置）加支持后，在**真机**跑失败/通过两条：

| 层/阶段 | 通过（T=11）| 失败（T=16） |
|---|---|---|
| layer00_pre | 0.307 | 0.307 |
| layer01_post | 0.703 | 0.656 |
| **layer02_post** | **0.512** | **1.36669e+30** ← 爆炸 |
| layer39_post | 43.75 | 9.51e+29 |

⇒ **layer 2 是第一个走 DCP 合并的层**（ratio=2），爆炸发生在这里，之后一直维持
1e30 量级 ⇒ LM head 溢出 ⇒ logits 全相同。

## 4. ★★ 根因：`all_reduce` 的 buffer 未对齐【实测 + 推断】

加了合并后**幅度诊断**（`V41_DCP_MERGE_DIAG=1`）后，真机 T=16 给出：

```
[MDIAG] rank=0 T=16 scaled[absmax=6.56] wsum[min=-5.73 max=9.23 mean=-3.84]
        denom[min=1e-30] out[absmax=6.56e+30] BIG=True
        dcp=8 keep=0.875 subtrahend=7
        w_local_sum=2924.75   w_postreduce_sum=nan      fold=True
[MDIAG] rank=0 T=16 ...  w_local_sum=1720.81  w_postreduce_sum=0
```

**`w_local_sum` 正常（2924.75）而 `w_postreduce_sum = nan`（另一条是 0）**
⇒ **`all_reduce` 之后的数据是坏的**。

**为什么**：`_pack = torch.cat([scaled(D=512), weights(1)], dim=-1)`
⇒ 最后一维 **513** ⇒ `513 × 4 B = 2052 B`，**不是 16 的倍数**
（`2052 = 16×128 + 4`）。HCCL 的 `all_reduce` 要求 16 字节对齐。

**旧的 `2D+2 = 1026` 同样不对**（`1026×4 = 4104 = 16×256 + 8`）
⇒ 这解释了**为什么历史所有版本都有这个故障**，只是坏法不同。

**放大链路**（为什么"坏 4 字节"会变成"logits 全相同"）：
1. `all_reduce` 把 buffer 弄坏 ⇒ `wsum` 出现**负数**（实测 min ≈ −5.7）；
2. 我在 `eb401e4` 把 `denom` 从 `where(wsum>0, wsum, 1)` 改成了
   **`clamp_min(1e-30)`** ⇒ 负数被压成 `1e-30`；
3. `out = scaled/1e-30 ≈ 6.6e+30` ⇒ LM head 溢出 ⇒ **logits 全相同**
   ⇒ softmax 均匀 ⇒ logprob 恰好 `−ln(129280)`。

⇒ **两个缺陷叠加**：HCCL 未对齐（根因）+ `clamp_min` 把错误放大 30 个数量级
（原 `where` 语义只会"结果错"，不会爆）。

## 5. 与"长针 Δlogprob 0.37~0.68"的关系【未确认】

2-chip 差分线（子代理 `dcp_fidelity`）用**当前** overlay 实测：
* DCP1 vs **DCP2**：首 token logprob **逐位相同**，T≤40 时 40 层 hidden **逐位相同**；
* DCP1 vs **DCP8**：hidden 差 `3e-5~4.6e-5`（≈5–17 个 bf16 ULP），
  且 L0=L1=L2=L20 **同量级**，没有"某层突然分叉"。

⇒ DCP8 的差异是 **8 rank 合并的舍入累积**，不是结构性错误。
**所以长针的 0.37~0.68 与本文的硬故障是两个独立现象**；
0.37~0.68 是否可接受、以及能否再压，**仍是未收口的项**。

## 6. 修复

| # | 改动 | 说明 |
|---|---|---|
| 1 | **pack 到 4 的倍数**（513 → 516）再 `all_reduce`，归约后精确切回 | 对齐 16 字节，去掉根因 |
| 2 | **`denom` 恢复 `torch.where(wsum>0, wsum, 1)`** | 去掉"×1e30"的放大器；坏值"可见但不放大" |
| 3 | 切片改精确（`[..., _out_dim : _out_dim+1]`）| pad 后 `[..., _out_dim:]` 会带上 padding |

**验证**：起服后跑短 prompt 扫描（8/12/16 三个长度）+ 长针 6 个用例 + 性能三元组。

## 7. 方法论教训

1. **"改文件即刻生效"的开关对 decode 无效**（整图捕获），但对 **prefill（eager）有效**
   —— `rank0_only` 就是这么用的。
2. **诊断代码自己会引入 capture 期 host 同步**：我第一版 MDIAG 里写了
   `float(device_tensor.sum())` ⇒ `Not_Supported(EE1016): stream is captured`
   ⇒ 8 个 worker 全挂、白等一轮起服。**所有诊断都要 `not _is_capturing()` 门。**
3. **诊断必须打印"归约前 vs 归约后"两个数**：只打印 `wsum`（归约后）会让人怀疑
   公式；同时打印 `w_local_sum` 才立刻指向 `all_reduce` 本身。
4. **子代理的独立测量把候选范围砍掉了一半**：它证实"tiny 对硬故障无分辨力"，
   并排除"空 rank 合并退化"、"复制态 SWA 寻址"两条假设 ⇒ 剩下的只能是真机特有的
   数值/通信问题，直接把我推向 `all_reduce`。
