# V4.1 DCP8 保真度缺陷 —— 根因定位报告（2026-09-30）

**一句话**：DCP8 的"短 prompt 硬故障"（logits 全相同 ⇒ 均匀分布）根因是
**HCCL 的 `all_reduce` 对未对齐的最后一维把 buffer 弄坏了**；
而"长针 Δlogprob 0.37~0.68"是**另一个独立现象**（见 §5）。

**约定**：【实测】= 真机跑出来的；【推断】= 由代码/公式推出；【未确认】= 没验。

---

## 1. 现象（端到端，同机同 overlay 对照）

| | DCP1 | DCP8 |
|---|---|---|
| 容量（5 GiB 池） | 1,242,687 token | **8,634,871**（6.95×） |
| ms/step | 28.54 | 35.00 |
| tok/s | 35.04 | 28.57 |
| 长针 2K/8K/16K × 2 | 6/6，回答**干净** | 6/6，回答**带噪声** |
| 短问答 | 5/6 | 4/6 |

**硬故障的精确签名**【实测】：失败时首 token 的 top-5 是
`BOS:−11.7697, EOS:−11.7697, PAD:−11.7697, '!':−11.7697, '"':−11.7697`
—— 5 个**不同** token 概率完全相同，而 `−11.7697 = −ln(129280)` 逐位等于
**词表大小的均匀分布** ⇒ **logits 全相同**（不是"答错"，是分布退化）。

## 2. 触发条件【实测】

**服务端 `prompt_tokens` ∈ {8, 12, 16}**（4 的倍数且 ≤16）失败；
`9,10,11,13,14,15,17…24` 全部通过。**20、24 也是 4 的倍数却通过。**

⚠️ 服务端长度 = 离线 tokenizer 数 **+ 4**（chat template）⇒ **做长度类实验必须用
`usage.prompt_tokens` 校准**，踩过一次。

## 3. 逐层快照定位【实测】

用仓库自带的 `V41_CED_LAYER_SNAPSHOT_*`（我们的 overlay
`models/deepseek_v41/model.py::_maybe_snapshot_ced_layer`），给 `POS=-1`
（本批最后一个位置）加支持后，在**真机**跑失败/通过两条：

| 层/阶段 | 通过（T=11）| 失败（T=16） |
|---|---|---|
| layer00_pre | 0.307 | 0.307 |
| layer01_post | 0.703 | 0.656 |
| **layer02_post** | **0.512** | **1.36669e+30** ← 爆炸 |
| layer39_post | 43.75 | 9.51e+29 |

⇒ **layer 2 是第一个走 DCP 合并的层**（ratio=2），爆炸发生在这里，之后一直维持
1e30 量级 ⇒ LM head 溢出 ⇒ logits 全相同。

## 4. ★★ 根因：`all_reduce` 的 buffer 未对齐【实测 + 推断】

加了合并后**幅度诊断**（`V41_DCP_MERGE_DIAG=1`）后，真机 T=16 给出：

```
[MDIAG] rank=0 T=16 scaled[absmax=6.56] wsum[min=-5.73 max=9.23 mean=-3.84]
        denom[min=1e-30] out[absmax=6.56e+30] BIG=True
        dcp=8 keep=0.875 subtrahend=7
        w_local_sum=2924.75   w_postreduce_sum=nan      fold=True
[MDIAG] rank=0 T=16 ...  w_local_sum=1720.81  w_postreduce_sum=0
```

**`w_local_sum` 正常（2924.75）而 `w_postreduce_sum = nan`（另一条是 0）**
⇒ **`all_reduce` 之后的数据是坏的**。

**为什么**：`_pack = torch.cat([scaled(D=512), weights(1)], dim=-1)`
⇒ 最后一维 **513** ⇒ `513 × 4 B = 2052 B`，**不是 16 的倍数**
（`2052 = 16×128 + 4`）。HCCL 的 `all_reduce` 要求 16 字节对齐。

**旧的 `2D+2 = 1026` 同样不对**（`1026×4 = 4104 = 16×256 + 8`）
⇒ 这解释了**为什么历史所有版本都有这个故障**，只是坏法不同。

**放大链路**（为什么"坏 4 字节"会变成"logits 全相同"）：
1. `all_reduce` 把 buffer 弄坏 ⇒ `wsum` 出现**负数**（实测 min ≈ −5.7）；
2. 我在 `eb401e4` 把 `denom` 从 `where(wsum>0, wsum, 1)` 改成了
   **`clamp_min(1e-30)`** ⇒ 负数被压成 `1e-30`；
3. `out = scaled/1e-30 ≈ 6.6e+30` ⇒ LM head 溢出 ⇒ **logits 全相同**
   ⇒ softmax 均匀 ⇒ logprob 恰好 `−ln(129280)`。

⇒ **两个缺陷叠加**：HCCL 未对齐（根因）+ `clamp_min` 把错误放大 30 个数量级
（原 `where` 语义只会"结果错"，不会爆）。

## 5. 与"长针 Δlogprob 0.37~0.68"的关系【未确认】

2-chip 差分线（子代理 `dcp_fidelity`）用**当前** overlay 实测：
* DCP1 vs **DCP2**：首 token logprob **逐位相同**，T≤40 时 40 层 hidden **逐位相同**；
* DCP1 vs **DCP8**：hidden 差 `3e-5~4.6e-5`（≈5–17 个 bf16 ULP），
  且 L0=L1=L2=L20 **同量级**，没有"某层突然分叉"。

⇒ DCP8 的差异是 **8 rank 合并的舍入累积**，不是结构性错误。
**所以长针的 0.37~0.68 与本文的硬故障是两个独立现象**；
0.37~0.68 是否可接受、以及能否再压，**仍是未收口的项**。

## 6. 修复

| # | 改动 | 说明 |
|---|---|---|
| 1 | **pack 到 4 的倍数**（513 → 516）再 `all_reduce`，归约后精确切回 | 对齐 16 字节，去掉根因 |
| 2 | **`denom` 恢复 `torch.where(wsum>0, wsum, 1)`** | 去掉"×1e30"的放大器；坏值"可见但不放大" |
| 3 | 切片改精确（`[..., _out_dim : _out_dim+1]`）| pad 后 `[..., _out_dim:]` 会带上 padding |

**验证结果（真机，8 chip）**【实测】：

| 判据 | 修复前 | 修复后 |
|---|---|---|
| 长度扫描里"均匀分布"的样本数 | **3** | **0** |
| L=12 的输出 | `#`（均匀分布） | `Bert 17` / `meck`（分布**正常**）|
| `17×23` 的输出 | `# 使用Python实现`（均匀）| `你说得对，我算错了。\(19 \times`（正常但**算错**）|
| 长针 2K/8K/16K × 2 | 6/6 | **6/6** |
| ms/step（单流，BAT=2048，A=1） | 35.00 / 35.18 / 35.35 | **35.95**（当时 load=30）|
| KV 容量 | 8,634,871 | **8,634,871** |

★ **对齐粒度**：先试 **16 字节**（pad 到 4 元素）**不够** —— 长度扫描仍残留 1/3 失败；
改成 **512 字节**（pad 到 128 元素）后失败**归零**。
⇒ Ascend HCCL 的 all_reduce 要求 **512 字节**对齐，不是 16。

## 6b. 仍然存在的（诚实标注）

L=12 等少数短 prompt 仍会**答错**（但分布正常，不再是硬故障）。
2-chip 差分线实测 DCP1 vs DCP8 的 hidden 差 `3e-5~4.6e-5`（≈5–17 个 bf16 ULP），
各层同量级、没有"某层突然分叉" ⇒ 属 **8 rank 合并的舍入累积**，
与 §5 的长针 Δlogprob 0.37~0.68 是同一类**精度**问题，
与本次修掉的结构性 bug **分开看待**。

## 6c. ★★ 2026-09-30 续查：对齐修复只消除了"爆炸"，**长度特异的错误答案仍在**

### 教训：判据错了会骗过自己
我之前用的判据是"首 token top-5 的 logprob 是否**互相相等**"（= 均匀分布签名）。
512 B 对齐修复后这个签名**消失**了，于是扫描显示"0 个失败样本"，我据此认为修好了。
**但那是错的**：T=16 现在给出**很自信的错误答案**
（`8+7=?` → `numbersaplenty.c`，首 token logprob `-0.0`），
签名从"均匀分布"变成"自信的错误"，而判据看不见。
⇒ **唯一可靠的判据是答案正确性**（有确定答案的算术题）。

### 用正确答案重测（8 组题 × 2 种收尾 × 5 种 padding 单元）

| server `prompt_tokens` | 答对率 | 判定 |
|---|---|---|
| 10 | 4/23 | ★★FAIL |
| 11 | **1/152** | ★★FAIL |
| 12 | **5/191** | ★★FAIL |
| 13 | 130/216 | OK |
| 14 | 147/185 | OK |
| 15 | 40/80 | OK |
| **16** | **0/25** | ★★FAIL |
| 17 | 16/16 | OK |
| 18 | 8/8 | OK |

**失败集合 = {10, 11, 12, 16}**；13/14/15 与 17/18 正常。

### 这是长度效应，不是"padding 让模型困惑"
同一个 padding 单元（`、`）、同一个问题（`17×23=?`）下逐 k 扫描：

| k | server T | 输出 |
|---|---|---|
| 0 | 12 | `391` ✅ |
| 1 | 12 | `#`（此时是均匀分布）❌ |
| 2 | 12 | `#` ❌ |
| 3 | **13** | `391` ✅ |
| … | 13 | `391` ✅ |

⇒ **同样的 T=12 会错、T=13 会对**，内容只差一个 padding token
⇒ 是**长度特异**的缺陷，不是内容困惑。

### 仍未定位的部分
`rank0_pure` 判别（数学上应精确等于 rank0 的 partial，T≤32 时正确）在 **T=16 上仍然是
均匀分布** ⇒ 问题在 **rank0 自己的注意力输出**，而不是跨 rank 合并（已记在 §4）。
用 `V41-RAW` 诊断看 T=16 的真实请求：rank0 的 `out[absmax=1.77]`、`lse` 有限、
`cmp_seq=[8]`、`cmp_idx max=7` —— **注意力本身是正常的**。

`V41-LAYER` 逐层曲线（真机 T=16，`V41_LAYER_DIAG=1`）：

```
layer14: 170  → layer15: 2160      (12×)
layer19: 2576 → layer20: 6.79e+08  (2.6e5×)  ← 主跳变
layer35: 4.5e8→ layer36: 1.86e+11  (400×)
layer39: 1.09e+12
```

模型拓扑（`config.json`）：`compress_ratios` 层 0-1 = 0、层 2-19 = **2**、层 20-39 = **1**；
`kv_source_layer_ids=[2,8,14,20]`；`engram_layer_ids=[1,14]`。

### 下一步（决定性对照）
**把同一份 `lenfail2.py` 跑在同配置的 DCP1 上** ——
若 DCP1 在这些长度上也失败，则是模型/prompt 固有性质；
若 DCP1 全对，则确认是 DCP 特有的长度相关缺陷，再针对
`{10,11,12,16}` 这四个长度做逐层/逐算子的定向定位。

## 6d. ★ tiny 线对这个 bug 是**盲的**（子代理 `dcp_lenbug` 实测）

**做法**：2-chip tiny（DCP2，TP2，真实拓扑 40 层/64 head/`hc_mult=4`），
`V41_LAYER_DIAG=1 V41_FOLD_DIAG=1 V41_DCP_DIAG_T=<21 个长度 6..64>`，扫全部长度。

**结果**【实测】：
* **1680 条 `[V41-LAYER]` 的 `hs_absmax` 全部是同一个值 `0.000999451`**
  （40 层 × 2 rank × 21 长度，无一例外）⇒ 逐层比值恒为 `1.000000`，**没有任何放大**；
* `[V41-FOLD]` 42 条：无零行、`collapsed` 恒为 `2×`。

**机制**【实测】：dummy 权重下**层内更新比残差小 8 个数量级** ——
MLP 输出 `absmax ≈ 1.8e-11`，而 hidden/残差 `≈ 1.0e-3`
⇒ 残差把幅度钉死，**非"爆炸级"的数值差根本改不动这个判据**。

⇒ **结论**：tiny 能复现"结构性/形状类"缺陷（如旧版 `rank1` 恒 0、q 未 gather），
但**复现不了"数值放大类"缺陷**。要在 tiny 上查这类问题必须换**不依赖幅度**的判据，
例如「DCP1 vs DCPN 在同一 prompt 上的逐层**相对差**」。

## 6e. 一个必须记住的对照设计（否则会得出错误结论）

长度扫描**必然改变 prompt 内容**（靠 padding 凑长度）⇒ "T=16 失败"与
"padding=4 失败"是**混淆**的。本次靠**同脚本跑 DCP1 做对照**才解开：
`lenfail2.py` 两臂用**完全相同的确定性 prompt 序列**，落到 T=16 的是**同一批 25 个 prompt**：

| 臂 | T=16 答对 |
|---|---|
| **DCP1** | **16/25** |
| **DCP8** | **0/25** |

⇒ 同一批 prompt 上 DCP1 能对 64%、DCP8 一个都对不了 ⇒ **确实是 DCP 特有缺陷**，
不是"这批 prompt 本身难"。**任何长度类实验都必须带这个同脚本多臂对照。**

## 7. 方法论教训

1. **"改文件即刻生效"的开关对 decode 无效**（整图捕获），但对 **prefill（eager）有效**
   —— `rank0_only` 就是这么用的。
2. **诊断代码自己会引入 capture 期 host 同步**：我第一版 MDIAG 里写了
   `float(device_tensor.sum())` ⇒ `Not_Supported(EE1016): stream is captured`
   ⇒ 8 个 worker 全挂、白等一轮起服。**所有诊断都要 `not _is_capturing()` 门。**
3. **诊断必须打印"归约前 vs 归约后"两个数**：只打印 `wsum`（归约后）会让人怀疑
   公式；同时打印 `w_local_sum` 才立刻指向 `all_reduce` 本身。
4. **判据本身会骗人**：只验"现象是否消失"（均匀分布签名）而不验**任务是否做对**，
   会把"从一种错法变成另一种错法"误判成"修好了"。正确性判据必须是
   **有确定答案的任务的答对率**。
5. **长度类实验必须用 `usage.prompt_tokens` 校准**，且 padding 单元要选
   **逐 token 可分**的（`\n` 连续会合并成一个 token，扫不出长度）。
6. **"能复现"要看探针的动态范围**：tiny 的幅度探针在 dummy 权重下恒等于同一个值，
   它证明不了"没问题"，只能证明"这个探针看不见"。
7. **子代理的独立测量把候选范围砍掉了一半**：它证实"tiny 对硬故障无分辨力"，
   并排除"空 rank 合并退化"、"复制态 SWA 寻址"两条假设 ⇒ 剩下的只能是真机特有的
   数值/通信问题，直接把我推向 `all_reduce`。
