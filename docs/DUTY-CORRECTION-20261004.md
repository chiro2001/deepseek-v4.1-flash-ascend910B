# ★ 纠正：decode 的"设备占空比 100%"是错的 —— AI core 实际 85.1%，有 14.9% 空闲

> 本文纠正 `REMAINING-TARGETS-20261004.md` 与 `FINDINGS-R3-20261004.md` 里
> **"两个 decode 维度的设备占空比都是 100.0%，所以只能削减工作量"** 这个结论。
> 它建立在一个测量错误上，而这个错误**掩盖了本轮最大的剩余机会**。

## 1. 错在哪

`tools/step_gap.py` 用"每个 gmm1 步窗口内，所有算子的 `max(end) - min(start)`"当作设备跨度。
但那个"所有算子"**包含了 `Task Type == AI_CPU` 的 metadata 任务**（它们也是 op_summary 的行）。
于是：

* 每一步里，AICPU 任务恰好填补了 AI core 的空隙 ⇒ `gap` 恒等于 0 ⇒ 得出"100% 占空比"；
* 而真实情况是 **AI core 在那些时刻是空闲的**，只是 AICPU 在跑。

## 2. 正确的分解（`scripts/duty_fix.py`，N=1 稳态窗口 12380.6 ms）

| 量 | 时长 | 占窗口 |
|---|---:|---:|
| **AI core 并集**（`Task Type != AI_CPU`） | 10533.1 ms | **85.1%** |
| AICPU 并集（三类 metadata） | 573.8 ms | **4.6%** |
| 并集（全部，含跨类重叠） | 11063.1 ms | 89.4% |
| ⇒ **AI core 空闲** | **1847.5 ms** | **14.9%** |
| 　其中被 AICPU 占用 | 573.8 ms | 4.6% |
| 　**纯空闲（谁都没跑）** | **1317.5 ms** | **10.6%** |

补充事实：

* AICPU 的 `sum == union`（比值 1.00）⇒ **所有 AICPU 任务严格串行**（无并发）；
* AICPU 占空比只有 4.6% ⇒ **不是 AICPU 饱和**，任务本身没有排队；
* 三类 metadata 的行**没有双记账**（`unique(start,dur) / rows = 1.00`，已单独核验 ——
  这是 allreduce 踩过的坑，metadata 不适用）。

## 3. 这改变了什么

| 之前的结论 | **修正后** |
|---|---|
| "没有 host 气泡可填，只能削减设备工作量" | **有 14.9% 的 AI core 空闲**，其中 4.6% 明确被 AICPU 占用 ⇒ **重叠是可行的方向** |
| metadata ×3 的 4.28% 只是"削减工作量"的目标 | 它同时是**重叠**的目标：若能把 metadata 挪到与设备并发执行，**最多回收 4.6%** |
| — | 另有 **10.6% 纯空闲**，来源未查（候选：步间同步、host 下发延迟、阶段切换）⇒ **可能是更大的目标** |

## 4. 下一步（按价值排序）

1. **查那 10.6% 纯空闲的分布**：是均匀散布在每步里（⇒ host 下发/同步气泡，可填），
   还是集中在阶段切换处（⇒ 结构性）。方法：把窗口切成 100 ms 桶，算每桶的
   AI core 占空比，看分布形状。
2. **metadata 重叠**：三类 metadata 在 decode 图内是独立的图节点。若能让第 i 层/第 i 段的
   metadata 与设备计算并发（另一条 stream，或提前算），可回收最多 4.6%。
   注意这与"降低单次成本"（子代理正在做的 35 µs 固定开销）**不冲突、可叠加**。
3. 子代理那条线的价值**上调**：它不仅能把 35 µs 打下来，其"减少调用次数"的改法
   同时也会缩短 AICPU 占用的 4.6%。

## 5. 保留的教训

**"设备占空比"这类指标必须显式排除 AICPU / host 类任务**，否则会把"谁在跑"
混在一起，得出方向相反的结论。`tools/step_gap.py` 已加注释指向本文；
需要严格占空比时用 `scripts/duty_fix.py`。
