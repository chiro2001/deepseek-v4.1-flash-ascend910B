# ★ decode 带宽利用率、片上缓存使用情况、以及 910B/910C 的缓存规格对比（2026-10-06）

> 回答四个问题：① decode 的带宽利用率；② 还有哪些空间；③ 片上缓存是否用满；
> ④ A2(910B) 与 A3(910C) 的片上缓存差异及其影响。
> 全部为【实测】，工具：`npu-smi -t usages`、`aclrtGetDeviceInfo`、CANN `platform_config/*.ini`、
> `kernel_details.csv` 算子级归因。**未改动交付实例配置**（tp8k5 全程在跑，用完核验：health=200、
> 容量 2,987,836、BAT=8192）。

## 0. 一句话

**decode 的 HBM 利用率只有 11%（并发 1）~17%（并发 8）**，AICore 却已 79%~100%；
每个 decode 步要下发 **约 2,878 个算子**、平均 8.5 µs 一个 ⇒ **瓶颈是「算子数与下发/依赖延迟」，
不是带宽**。真正吃带宽的那部分（MoE 专家 GEMM）**已经跑到可达带宽的 ~91%**，几乎没有余量。

## 1. 基准标定（先定分母，否则"利用率"没有意义）

### 1.1 HBM 可达带宽【实测】

| 流式模式 | 实测 | 说明 |
|---|---:|---|
| 三地址流 `out = a+b`（3n 字节），6 GB 工作集 | **1181.7 GB/s** | 反复测 1184 / 1175 / 1185，稳定 |
| in-place `a.add_(1)`（2n） | 1206.6 GB/s | |
| pure write `fill_`（1n） | **1491.9 GB/s** | 写比读快 |

### 1.2 `npu-smi` 的百分比 ↔ 绝对带宽【实测·标定】

同一次 1181.7 GB/s 的流量，`npu-smi info -t usages` 稳定报 **73%**
⇒ **100% 对应 1,619 GB/s ≈ 1.6 TB/s**（即 **1% ≈ 16.2 GB/s**）。
本节所有"%"都按这个标定换算。

### 1.3 decode 实测【实测】

在交付实例（tp8k5，TP8/EP8/BAT=8192/SPEC=1 K=5）上跑地火 1024/256，同时采样 HBM 带宽：

| 并发 | 单流 tok/s | 总吞吐 tok/s | **HBM 带宽%** | 换算 GB/s | **AICore%** | `[bneck] hp` |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 91.0 | 91.2 | **11%**（中位，n=20 采样） | **178** | 79% | 24.59 ms @n=6 |
| 8 | 68.3 | 374.7 | **17%**（中位，n=127） | **275** | **100%** | — |

**交叉验证**：解析式算每步搬运量 ≈ **4.2–4.4 GiB/die**（见 §2.1），
除以 24.59 ms = **~180 GB/s**，与实测的 178 GB/s 吻合 ⇒ 两套口径都对。

⇒ **decode 既不是带宽受限（11–17%），也不是算力受限（FLOPs ≈ 2% of peak）**，
而是**下发/依赖延迟受限**。并发 8 时 AICore 已 100%、带宽才 17%，说明瓶颈在核内与核间调度。

## 2. 每步到底在干什么（算子级归因）【实测】

数据：`results/armF_r6_base/prof/...rank0.../kernel_details.csv`（交付口径、纯 decode）。
该 profile 共 **85 步**、**244,691 个算子** ⇒ **每步 2,878 个算子**；
profile 步长 43.1 ms（含 msprof 开销），按比例缩放到真实步长 24.59 ms。

### 2.2 Top 算子（按步折算，真实步长 24.59 ms 口径）

### 2.3 ★ 三条可直接读出的结论

**(a) 吃带宽的那部分已经接近上限 —— 几乎没有余量**
MoE 两个 grouped GEMM 合计 **3.67 ms/步**，读 3.1 GiB ⇒ **845 GB/s ≈ 可达带宽的 71%**
（按算子净时长算 ~91%）。**再想从专家权重上榨带宽，空间很小。**

**(b) 大量"小张量 elementwise"的耗时是纯下发开销**
`HcPre` 对 `M=6 × 5120` 的 bf16 = **60 KB** 数据花了 **40.3 µs** ——
比带宽受限所需的时间高 **~3 个数量级** ⇒ 纯粹是下发/同步。
同类：`AivKernel` 65.6 µs、`RmsNorm` 13.5 µs、`HcPost` 18.5 µs。
`HcPre+HcPost+AivKernel+RmsNorm` 合计 **≈ 5.96 ms/步 = 24%**。

**(c) 每步 2,878 个算子 ⇒ 平均 8.5 µs/算子**
24 个 cube 核并行，相当于每核每步 ~120 个算子。**这是 decode 的主结构特征。**

## 3. 片上缓存：有什么、我们用了多少【实测】

### 3.1 容量与带宽

| 层级 | 容量（910C） | 实测带宽 |
|---|---:|---:|
| **L2**（片上，全局共享） | **192 MiB**（`aclrtGetDeviceInfo` 报 201,326,592 B） | **~6.0 TB/s**（= HBM 的 **5.0×**） |
| L1（每核） | 512 KiB | —（CANN 规格） |
| L0A / L0B / L0C（每核） | 64 / 64 / 128 KiB | — |
| UB（向量核） | 192 KiB | — |

**L2 拐点实测**（三地址流，足迹扫描）：60→200 MB 足迹恒为 **4.9–6.0 TB/s**；
210 MB 掉到 4.2、230 MB 掉到 **1.2 TB/s** ⇒ 拐点 **≈200 MB**，与规格 192 MiB 精确吻合。
**这条实测同时验证了"用带宽拐点反推缓存容量"的方法可用。**

### 3.2 我们用了多少？

| 用法 | 现状 | 证据 |
|---|---|---|
| kernel 内 L1/L0 双缓冲 | ✅ 标准用法（CANN/ATB 生成的算子自带） | 算子实现 |
| **跨层/跨算子的 L2 预取** | ❌ **完全没用** | `grep npu_prefetch / CMO_TYPE_PREFETCH` 在 `vllm_ascend/` 里**零命中**；CANN 提供了 `aclrtCmoAsyncWithBarrier(..., ACL_RT_CMO_TYPE_PREFETCH, ...)` 与 `torch_npu.npu_prefetch`，只有 KDA 自定义核用它 |
| L2 驻留控制 / 权重常驻 | ❌ 无 | 无对应 API 被调用 |
| 通信缓冲 | `HCCL_BUFFSIZE=1024`（MB） | 容器 env |

### 3.3 为什么"没预取"不是缺陷（本轮做了 A/B 否证）【实测】

模拟 decode 的权重流：41 个互不相同的专家权重（共 922 MiB，**远超 192 MiB**），
每个只用一次 —— A 臂顺序算，B 臂用 `torch_npu.npu_prefetch` 预取下一层：

| 臂 | 41 层耗时 | 有效带宽 |
|---|---:|---:|
| **A 顺序** | **0.969 ms** | **998 GB/s**（= 可达的 84%） |
| B 预取下一层 | 1.612 ms | 600 GB/s（**+66%，更慢**） |

⇒ **纯权重流本来就已经跑到 84% 可达带宽，L2 预取帮不上忙**（这里的 192 MiB 缓存对
922 MiB 的无复用流本来就无能为力，预取还引入了竞争）。
**这否证了"上 L2 预取能提速 decode"这个直觉。**

### 3.4 那 L2 到底有没有用得上的地方？

**有，但在长上下文侧，且当前无复用可言**：KV/索引缓存的字节数 = `≈4 KB/token`
⇒ 上下文 ≤ ~48K token 时 KV **能装进 L2**；而 decode 每步都要重读。
理论上"把 KV 钉在 L2"能省掉这部分 HBM 往返 —— 但：
* 权重流 4.2 GiB/步 会把 L2 冲干净（除非有驻留机制，而 CANN 未见对应开关）；
* 短上下文（我们的 KPI 口径 1K）下 KV 只有几 MB，**收益可忽略**；
* 【未确认】本项目**未做**"KV 钉 L2"的实验，因为缺驻留接口 + 权重流必然冲刷。

## 5. ④ A2(910B) 与 A3(910C) 的片上缓存对比【实测·规格表】

来源：CANN 9.1.0 自带 `aarch64-linux/data/platform_config/*.ini`（每个 SoC 一份硬件规格表）
+ A3 运行期 `aclrtGetDeviceInfo` 交叉验证。

### 5.1 先定死 A2 是哪个 SoC

仓库里 **A2 = 8 × 910B3** 的表述有 6 处一致（`a2/docs/A2-GO-LIVE.md`、`A2-DEPLOY-NOW.md`
§B0/§543、`A3-VALIDATION-ROADMAP.md`、`a2/logs/001`、`a2/logs/002`）；
仅 `docs/V41-TP8-DSPARK-MULTISTREAM-PERF-20261003.md:234` 写作"910B4"，
但它同时说"20 cube/die"——**910B3 与 910B4 都是 20 cube**，而 **910B4 只有 32 GiB/片**，
装不下 38.7 GiB/片的权重 ⇒ **该处应为笔误，A2 = 910B3**。

### 5.2 逐项对比

| 项 | **A2 = 910B3** | **A3 = 910_938x**（实测 24 cube） | 差异 |
|---|---:|---:|---|
| **L2 容量** | **192 MiB** | **192 MiB** | **✅ 相同** |
| L1（每核） | 512 KiB | 512 KiB | 相同 |
| L0A / L0B / L0C | 64 / 64 / 128 KiB | 64 / 64 / 128 KiB | 相同 |
| UB（向量核） | 192 KiB | 192 KiB | 相同 |
| **cube 核数** | **20** | **24** | **1.20×** |
| **vector 核数** | **40** | **48** | **1.20×** |
| AI CPU | 6 | 6 | 相同 |
| HBM 容量 | 64 GiB/die | 64 GiB/die（实测 61.27 GiB 可用） | 相同 |
| 记忆速率比（规格） | `l2_rate=110 / ddr_rate=32` | **同为 110 / 32** | 相同 |
| cube 频率 | 1800 | 1800（9381/9382）/1850（9391/9392） | ≤1.03× |

> 对照：**910B4（A2 不是它）** 才是"小缓存"版 —— `l2_size=100663296 = **96 MiB**`、
> memory 32 GiB/die。若将来换到 B4 机型，**L2 会腰斩成一半**。

### 5.3 对 A2 性能的影响（回答"是否会受影响"）

**结论：缓存维度上 A2 不受影响（与 A3 完全相同）；差异集中在核心数（1.2×）。**

【推断】按本轮的归因（decode 是算子数/下发延迟受限，不是带宽受限）推导：

1. **缓存敏感的部分**（L1/L0 双缓冲、attention 的 KV 复用）：A2 与 A3 同规格 ⇒ **无差异**；
2. **核数敏感的部分**：A2 少 20% cube 与 vector ⇒ 纯计算与向量算子**慢约 1.2×**；
   本仓已有旁证："A3（910C，24 cube/die）与 A2（910B4，20 cube/die）算力差 1.2×"；
3. **下发延迟敏感的部分**（占我们 decode 大头）：核数少 ⇒ 同一步的算子排队更长，
   因此在**同样 2,878 算子/步**下，A2 的劣势**可能大于 1.2×**（【推断】，未在 A2 实测）；
4. **带宽敏感的部分**：两边 HBM 都 64 GiB、dcr 比相同，**无差异**。

> ⚠️ **本轮无法在 A2 上复测**（外网不可达，用户已确认不做）。
> 上面 1–4 的可验证办法：在 A2 上跑 `npu-smi info -t usages` 采样 HBM 带宽%，
> 与本文 §1.3 的 11%/17% 对比；若 A2 的% 与 A3 接近而 tok/s 低 1.2× 以上，
> 就说明瓶颈确实从"带宽"转到了"核数/下发"。

## 6. 复现

```bash
# ① HBM 可达带宽 + L2 拐点（任一空闲 die）
python3 /tmp/bw_l2_probe2.py --iters 80      # 拐点在 200→210 MB 之间
python3 /tmp/l2_knee.py                      # 60→300 MB 细扫

# ② 标定 npu-smi 的 % ↔ GB/s：跑流式的同时采样
nohup python3 hbm_bw_sample.py <card> 60 0.05 > bw.csv &   # 卡号 0-7 不是 die 号！

# ③ 读硬件规格（无需设备）
python3 acl_dev_attr.py                      # aclrtGetDeviceInfo：L2/核数/显存
sed -n '/\[SoCInfo\]/,/\[AICoreSpec\]/p' \
  /usr/local/Ascend/cann-9.1.0/aarch64-linux/data/platform_config/Ascend910B3.ini

# ④ 算子级归因
python3 tools/kernel_breakdown.py <rank0>/ASCEND_PROFILER_OUTPUT 12

# ⑤ L2 预取 A/B（否证）
python3 prefetch_ab.py 41 6
```

**关键口径提醒**：`npu-smi -i N` 里的 **N 是卡号（0–7）**，die 号 = `N×2 + chip`；
本机按卡号查 `-i 4` 才是物理 die 8/9。本轮第一次标定就采错了卡（写成 `-i 2` 才对上 die 4/5）。
