## 0. 一句话

**这个步不是在"算"，而是在"搬 + 找地址 + 等"。**

| 口径 | 数学 | 标量 | 搬运 | 未归因（同步/等待） |
|---|---:|---:|---:|---:|
| **全步**（Σ 时长 29.824 ms） | **7.4%** | 31.5% | 40.8% | 37.5% |
| **主流**（busy 15.862 ms） | **8%** | 35% | 43% | 13% |

**单流 −12% 需要 −3.0 ms。已识别的每一项单杠杆都在 0.3~0.9 ms（1~2%），且多数已被实测堵死。**

## 1. 步长是怎么构成的

```
步长 25.458 ms
├── 主流跨度 25.287 ms（99.3% 步长）  ← 步长 = 主流跨度
│   ├── 主流 busy        15.862 ms（62.3%）
│   │   ├── 数学          1.323 ms（8%）
│   │   ├── 标量          5.600 ms（35%）
│   │   ├── 搬运          6.889 ms（43%）
│   │   └── 未归因        2.051 ms（13%）
│   └── 主流"等待"        9.425 ms（37%）
│        ├── 被其它流填充  ~8.1 ms（86%）
│        └── 真正空白      ~1.3 ms
└── 尾链超出主流           0.128 ms
```

**三条结构性事实**：
1. **`步长 = 主流跨度`** ⇒ 只有缩短主流自己的串行链才能缩短步长；
2. **主流 busy 里数学只占 8%** ⇒ 优化对象不是"算得慢"，而是"搬得多 + 找地址 + 等同步"；
3. **主流等待的 86% 被其它流填充**（通信 2.82 ms、draft、采样、metadata）⇒ 关键路径是"主流 + 它等的侧流"交替。

### 5.1 为什么"逐项做"注定失败

```
现状:  25.0 ms
目标:  ≤22.0 ms  ⇒  需要 −3.0 ms

剩余机会总和（乐观、无重叠）:  1. 2.5 + 2. 0.6 + 3. 1.0 + 4. 0.3 + 5. 0.27 + 6. 1.0  ≈ 5.7 ms
但每一项单独都 ≤1~2%，而判据下限是 1%
⇒ 必须"批量做、用累计值验证"；且第 1/2/3 项都是 kernel 开发
```

## 6. 结论与建议

### 6.1 诚实结论

**"单流 ms/step 降到 ≤22.0（−12%）"在当前**非 kernel 开发**的手段下不可达。**

理由（三条独立证据）：
1. **数学只占 8%** ⇒ 无论怎么优化算子实现，上限是那 92% 的"搬 + 找地址 + 等"；
2. **每算子净开销 1.9~2.0 µs（图下实测）**，而主流上的算子只有 952 个 ⇒ 全融合的上限 ≈2.5 ms；
3. **判据下限 1%** ⇒ 任何 ≤1% 的改进都不可验证，而现有每一项都在 1~2%。

### 6.2 建议的三条路（需决策）

| 选项 | 内容 | 预期 | 成本 | 风险 |
|---|---|---|---|---|
| **A. 收窄目标** | 落地 §5 的第 4/5/6 项（配置 + 1~2 个融合 kernel），把目标改为 **−4%** | 0.7~1.3 ms | 1~2 周 | 低 |
| **B. 立项"多合 1"深度融合** | 以 §5 第 1 项为主，把主流算子数 952 → <300 | **1.4~2.5 ms（5.6~9.8%）** | **3~5 周**（5~8 个新 kernel） | 中高（精度+工程） |
| **C. 转吞吐侧** | 放弃单流 ms/step，回到 conc 8~16 的总吞吐（已有 +15~30% 基础）与 PD 分离（prefill 2.07×） | 已有基础 | 低 | 低 |

**我的建议**：若要"近期可交付"选 **A**；若目标必须 −12%，只有 **B**（且要接受 3~5 周与 2/3 兑现率）。
**C 是把已有收益兑现**，风险最低。
