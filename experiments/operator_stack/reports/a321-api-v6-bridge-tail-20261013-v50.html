2026-10-13 · a3-21 physical8–15 · 正式40层/W4A8_DYNAMIC/Engram int8/strict · DSpark 真实 ON（graph+async） · 目标 ≤20ms/step 未达成（当前 28.0921）

1. 发现：每请求 133–725ms 的窗口内尾部伪影

对既有正式窗口（v4 async、v5 async、api_v1 sync）逐请求做窗口分解 （decode_start → 首轮 execute_start = pre；Σ 逐轮 span = rounds；末轮 sample_end → client_end = post）：

窗口 pre 合计 rounds 逐轮中位 post 合计（8 请求）
v4 async（32.97） 238ms 27.1–28.1ms 3533ms
v5 async（32.89） 254ms 26.9–28.0ms 3514ms
api_v1 sync（46.49） 134ms 37.1–39.1ms 3602ms

post 逐请求 133、182、336、391、458、645、664、725ms（两臂几乎相同、随请求序号递增）—— 定位到桥的状态机：CounterBridge._write() 每个事件把全部历史窗口（含 8 rank 全量 receipts） 以 indent=2 同步重写 bridge_windows.json，运行结束时该文件 33.2MB；随着历史增长， 每次同步序列化阻塞 ASGI 事件循环数百毫秒，表现为"响应就绪 → http_output_send_begin"之间的空洞 （v5 窗口 5：+21.7ms 响应就绪 → +643.9ms 才开始发送）以及随后客户端 finish RPC 同样被推迟。

结论：post 是诊断 harness 自身的证据写开销，不是模型/引擎/解码工作；它在两臂等量存在， 不改变 async 相对收益，但把 ms/step 抬高约 5.1ms。

2. 修复（新快照 src_dspark_native_graph_api_async_v2）

仅改 _write() 的序列化视图：状态文件里每个窗口剥离 rank_receipts （全量 receipts 仍原样经 HTTP finish 返回并由客户端落盘）；stage 机、校验、事件、收据字节全部不变。 CPU 自检：8 窗口历史 + 全量 receipts（内存）时 _write = 0.17ms / 1716 字节（原 33MB 级）。 基线 api_async_v1 快照及其全部历史证据保持字节不变。
